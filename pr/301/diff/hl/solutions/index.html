19--- ## Behavioral Equivaleence
20-
21--- In an earlier chapter, we investigated the correctness of a very simple
22--- program transformation: the `optimize0plus` function. The programming
23--- language we were considering was the first version of the language of
24--- arithmetic expressions -- with no variables -- so in that setting it was
25--- very easy to define what it means for a program transformation to be
26--- correct: it should always yield a program that evaluates to the same number
27--- as the original.
28-
29--- To talk about the correctness of program transformations for the full Imp
30--- language -- in particular, assignment -- we need to consider the role of
31--- mutable state and develop a more sophisticated notion of correctness, which
32--- we'll call *behavioral equivalence*.
33-
34--- For example:
35-
36--- - `X + 2` is behaviorally equivalent to `1 + X + 1`
37--- - `X - X` is behaviorally equivalent to `0`
38--- - `(X - 1) + 1` is *not* behaviorally equivalent to `X`
39-

77--- For commands, the situation is a little more subtle. We can't simply say
78--- "two commands are behaviorally equivalent if they evaluate to the same
79--- ending state whenever they are started in the same initial state," because
80--- some commands, when run in some starting states, don't terminate in any
81--- final state at all!
82-
83--- What we need instead is this: two commands are behaviorally equivalent if,
84--- for any given starting state, they either (1) both diverge or else (2) both
85--- terminate in the same final state. A compact way to express this is "if the
86--- first one terminates in a particular state then so does the second, and
87--- vice versa."
88-
89-def Com.Equiv (c₁ c₂ : Com) : Prop :=
90-    ∀ {st st' : State},
91-      (st =[ c₁ ]=> st') ↔ (st =[ c₂ ]=> st')

545--- *Theorem*: Equivalence is a congruence for `while` -- that is, if `b` is
546--- equivalent to `b'` and `c` is equivalent to `c'`, then `while (~b) {~c}` is
547--- equivalent to `while (~b') {~c'}`.
548-
549--- *Proof*: Suppose `b` is equivalent to `b'` and `c` is equivalent to `c'`.
550--- We must show, for every `st` and `st'`, that
551--- `st =[ while (~b) {~c} ]=> st'` iff `st = while (~b') {~c'}
552--- ]=> st'`. We
553--- consider the two directions separately.
554-
555--- - (`->`) We show that `st =[ while (~b) {~c} ]=> st'` implies
556---   `st =[ while (~b') {~c'} ]=> st'`, by induction on a derivation of
557---   `st =[ while (~b) {~c} ]=> st'`. The only nontrivial cases are when the
558---   final rule in the derivation is `Com.EvalR.whileFalse` or
559---   `Com.EvalR.whileTrue`.
560-
561---   - `Com.EvalR.whileFalse`: In this case, the form of the rule gives us
562---     `beval st b = false` and `st = st'`. But then, since `b` and `b'` are
563---     equivalent, we have `beval st b' =false`, and `Com.EvalR.whileFalse`
564---     applies, giving us `st =[ while (~b') {~c'} ]=> st'`, as required.
565-
