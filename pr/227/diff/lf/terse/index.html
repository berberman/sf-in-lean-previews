25+-- ######################################################################
26+-- Welcome
27+
28+-- This is Lean-based entry point to a series of electronic
29+-- textbooks on various aspects of *Software Foundations*, the
30+-- mathematical underpinnings of reliable software. Topics in
31+-- the series include basic concepts of logic,
32+-- computer-assisted theorem proving, the Lean prover,
33+-- functional programming, operational semantics, logics and
34+-- techniques for reasoning about programs, static type
35+-- systems, property-based random testing, and verification of
36+-- practical C code. The exposition is intended for a broad
37+-- range of readers, from advanced undergraduates to PhD
38+-- students and researchers. No specific background in logic or
39+-- programming languages is assumed, though a degree of
40+-- mathematical maturity will be helpful.
41+
42+-- It is important to note that the *Software Foundations*
43+-- series is originally written using the *Rocq* proof
44+-- assistant-- another theorem prover which is similar to but
45+-- distinct from Lean. This book marks the first effort in
46+-- translating the Rocq-based series to Lean-- an effort that
47+-- will (hopefully!) continue with the generous support of the
48+-- Lean and Rocq communities.
49+
50+-- The principal novelty of the series is that it is one
51+-- hundred percent formalized and machine-checked: each text is
52+-- literally a script for Lean. The books are intended to be
53+-- read alongside (or inside) an interactive session with Lean.
54+-- All the details in the text are fully formalized in Lean,
55+-- and most of the exercises are designed to be worked using
56+-- Lean.
57+
58+-- The files in each book are organized into a sequence of core
59+-- chapters, covering about one semester's worth of material
60+-- and organized into a coherent linear narrative, plus a
61+-- number of "offshoot" chapters covering additional topics.
62+-- All the core chapters are suitable for both upper-level
63+-- undergraduate and graduate students.
64+
65+-- This book, *Logical Foundations*, lays groundwork for the
66+-- others, introducing the reader to the basic ideas of
67+-- functional programming, constructive logic, and the Lean
68+-- prover.

70+-- ######################################################################
71+-- Overview
72+
73+-- Building reliable software is hard -- really hard. The scale
74+-- and complexity of modern systems, the number of people
75+-- involved, and the range of demands placed on them make it
76+-- challenging to build software that is even more-or-less
77+-- correct, much less 100%% correct. At the same time, the
78+-- increasing degree to which information processing is woven
79+-- into every aspect of society greatly amplifies the cost of
80+-- bugs and insecurities.
81+
82+-- Computer scientists and software engineers have responded to
83+-- these challenges by developing a host of techniques for
84+-- improving software reliability, ranging from recommendations
85+-- about managing software projects teams (e.g., extreme
86+-- programming) to design philosophies for libraries (e.g.,
87+-- model-view-controller, publish-subscribe, etc.) and
88+-- programming languages (e.g., object-oriented programming,
89+-- functional programming, ...) to mathematical techniques for
90+-- specifying and reasoning about properties of software and
91+-- tools for helping validate these properties. The *Software
92+-- Foundations* series is focused on this last set of tools.
93+
94+-- This volume weaves together three conceptual threads:
95+
96+-- (A) basic tools from *logic* for making and justifying
97+-- precise claims about programs;
98+
99+-- (B) the use of *proof assistants* (or *provers*) to
100+-- construct rigorous logical arguments;
101+
102+-- (C) *functional programming*, both as a method of
103+-- programming that simplifies reasoning about programs and as
104+-- a bridge between programming and logic.
105+
106+-- Logic
107+
108+-- Logic is the field of study whose subject matter is *proofs*
109+-- -- unassailable arguments for the truth of particular
110+-- propositions. Volumes have been written about the central
111+-- role of logic in computer science. Manna and Waldinger
112+-- called it "the calculus of computer science," while Halpern
113+-- et al.'s paper *On the Unusual Effectiveness of Logic in
114+-- Computer Science* catalogs scores of ways in which logic
115+-- offers critical tools and insights. Indeed, they observe
116+-- that, "As a matter of fact, logic has turned out to be
117+-- significantly more effective in computer science than it has
118+-- been in mathematics. This is quite remarkable, especially
119+-- since much of the impetus for the development of logic
120+-- during the past one hundred years came from mathematics."
121+
122+-- In particular, the fundamental tools of *inductive proof*
123+-- are ubiquitous in all of computer science. You have surely
124+-- seen them before, perhaps in a course on discrete math or
125+-- analysis of algorithms, but in this course we will examine
126+-- them more deeply than you have probably done so far.

132+-- Proof Assistants
133+
134+-- The flow of ideas between logic and computer science has not
135+-- been unidirectional: CS has also made important
136+-- contributions to logic. One of these has been the
137+-- development of software tools for helping construct proofs
138+-- of logical propositions. These tools fall into two broad
139+-- categories:
140+
141+-- - *Automated theorem provers* provide "push-button" operation:
142+--   you give them a proposition and they return either *true* or
143+--   *false* (or, sometimes, *don't know: ran out of time*).
144+--   Although their reasoning capabilities are still limited,
145+--   they have matured tremendously in recent decades and are
146+--   used now in a multitude of settings. Examples of such tools
147+--   include SAT solvers, SMT solvers, and model checkers.
148+
149+-- - *Proof assistants* are hybrid tools that automate the more
150+--   routine aspects of building proofs while depending on human
151+--   guidance for more difficult aspects. Widely used proof
152+--   assistants include Isabelle, Agda, Twelf, ACL2, PVS, F⋆,
153+--   HOL4, Rocq, and Lean, among many others.
154+
155+-- This course is based around Lean, a proof assistant that has
156+-- been under development since 2013 and has attracted a large
157+-- community of users in both research and industry. Lean
158+-- provides a rich environment for interactive development of
159+-- machine-checked formal reasoning. The kernel of the Lean
160+-- system is a simple proof-checker, which guarantees that only
161+-- correct deduction steps are ever performed. On top of this
162+-- kernel, the Lean environment provides high-level facilities
163+-- for proof development, including a large library of common
164+-- definitions and lemmas, powerful tactics for constructing
165+-- complex proofs semi-automatically, and a special-purpose
166+-- programming language for defining new proof-automation
167+-- tactics for specific situations.
168+
169+-- Lean has been a critical enabler for a huge variety of work
170+-- across computer science and mathematics:

199+-- The term *functional programming* refers both to a
200+-- collection of programming idioms that can be used in almost
201+-- any programming language and to a family of programming
202+-- languages designed to emphasize these idioms, including
203+-- Haskell, OCaml, Standard ML, F##, Scala, Scheme, Racket,
204+-- Common Lisp, Clojure, Erlang, F⋆, and Lean.
205+
206+-- Functional programming has been developed over many decades
207+-- -- indeed, its roots go back to Church's lambda-calculus,
208+-- which was invented in the 1930s, well *before* the first
209+-- electronic computers! But since the early '90s it has
210+-- enjoyed a surge of interest among industrial engineers and
211+-- language designers, playing a key role in high-value systems
212+-- at companies like Jane Street Capital, Microsoft, Facebook,
213+-- Twitter, and Ericsson.
214+
215+-- Note to developers:
216+--     companies should be updated!
217+
218+-- The most basic tenet of functional programming is that, as
219+-- much as possible, computation should be *pure*, in the sense
220+-- that the only effect of execution should be to produce a
221+-- result: it should be free from *side effects* such as I/O,
222+-- assignments to mutable variables, redirecting pointers, etc.
223+-- For example, whereas an *imperative* sorting function might
224+-- take a list of numbers and rearrange its pointers to put the
225+-- list in order, a pure sorting function would take the
226+-- original list and return a *new* list containing the same
227+-- numbers in sorted order.
228+
229+-- A significant benefit of this style of programming is that
230+-- it makes programs easier to understand and reason about. If
231+-- every operation on a data structure yields a new data
232+-- structure, leaving the old one intact, then there is no need
233+-- to worry about how that structure is being shared and
234+-- whether a change by one part of the program might break an
235+-- invariant relied on by another part of the program. These
236+-- considerations are particularly critical in concurrent
237+-- systems, where every piece of mutable state that is shared
238+-- between threads is a potential source of pernicious bugs.
239+-- Indeed, a large part of the recent interest in functional
240+-- programming in industry is due to its simpler behavior in
241+-- the presence of concurrency.
242+
243+-- Another reason for the current excitement about functional
244+-- programming is related to the first: functional programs are
245+-- often much easier to parallelize and physically distribute
246+-- than their imperative counterparts. If running a computation
247+-- has no effect other than producing a result, then it does
248+-- not matter *where* it is run. Similarly, if a data structure
249+-- is never modified destructively, then it can be copied
250+-- freely, across cores or across the network. Indeed, the
251+-- "Map-Reduce" idiom, which lies at the heart of massively
252+-- distributed query processors like Hadoop and is used by
253+-- Google to index the entire web is a classic example of
254+-- functional programming.
255+
256+-- For purposes of this course, functional programming has yet
257+-- another significant attraction: it serves as a bridge
258+-- between logic and computer science. Indeed, Lean itself can
259+-- be viewed as a combination an extremely expressive
260+-- functional programming language plus a set of tools for
261+-- stating and proving logical assertions. Moreover, when we
262+-- come to look more closely, we find that these two sides of
263+-- Lean are actually aspects of the very same underlying
264+-- machinery -- i.e., *proofs are programs*.
