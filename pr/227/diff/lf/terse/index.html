5+-- ## Welcome
6+
7+-- This is the entry point to a series of electronic textbooks
8+-- on various aspects of *Software Foundations*, the
9+-- mathematical underpinnings of reliable software. Topics in
10+-- the series include basic concepts of logic, functional
11+-- programming, computer-assisted theorem proving, operational
12+-- semantics, logics and techniques for reasoning about
13+-- programs, static type systems, property-based random
14+-- testing, and verification of practical C code. The
15+-- exposition is intended for a broad range of readers, from
16+-- advanced undergraduates to PhD students and researchers. No
17+-- specific background in logic or programming languages is
18+-- assumed, though a degree of mathematical maturity will be
19+-- helpful.
20+
21+-- The principal novelty of the series is that it is one
22+-- hundred percent formalized and machine-checked: each text is
23+-- literally a script for Lean. The books are intended to be
24+-- read alongside (or inside) an interactive session with Lean.
25+-- All the details in the text are fully formalized in Lean,
26+-- and almost all of the exercises are designed to be worked
27+-- using Lean.
28+
29+-- This book, *Logical Foundations in Lean*, lays groundwork
30+-- for the others, introducing the reader to the basic ideas of
31+-- functional programming, formal logic, and Lean itself.
32+
33+-- ## Overview
34+
35+-- Building reliable software is hard -- really hard. The scale
36+-- and complexity of modern systems, the number of people
37+-- involved, and the range of demands placed on them make it
38+-- challenging to build software that is even more-or-less
39+-- correct, much less 100% correct. At the same time, the
40+-- increasing degree to which information processing is woven
41+-- into every aspect of society greatly amplifies the cost of
42+-- bugs and insecurities.
43+
44+-- Computer scientists and software engineers have responded to
45+-- these challenges with a host of techniques for improving
46+-- software reliability, ranging from recommendations about
47+-- managing software projects teams (e.g., extreme programming)
48+-- to design philosophies for libraries (e.g.,
49+-- model-view-controller, publish-subscribe, etc.) and whole
50+-- programming languages (e.g., object-oriented programming,
51+-- functional programming, ...) to mathematical techniques for
52+-- specifying and reasoning about properties of software and
53+-- tools for helping validate these properties. The *Software
54+-- Foundations* books are focused on this last set of tools.
55+
56+-- The present volume weaves together three conceptual threads:
57+
58+-- (A) basic tools from *logic* for making and justifying
59+-- precise claims about programs;
60+
61+-- (B) the use of *provers* (or *proof assistants*) to
62+-- construct rigorous logical arguments;
63+
64+-- (C) *functional programming*, both as a programming method
65+-- that simplifies reasoning about programs and as a bridge
66+-- between programming and logic.
67+
68+-- ### Logic
69+
70+-- Logic is the field of study whose subject matter is *proofs*
71+-- -- unassailable arguments for the truth of particular
72+-- propositions. Volumes have been written about the central
73+-- role of logic in computer science. Manna and Waldinger
74+-- called it "the calculus of computer science," while Halpern
75+-- et al.'s paper *On the Unusual Effectiveness of Logic in
76+-- Computer Science* catalogs scores of ways in which logic
77+-- offers critical tools and insights. Indeed, they observe
78+-- that, "As a matter of fact, logic has turned out to be
79+-- significantly more effective in computer science than it has
80+-- been in mathematics. This is quite remarkable, especially
81+-- since much of the impetus for the development of logic
82+-- during the past one hundred years came from mathematics."
83+
84+-- In particular, the fundamental tools of *inductive proof*
85+-- are ubiquitous across computer science. You have surely seen
86+-- them before, perhaps in a course on discrete math or
87+-- analysis of algorithms, but in this book we will examine
88+-- them more deeply than you have probably done so far.
89+
90+-- ### Proof Assistants
91+
92+-- The flow of ideas between logic and computer science over
93+-- the years has run in both directions, with CS also making
94+-- contributions to logic. One of these has been the
95+-- development of software tools for helping construct and
96+-- validate proofs of logical statements. These tools fall into
97+-- two broad categories:
98+
99+-- - *Automated theorem provers* provide "push-button" operation:
100+--   you give them a proposition and they return either *true* or
101+--   *false* (or, sometimes, *don't know: ran out of time*).
102+--   Although their reasoning capabilities are limited, they have
103+--   matured tremendously in recent decades and are used now in a
104+--   multitude of settings. Examples of such tools include SAT
105+--   solvers, SMT solvers, and model checkers.
106+
107+-- - *Proof assistants* — or just *provers* — are hybrid tools
108+--   that automate the more routine aspects of creating proofs
109+--   while depending on human guidance for more difficult
110+--   aspects. Widely used proof assistants include Isabelle,
111+--   Agda, Twelf, ACL2, PVS, F*, HOL4, Rocq, and Lean, among many
112+--   others.
113+
114+-- This course is based around Lean, a proof assistant that has
115+-- been under development since 2013 and has attracted a large
116+-- and active community of users in both research and at
117+-- companies like DeepMind, OpenAI, Anthropic, MSR, and AWS.
118+
119+-- Lean provides a rich environment for interactive development
120+-- of machine-checked formal reasoning. The kernel of the Lean
121+-- system is a simple proof-checker, which guarantees that only
122+-- correct deduction steps are ever performed. On top of this
123+-- kernel, the Lean environment provides high-level facilities
124+-- for proof development, including a large library of common
125+-- definitions and lemmas, powerful tactics for constructing
126+-- complex proofs semi-automatically, and a highly extensible
127+-- system for defining new proof-automation tactics and
128+-- notations for specific situations.
129+
130+-- Lean and its relatives have become a critical enablers for a
131+-- huge variety of work across computer science and
132+-- mathematics:
133+
134+-- Note to developers (Benjamin Pierce @bcpierce00):

143+-- - As a *platform for modeling programming languages*, they
144+--   have become standard tools for researchers who need to
145+--   describe and reason about complex language definitions. They
146+--   have been used, for example, to check the security of the
147+--   JavaCard platform, obtaining the highest level of common
148+--   criteria certification, and for formal specifications of the
149+--   x86 and LLVM instruction sets and programming languages such
150+--   as C.
151+
152+-- - As *environments for developing formally certified software
153+--   and hardware*, they been used, for example, to build
154+--   CompCert, a fully-verified optimizing compiler for C, and
155+--   CertiKOS, a fully verified hypervisor, for proving the
156+--   correctness of subtle algorithms involving floating point
157+--   numbers, and as the basis for CertiCrypt, FCF, and SSProve,
158+--   which are frameworks for proving cryptographic algorithms
159+--   secure. They are also being used to build verified
160+--   implementations of the open-source RISC-V processor
161+--   architecture.
162+
163+-- - As *proof assistants for mathematics*, they have been used
164+--   to validate and help develop a number of important results.
165+--   For example, the ability to include complex computations
166+--   inside proofs made it possible to develop the first formally
167+--   verified proof of the 4-color theorem. This proof had
168+--   previously been controversial among mathematicians because
169+--   it required checking a large number of configurations using
170+--   a program. More recently, an even more massive effort led to
171+--   a formalization of the Feit-Thompson Theorem, the first
172+--   major step in the classification of finite simple groups.
173+
174+-- ### Functional Programming
175+
176+-- *Functional programming* refers both to a collection of
177+-- idioms that can be used in almost any programming language
178+-- and to a family of languages designed to foreground these
179+-- idioms, including Haskell, OCaml, Standard ML, F##, Scala,
180+-- Scheme, Racket, Common Lisp, Clojure, Erlang, F*, and Lean
181+-- itself.
182+
183+-- Functional programming has been developed over many decades
184+-- — indeed, its roots go back to Church's lambda-calculus from
185+-- the 1930s, well *before* the first electronic computers! But
186+-- since the early '90s it has enjoyed a surge of interest
187+-- among both software engineers and language designers.
188+
189+-- The most basic tenet of functional programming is that,
190+-- whenever possible, computation should be *pure*, in the
191+-- sense that the only effect of execution should be to produce
192+-- a result: it should be free from *side effects* such as I/O,
193+-- assignments to mutable variables, redirecting pointers, etc.
194+-- For example, whereas an *imperative* sorting function might
195+-- take a list of numbers and rearrange its pointers to put the
196+-- list in order, a pure sorting function would take the
197+-- original list and return a fresh list containing the same
198+-- numbers in sorted order.
199+
200+-- A significant benefit of this style of programming is that
201+-- it makes programs easier to understand and reason about. If
202+-- every operation on a data structure yields a new data
203+-- structure, leaving the old one intact, then there is no need
204+-- to worry about how that structure is being shared and
205+-- whether a change by one part of the program might break an
206+-- invariant relied on by another part of the program. These
207+-- considerations are particularly critical in concurrent
208+-- systems, where every piece of mutable state shared between
209+-- threads is a potential source of pernicious bugs.
210+
211+-- Another reason for the popularity of functional programming
212+-- is related to the first: functional programs are often much
213+-- easier to parallelize and physically distribute than their
214+-- imperative counterparts. If running a computation has no
215+-- effect other than producing a result, then it does not
216+-- matter *where* it is run. Similarly, if a data structure is
217+-- never modified destructively, it can be copied freely,
218+-- across cores or across the network. Indeed, the "Map-Reduce"
219+-- idiom, which lies at the heart of massively distributed
220+-- query processors like Hadoop and is used by Google to index
221+-- the entire web, is a classic example of functional
222+-- programming.
223+
224+-- For purposes of these books, functional programming has yet
225+-- another significant attraction: it serves as a bridge
226+-- between logic and computer science. Indeed, Lean itself can
227+-- be viewed as a combination of a small but extremely
228+-- expressive functional programming language and a set of
229+-- tools for stating and proving logical assertions. Moreover,
230+-- when we come to look more closely, we find that these two
231+-- sides of Lean are actually aspects of the very same
232+-- underlying machinery -- i.e., *proofs are programs*.
233+
