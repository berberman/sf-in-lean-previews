19+-- ## Behavioral Equivaleence
20+
21+-- In an earlier chapter, we investigated the correctness of a very simple
22+-- program transformation: the `optimize_0plus` function. The programming
23+-- language we were considering was the first version of the language of
24+-- arithmetic expressions -- with no variables -- so in that setting it was
25+-- very easy to define what it means for a program transformation to be
26+-- correct: it should always yield a program that evaluates to the same number
27+-- as the original.
28+
29+-- To talk about the correctness of program transformations for the full Imp
30+-- language -- in particular, assignment -- we need to consider the role of
31+-- mutable state and develop a more sophisticated notion of correctness, which
32+-- we'll call *behavioral equivalence*.
33+
34+-- For example:
35+
36+-- - `X + 2` is behaviorally equivalent to `1 + X + 1`
37+-- - `X - X` is behaviorally equivalent to `0`
38+-- - `(X - 1) + 1` is *not* behaviorally equivalent to `X`
39+
40+-- ### Definitions
41+
42+-- For `aexp`s and `bexp`s with variables, the definition we want is clear:
43+-- Two `aexp`s or `bexp`s are "behaviorally equivalent" if they evaluate to
44+-- the same result in every state.
45+
46+def Aexp.equiv (a₁ a₂ : Aexp) : Prop :=
47+  ∀ (st: State),
48+    a₁.eval st = a₂.eval st
49+
50+def Bexp.equiv (b₁ b₂ : Bexp) : Prop :=
51+  ∀ (st: State),
52+    b₁.eval st = b₂.eval st
53+
54+-- -- ::::full -- Here are some simple examples of equivalences of arithmetic
55+-- -- and boolean expressions. -- ::::
56+
57+example : Aexp.equiv
58+          (aexp { X - X })
59+          (aexp { 0 }) :=
60+  by
61+    intros st
62+    simp
63+
64+example : Bexp.equiv
65+          (bexp { X - X = 0 })
66+          (bexp { true }) :=
67+  by
68+    intros st
69+    simp
70+
71+-- For commands, the situation is a little more subtle. We can't simply say
72+-- "two commands are behaviorally equivalent if they evaluate to the same
73+-- ending state whenever they are started in the same initial state," because
74+-- some commands, when run in some starting states, don't terminate in any
75+-- final state at all!
76+
77+-- What we need instead is this: two commands are behaviorally equivalent if,
78+-- for any given starting state, they either (1) both diverge or else (2) both
79+-- terminate in the same final state. A compact way to express this is "if the
80+-- first one terminates in a particular state then so does the second, and
81+-- vice versa."
82+
83+def Com.equiv (c₁ c₂: Com) : Prop :=
84+    ∀ (st st': State),
85+      (st =[ c₁ ]=> st') ↔ (st =[ c₂ ]=> st')
86+

103+        | skip => assumption

105+      apply Com.EvalR.seq _ _ _ st

137+theorem if_true_simple: ∀ c₁ c₂,

139+    (imp {if (true) {~c₁} else {~c₂}})

145+    | ifTrue => assumption
146+    | ifFalse => contradiction

148+    apply Com.EvalR.ifTrue
149+    · rfl

152+-- Of course, no programmer would write a conditional whose condition is
153+-- literally `true`. (At least, no human programmer -- compilers and macro
154+-- preprocessors do this sort of thing internally all the time!) But they
155+-- might write one whose condition is *equivalent* to true:
156+
157+-- Note to developers (Sati @satiscugcat):
158+--     The to_verso script seems to use `\[\]` blocks, but these seem to cause
159+--     problems with the tilde. Currently skipping them and just using
160+--     backticks.

162+-- *Theorem*: If `b` is equivalent to `true`, then `if (~b) {~c₁}
163+-- else {~c₂}`
164+-- is equivalent to `c₁`. *Proof*:
165+
166+-- - (`->`) We must show, for all `st` and `st'`, that if
167+--   `st =[ imp {if (~b) {~c₁} else {~c₂}} ]=> st'` then `st =[ c₁ ]=> st'`.
168+
169+--   Proceed by cases on the rules that could possibly have been used to show
170+--   `st =[ imp {if (~b) {~c₁} else {~c₂}} ]=> st'`, namely `Com.EvalR.ifTrue`
171+--   and `Com.EvalR.ifFalse`.
172+
173+--   - Suppose the final rule in the derivation of
174+--     `st =[ imp {if (~b) {~c₁} else {~c₂}} ]=> st'` was `Com.EvalR.ifTrue`. We
175+--     then have, by the premises of `Com.EvalR.ifTrue`, that `st =[ c₁ ]=> st'`.
176+--     This is exactly what we set out to prove.
177+
178+--   - On the other hand, suppose the final rule in the derivation of
179+--     `st =[ imp {if (~b) {~c₁} else {~c₂}} ]=> st'` was `Com.EvalR.ifFalse`. We
180+--     then know that `b.eval st = false` and `st =[ c₂ ]=> st'`.
181+
182+--     Recall that `b` is equivalent to `true`, i.e., forall `st`,
183+--     `b.eval st = (bexp {true}).eval st`. In particular, this means that
184+--     `b.eval st = true`, since `(bexp {true}).eval st = true`. But this is a
185+--     contradiction, since `Com.EvalR.ifFalse` requires that `b.eval st = false`.
186+--     Thus, the final rule could not have been `Com.EvalR.ifFalse`.
187+
188+-- - (`<-`) We must show, for all `st` and `st'`, that if `st =[ c₁ ]=> st'`
189+--   then `st =[ imp {if (~b) {~c₁} else {~c₂}} ]=> st'`.
190+
191+--   Since `b` is equivalent to `true`, we know that `b.eval st` =
192+--   `(bexp {true}).eval st = true` = `true`. Together with the assumption that
193+--   `st =[ c₁ ]=> st'`, we can apply `Com.EvalR.ifTrue` to derive
194+--   `st =[ imp {if (~b) {~c₁} else {~c₂}} ]=> st'`.
195+
196+-- Here is the formal version of this proof:
197+
198+-- Note to developers (Sati @satiscugcat):
199+--     `if_true` causes a naming conflict, I don't know with what.
200+
201+theorem if_true_equiv: ∀ b c₁ c₂,
202+  Bexp.equiv b (bexp {true}) ->
203+  Com.equiv
204+    (imp {if (~b) {~c₁} else {~c₂}})
205+    c₁ := by
206+  intro b c₁ c₂ hb st st'
207+  constructor <;> intro h
208+  case mp =>
209+    cases h with
210+    | ifTrue => assumption
211+    | ifFalse _ _ _ _ _ hb' hc =>
212+      unfold Bexp.equiv at hb; simp at hb
213+      rw [hb] at hb'
214+      contradiction
215+  case mpr =>
216+    apply Com.EvalR.ifTrue <;> try assumption
217+    unfold Bexp.equiv at hb; dsimp at hb
218+    apply hb

273+-- For `while` loops, we can give a similar pair of theorems. A loop whose
274+-- guard is equivalent to `false` is equivalent to `skip`, while a loop whose

280+theorem while_false_equiv : ∀ b c,

301+-- Write an informal proof of `while_false_equiv`.
302+
303+-- To prove the second fact, we need an auxiliary lemma stating that `while`
304+-- loops whose guards are equivalent to `true` never terminate.
305+
306+-- *Lemma*: If `b` is equivalent to `true`, then it cannot be the case that
307+-- `st =[ while (~b) {~c} ]=> st'`.
308+
309+-- *Proof*: Suppose that `st =[ while (~b) {~c} ]=> st'`. We show, by
310+-- induction on a derivation of `st =[ while (~b) {~c} ]=> st'`, that this
311+-- assumption leads to a contradiction. The only two cases to consider are
312+-- `Com.EvalR.whileFalse` and `Com.EvalR.whileTrue`; the others are
313+-- contradictory.
314+
315+-- - Suppose `st =[ while (~b) {~c} ]=> st'` is proved using rule
316+--   `Com.EvalR.whileFalse`. Then by assumption `b.eval st = false`. But this
317+--   contradicts the assumption that `b` is equivalent to `true`.
318+
319+-- - Suppose `st =[ while (~b) {~c} ]=> st'` is proved using rule
320+--   `Com.EvalR.whileTrue`. We must have:
321+
322+--   1. `b.eval st = true`, and
323+
324+--   2. there is some `st₀` such that `st =[ c ] => st₀` and
325+--      `st₀ =[ while (~b) {~c} ]=> st'`.
326+
327+--   3. Also, we are given an induction hypothesis saying that
328+--      `st₀ =[ while (~b) {~c} ]=> st'` leads to a contradiction,
329+
330+--   We obtain a contradiction by 2 and 3.
331+
332+theorem while_true_nonterm : ∀ b c st st',
333+  Bexp.equiv b (bexp {true}) ->
334+  ¬ (st =[ while (~b) {~c} ]=> st') := by
335+  all_goals
336+    intro b c st st' hb contra
337+    have key : ∀ (c': Com) (s s': State), (s =[ c' ]=> s') -> c' = (imp {while (~b) {~c}}) -> False :=
338+      by
339+        intro c' s s' hce
340+        induction hce with
341+        | whileFalse b' s0 c0 hb' =>
342+          intro heq; injection heq with beq ceq
343+          subst beq; rw [hb] at hb'
344+          simp at hb'
345+        | whileTrue s0 s0' s0'' b' c0 hb hc' hwhile ih1 ih2 => exact ih2
346+        | skip => simp
347+        | asgn => simp
348+        | seq => simp
349+        | ifTrue => simp
350+        | ifFalse => simp
351+    exact key (imp {while (~b) {~c}}) st st' contra (by rfl)
352+

490+-- ### Behavioral Equivalence is an Equivalence
491+
492+-- First, let's verify that the equivalences on `Aexp`s, `Bexp`s, and `Com`s
493+-- really are *equivalences* -- ie, that they are reflexive, symmetric, and
494+-- transitive. These proofs are all easy.
495+
496+theorem Aexp.equiv.refl : ∀ (a : Aexp),
497+  a.equiv a := by
498+  intros a st
499+  rfl
500+
501+theorem Aexp.equiv.sym : ∀ (a₁ a₂ : Aexp),
502+  a₁.equiv a₂ → a₂.equiv a₁ := by
503+  intro a₁ a₂ h st
504+  rw [h]
505+
506+theorem Aexp.equiv.trans : ∀ (a₁ a₂ a₂ : Aexp),
507+  a₁.equiv a₂ → a₂.equiv a₃ → a₁.equiv a₃ := by
508+  intro a₁ a₂ a₃ h₁ h₂ st
509+  rw [h₁, h₂]
510+
511+theorem Bexp.equiv.refl : ∀ (b : Bexp),
512+  b.equiv b := by
513+  intros b st
514+  rfl
515+
516+theorem Bexp.equiv.sym : ∀ (b₁ b₂ : Bexp),
517+  b₁.equiv b₂ → b₂.equiv b₁ := by
518+  intro b₁ b₂ h st
519+  rw [h]
520+
521+theorem Bexp.equiv.trans : ∀ (b₁ b₂ b₂ : Bexp),
522+  b₁.equiv b₂ → b₂.equiv b₃ → b₁.equiv b₃ := by
523+  intro b₁ b₂ b₃ h₁ h₂ st
524+  rw [h₁, h₂]
525+
526+theorem Com.equiv.refl : ∀ (c : Com),
527+  c.equiv c := by
528+  intros c st st'
529+  rfl

532+  c₁.equiv c₂ → c₂.equiv c₁ := by

534+  rw [h]

541+-- ### Behavioral Equivalence is a Congruence
542+
543+-- Less obviously, behavioral equivalence is also a *congruence*. That is, the
544+-- equivalence of two subprograms implies the equivalence of the larger
545+-- programs in which they are embedded:
546+
547+-- aequiv a a' ------------------------- cequiv (x := a) (x := a')
548+
549+-- cequiv c1 c1' cequiv c2 c2' -------------------------- cequiv (c1;c2)
550+-- (c1';c2')
551+
552+-- ... and so on for the other forms of commands.
553+
554+-- (Note that we are using the inference rule notation here not as part of an
555+-- inductive definition, but simply to write down some valid implications in a
556+-- readable format. We prove these implications below.)
557+
558+-- We will see a concrete example of why these congruence properties are
559+-- important in the following section (in the proof of
560+-- `fold_constants_com_sound`), but the main idea is that they allow us to
561+-- replace a small part of a large program with an equivalent small part and
562+-- know that the whole large programs are equivalent *without* doing an
563+-- explicit proof about the parts that didn't change -- i.e., the "proof
564+-- burden" of a small change to a large program is proportional to the size of
565+-- the change, not the program!
