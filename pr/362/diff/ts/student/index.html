8+--  # Sub: Subtyping
9+
10+--  ## Concepts
11+
12+--  We now turn to *subtyping*, a key feature of - in particular -
13+--  object-oriented programming languages.
14+
15+--  ### A Motivating Example
16+
17+--  Suppose we are writing a program involving two record types defined as
18+--  follows:
19+--
20+--            Person  = {name:String, age:Nat}
21+--            Student = {name:String, age:Nat, gpa:Nat}
22+
23+--  In the simply typed lamdba-calculus with records, the term
24+--
25+--          (λ r:Person. (r.age)+1) {name="Pat", age=21, gpa=1}
26+--
27+--  is not typable, since it applies a function that wants a two-field
28+--  record to an argument that actually provides three fields, while the
29+--  `app` rule demands that the domain type of the function being applied
30+--  must match the type of the argument precisely.
31+--
32+--  But this is silly: we're passing the function a *better* argument than
33+--  it needs! The only thing the body of the function can possibly do with
34+--  its record argument `r` is project the field `age` from it: nothing
35+--  else is allowed by the type, and the presence or absence of an extra
36+--  `gpa` field makes no difference at all. So, intuitively, it seems that
37+--  this function should be applicable to any record value that has at
38+--  least an `age` field.
39+--
40+--  More generally, a record with more fields is "at least as good in any
41+--  context" as one with just a subset of these fields, in the sense that
42+--  any value belonging to the longer record type can be used *safely* in
43+--  any context expecting the shorter record type. If the context expects
44+--  something with the shorter type but we actually give it something with
45+--  the longer type, nothing bad will happen (formally, the program will
46+--  not get stuck).
47+--
48+--  The principle at work here is called *subtyping*. We say that "`σ` is a
49+--  subtype of `τ`", written `σ <: τ`, if a value of type `σ` can safely be
50+--  used in any context where a value of type `τ` is expected. The idea of
51+--  subtyping applies not only to records, but to all of the type
52+--  constructors in the language -- functions, pairs, etc.
53+
54+--  Safe substitution principle:
55+--
56+--  - `σ` is a subtype of `τ`, written `σ <: τ`, if a value of type `σ` can
57+--    safely be used in any context where a value of type `τ` is expected.
58+
59+--  ### Subtyping and Object-Oriented Languages
60+
61+--  Subtyping plays a fundamental role in many programming languages -- in
62+--  particular, it is central to the design of object-oriented languages
63+--  and their libraries.
64+--
65+--  An *object* in Java, C#, etc. can be thought of as a record, some of
66+--  whose fields are functions ("methods") and some of whose fields are
67+--  data values ("fields" or "instance variables"). Invoking a method `m`
68+--  of an object `o` on some arguments `a₁..an` roughly consists of
69+--  projecting out the `m` field of `o` and applying it to `a₁..an`.
70+--
71+--  The type of an object is called a *class* -- or, in some languages, an
72+--  *interface*. It describes which methods and which data fields the
73+--  object offers. Classes and interfaces are related by the *subclass* and
74+--  *subinterface* relations. An object belonging to a subclass (or
75+--  subinterface) is required to provide all the methods and fields of one
76+--  belonging to a superclass (or superinterface), plus possibly some more.
77+--
78+--  The fact that an object from a subclass can be used in place of one
79+--  from a superclass provides a degree of flexibility that is extremely
80+--  handy for organizing complex libraries. For example, a GUI toolkit like
81+--  Java's Swing framework might define an abstract interface `Component`
82+--  that collects together the common fields and methods of all objects
83+--  having a graphical representation that can be displayed on the screen
84+--  and interact with the user, such as the buttons, checkboxes, and
85+--  scrollbars of a typical GUI. A method that relies only on this common
86+--  interface can now be applied to any of these objects.
87+--
88+--  Of course, real object-oriented languages include many other features
89+--  besides these. For example, fields can be updated. Fields and methods
90+--  can be declared "private". Classes can give *initializers* that are
91+--  used when constructing objects. Code in subclasses can cooperate with
92+--  code in superclasses via *inheritance*. Classes can have static methods
93+--  and fields. Etc., etc.
94+--
95+--  To keep things simple here, we won't deal with any of these issues --
96+--  in fact, we won't even talk any more about objects or classes. (There
97+--  is a lot of discussion in Pierce (2002), if you are interested.)
98+--  Instead, we'll study the core concepts behind the subclass /
99+--  subinterface relation in the simplified setting of the STLC.
100+
101+--  ### The Subsumption Rule
102+
103+--  τ₂ Our goal for this chapter is to add subtyping to the simply typed
104+--  lambda-calculus (with some basic extensions). This involves two steps:
105+--
106+--  - Defining a binary *subtype relation* between types.
107+--  - Enriching the typing relation to take subtyping into account.
108+--
109+--  The second step is actually very simple. We add just a single rule to
110+--  the typing relation: the so-called *rule of subsumption*:
111+--
112+--                               Γ ⊢ t₁ ⦂ τ₁     τ₁ <: τ₂
113+--                               --------------------------           (sub)
114+--                                     Γ ⊢ t₁ ⦂ τ₂
115+--
116+--  This rule says, intuitively, that it is OK to "forget" some of what we
117+--  know about a term.
118+
119+--  For example, we may know that `t₁` is a record with two fields (e.g.,
120+--  `τ₁ = {x:α→α, y:β→β}`, but choose to forget about one of the fields
121+--  (`τ₂ = {y:β→β}`) so that we can pass `t₁` to a function that requires
122+--  just a single-field record.
123+
124+--  ### The Subtype Relation
125+
126+--  The first step -- the definition of the relation `σ <: τ` -- is where
127+--  all the action is. Let's look at each of the clauses of its definition.
128+
129+--  #### Structural Rules
130+
131+--  To start off, we impose two "structural rules" that are independent of
132+--  any particular type constructor: a rule of *transitivity*, which says
133+--  intuitively that, if `σ` is better (richer, safer) than `υ` and `υ` is
134+--  better than `τ`, then `σ` is better than `τ`...
135+--
136+--                                    σ <: υ    υ <: τ
137+--                                    ----------------                        (trans)
138+--                                         σ <: τ
139+--
140+--  ... and a rule of *reflexivity*, since certainly any type `τ` is as
141+--  good as itself:
142+--
143+--                                         ------                              (refl)
144+--                                         τ <: τ
145+
146+--  #### Products
147+
148+--  Now we consider the individual type constructors, one by one, beginning
149+--  with product types. We consider one pair to be a subtype of another if
150+--  each of its components is.
151+--
152+--                                  σ₁ <: τ₁    σ₂ <: τ₂
153+--                                  --------------------                        (prod)
154+--                                   σ₁ × σ₂ <: τ₁ × τ₂
155+
156+--  The subtyping rule for arrows is a little less intuitive. Suppose we
157+--  have functions `f` and `g` with these types:
158+--
159+--             f : C → Student
160+--             g : (C→Person) → D
161+--
162+--  That is, `f` is a function that yields a record of type `Student`, and
163+--  `g` is a (higher-order) function that expects its argument to be a
164+--  function yielding a record of type `Person`. Also suppose that
165+--  `Student` is a subtype of `Person`. Then the application `g f` is safe
166+--  even though their types do not match up precisely, because the only
167+--  thing `g` can do with `f` is to apply it to some argument (of type
168+--  `C`); the result will actually be a `Student`, while `g` will be
169+--  expecting a `Person`, but this is safe because the only thing `g` can
170+--  then do is to project out the two fields that it knows about (`name`
171+--  and `age`), and these will certainly be among the fields that are
172+--  present.
173+--
174+--  This example suggests that the subtyping rule for arrow types should
175+--  say that two arrow types are in the subtype relation if their results
176+--  are:
177+--
178+--                                        σ₂ <: τ₂
179+--                                    ----------------                     (arrow_co)
180+--                                  σ₁ → σ₂ <: σ₁ → τ₂
181+--
182+--  We can generalize this to allow the arguments of the two arrow types to
183+--  be in the subtype relation as well:
184+--
185+--                                  τ₁ <: σ₁    σ₂ <: τ₂
186+--                                  --------------------                      (arrow)
187+--                                    σ₁ → σ₂ <: τ₁ → τ₂
188+--
189+--  But notice that the argument types are subtypes "the other way round":
190+--  in order to conclude that `σ₁→σ₂` to be a subtype of `τ₁→τ₂`, it must
191+--  be the case that `τ₁` is a subtype of `σ₁`. The arrow constructor is
192+--  said to be *contravariant* in its first argument and *covariant* in its
193+--  second.
194+--
195+--  Here is an example that illustrates this:
196+--
197+--             f : Person → C
198+--             g : (Student → C) → D
199+--
200+--  The application `g f` is safe, because the only thing the body of `g`
201+--  can do with `f` is to apply it to some argument of type `Student`.
202+--  Since `f` requires records having (at least) the fields of a `Person`,
203+--  this will always work. So `Person → C` is a subtype of `Student → C`
204+--  since `Student` is a subtype of `Person`.
205+--
206+--  The intuition is that, if we have a function `f` of type `σ₁→σ₂`, then
207+--  we know that `f` accepts elements of type `σ₁`; clearly, `f` will also
208+--  accept elements of any subtype `τ₁` of `σ₁`. The type of `f` also tells
209+--  us that it returns elements of type `σ₂`; we can also view these
210+--  results belonging to any supertype `τ₂` of `σ₂`. That is, any function
211+--  `f` of type `σ₁→σ₂` can also be viewed as having type `τ₁→τ₂`.
212+

249+--  #### Records
250+
251+--  What about subtyping for record types?
252+--
253+--  The basic intuition is that it is always safe to use a "bigger" record
254+--  in place of a "smaller" one. That is, given a record type, adding extra
255+--  fields will always result in a subtype. If some code is expecting a
256+--  record with fields `x` and `y`, it is perfectly safe for it to receive
257+--  a record with fields `x`, `y`, and `z`; the `z` field will simply be
258+--  ignored. For example,
259+--
260+--          {name:String, age:Nat, gpa:Nat} <: {name:String, age:Nat}
261+--          {name:String, age:Nat} <: {name:String}
262+--          {name:String} <: {}
263+--
264+--  This is known as "width subtyping" for records.
265+--
266+--  We can also create a subtype of a record type by replacing the type of
267+--  one of its fields with a subtype. If some code is expecting a record
268+--  with a field `x` of type `τ`, it will be happy with a record having a
269+--  field `x` of type `σ` as long as `σ` is a subtype of `τ`. For example,
270+--
271+--          {x:Student} <: {x:Person}
272+--
273+--  This is known as "depth subtyping".
274+--
275+--  Finally, although the fields of a record type are written in a
276+--  particular order, the order does not really matter. For example,
277+--
278+--          {name:String,age:Nat} <: {age:Nat,name:String}
279+--
280+--  This is known as "permutation subtyping".
281+--
282+--  We *could* formalize these requirements in a single subtyping rule for
283+--  records as follows:
284+--
285+--                              ∀ jk in j₁..jn,
286+--                          ∃ ip in i₁..im, such that
287+--                              jk=ip and σp <: τk
288+--                        ----------------------------------                    (rcd)
289+--                        {i₁:σ₁...im:σm} <: {j₁:τ₁...jn:τn}
290+--
291+--  That is, the record on the left should have all the field labels of the
292+--  one on the right (and possibly more), while the types of the common
293+--  fields should be in the subtype relation.
294+--
295+--  However, this rule is rather heavy and hard to read, so it is often
296+--  decomposed into three simpler rules, which can be combined using
297+--  `trans` to achieve all the same effects.
298+--
299+--  First, adding fields to the end of a record type gives a subtype:
300+--
301+--                                     n > m
302+--                       ---------------------------------                 (rcdWidth)
303+--                       {i₁:τ₁...in:τn} <: {i₁:τ₁...im:τm}
304+--
305+--  We can use `rcdWidth` to drop later fields of a multi-field record
306+--  while keeping earlier fields, showing for example that
307+--  `{age:Nat,name:String} <: {age:Nat}`.
308+--
309+--  Second, subtyping can be applied inside the components of a compound
310+--  record type:
311+--
312+--                             σ₁ <: τ₁  ...  σn <: τn
313+--                        ----------------------------------               (rcdDepth)
314+--                        {i₁:σ₁...in:σn} <: {i₁:τ₁...in:τn}
315+--
316+--  For example, we can use `rcdDepth` and `rcdWidth` together to show that
317+--  `{y:Student, x:Nat} <: {y:Person}`.
318+--
319+--  Third, subtyping can reorder fields. For example, we want
320+--  `{name:String, gpa:Nat, age:Nat} <: Person`, but we haven't quite
321+--  achieved this yet: using just `rcdDepth` and `rcdWidth` we can only
322+--  drop fields from the *end* of a record type. So we add:
323+--
324+--               {i₁:σ₁...in:σn} is a permutation of {j₁:τ₁...jn:τn}
325+--               ---------------------------------------------------        (rcdPerm)
326+--                        {i₁:σ₁...in:σn} <: {j₁:τ₁...jn:τn}
327+--
328+--  It is worth noting that full-blown language designs may choose not to
329+--  adopt all of these subtyping rules. For example, in Java:
330+--
331+--  - Each class member (field or method) can be assigned a single index,
332+--    adding new indices "on the right" as more members are added in
333+--    subclasses (i.e., no permutation for classes).
334+--
335+--  - A class may implement multiple interfaces -- so-called "multiple
336+--    inheritance" of interfaces (i.e., permutation is allowed for
337+--    interfaces).
338+--
339+--  - In early versions of Java, a subclass could not change the argument
340+--    or result types of a method of its superclass (i.e., no depth
341+--    subtyping or no arrow subtyping, depending how you look at it).
342+

362+--  #### ⊤
363+
364+--  Finally, it is convenient to give the subtype relation a maximum
365+--  element -- a type that lies above every other type and is inhabited by
366+--  all (well-typed) values. We do this by adding to the language one new
367+--  type constant, called `⊤` (pronounced "⊤" and written ⊤), together with
368+--  a subtyping rule that places it above every other type in the subtype
369+--  relation:
370+--
371+--                                         --------                             (⊤)
372+--                                         σ <: ⊤
373+--
374+--  The `⊤` type is an analog of the `Object` type in Java and C#.
375+
376+--  #### Summary
377+
378+--  In summary, we form the STLC with subtyping by starting with the pure
379+--  STLC (over some set of base types) and then...
380+--
381+--  - adding a base type `⊤`,
382+--  - adding the rule of subsumption
383+--
384+--                               Γ ⊢ t₁ ⦂ τ₁     τ₁ <: τ₂
385+--                               --------------------------------            (sub)
386+--                                     Γ ⊢ t₁ ⦂ τ₂
387+--
388+--  to the typing relation, and
389+--
390+--  - defining a subtype relation as follows:
391+--
392+--                                    σ <: υ    υ <: τ
393+--                                    ----------------                        (trans)
394+--                                         σ <: τ
395+--
396+--                                         ------                              (refl)
397+--                                         τ <: τ
398+--
399+--                                         --------                             (⊤)
400+--                                         σ <: ⊤
401+--
402+--                                  σ₁ <: τ₁    σ₂ <: τ₂
403+--                                  --------------------                       (prod)
404+--                                   σ₁ × σ₂ <: τ₁ × τ₂
405+--
406+--                                  τ₁ <: σ₁    σ₂ <: τ₂
407+--                                  --------------------                      (arrow)
408+--                                  σ₁ → σ₂ <: τ₁ → τ₂
409+--
410+--                                     n > m
411+--                       ---------------------------------                 (rcdWidth)
412+--                       {i₁:τ₁...in:τn} <: {i₁:τ₁...im:τm}
413+--
414+--                             σ₁ <: τ₁  ...  σn <: τn
415+--                        ----------------------------------               (rcdDepth)
416+--                        {i₁:σ₁...in:σn} <: {i₁:τ₁...in:τn}
417+--
418+--               {i₁:σ₁...in:σn} is a permutation of {j₁:τ₁...jn:τn}
419+--               ---------------------------------------------------        (rcdPerm)
420+--                        {i₁:σ₁...in:σn} <: {j₁:τ₁...jn:τn}
421+

1387+--  ### Progress
1388+
1389+--  The proof of progress now proceeds just like the one for the pure STLC,
1390+--  except that in several places we invoke canonical forms lemmas...
1391+--
1392+--  *Theorem* (Progress): For any term `t` and type `τ`, if `∅ ⊢ t ⦂ τ`
1393+--  then `t` is a value or `t ⟶ t'` for some term `t'`.
1394+--
1395+--  *Proof*: Let `t` and `τ` be given, with `∅ ⊢ t ⦂ τ`. Proceed by
1396+--  induction on the typing derivation.
1397+--
1398+--  The cases for `abs`, `unit`, `tru` and `fls` are immediate because
1399+--  abstractions, `unit`, `true`, and `false` are already values. The `var`
1400+--  case is vacuous because variables cannot be typed in the empty context.
1401+--  The remaining cases are more interesting:
1402+--
1403+--  - If the last step in the typing derivation uses rule `app`, then there
1404+--    are terms `t₁` `t₂` and types `τ₁` and `τ₂` such that `t = t₁ t₂`,
1405+--    `τ = τ₂`, `∅ ⊢ t₁ ⦂ τ₁ → τ₂`, and `∅ ⊢ t₂ ⦂ τ₁`. Moreover, by the
1406+--    induction hypothesis, either `t₁` is a value or it steps, and either
1407+--    `t₂` is a value or it steps. There are three possibilities to
1408+--    consider:
1409+--
1410+--    - First, suppose `t₁ ⟶ t₁'` for some term `t₁'`. Then
1411+--      `t₁ t₂ ⟶ t₁' t₂` by `app₁'`.
1412+--
1413+--    - Second, suppose `t₁` is a value and `t₂ ⟶ t₂'` for some term `t₂'`.
1414+--      Then `t₁ t₂ ⟶ t₁ t₂'` by rule `app₂` because `t₁` is a value.
1415+--
1416+--    - Third, suppose `t₁` and `t₂` are both values. By the canonical
1417+--      forms lemma for arrow types, we know that `t₁` has the form
1418+--      `λ x : σ₁ . t₂` for some `x`, `σ₁`, and `s₂`. But then
1419+--      `(λ x : σ₁ . s₂) t₂ ⟶ [x := t₂] s₂` by `appAbs`, since `t₂` is a
1420+--      value.
1421+--
1422+--  - If the final step of the derivation uses rule `if`, then there are
1423+--    terms `t₁`, `t₂`, and `t₃` such that `t = if t₁ then t₂ else t₃`,
1424+--    with `∅ ⊢ t₁ ⦂ Bool` and with `∅ ⊢ t₂ ⦂ τ` and `∅ ⊢ t₃ ⦂ τ`.
1425+--    Moreover, by the induction hypothesis, either `t₁` is a value or it

1483+--  ### Inversion Lemmas for Typing
1484+
1485+--  The proof of the preservation theorem also becomes a little more
1486+--  complex with the addition of subtyping. The reason is that, as with the
1487+--  "inversion lemmas for subtyping" above, there are a number of facts
1488+--  about the typing relation that are immediate from the definition in the
1489+--  pure STLC (formally: that can be obtained directly from the `inversion`
1490+--  tactic) but that require real proofs in the presence of subtyping
1491+--  because there are multiple ways to derive the same `HasType` statement.
1492+--
1493+--  The following inversion lemma tells us that, if we have a derivation of
1494+--  some typing statement `Γ ⊢ λ x : σ₁ . t₂ ⦂ τ` whose subject is an
1495+--  abstraction, then there must be some subderivation giving a type to the
1496+--  body `t₂`.
1497+
1498+--  *Lemma*: If `Γ ⊢ λ x : σ₁ . t₂ ⦂ τ`, then there is a type `σ₂` such
1499+--  that `x ↦ σ₁ ;  Γ ⊢ t₂ ⦂ σ` and `σ₁ → σ₂ <: τ`.
1500+--
1501+--  Notice that the lemma does *not* say, "then `τ` itself is an arrow
1502+--  type" -- this is tempting, but false! (Why?)
1503+
1504+--  *Proof*: Let `Γ`, `x`, `σ₁`, `t₂` and `τ` be given as described.
1505+--  Proceed by induction on the derivation of `Γ ⊢ λ x : σ₁ . t₂ ⦂ τ`. The
1506+--  cases for `var` and `app` are vacuous as those rules cannot be used to
1507+--  give a type to a syntactic abstraction.
1508+--
1509+--  - If the last step of the derivation is a use of `abs` then there is a
1510+--    type `τ₁₂` such that `τ = σ₁ → τ₁₂` and `x ↦ σ₁; Γ ⊢ t₂ ⦂ τ₁₂`.
1511+--    Picking `τ₁₂` for `σ₂` gives us what we need, since
1512+--    `σ₁ → τ₁₂ <: σ₁ → τ₁₂` follows from `rfl`.
1513+--
1514+--  - If the last step of the derivation is a use of `sub` then there is a
1515+--    type `σ` such that `σ <: τ` and `Γ ⊢ λx : σ₁, t₂ ⦂ σ`. The IH for the
1516+--    typing subderivation tells us that there is some type `σ₂` with
1517+--    `σ₁ → σ₂ <: σ` and `x↦σ₁; Γ ⊢ t₂ ⦂ σ₂`. Picking type `σ₂` gives us
1518+--    what we need, since `σ₁ → σ₂ <: τ` then follows by `trans`.
1519+--
1520+--  Formally:
1521+
1522+theorem typing_inversion_abs {Γ : Context} {x : String} {σ₁ : Ty} {t₂ : Tm} {τ : Ty}
1523+  (h : <{ ~Γ ⊢ λ ~x : ~σ₁ . ~t₂ ⦂ ~τ }>) :
1524+    ∃ σ₂, <{ ~σ₁ → ~σ₂ }> <: τ ∧ <{ ~x ↦ ~σ₁ ; ~Γ ⊢ ~t₂ ⦂ ~σ₂ }> := by
1525+
1526+  generalize heq : <{ λ ~x : ~σ₁ . ~t₂ }> = t at h
1527+  induction h with (subst_vars; try contradiction)
1528+  | abs Γ x τ₁ τ₂ t₁ h i =>
1529+      inversion heq; exists τ₁; solve_by_elim using StlcSubTyping
1530+  | sub Γ t₁ τ₁ τ₂ ht hs ih =>
1531+      obtain ⟨σ₂, hs', ht'⟩ := ih rfl
1532+      exists σ₂; solve_by_elim using StlcSubTyping

1601+--  induction on typing derivations, rather than on terms. The

1606+theorem substitution_preserves_typing {Γ : Context} {x : String} {τ₁ : Ty} {t v : Tm} {τ : Ty}
1607+    (ht : <{ ~x ↦ ~τ₁ ; ~Γ ⊢ ~t ⦂ ~τ }>)

1609+    <{ ~Γ ⊢ [~x := ~v] ~t ⦂ ~τ }> := by

1614+  | var Γ y σ h =>

1617+        apply weakening_empty at hv
1618+        simp; assumption
1619+      · rw [PartialMap.update_neq] at h <;> simp_all
1620+        apply_rules using StlcSubTyping

1628+--  ### Preservation
1629+
1630+--  The proof of preservation now proceeds pretty much as in earlier
1631+--  chapters, using the substitution lemma at the appropriate point and the
1632+--  inversion lemma from above to extract structural information from
1633+--  typing assumptions.
1634+--
1635+--  *Theorem* (Preservation): If `t`, `t'` are terms and `τ` is a type such
1636+--  that `∅ ⊢ t ⦂ τ` and `t ⟶ t'`, then `∅ ⊢ t' ⦂ τ`.
1637+--
1638+--  *Proof*: Let `t` and `τ` be given such that `∅ ⊢ t ⦂ τ`. We proceed by
1639+--  induction on the structure of this typing derivation. The `abs`,
1640+--  `unit`, `tru`, and `fls` cases are vacuous because abstractions and
1641+--  constants don't step. Case `var` is vacuous as well, since the context
1642+--  is empty.
1643+--
1644+--  - If the final step of the derivation is by `app`, then there are terms
1645+--    `t₁` and `t₂` and types `τ₁` and `τ₂` such that `t = t₁ t₂`,
1646+--    `τ = τ₂`, `∅ ⊢ t₁ ⦂ τ₁ → τ₂`, and `∅ ⊢ t₂ ⦂ τ₁`.
1647+--
1648+--    By the definition of the step relation, there are three ways `t₁ t₂`
1649+--    can step. Cases `app₁'` and `app₂` follow immediately by the
1650+--    induction hypotheses for the typing subderivations and a use of
1651+--    `app`.
1652+--
1653+--    Suppose instead `t₁ t₂` steps by `appAbs`. Then `t₁ = λ x:σ . τ₁₂`
1654+--    for some type `σ` and term `τ₁₂`, and `t' = [x:=t₂] τ₁₂`.
1655+--
1656+--    By lemma `abs_arrow`, we have `τ₁ <: σ` and `x:σ₁ ⊢ t₂ ⦂ τ₂`. It then
1657+--    follows by the substitution lemma (`substitution_preserves_typing`)
1658+--    that `∅ ⊢ [x:=t₂] τ₁₂ ⦂ τ₂` as desired.
1659+--
1660+--  - If the final step of the derivation uses rule `if`, then there are
1661+--    terms `t₁`, `t₂`, and `t₃` such that `t = if t₁ then t₂ else t₃`,
1662+--    with `∅ ⊢ t₁ ⦂ Bool` and with `∅ ⊢ t₂ ⦂ τ` and `∅ ⊢ t₃ ⦂ τ`.
1663+--    Moreover, by the induction hypothesis, if `t₁` steps to `t₁'` then
1664+--    `∅ ⊢ t₁' : Bool`. There are three cases to consider, depending on
1665+--    which rule was used to show `t ⟶ t'`.
1666+--
1667+--    - If `t ⟶ t'` by rule `if`, then `t' = if t₁' then t₂ else t₃` with
1668+--      `t₁ ⟶ t₁'`. By the induction hypothesis, `∅ ⊢ t₁' ⦂ Bool`, and so
1669+--      `∅ ⊢ t' ⦂ τ` by `if`.
1670+--
1671+--    - If `t ⟶ t'` by rule `ifTrue` or `ifFalse`, then either `t' = t₂` or
1672+--      `t' = t₃`, and `∅ ⊢ t' ⦂ τ` follows by assumption.
1673+--
1674+--  - If the final step of the derivation is by `sub`, then there is a type
1675+--    `σ` such that `σ <: τ` and `∅ ⊢ t ⦂ σ`. The result is immediate by
1676+--    the induction hypothesis for the typing subderivation and an
1677+--    application of `sub`.
1678+--
1679+--  Qed.
1680+
1681+theorem preservation {t t' : Tm} {τ : Ty}
1682+  (ht : <{ ∅ ⊢ ~t ⦂ ~τ }>)
1683+  (hs : t ⟶ t') :
1684+  <{ ∅ ⊢ ~t' ⦂ ~τ }> := by
1685+
1686+  generalize heq : (∅ : Context) = Γ at ht
1687+  induction ht generalizing t' with (subst_vars; first
1688+    -- discharge the goals where `t` doesn't step
1689+    | inversion hs <;> constructor <;> simp_all; done
1690+    | try (inversion hs; apply_rules using StlcSubTyping; done))
1691+  | app Γ τ₁' τ₂' t₁' t₂ h₁ h₂ ih₁ ih₂ =>
1692+    inversion hs with (try (constructor <;> apply_rules; done))
1693+    | appAbs _ τ₂ t₁ h =>
1694+        obtain ⟨h₁, h₂⟩ := abs_arrow h₁

1699+    inversion hs with (try (constructor <;> solve_by_elim using StlcSubEval))
