8+--  # Sub: Subtyping
9+
10+--  ## Concepts
11+
12+--  ### A Motivating Example
13+
14+--  Suppose we are writing a program involving two record
15+--  types defined as follows:
16+--
17+--            Person  = {name:String, age:Nat}
18+--            Student = {name:String, age:Nat, gpa:Nat}
19+
20+--  *Problem*: In the pure STLC with records, the following
21+--  term is not typable:
22+--
23+--          (λr:Person. (r.age)+1) {name="Pat",age=21,gpa=1}
24+--
25+--  This is a shame.
26+
27+--  *Idea*: Introduce *subtyping*, formalizing the
28+--  observation that "some types are better than others."
29+
30+--  Safe substitution principle:
31+--
32+--  - `σ` is a subtype of `τ`, written `σ <: τ`, if a value
33+--    of type `σ` can safely be used in any context where a
34+--    value of type `τ` is expected.
35+
36+--  ### Subtyping and Object-Oriented Languages
37+
38+--  Subtyping plays a fundamental role in OO programming
39+--  languages.
40+--
41+--  Roughly, an *object* can be thought of as a record of
42+--  functions ("methods") and data values ("fields" or
43+--  "instance variables").
44+--
45+--  - Invoking a method `m` of an object `o` on some
46+--    arguments `a₁..an` consists of projecting out the `m`
47+--    field of `o` and applying it to `a₁..an`.
48+--
49+--  The type of an object is a *class* (or an *interface*).
50+--
51+--  Classes are related by the *subclass* relation.
52+--
53+--  - An object belonging to a subclass must provide all the
54+--    methods and fields of one belonging to a superclass,
55+--    plus possibly some more.
56+--
57+--  - Thus a subclass object can be used anywhere a
58+--    superclass object is expected.
59+--
60+--  - Very handy for organizing large libraries
61+
62+--  "Of course, real OO languages have lots of other
63+--  features...
64+--
65+--  - mutable fields
66+--  - "private" and other visibility modifiers
67+--  - method inheritance
68+--  - static components
69+--  - etc., etc.
70+--
71+--  We'll ignore all these and focus on core mechanisms.
72+
73+--  ### The Subsumption Rule
74+
75+--  τ₂ Our goal for this chapter is to add subtyping to the
76+--  simply typed lambda-calculus (with some basic
77+--  extensions). This involves two steps:
78+--
79+--  - Defining a binary *subtype relation* between types.
80+--
81+--  - Enriching the typing relation to take subtyping into
82+--    account.
83+--
84+--  The second step is actually very simple. We add just a
85+--  single rule to the typing relation: the so-called *rule
86+--  of subsumption*:
87+--
88+--                               Γ ⊢ t₁ ⦂ τ₁     τ₁ <: τ₂
89+--                               --------------------------           (sub)
90+--                                     Γ ⊢ t₁ ⦂ τ₂
91+--
92+--  This rule says, intuitively, that it is OK to "forget"
93+--  some of what we know about a term.
94+
95+--  ### The Subtype Relation
96+
97+--  The first step -- the definition of the relation
98+--  `σ <: τ` -- is where all the action is. Let's look at
99+--  each of the clauses of its definition.
100+
101+--  #### Structural Rules
102+
103+--  To start off, we impose two "structural rules" that are
104+--  independent of any particular type constructor: a rule
105+--  of *transitivity*, which says intuitively that, if `σ`
106+--  is better (richer, safer) than `υ` and `υ` is better
107+--  than `τ`, then `σ` is better than `τ`...
108+--
109+--                                    σ <: υ    υ <: τ
110+--                                    ----------------                        (trans)
111+--                                         σ <: τ
112+--
113+--  ... and a rule of *reflexivity*, since certainly any
114+--  type `τ` is as good as itself:
115+--
116+--                                         ------                              (refl)
117+--                                         τ <: τ
118+
119+--  #### Products
120+
121+--  Now we consider the individual type constructors, one by
122+--  one, beginning with product types. We consider one pair
123+--  to be a subtype of another if each of its components is.
124+--
125+--                                  σ₁ <: τ₁    σ₂ <: τ₂
126+--                                  --------------------                        (prod)
127+--                                   σ₁ × σ₂ <: τ₁ × τ₂
128+
129+--  Suppose we have functions `f` and `g` with these types:
130+--
131+--          f : C → Student
132+--          g : (C→Person) → D
133+--
134+--  Is it safe to allow the application `g f`?
135+--
136+--  Yes.
137+--
138+--  So we want:
139+--
140+--            C→Student  <:  C→Person
141+--
142+--  I.e., arrow is *covariant* in its right-hand argument.
143+--
144+--  Now suppose we have:
145+--
146+--             f : Person → C
147+--             g : (Student→C) → D
148+--
149+--  Is it safe to allow the application `g f`?
150+--
151+--  Again yes.
152+--
153+--  So we want:
154+--
155+--            Person → C  <:  Student → C
156+--
157+--  I.e., arrow is *contravariant* in its left-hand
158+--  argument.
159+--
160+--  Putting these together...
161+--
162+--                                  τ₁ <: σ₁    σ₂ <: τ₂
163+--                                  --------------------                      (arrow)
164+--                                  σ₁ → σ₂ <: τ₁ → τ₂
165+
166+--   ----------------------------------------
167+
168+--  _Quiz:_
169+
170+--  Suppose we have `σ <: τ` and `υ <: δ`. Which of the
171+--  following subtyping assertions is *false*?
172+--
173+--  (A) `σ×υ <: τ×δ`
174+--
175+--  (B) `τ→υ <: σ→υ`
176+--
177+--  (C) `(σ→υ) → (σ×δ)  <:  (σ→υ) → (τ×υ)`
178+--
179+--  (D) `(τ×υ) → δ  <:  (σ×υ) → δ`
180+--
181+--  (E) `σ→υ <: σ→δ`
182+
183+--   ----------------------------------------
184+
185+--  _Quiz:_
186+
187+--  Suppose again that we have `σ <: τ` and `υ <: δ`. Which
188+--  of the following is incorrect?
189+--
190+--  (A) `(τ→τ)×υ  <: (σ→τ)×δ`
191+--
192+--  (B) `τ→υ <: σ→δ`
193+--
194+--  (C) `(σ→υ) → (σ→δ)  <:  (τ→υ) → (τ→δ)`
195+--
196+--  (D) `(σ→δ) → δ  <:  (τ→υ) → δ`
197+--
198+--  (E) `σ → (δ→υ) <: σ → (υ→υ)`
199+
200+--   ----------------------------------------
201+
202+--  #### Records
203+
204+--  What about subtyping for record types?
205+--
206+--  The basic intuition is that it is always safe to use a
207+--  "bigger" record in place of a "smaller" one. That is,
208+--  given a record type, adding extra fields will always
209+--  result in a subtype. If some code is expecting a record
210+--  with fields `x` and `y`, it is perfectly safe for it to
211+--  receive a record with fields `x`, `y`, and `z`; the `z`
212+--  field will simply be ignored. For example,
213+--
214+--          {name:String, age:Nat, gpa:Nat} <: {name:String, age:Nat}
215+--          {name:String, age:Nat} <: {name:String}
216+--          {name:String} <: {}
217+--
218+--  This is known as "width subtyping" for records.
219+--
220+--  We can also create a subtype of a record type by
221+--  replacing the type of one of its fields with a subtype.
222+--  If some code is expecting a record with a field `x` of
223+--  type `τ`, it will be happy with a record having a field
224+--  `x` of type `σ` as long as `σ` is a subtype of `τ`. For
225+--  example,
226+--
227+--          {x:Student} <: {x:Person}
228+--
229+--  This is known as "depth subtyping".
230+--
231+--  Finally, although the fields of a record type are
232+--  written in a particular order, the order does not really
233+--  matter. For example,
234+--
235+--          {name:String,age:Nat} <: {age:Nat,name:String}
236+--
237+--  This is known as "permutation subtyping".
238+--
239+--  We *could* formalize these requirements in a single
240+--  subtyping rule for records as follows:
241+--
242+--                              ∀ jk in j₁..jn,
243+--                          ∃ ip in i₁..im, such that
244+--                              jk=ip and σp <: τk
245+--                        ----------------------------------                    (rcd)
246+--                        {i₁:σ₁...im:σm} <: {j₁:τ₁...jn:τn}
247+--
248+--  That is, the record on the left should have all the
249+--  field labels of the one on the right (and possibly
250+--  more), while the types of the common fields should be in
251+--  the subtype relation.
252+--
253+--  However, this rule is rather heavy and hard to read, so
254+--  it is often decomposed into three simpler rules, which
255+--  can be combined using `trans` to achieve all the same
256+--  effects.
257+--
258+--  First, adding fields to the end of a record type gives a
259+--  subtype:
260+--
261+--                                     n > m
262+--                       ---------------------------------                 (rcdWidth)
263+--                       {i₁:τ₁...in:τn} <: {i₁:τ₁...im:τm}
264+--
265+--  We can use `rcdWidth` to drop later fields of a
266+--  multi-field record while keeping earlier fields, showing
267+--  for example that `{age:Nat,name:String} <: {age:Nat}`.
268+--
269+--  Second, subtyping can be applied inside the components
270+--  of a compound record type:
271+--
272+--                             σ₁ <: τ₁  ...  σn <: τn
273+--                        ----------------------------------               (rcdDepth)
274+--                        {i₁:σ₁...in:σn} <: {i₁:τ₁...in:τn}
275+--
276+--  For example, we can use `rcdDepth` and `rcdWidth`
277+--  together to show that
278+--  `{y:Student, x:Nat} <: {y:Person}`.
279+--
280+--  Third, subtyping can reorder fields. For example, we
281+--  want `{name:String, gpa:Nat, age:Nat} <: Person`, but we
282+--  haven't quite achieved this yet: using just `rcdDepth`
283+--  and `rcdWidth` we can only drop fields from the *end* of
284+--  a record type. So we add:
285+--
286+--               {i₁:σ₁...in:σn} is a permutation of {j₁:τ₁...jn:τn}
287+--               ---------------------------------------------------        (rcdPerm)
288+--                        {i₁:σ₁...in:σn} <: {j₁:τ₁...jn:τn}
289+--
290+--  It is worth noting that full-blown language designs may
291+--  choose not to adopt all of these subtyping rules. For
292+--  example, in Java:
293+--
294+--  - Each class member (field or method) can be assigned a
295+--    single index, adding new indices "on the right" as
296+--    more members are added in subclasses (i.e., no
297+--    permutation for classes).
298+--
299+--  - A class may implement multiple interfaces -- so-called
300+--    "multiple inheritance" of interfaces (i.e.,
301+--    permutation is allowed for interfaces).
302+--
303+--  - In early versions of Java, a subclass could not change
304+--    the argument or result types of a method of its
305+--    superclass (i.e., no depth subtyping or no arrow
306+--    subtyping, depending how you look at it).
307+
308+--  #### ⊤
309+
310+--  Finally, it is convenient to give the subtype relation a
311+--  maximum element -- a type that lies above every other
312+--  type and is inhabited by all (well-typed) values. We do
313+--  this by adding to the language one new type constant,
314+--  called `⊤` (pronounced "⊤" and written ⊤), together with
315+--  a subtyping rule that places it above every other type
316+--  in the subtype relation:
317+--
318+--                                         --------                             (⊤)
319+--                                         σ <: ⊤
320+--
321+--  The `⊤` type is an analog of the `Object` type in Java
322+--  and C#.
323+
324+--  #### Summary
325+
326+--  In summary, we form the STLC with subtyping by starting
327+--  with the pure STLC (over some set of base types) and
328+--  then...
329+--
330+--  - adding a base type `⊤`,
331+--  - adding the rule of subsumption
332+--
333+--                               Γ ⊢ t₁ ⦂ τ₁     τ₁ <: τ₂
334+--                               --------------------------------            (sub)
335+--                                     Γ ⊢ t₁ ⦂ τ₂
336+--
337+--  to the typing relation, and
338+--
339+--  - defining a subtype relation as follows:
340+--
341+--                                    σ <: υ    υ <: τ
342+--                                    ----------------                        (trans)
343+--                                         σ <: τ
344+--
345+--                                         ------                              (refl)
346+--                                         τ <: τ
347+--
348+--                                         --------                             (⊤)
349+--                                         σ <: ⊤
350+--
351+--                                  σ₁ <: τ₁    σ₂ <: τ₂
352+--                                  --------------------                       (prod)
353+--                                   σ₁ × σ₂ <: τ₁ × τ₂
354+--
355+--                                  τ₁ <: σ₁    σ₂ <: τ₂
356+--                                  --------------------                      (arrow)
357+--                                  σ₁ → σ₂ <: τ₁ → τ₂
358+--
359+--                                     n > m
360+--                       ---------------------------------                 (rcdWidth)
361+--                       {i₁:τ₁...in:τn} <: {i₁:τ₁...im:τm}
362+--
363+--                             σ₁ <: τ₁  ...  σn <: τn
364+--                        ----------------------------------               (rcdDepth)
365+--                        {i₁:σ₁...in:σn} <: {i₁:τ₁...in:τn}
366+--
367+--               {i₁:σ₁...in:σn} is a permutation of {j₁:τ₁...jn:τn}
368+--               ---------------------------------------------------        (rcdPerm)
369+--                        {i₁:σ₁...in:σn} <: {j₁:τ₁...jn:τn}
370+

1192+
1193+--  The proof of preservation now proceeds pretty much as in
1194+--  earlier chapters, using the substitution lemma at the
1195+--  appropriate point and the inversion lemma from above to
1196+--  extract structural information from typing assumptions.
1197+--
1198+--  *Theorem* (Preservation): If `t`, `t'` are terms and `τ`
1199+--  is a type such that `∅ ⊢ t ⦂ τ` and `t ⟶ t'`, then
1200+--  `∅ ⊢ t' ⦂ τ`.
1201+--
1202+--  *Proof*: Let `t` and `τ` be given such that `∅ ⊢ t ⦂ τ`.
1203+--  We proceed by induction on the structure of this typing
1204+--  derivation. The `abs`, `unit`, `tru`, and `fls` cases
1205+--  are vacuous because abstractions and constants don't
1206+--  step. Case `var` is vacuous as well, since the context
1207+--  is empty.
1208+--
1209+--  - If the final step of the derivation is by `app`, then
1210+--    there are terms `t₁` and `t₂` and types `τ₁` and `τ₂`
1211+--    such that `t = t₁ t₂`, `τ = τ₂`, `∅ ⊢ t₁ ⦂ τ₁ → τ₂`,
1212+--    and `∅ ⊢ t₂ ⦂ τ₁`.
1213+--
1214+--    By the definition of the step relation, there are
1215+--    three ways `t₁ t₂` can step. Cases `app₁'` and `app₂`
1216+--    follow immediately by the induction hypotheses for the
1217+--    typing subderivations and a use of `app`.
1218+--
1219+--    Suppose instead `t₁ t₂` steps by `appAbs`. Then
1220+--    `t₁ = λ x:σ . τ₁₂` for some type `σ` and term `τ₁₂`,
1221+--    and `t' = [x:=t₂] τ₁₂`.
1222+--
1223+--    By lemma `abs_arrow`, we have `τ₁ <: σ` and
1224+--    `x:σ₁ ⊢ t₂ ⦂ τ₂`. It then follows by the substitution
1225+--    lemma (`substitution_preserves_typing`) that
1226+--    `∅ ⊢ [x:=t₂] τ₁₂ ⦂ τ₂` as desired.
1227+--
1228+--  - If the final step of the derivation uses rule `if`,
1229+--    then there are terms `t₁`, `t₂`, and `t₃` such that
1230+--    `t = if t₁ then t₂ else t₃`, with `∅ ⊢ t₁ ⦂ Bool` and
1231+--    with `∅ ⊢ t₂ ⦂ τ` and `∅ ⊢ t₃ ⦂ τ`. Moreover, by the
1232+--    induction hypothesis, if `t₁` steps to `t₁'` then
1233+--    `∅ ⊢ t₁' : Bool`. There are three cases to consider,
1234+--    depending on which rule was used to show `t ⟶ t'`.
1235+--
1236+--    - If `t ⟶ t'` by rule `if`, then
1237+--      `t' = if t₁' then t₂ else t₃` with `t₁ ⟶ t₁'`. By
1238+--      the induction hypothesis, `∅ ⊢ t₁' ⦂ Bool`, and so
1239+--      `∅ ⊢ t' ⦂ τ` by `if`.
1240+--
1241+--    - If `t ⟶ t'` by rule `ifTrue` or `ifFalse`, then
1242+--      either `t' = t₂` or `t' = t₃`, and `∅ ⊢ t' ⦂ τ`
1243+--      follows by assumption.
1244+--
1245+--  - If the final step of the derivation is by `sub`, then
1246+--    there is a type `σ` such that `σ <: τ` and
1247+--    `∅ ⊢ t ⦂ σ`. The result is immediate by the induction
1248+--    hypothesis for the typing subderivation and an
1249+--    application of `sub`.
1250+--
1251+--  Qed.
