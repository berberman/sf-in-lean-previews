58--- ### Logic
59-
60--- Logic is the field of study whose subject matter is *proofs* --
61--- unassailable arguments for the truth of particular propositions. Volumes
62--- have been written about the central role of logic in computer science.
63--- Manna and Waldinger called it "the calculus of computer science," while
64--- Halpern et al.'s paper *On the Unusual Effectiveness of Logic in Computer
65--- Science* catalogs scores of ways in which logic offers critical tools and
66--- insights. Indeed, they observe that, "As a matter of fact, logic has turned
67--- out to be significantly more effective in computer science than it has been
68--- in mathematics. This is quite remarkable, especially since much of the
69--- impetus for the development of logic during the past one hundred years came

74--- course on discrete math or analysis of algorithms, but in this book we will
75--- examine them more deeply than you have probably done so far.

77--- ### Proof Assistants
78-
79--- The flow of ideas between logic and computer science over the years has run
80--- in both directions, with CS also making contributions to logic. One of
81--- these has been the development of software tools for helping construct and
82--- validate proofs of logical statements. These tools fall into two broad
83--- categories:
84-
85--- - *Automated theorem provers* provide "push-button" operation: you give them
86---   a proposition and they return either *true* or *false* (or, sometimes,
87---   *don't know: ran out of time*). Although their reasoning capabilities are
88---   limited, they have matured tremendously in recent decades and are used now
89---   in a multitude of settings. Examples of such tools include SAT solvers, SMT
90---   solvers, and model checkers.
91-
92--- - *Proof assistants* — or just *provers* — are hybrid tools that automate the
93---   more routine aspects of creating proofs while depending on human guidance
94---   for more difficult aspects. Widely used proof assistants include Isabelle,
95---   Agda, Twelf, ACL2, PVS, F*, HOL4, Rocq, and Lean, among many others.
96-

98--- development since 2013 and has attracted a large and active community of
99--- users in both research and at companies like DeepMind, OpenAI, Anthropic,
100--- MSR, and AWS.

103--- machine-checked formal reasoning. The kernel of the Lean system is a simple
104--- proof-checker, which guarantees that only correct deduction steps are ever
105--- performed. On top of this kernel, the Lean environment provides high-level
106--- facilities for proof development, including a large library of common
107--- definitions and lemmas, powerful tactics for constructing complex proofs
108--- semi-automatically, and a highly extensible system for defining new
109--- proof-automation tactics and notations for specific situations.

147--- ### Functional Programming
148-
149--- *Functional programming* refers both to a collection of idioms that can be
150--- used in almost any programming language and to a family of languages
151--- designed to foreground these idioms, including Haskell, OCaml, Standard ML,
152--- F#, Scala, Scheme, Racket, Common Lisp, Clojure, Erlang, F*, and Lean
153--- itself.
154-
155--- Functional programming has been developed over many decades — indeed, its
156--- roots go back to Church's lambda-calculus from the 1930s, well *before* the
157--- first electronic computers! But since the early '90s it has enjoyed a surge
158--- of interest among both software engineers and language designers.
159-
160--- The most basic tenet of functional programming is that, whenever possible,
161--- computation should be *pure*, in the sense that the only effect of
162--- execution should be to produce a result: it should be free from *side
163--- effects* such as I/O, assignments to mutable variables, redirecting
164--- pointers, etc. For example, whereas an *imperative* sorting function might
165--- take a list of numbers and rearrange its pointers to put the list in order,
166--- a pure sorting function would take the original list and return a fresh
167--- list containing the same numbers in sorted order.
168-
169--- A significant benefit of this style of programming is that it makes
170--- programs easier to understand and reason about. If every operation on a
171--- data structure yields a new data structure, leaving the old one intact,
172--- then there is no need to worry about how that structure is being shared and
173--- whether a change by one part of the program might break an invariant relied
174--- on by another part of the program. These considerations are particularly
175--- critical in concurrent systems, where every piece of mutable state shared
176--- between threads is a potential source of pernicious bugs.
177-
178--- Another reason for the popularity of functional programming is related to
179--- the first: functional programs are often much easier to parallelize and
180--- physically distribute than their imperative counterparts. If running a
181--- computation has no effect other than producing a result, then it does not
182--- matter *where* it is run. Similarly, if a data structure is never modified
183--- destructively, it can be copied freely, across cores or across the network.
184--- Indeed, the "Map-Reduce" idiom, which lies at the heart of massively
185--- distributed query processors like Hadoop and is used by Google to index the
186--- entire web, is a classic example of functional programming.
187-
188--- For purposes of these books, functional programming has yet another
189--- significant attraction: it serves as a bridge between logic and computer
190--- science. Indeed, Lean itself can be viewed as a combination of a small but
191--- extremely expressive functional programming language and a set of tools for
192--- stating and proving logical assertions. Moreover, when we come to look more
193--- closely, we find that these two sides of Lean are actually aspects of the
194--- very same underlying machinery -- i.e., *proofs are programs*.
