124+-- ## Decorated Programs
125+
126+-- The beauty of Hoare Logic is that it is *syntax directed*:
127+-- the structure of proofs exactly follows the structure of
128+-- programs.
129+
130+-- We can record the essential ideas of a Hoare-logic proof —
131+-- omitting low-level calculational details — by "decorating" a
132+-- program with appropriate assertions on each of its commands.
133+
134+-- Such a *decorated program* carries within itself an argument
135+-- for its own correctness.
136+
137+-- For example, consider the program:
138+
139+--   X := m;
140+--   Z := p;
141+--   while X <> 0 do
142+--     Z := Z - 1;
143+--     X := X - 1
144+--   end
145+
146+-- Here is one possible specification for this program, in the
147+-- form of a Hoare triple:
148+
149+--   {{ True }}
150+--   X := m;
151+--   Z := p;
152+--   while X <> 0 do
153+--     Z := Z - 1;
154+--     X := X - 1
155+--   end
156+--   {{ Z = p - m }}
157+
158+-- Here is a decorated version of this program, embodying a
159+-- proof of this specification:
160+
161+--   {{ True }} ->>
162+--   {{ m = m }}
163+--     X := m
164+--                        {{ X = m }} ->>
165+--                        {{ X = m /\ p = p }};
166+--     Z := p;
167+--                        {{ X = m /\ Z = p }} ->>
168+--                        {{ Z - X = p - m }}
169+--     while X <> 0 do
170+--                        {{ Z - X = p - m /\ X <> 0 }} ->>
171+--                        {{ (Z - 1) - (X - 1) = p - m }}
172+--       Z := Z - 1
173+--                        {{ Z - (X - 1) = p - m }};
174+--       X := X - 1
175+--                        {{ Z - X = p - m }}
176+--     end
177+--   {{ Z - X = p - m /\ ~ (X <> 0) }} ->>
178+--   {{ Z = p - m }}
179+

203+-- Concretely, a decorated program consists of the program's
204+-- text interleaved with assertions (sometimes multiple
205+-- assertions separated by ->>).
206+
207+-- A decorated program can be viewed as a compact
208+-- representation of a proof in Hoare Logic: the assertions
209+-- surrounding each command specify the Hoare triple to be
210+-- proved for that part of the program using one of the Hoare
211+-- Logic rules, and the structure of the program itself shows
212+-- how to assemble all these individual steps into a proof for
213+-- the whole program.

351+-- ## Formal Decorated Programs
352+
353+-- With a little more work, we can *formalize* the definition
354+-- of well-formed decorated programs and *automate* the boring
355+-- mechanical steps in proving that the decorations are
356+-- correct.
357+
358+-- ### Syntax
359+
360+-- The first thing we need to do is to formalize a variant of
361+-- the syntax of Imp commands that includes embedded
362+-- assertions, which we'll call "decorations." We call the new
363+-- commands *decorated commands*, or `dcom`s.
364+
365+-- The choice of exactly where to put assertions in the
366+-- definition of `dcom` is a bit subtle. The simplest thing to
367+-- do would be to annotate every `dcom` with a precondition and
368+-- postcondition — something like this...
369+
370+namespace DComFirstTry
371+
372+inductive DCom where
373+  | skip (pre : Assertion)
374+  | seq (pre : Assertion) (first : DCom)
375+      (middle : Assertion)
376+      (second : DCom) (post : Assertion)
377+  | asgn (x : Ident) (a : Aexp) (post : Assertion)
378+  | cond (pre : Assertion) (b : Bexp)
379+      (thenPre : Assertion) (thenBranch : DCom)
380+      (elsePre : Assertion) (elseBranch : DCom)
381+      (post : Assertion)
382+  | whileDo (pre : Assertion) (b : Bexp)
383+      (bodyPre : Assertion) (body : DCom)
384+      (bodyPost : Assertion) (post : Assertion)
385+  | strengthenPre (pre : Assertion) (body : DCom)
386+  | weakenPost (body : DCom) (post : Assertion)
387+
388+end DComFirstTry
389+
390+-- But this would result in *very* verbose decorated programs
391+-- with a lot of repeated annotations: a simple program like
392+-- `skip;skip` would be decorated like this,
393+
394+--   {{P}} ({{P}} skip {{P}}) ; ({{P}} skip {{P}}) {{P}}
395+
396+-- with pre- and post-conditions around each `skip`, plus
397+-- identical pre- and post-conditions on the semicolon!
398+
399+-- In other words, we don't want both preconditions and
400+-- postconditions on each command, because a sequence of two
401+-- commands would contain redundant decorations — the
402+-- postcondition of the first likely being the same as the
403+-- precondition of the second.
404+
405+-- Instead, our formal syntax of decorated commands will omit
406+-- preconditions whenever possible and embed just
407+-- postconditions.
408+
409+-- - The `skip` command, for example, is decorated only with its
410+--   postcondition
411+
412+--   skip {{ Q }}
413+
414+-- on the assumption that the precondition will be provided by
415+-- somebody else.
416+
417+-- We carry the same assumption through the other syntactic
418+-- forms: each decorated command is assumed to carry its own
419+-- postcondition within itself but take its precondition from
420+-- its context in which it is used.
421+
422+-- - Sequences `d1 ; d2` need no additional decorations.
423+
424+-- Why?
425+
426+-- Because inside `d2` there will be a postcondition, which
427+-- also serves as the postcondition of `d1;d2`.
428+
429+-- Similarly, inside `d1` there will also be a postcondition,
430+-- which additionally serves as the *precondition* for `d2`.
431+
432+-- - An assignment `X := a` is decorated only with its
433+--   postcondition:
434+
435+--   X := a {{ Q }}
436+
437+-- - A conditional `if b then d1 else d2` is decorated with a
438+--   postcondition for the entire statement, as well as
439+--   preconditions for each branch:
440+
441+--   if b then {{ P1 }} d1 else {{ P2 }} d2 end {{ Q }}
442+
443+-- Note to developers (Benjamin Pierce @bcpierce00, before next release, 2025):
444+--     Maybe we need a note here about why we don't just
445+--     calculate P1 and P2 later, once we know the precondition
446+--     of the whole loop. Indeed, we could (and perhaps should,
447+--     as discussed elsewhere), but we are doing something
448+--     simpler for the moment.
449+
450+-- - A loop `while b do d end` is decorated with its final
451+--   postcondition plus a precondition for the body:
452+
453+--   while b do {{ P }} d end {{ Q }}
454+
455+-- The postcondition embedded in `d` serves as the loop
456+-- invariant.
457+
458+-- - Implications `->>` can be added as decorations either for a
459+--   precondition...
460+
461+--   ->> {{ P }} d
462+
463+-- ...or for a postcondition:
464+
465+--   d ->> {{ Q }}
466+
467+-- The former is waiting for another precondition to be
468+-- supplied by the context; the latter relies on the
469+-- postcondition already embedded in `d`.
470+
471+-- Putting this all together gives us the formal syntax of
472+-- decorated commands:
473+
474+inductive DCom where
475+  | skip (post : Assertion)
476+  | seq (first second : DCom)
477+  | asgn (x : Ident) (a : Aexp) (post : Assertion)
478+  | cond (b : Bexp)
479+      (thenPre : Assertion) (thenBranch : DCom)
480+      (elsePre : Assertion) (elseBranch : DCom)
481+      (post : Assertion)
482+  | whileDo (b : Bexp) (bodyPre : Assertion) (body : DCom)
483+      (post : Assertion)
484+  | pre (pre : Assertion) (body : DCom)
485+  | post (body : DCom) (post : Assertion)

595+-- It is easy to go from a `dcom` to a `com` by erasing all
596+-- annotations.
597+
598+def DCom.erase (d : DCom) : Com :=
599+  match d with
600+  | .skip _ => .skip
601+  | .seq d1 d2 => .seq d1.erase d2.erase
602+  | .asgn x a _ => .asgn x a
603+  | .cond b _ d1 _ d2 _ => .cond b d1.erase d2.erase
604+  | .whileDo b _ body _ => .whileDo b body.erase
605+  | .pre _ body => body.erase
606+  | .post body _ => body.erase
607+
608+def Decorated.erase (dec : Decorated) : Com :=
609+  dec.body.erase

611+-- It is also straightforward to extract the precondition and
612+-- postcondition from a decorated program.
613+
614+def Decorated.precondition (dec : Decorated) : Assertion :=

656+  rfl

658+-- The outer Hoare triple of a decorated program is just a
659+-- `Prop`; thus, to show that it is *valid*, we need to produce
660+-- a proof of this proposition.
661+
662+-- We will do this by extracting "proof obligations" from the
663+-- decorations sprinkled throughout the program.
664+
665+-- These obligations are often called *verification
666+-- conditions*, because they are the facts that must be
667+-- verified to see that the decorations are locally consistent
668+-- and thus constitute a proof of validity of the outer triple.
669+
670+-- ### Extracting Verification Conditions
671+
672+-- The function `DCom.VerificationConditions` takes a decorated
673+-- command `d` together with a precondition `P` and returns a
674+-- *proposition* that, if it can be proved, implies that the
675+-- triple
676+
677+--   {{P}} d.erase {{d.postcondition}}
678+
679+-- is valid.
680+
681+-- It does this by walking over `d` and generating a big
682+-- conjunction that includes
683+
684+-- - local consistency checks for each form of command, plus
685+
686+-- - uses of `->>` to bridge the gap between the assertions found
687+--   inside a decorated command and the assertions imposed by the
688+--   external precondition; these uses correspond to applications
689+--   of the consequence rule.
690+
691+-- *Local consistency* is defined as follows...
692+
693+-- - The decorated command
694+
695+--   skip {{Q}}
696+
697+-- is locally consistent with respect to a precondition `P` if
698+-- `P ->> Q`.
699+
700+-- - The sequential composition of `d1` and `d2` is locally
701+--   consistent with respect to `P` if `d1` is locally consistent
702+--   with respect to `P` and `d2` is locally consistent with
703+--   respect to the postcondition of `d1`.
704+
705+-- - An assignment
706+
707+--   X := a {{Q}}
708+
709+-- is locally consistent with respect to a precondition `P` if:
710+
711+--   P ->> Q [X |-> a]
712+
713+-- - A conditional
714+
715+--   if b then {{P1}} d1 else {{P2}} d2 end {{Q}}
716+
717+-- is locally consistent with respect to precondition `P` if
718+
719+-- (1) `P /\ b ->> P1`
720+
721+-- (2) `P /\ ~b ->> P2`
722+
723+-- (3) `d1` is locally consistent with respect to `P1`
724+
725+-- (4) `d2` is locally consistent with respect to `P2`
726+
727+-- (5) `d1.postcondition ->> Q`
728+
729+-- (6) `d2.postcondition ->> Q`
730+
731+-- - A loop
732+
733+--   while b do {{Q}} d end {{R}}
734+
735+-- is locally consistent with respect to precondition `P` if:
736+
737+-- (1) `P ->> d.postcondition`
738+
739+-- (2) `d.postcondition /\ b ->> Q`
740+
741+-- (3) `d.postcondition /\ ~b ->> R`
742+
743+-- (4) `d` is locally consistent with respect to `Q`
744+
745+-- - A command with an extra assertion at the beginning
746+
747+--   ->> {{Q}} d
748+
749+-- is locally consistent with respect to a precondition `P` if:
750+
751+-- (1) `P ->> Q`
752+
753+-- (2) `d` is locally consistent with respect to `Q`
754+
755+-- - A command with an extra assertion at the end
756+
757+--   d ->> {{Q}}
758+
759+-- is locally consistent with respect to a precondition `P` if:
760+
761+-- (1) `d` is locally consistent with respect to `P`
762+
763+-- (2) `d.postcondition ->> Q`
764+
765+-- With all this in mind, we can write a *verification
766+-- condition generator* that takes a decorated command and
767+-- reads off a proposition saying that all its decorations are
768+-- locally consistent.
769+
770+-- Formally, since a decorated command is "waiting for its
771+-- precondition" the main VC generator takes a `dcom` plus a
772+-- given precondition as arguments.
773+
774+-- Note to developers:
775+--     HIDE: There was some discussion in 2016 about whether
776+--     the VC generator should should use equivalence or
777+--     implication in a few places. I (BCP) believe Phil
778+--     (Wadler) changed some instances of the former to the
779+--     latter.
780+--
781+--     HIDE: MRC'20: a written explanation of each part of this
782+--     would be quite nice. BCP 21: Agreed!! (BCP 23: But it's
783+--     kind of what's just above...)
784+
785+def DCom.VerificationConditions
786+    (P : Assertion) (d : DCom) : Prop :=
787+  match d with
788+  | .skip Q =>
789+      P ->> Q
790+  | .seq d1 d2 =>
791+      d1.VerificationConditions P ∧
792+      d2.VerificationConditions d1.postcondition
793+  | .asgn x a Q =>
794+      P ->> Q [x ↦ ~a]
795+  | .cond b P1 d1 P2 d2 Q =>
796+      ({{ P ∧ b }} ->> P1) ∧
797+      ({{ P ∧ ¬ b }} ->> P2) ∧
798+      (d1.postcondition ->> Q) ∧
799+      (d2.postcondition ->> Q) ∧
800+      d1.VerificationConditions P1 ∧
801+      d2.VerificationConditions P2
802+  | .whileDo b bodyPre body q =>
803+      -- The body's postcondition is both the loop invariant
804+      -- and the precondition for the first iteration.
805+      (P ->> body.postcondition) ∧
806+      ({{ body.postcondition ∧ b }} ->> bodyPre) ∧
807+      ({{ body.postcondition ∧ ¬ b }} ->> q) ∧
808+      body.VerificationConditions bodyPre
809+  | .pre P' body =>
810+      (P ->> P') ∧ body.VerificationConditions P'
811+  | .post body Q =>
812+      body.VerificationConditions P ∧
813+      (body.postcondition ->> Q)
814+
815+-- The following key theorem states that
816+-- `DCom.VerificationConditions` does its job correctly. Not
817+-- surprisingly, each of the Hoare Logic rules plays a critical
818+-- role at some point in the proof.
819+
820+theorem verification_correct (d : DCom) (P : Assertion)
821+    (hvc : d.VerificationConditions P) :
822+    ValidHoareTriple P d.erase d.postcondition := by
823+  sorry
824+
825+-- Now that all the pieces are in place, we can define what it
826+-- means to verify an entire program.
827+
828+def Decorated.VerificationConditions
829+    (dec : Decorated) : Prop :=
830+  dec.body.VerificationConditions dec.pre
831+
832+-- And this brings us to the main theorem of this section:
833+
834+theorem verification_conditions_correct (dec : Decorated)
835+    (hvc : dec.VerificationConditions) :
836+    dec.OuterTripleValid := by
837+  exact verification_correct dec.body dec.pre hvc

883+-- Once the outer pre- and postcondition are chosen, the only
884+-- creative part in verifying programs using Hoare Logic is
885+-- finding the right loop invariants...

887+-- ### Example: Slow Subtraction
888+
889+-- The following program subtracts the value of `X` from the
890+-- value of `Y` by repeatedly decrementing both `X` and `Y`. We
891+-- want to verify its correctness with respect to the pre- and
892+-- postconditions shown:
893+
894+--   {{ X = m /\ Y = n }}
895+--     while X <> 0 do
896+--       Y := Y - 1;
897+--       X := X - 1
898+--     end
899+--   {{ Y = n - m }}
900+
901+-- To verify this program, we need to find an invariant `Inv`
902+-- for the loop. As a first step we can leave `Inv` as an
903+-- unknown and build a *skeleton* for the proof by applying the
904+-- rules for local consistency, working from the end of the
905+-- program to the beginning, as usual, and without doing any
906+-- thinking at all yet.
907+
908+-- This leads to the following skeleton:
909+
910+--   (1)    {{ X = m /\ Y = n }}  ->>                   (a)
911+--   (2)    {{ Inv }}
912+--            while X <> 0 do
913+--   (3)              {{ Inv /\ X <> 0 }}  ->>          (c)
914+--   (4)              {{ Inv [X |-> X-1] [Y |-> Y-1] }}
915+--              Y := Y - 1;
916+--   (5)              {{ Inv [X |-> X-1] }}
917+--              X := X - 1
918+--   (6)              {{ Inv }}
919+--            end
920+--   (7)    {{ Inv /\ ~ (X <> 0) }}  ->>                (b)
921+--   (8)    {{ Y = n - m }}
922+
923+-- Examining this skeleton, we can see that any valid `Inv`
924+-- will have to respect three conditions:
925+
926+-- - (a) it must be *weak* enough to be implied by the loop's
927+--   precondition, i.e., (1) must imply (2);
928+
929+-- - (b) it must be *strong* enough to imply the program's
930+--   postcondition, i.e., (7) must imply (8);
931+
932+-- - (c) it must be *preserved* by a single iteration of the
933+--   loop, assuming that the loop guard also evaluates to true,
934+--   i.e., (3) must imply (4).

989+-- ## Weakest Preconditions (Optional)
990+
991+-- Note to developers:
992+--     HIDE: BCP 21: We talked about moving this stuff to the
993+--     HoareAsLogic chapter to lighten this chapter, but it
994+--     fits awkwardly there, so I'm leaving it here. It's
995+--     optional anyway. We might consider assigning one of the
996+--     exercises as advanced-only though.
997+
998+-- A useless (though valid) Hoare triple:
999+
1000+--   {{ False }}  X := Y + 1  {{ X <= 5 }}
1001+
1002+-- A better precondition:
1003+
1004+--   {{ Y <= 4 /\ Z = 0 }}  X := Y + 1 {{ X <= 5 }}
1005+
1006+-- The *best* precondition:
1007+
1008+--   {{ Y <= 4 }}  X := Y + 1  {{ X <= 5 }}
1009+
1010+-- Assertion `Y <= 4` is a *weakest precondition* of command
1011+-- `X := Y + 1` with respect to postcondition `X <= 5`. Think
1012+-- of *weakest* here as meaning "easiest to satisfy": a weakest
1013+-- precondition is one that as many states as possible can
1014+-- satisfy.
1015+
1016+-- `P` is a weakest precondition of command `c` for
1017+-- postcondition `Q` if
1018+
1019+-- - `P` is a precondition, that is, `{{P}} c {{Q}}`; and
1020+
1021+-- - `P` is at least as weak as all other preconditions, that is,
1022+--   if `{{P'}} c {{Q}}` then `P' ->> P`.
1023+
1024+-- Note that weakest preconditions need not be unique. For
1025+-- example, `Y <= 4` was a weakest precondition above, but so
1026+-- are the logically equivalent assertions `Y < 5`,
1027+-- `Y <= 2 * 2`, etc. It is easy to show that any two weakest
1028+-- preconditions `P` and `P'` of a command `c` with respect to
1029+-- postcondition `Q` are logically equivalent; that is,
1030+-- `P <<->> P'`.
1031+
1032+def IsWp (P : Assertion) (c : Com) (Q : Assertion) : Prop :=
1033+  ValidHoareTriple P c Q ∧
1034+  ∀ P' : Assertion, ValidHoareTriple P' c Q → P' ->> P
