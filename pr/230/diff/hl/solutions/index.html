109+-- ## Decorated Programs
110+
111+-- The beauty of Hoare Logic is that it is *syntax directed*: the structure of
112+-- proofs exactly follows the structure of programs.
113+
114+-- We can record the essential ideas of a Hoare-logic proof — omitting
115+-- low-level calculational details — by "decorating" a program with
116+-- appropriate assertions on each of its commands.
117+
118+-- Such a *decorated program* carries within itself an argument for its own
119+-- correctness.
120+
121+-- For example, consider the program:
122+
123+--   X := m;
124+--   Z := p;
125+--   while X <> 0 do
126+--     Z := Z - 1;
127+--     X := X - 1
128+--   end
129+
130+-- Here is one possible specification for this program, in the form of a Hoare
131+-- triple:
132+
133+--   {{ True }}
134+--   X := m;
135+--   Z := p;
136+--   while X <> 0 do
137+--     Z := Z - 1;
138+--     X := X - 1
139+--   end
140+--   {{ Z = p - m }}
141+
142+-- (Note the *parameters* `m` and `p`, which stand for fixed-but-arbitrary
143+-- numbers. Formally, they are simply Lean variables of type `Nat`.)
144+
145+-- Here is a decorated version of this program, embodying a proof of this
146+-- specification:
147+
148+--   {{ True }} ->>
149+--   {{ m = m }}
150+--     X := m
151+--                        {{ X = m }} ->>
152+--                        {{ X = m /\ p = p }};
153+--     Z := p;
154+--                        {{ X = m /\ Z = p }} ->>
155+--                        {{ Z - X = p - m }}
156+--     while X <> 0 do
157+--                        {{ Z - X = p - m /\ X <> 0 }} ->>
158+--                        {{ (Z - 1) - (X - 1) = p - m }}
159+--       Z := Z - 1
160+--                        {{ Z - (X - 1) = p - m }};
161+--       X := X - 1
162+--                        {{ Z - X = p - m }}
163+--     end
164+--   {{ Z - X = p - m /\ ~ (X <> 0) }} ->>
165+--   {{ Z = p - m }}

190+-- Concretely, a decorated program consists of the program's text interleaved
191+-- with assertions (sometimes multiple assertions separated by ->>).
192+
193+-- A decorated program can be viewed as a compact representation of a proof in
194+-- Hoare Logic: the assertions surrounding each command specify the Hoare
195+-- triple to be proved for that part of the program using one of the Hoare
196+-- Logic rules, and the structure of the program itself shows how to assemble
197+-- all these individual steps into a proof for the whole program.
198+
199+-- Our goal is to verify such decorated programs "mostly automatically." But,
200+-- before we can verify anything, we need to be able to *find* a proof for a
201+-- given specification, and for this we need to discover the right assertions.
202+-- This can be done in an almost mechanical way, with the exception of finding
203+-- loop invariants. In the remainder of this section, we explain in detail how
204+-- to construct decorations for several short programs, all of which are loop
205+-- free or have simple loop invariants. We'll return to finding more
206+-- interesting loop invariants later in the chapter.
207+
208+-- ### Example: Swapping
209+
210+-- Consider the following program, which swaps the values of two variables
211+-- using addition and subtraction, instead of by assigning to a temporary
212+-- variable.
213+
214+--   X := X + Y;
215+--   Y := X - Y;
216+--   X := X - Y
217+
218+-- We can give a proof, in the form of decorations, that this program is
219+-- correct — i.e., it really swaps `X` and `Y` — as follows.
220+
221+--   (1)    {{ X = m /\ Y = n }} ->>
222+--   (2)    {{ (X + Y) - ((X + Y) - Y) = n /\ (X + Y) - Y = m }}
223+--            X := X + Y
224+--   (3)                     {{ X - (X - Y) = n /\ X - Y = m }};
225+--            Y := X - Y
226+--   (4)                     {{ X - Y = n /\ Y = m }};
227+--            X := X - Y
228+--   (5)    {{ X = n /\ Y = m }}
229+
230+-- The decorations can be constructed as follows:
231+
232+-- - We begin with the undecorated program (the unnumbered lines).
233+
234+-- - We add the specification — i.e., the outer precondition (1) and
235+--   postcondition (5). In the precondition, we use parameters `m` and `n` to
236+--   remember the initial values of variables `X` and `Y` so that we can refer
237+--   to them in the postcondition (5).
238+
239+-- - We work backwards, mechanically, starting from (5) and proceeding until we
240+--   get to (2). At each step, we obtain the precondition of the assignment from
241+--   its postcondition by substituting the assigned variable with the
242+--   right-hand-side of the assignment. For instance, we obtain (4) by
243+--   substituting `X` with `X - Y` in (5), and we obtain (3) by substituting `Y`
244+--   with `X - Y` in (4).
245+
246+-- - Finally, we verify that (1) logically implies (2) — i.e., that the step
247+--   from (1) to (2) is a valid use of the law of consequence — by doing a bit
248+--   of high-school algebra.
249+

261+-- ### Example: Simple Conditionals
262+
263+-- Here is a simple decorated program using conditionals:
264+
265+--   (1)   {{ True }}
266+--           if X <= Y then
267+--   (2)                    {{ True /\ X <= Y }} ->>
268+--   (3)                    {{ (Y - X) + X = Y \/ (Y - X) + Y = X }}
269+--             Z := Y - X
270+--   (4)                    {{ Z + X = Y \/ Z + Y = X }}
271+--           else
272+--   (5)                    {{ True /\ ~(X <= Y) }} ->>
273+--   (6)                    {{ (X - Y) + X = Y \/ (X - Y) + Y = X }}
274+--             Z := X - Y
275+--   (7)                    {{ Z + X = Y \/ Z + Y = X }}
276+--           end
277+--   (8)   {{ Z + X = Y \/ Z + Y = X }}
278+
279+-- These decorations can be constructed as follows:
280+
281+-- - We start with the outer precondition (1) and postcondition (8).
282+
283+-- - Following the format dictated by the `hoare_if` rule, we copy the
284+--   postcondition (8) to (4) and (7). We conjoin the precondition (1) with the
285+--   guard of the conditional to obtain (2). We conjoin (1) with the negated
286+--   guard of the conditional to obtain (5).
287+
288+-- - In order to use the assignment rule and obtain (3), we substitute `Z` by
289+--   `Y - X` in (4). To obtain (6) we substitute `Z` by `X - Y` in (7).
290+
291+-- - Finally, we verify that (2) implies (3) and (5) implies (6). Both of these
292+--   implications crucially depend on the ordering of `X` and `Y` obtained from
293+--   the guard. For instance, knowing that `X <= Y` ensures that subtracting `X`
294+--   from `Y` and then adding back `X` produces `Y`, as required by the first
295+--   disjunct of (3). Similarly, knowing that `~ (X <= Y)` ensures that
296+--   subtracting `Y` from `X` and then adding back `Y` produces `X`, as needed
297+--   by the second disjunct of (6). Note that `n - m + m = n` does *not* hold
298+--   for arbitrary natural numbers `n` and `m` (for example, [3 - 5 + 5 = 5]).
299+

379+-- ### Example: Division
380+
381+-- Let's do one more example of simple reasoning about a loop.
382+
383+-- The following Imp program calculates the integer quotient and remainder of
384+-- parameters `m` and `n`.
385+
386+--   X := m;
387+--   Y := 0;
388+--   while n <= X do
389+--     X := X - n;
390+--     Y := Y + 1
391+--   end;
392+
393+-- If we replace `m` and `n` by concrete numbers and execute the program, it
394+-- will terminate with the variable `X` set to the remainder when `m` is
395+-- divided by `n` and `Y` set to the quotient.
396+
397+-- In order to give a specification to this program we need to remember that
398+-- dividing `m` by `n` produces a remainder `X` and a quotient `Y` such that
399+-- `n * Y + X = m /\ X < n`.
400+
401+-- It turns out that we get lucky with this program and don't have to think
402+-- very hard about the loop invariant: the loop invariant is just the first
403+-- conjunct, `n * Y + X = m`, and we can use this to decorate the program.
404+
405+--    (1)  {{ True }} ->>
406+--    (2)  {{ n * 0 + m = m }}
407+--           X := m;
408+--    (3)                     {{ n * 0 + X = m }}
409+--           Y := 0;
410+--    (4)                     {{ n * Y + X = m }}
411+--           while n <= X do
412+--    (5)                     {{ n * Y + X = m /\ n <= X }} ->>
413+--    (6)                     {{ n * (Y + 1) + (X - n) = m }}
414+--             X := X - n;
415+--    (7)                     {{ n * (Y + 1) + X = m }}
416+--             Y := Y + 1
417+--    (8)                     {{ n * Y + X = m }}
418+--           end
419+--    (9)  {{ n * Y + X = m /\ ~ (n <= X) }} ->>
420+--   (10)  {{ n * Y + X = m /\ X < n }}
421+
422+-- Assertions (4), (5), (8), and (9) are derived mechanically from the loop
423+-- invariant and the loop's guard. Assertions (8), (7), and (6) are derived
424+-- using the assignment rule going backwards from (8) to (6). Assertions (4),
425+-- (3), and (2) are again backwards applications of the assignment rule.
426+
427+-- Now that we've decorated the program it only remains to check that the uses
428+-- of the consequence rule are correct — i.e., that (1) implies (2), that (5)
429+-- implies (6), and that (9) implies (10). This is indeed the case:
430+
431+-- - (1) ->> (2): trivial, by algebra.
432+
433+-- - (5) ->> (6): because `n <= X`, we are guaranteed that the subtraction in
434+--   (6) does not get zero-truncated. We can therefore rewrite (6) as
435+--   `n * Y + n + X - n` and cancel the `n`s, which results in the left conjunct
436+--   of (5).
437+
438+-- - (9) ->> (10): if `~ (n <= X)` then `X < n`. That's straightforward from
439+--   high-school algebra. So, we have a valid decorated program.

467+-- automate proofs involving assertions.

491+-- ## Formal Decorated Programs
492+
493+-- Our informal conventions for decorated programs amount to a way of
494+-- "displaying" Hoare triples, in which commands are annotated with enough
495+-- embedded assertions that checking the validity of a triple is reduced to
496+-- simple logical and algebraic calculations showing that some assertions
497+-- imply others.
498+
499+-- In this section, we show that this presentation style can be made
500+-- completely formal — and indeed that checking the validity of decorated
501+-- programs can be largely automated.
502+
503+-- ### Syntax
504+
505+-- The first thing we need to do is to formalize a variant of the syntax of
506+-- Imp commands that includes embedded assertions, which we'll call
507+-- "decorations." We call the new commands *decorated commands*, or `dcom`s.
508+
509+-- The choice of exactly where to put assertions in the definition of `dcom`
510+-- is a bit subtle. The simplest thing to do would be to annotate every `dcom`
511+-- with a precondition and postcondition — something like this...
512+
513+namespace DComFirstTry
514+
515+inductive DCom where
516+  | skip (pre : Assertion)
517+  | seq (pre : Assertion) (first : DCom)
518+      (middle : Assertion)
519+      (second : DCom) (post : Assertion)
520+  | asgn (x : Ident) (a : Aexp) (post : Assertion)
521+  | cond (pre : Assertion) (b : Bexp)
522+      (thenPre : Assertion) (thenBranch : DCom)
523+      (elsePre : Assertion) (elseBranch : DCom)
524+      (post : Assertion)
525+  | whileDo (pre : Assertion) (b : Bexp)
526+      (bodyPre : Assertion) (body : DCom)
527+      (bodyPost : Assertion) (post : Assertion)
528+  | strengthenPre (pre : Assertion) (body : DCom)
529+  | weakenPost (body : DCom) (post : Assertion)
530+
531+end DComFirstTry
532+
533+-- But this would result in *very* verbose decorated programs with a lot of
534+-- repeated annotations: a simple program like `skip;skip` would be decorated
535+-- like this,
536+
537+--   {{P}} ({{P}} skip {{P}}) ; ({{P}} skip {{P}}) {{P}}
538+
539+-- with pre- and post-conditions around each `skip`, plus identical pre- and
540+-- post-conditions on the semicolon!
541+
542+-- In other words, we don't want both preconditions and postconditions on each
543+-- command, because a sequence of two commands would contain redundant
544+-- decorations — the postcondition of the first likely being the same as the
545+-- precondition of the second.
546+
547+-- Instead, our formal syntax of decorated commands will omit preconditions
548+-- whenever possible and embed just postconditions.
549+
550+-- - The `skip` command, for example, is decorated only with its postcondition
551+
552+--   skip {{ Q }}
553+
554+-- on the assumption that the precondition will be provided by somebody else.
555+
556+-- We carry the same assumption through the other syntactic forms: each
557+-- decorated command is assumed to carry its own postcondition within itself
558+-- but take its precondition from its context in which it is used.
559+
560+-- - Sequences `d1 ; d2` need no additional decorations.
561+
562+-- Why?
563+
564+-- Because inside `d2` there will be a postcondition, which also serves as the
565+-- postcondition of `d1;d2`.
566+
567+-- Similarly, inside `d1` there will also be a postcondition, which
568+-- additionally serves as the *precondition* for `d2`.
569+
570+-- - An assignment `X := a` is decorated only with its postcondition:
571+
572+--   X := a {{ Q }}
573+
574+-- - A conditional `if b then d1 else d2` is decorated with a postcondition for
575+--   the entire statement, as well as preconditions for each branch:
576+
577+--   if b then {{ P1 }} d1 else {{ P2 }} d2 end {{ Q }}

585+-- - A loop `while b do d end` is decorated with its final postcondition plus a
586+--   precondition for the body:
587+
588+--   while b do {{ P }} d end {{ Q }}
589+
590+-- The postcondition embedded in `d` serves as the loop invariant.
591+
592+-- - Implications `->>` can be added as decorations either for a precondition...
593+
594+--   ->> {{ P }} d
595+

597+
598+--   d ->> {{ Q }}

799+-- The outer Hoare triple of a decorated program is just a `Prop`; thus, to
800+-- show that it is *valid*, we need to produce a proof of this proposition.
801+
802+-- We will do this by extracting "proof obligations" from the decorations
803+-- sprinkled throughout the program.
804+
805+-- These obligations are often called *verification conditions*, because they
806+-- are the facts that must be verified to see that the decorations are locally
807+-- consistent and thus constitute a proof of validity of the outer triple.
808+
809+-- ### Extracting Verification Conditions
810+
811+-- The function `DCom.VerificationConditions` takes a decorated command `d`
812+-- together with a precondition `P` and returns a *proposition* that, if it
813+-- can be proved, implies that the triple
814+
815+--   {{P}} d.erase {{d.postcondition}}
816+
817+-- is valid.
818+
819+-- It does this by walking over `d` and generating a big conjunction that
820+-- includes
821+
822+-- - local consistency checks for each form of command, plus
823+
824+-- - uses of `->>` to bridge the gap between the assertions found inside a
825+--   decorated command and the assertions imposed by the external precondition;
826+--   these uses correspond to applications of the consequence rule.
827+
828+-- *Local consistency* is defined as follows...
829+
830+-- - The decorated command
831+
832+--   skip {{Q}}
833+
834+-- is locally consistent with respect to a precondition `P` if `P ->> Q`.
835+
836+-- - The sequential composition of `d1` and `d2` is locally consistent with
837+--   respect to `P` if `d1` is locally consistent with respect to `P` and `d2`
838+--   is locally consistent with respect to the postcondition of `d1`.
839+
840+-- - An assignment
841+
842+--   X := a {{Q}}
843+
844+-- is locally consistent with respect to a precondition `P` if:
845+
846+--   P ->> Q [X |-> a]
847+
848+-- - A conditional
849+
850+--   if b then {{P1}} d1 else {{P2}} d2 end {{Q}}
851+
852+-- is locally consistent with respect to precondition `P` if
853+
854+-- (1) `P /\ b ->> P1`
855+
856+-- (2) `P /\ ~b ->> P2`
857+
858+-- (3) `d1` is locally consistent with respect to `P1`
859+
860+-- (4) `d2` is locally consistent with respect to `P2`
861+
862+-- (5) `d1.postcondition ->> Q`
863+
864+-- (6) `d2.postcondition ->> Q`
865+
866+-- - A loop
867+
868+--   while b do {{Q}} d end {{R}}
869+
870+-- is locally consistent with respect to precondition `P` if:
871+
872+-- (1) `P ->> d.postcondition`
873+
874+-- (2) `d.postcondition /\ b ->> Q`
875+
876+-- (3) `d.postcondition /\ ~b ->> R`
877+
878+-- (4) `d` is locally consistent with respect to `Q`
879+
880+-- - A command with an extra assertion at the beginning
881+
882+--   ->> {{Q}} d
883+
884+-- is locally consistent with respect to a precondition `P` if:
885+
886+-- (1) `P ->> Q`
887+
888+-- (2) `d` is locally consistent with respect to `Q`
889+
890+-- - A command with an extra assertion at the end
891+
892+--   d ->> {{Q}}
893+
894+-- is locally consistent with respect to a precondition `P` if:
895+
896+-- (1) `d` is locally consistent with respect to `P`
897+
898+-- (2) `d.postcondition ->> Q`
899+
900+-- With all this in mind, we can write a *verification condition generator*
901+-- that takes a decorated command and reads off a proposition saying that all
902+-- its decorations are locally consistent.
903+
904+-- Formally, since a decorated command is "waiting for its precondition" the
905+-- main VC generator takes a `dcom` plus a given precondition as arguments.
906+
907+-- Note to developers:
908+--     HIDE: There was some discussion in 2016 about whether the VC generator
909+--     should should use equivalence or implication in a few places. I (BCP)
910+--     believe Phil (Wadler) changed some instances of the former to the
911+--     latter.
912+--
913+--     HIDE: MRC'20: a written explanation of each part of this would be quite
914+--     nice. BCP 21: Agreed!! (BCP 23: But it's kind of what's just above...)
915+
916+def DCom.VerificationConditions
917+    (P : Assertion) (d : DCom) : Prop :=
918+  match d with
919+  | .skip Q =>
920+      P ->> Q
921+  | .seq d1 d2 =>
922+      d1.VerificationConditions P ∧
923+      d2.VerificationConditions d1.postcondition
924+  | .asgn x a Q =>
925+      P ->> Q [x ↦ ~a]
926+  | .cond b P1 d1 P2 d2 Q =>
927+      ({{ P ∧ b }} ->> P1) ∧
928+      ({{ P ∧ ¬ b }} ->> P2) ∧
929+      (d1.postcondition ->> Q) ∧
930+      (d2.postcondition ->> Q) ∧
931+      d1.VerificationConditions P1 ∧
932+      d2.VerificationConditions P2
933+  | .whileDo b bodyPre body q =>
934+      -- The body's postcondition is both the loop invariant
935+      -- and the precondition for the first iteration.
936+      (P ->> body.postcondition) ∧
937+      ({{ body.postcondition ∧ b }} ->> bodyPre) ∧
938+      ({{ body.postcondition ∧ ¬ b }} ->> q) ∧
939+      body.VerificationConditions bodyPre
940+  | .pre P' body =>
941+      (P ->> P') ∧ body.VerificationConditions P'
942+  | .post body Q =>
943+      body.VerificationConditions P ∧
944+      (body.postcondition ->> Q)
945+
946+-- The following key theorem states that `DCom.VerificationConditions` does
947+-- its job correctly. Not surprisingly, each of the Hoare Logic rules plays a
948+-- critical role at some point in the proof.
949+
950+theorem verification_correct (d : DCom) (P : Assertion)
951+    (hvc : d.VerificationConditions P) :
952+    ValidHoareTriple P d.erase d.postcondition := by
953+  sorry
954+
955+-- Now that all the pieces are in place, we can define what it means to verify
956+-- an entire program.
957+
958+def Decorated.VerificationConditions
959+    (dec : Decorated) : Prop :=
960+  dec.body.VerificationConditions dec.pre
961+
962+-- And this brings us to the main theorem of this section:
963+
964+theorem verification_conditions_correct (dec : Decorated)
965+    (hvc : dec.VerificationConditions) :
966+    dec.OuterTripleValid := by
967+  exact verification_correct dec.body dec.pre hvc

1100+-- ## Finding Loop Invariants
1101+
1102+-- Once the outermost precondition and postcondition are chosen, the only
1103+-- creative part of a verifying program using Hoare Logic is finding the right
1104+-- loop invariants. The reason this is difficult is the same as the reason
1105+-- that inductive mathematical proofs are:
1106+
1107+-- - Strengthening a *loop invariant* means that you have a stronger assumption
1108+--   to work with when trying to establish the postcondition of the loop body,
1109+--   but it also means that the loop body's postcondition is harder to prove.
1110+
1111+-- - Similarly, strengthening an *induction hypothesis* means that you have a
1112+--   stronger assumption to work with when trying to complete the induction step
1113+--   of the proof, but it also means that the statement being proved inductively
1114+--   is harder to prove.
1115+
1116+-- This section explains how to approach the challenge of finding loop
1117+-- invariants through a series of examples and exercises.
1118+
1119+-- ### Example: Slow Subtraction
1120+
1121+-- The following program subtracts the value of `X` from the value of `Y` by
1122+-- repeatedly decrementing both `X` and `Y`. We want to verify its correctness
1123+-- with respect to the pre- and postconditions shown:
1124+
1125+--   {{ X = m /\ Y = n }}
1126+--     while X <> 0 do
1127+--       Y := Y - 1;
1128+--       X := X - 1
1129+--     end
1130+--   {{ Y = n - m }}
1131+
1132+-- To verify this program, we need to find an invariant `Inv` for the loop. As
1133+-- a first step we can leave `Inv` as an unknown and build a *skeleton* for
1134+-- the proof by applying the rules for local consistency, working from the end
1135+-- of the program to the beginning, as usual, and without doing any thinking
1136+-- at all yet.
1137+
1138+-- This leads to the following skeleton:
1139+
1140+--   (1)    {{ X = m /\ Y = n }}  ->>                   (a)
1141+--   (2)    {{ Inv }}
1142+--            while X <> 0 do
1143+--   (3)              {{ Inv /\ X <> 0 }}  ->>          (c)
1144+--   (4)              {{ Inv [X |-> X-1] [Y |-> Y-1] }}
1145+--              Y := Y - 1;
1146+--   (5)              {{ Inv [X |-> X-1] }}
1147+--              X := X - 1
1148+--   (6)              {{ Inv }}
1149+--            end
1150+--   (7)    {{ Inv /\ ~ (X <> 0) }}  ->>                (b)
1151+--   (8)    {{ Y = n - m }}
1152+
1153+-- Examining this skeleton, we can see that any valid `Inv` will have to
1154+-- respect three conditions:
1155+
1156+-- - (a) it must be *weak* enough to be implied by the loop's precondition,
1157+--   i.e., (1) must imply (2);
1158+
1159+-- - (b) it must be *strong* enough to imply the program's postcondition, i.e.,
1160+--   (7) must imply (8);
1161+
1162+-- - (c) it must be *preserved* by a single iteration of the loop, assuming that
1163+--   the loop guard also evaluates to true, i.e., (3) must imply (4).
1164+
1165+-- These conditions are actually independent of the particular program and
1166+-- specification we are considering: every loop invariant has to satisfy them.
1167+
1168+-- One way to find a loop invariant that simultaneously satisfies these three
1169+-- conditions is by using an iterative process: start with a "candidate"
1170+-- invariant (e.g., a guess or a heuristic choice) and check the three
1171+-- conditions above; if any of the checks fails, try to use the information
1172+-- that we get from the failure to produce another — hopefully better —
1173+-- candidate invariant, and repeat.
1174+
1175+-- For instance, in the reduce-to-zero example above, we saw that, for a very
1176+-- simple loop, choosing `True` as a loop invariant did the job. Maybe it will
1177+-- work here too. To find out, let's try instantiating `Inv` with `True` in
1178+-- the skeleton above and see what we get...
1179+
1180+--   (1)    {{ X = m /\ Y = n }} ->>                    (a - OK)
1181+--   (2)    {{ True }}
1182+--            while X <> 0 do
1183+--   (3)                   {{ True /\ X <> 0 }} ->>     (c - OK)
1184+--   (4)                   {{ True }}
1185+--              Y := Y - 1;
1186+--   (5)                   {{ True }}
1187+--              X := X - 1
1188+--   (6)                   {{ True }}
1189+--            end
1190+--   (7)    {{ True /\ ~(X <> 0) }} ->>                 (b - WRONG!)
1191+--   (8)    {{ Y = n - m }}
1192+
1193+-- While conditions (a) and (c) are trivially satisfied, (b) is wrong: it is
1194+-- not the case that `True /\ X = 0` (7) implies `Y = n - m` (8). In fact, the
1195+-- two assertions are completely unrelated, so it is very easy to find a
1196+-- counterexample to the implication (say, `Y = X = m = 0` and `n = 1`).
1197+
1198+-- If we want (b) to hold, we need to strengthen the loop invariant so that it
1199+-- implies the postcondition (8). One simple way to do this is to let the loop
1200+-- invariant *be* the postcondition. So let's return to our skeleton,
1201+-- instantiate `Inv` with `Y = n - m`, and try checking conditions (a) to (c)
1202+-- again.
1203+
1204+--   (1)    {{ X = m /\ Y = n }} ->>                        (a - WRONG!)
1205+--   (2)    {{ Y = n - m }}
1206+--            while X <> 0 do
1207+--   (3)                     {{ Y = n - m /\ X <> 0 }} ->>  (c - WRONG!)
1208+--   (4)                     {{ Y - 1 = n - m }}
1209+--              Y := Y - 1;
1210+--   (5)                     {{ Y = n - m }}
1211+--              X := X - 1
1212+--   (6)                     {{ Y = n - m }}
1213+--            end
1214+--   (7)    {{ Y = n - m /\ ~(X <> 0) }} ->>                (b - OK)
1215+--   (8)    {{ Y = n - m }}
1216+
1217+-- This time, condition (b) holds trivially, but (a) and (c) are broken.
1218+-- Condition (a) requires that (1) `X = m /\ Y = n` implies (2) `Y = n - m`.
1219+-- If we substitute `Y` by `n` we have to show that `n = n - m` for arbitrary
1220+-- `m` and `n`, which is not the case (for instance, when `m = n = 1`).
1221+-- Condition (c) requires that `n - m - 1 = n - m`, which fails, for instance,
1222+-- for `n = 1` and `m = 0`. So, although `Y = n - m` holds at the end of the
1223+-- loop, it does not hold from the start, and it doesn't hold on each
1224+-- iteration; it is not a correct loop invariant.
1225+
1226+-- This failure is not very surprising: the variable `Y` changes during the
1227+-- loop, while `m` and `n` are constant, so the assertion we chose didn't have
1228+-- much chance of being a loop invariant!
1229+
1230+-- To do better, we need to generalize (7) to some statement that is
1231+-- equivalent to (8) when `X` is `0`, since this will be the case when the
1232+-- loop terminates, and that "fills the gap" in some appropriate way when `X`
1233+-- is nonzero. Looking at how the loop works, we can observe that `X` and `Y`
1234+-- are decremented together until `X` reaches `0`. So, if `X = 2` and `Y = 5`
1235+-- initially, after one iteration of the loop we obtain `X = 1` and `Y = 4`;
1236+-- after two iterations `X = 0` and `Y = 3`; and then the loop stops. Notice
1237+-- that the difference between `Y` and `X` stays constant between iterations:
1238+-- initially, `Y = n` and `X = m`, and the difference is always `n - m`. So
1239+-- let's try instantiating `Inv` in the skeleton above with `Y - X = n - m`.
1240+
1241+--   (1)    {{ X = m /\ Y = n }} ->>                            (a - OK)
1242+--   (2)    {{ Y - X = n - m }}
1243+--            while X <> 0 do
1244+--   (3)                    {{ Y - X = n - m /\ X <> 0 }} ->>   (c - OK)
1245+--   (4)                    {{ (Y - 1) - (X - 1) = n - m }}
1246+--              Y := Y - 1;
1247+--   (5)                    {{ Y - (X - 1) = n - m }}
1248+--              X := X - 1
1249+--   (6)                    {{ Y - X = n - m }}
1250+--            end
1251+--   (7)    {{ Y - X = n - m /\ ~(X <> 0) }} ->>                (b - OK)
1252+--   (8)    {{ Y = n - m }}
1253+
1254+-- Success! Conditions (a), (b) and (c) all hold now. (To verify (c), we need
1255+-- to check that, under the assumption that `X <> 0`, we have
1256+-- `Y - X = (Y - 1) - (X - 1)`; this holds for all natural numbers `X` and
1257+-- `Y`.)
1258+
1259+-- Here is the final version of the decorated program:
1260+
1261+def subtractSlowlyDec (m n : Nat) : Decorated where
1262+  pre := ({{ X = m ∧ Y = n }})
1263+  body := dcom {
1264+    ->> {{ Y - X = n - m }}
1265+    while (X ≠ 0) do
1266+      {{ Y - X = n - m ∧ ¬ X = 0 }}
1267+      ->> {{ (Y - 1) - (X - 1) = n - m }}
1268+      Y := Y - 1 {{ Y - (X - 1) = n - m }};
1269+      X := X - 1 {{ Y - X = n - m }}
1270+    end
1271+      {{ Y - X = n - m ∧ X = 0 }}
1272+    ->> {{ Y = n - m }}
1273+  }

1276+    (subtractSlowlyDec m n).OuterTripleValid := by
1277+  sorry

1332+-- a bit about what this loop does. On each iteration it decrements `X` by
1333+-- `2`, which preserves the parity of `X`. So the parity of `X` does not
1334+-- change, i.e., it is invariant. The initial value of `X` is `m`, so the
1335+-- parity of `X` is always equal to the parity of `m`. Using

2741+
2742+-- Some preconditions are more interesting than others. For example, the Hoare
2743+-- triple
2744+
2745+--   {{ False }}  X := Y + 1  {{ X <= 5 }}
2746+
2747+-- is *not* very interesting: although it is perfectly valid, it tells us
2748+-- nothing useful. Since the precondition isn't satisfied by any state, it
2749+-- doesn't describe any situations where we can use the command `X := Y + 1`
2750+-- to achieve the postcondition `X <= 5`.
2751+
2752+-- By contrast,
2753+
2754+--   {{ Y <= 4 /\ Z = 0 }}  X := Y + 1 {{ X <= 5 }}
2755+
2756+-- has a useful precondition: it tells us that, if we can somehow create a
2757+-- situation in which we know that `Y <= 4 /\ Z = 0`, then running this
2758+-- command will produce a state satisfying the postcondition. However, this
2759+-- precondition is not as useful as it could be, because the `Z = 0` clause in
2760+-- the precondition actually has nothing to do with the postcondition
2761+-- `X <= 5`.
2762+
2763+-- The *most* useful precondition for this command is this one:
2764+
2765+--   {{ Y <= 4 }}  X := Y + 1  {{ X <= 5 }}
2766+
2767+-- The assertion `Y <= 4` is called the *weakest precondition* of `X := Y + 1`
2768+-- with respect to the postcondition `X <= 5`.
2769+
2770+-- Assertion `Y <= 4` is a *weakest precondition* of command `X := Y + 1` with
2771+-- respect to postcondition `X <= 5`. Think of *weakest* here as meaning
2772+-- "easiest to satisfy": a weakest precondition is one that as many states as
2773+-- possible can satisfy.
2774+
2775+-- `P` is a weakest precondition of command `c` for postcondition `Q` if
2776+
2777+-- - `P` is a precondition, that is, `{{P}} c {{Q}}`; and
2778+
2779+-- - `P` is at least as weak as all other preconditions, that is, if
2780+--   `{{P'}} c {{Q}}` then `P' ->> P`.
2781+
2782+-- Note that weakest preconditions need not be unique. For example, `Y <= 4`
2783+-- was a weakest precondition above, but so are the logically equivalent
2784+-- assertions `Y < 5`, `Y <= 2 * 2`, etc. It is easy to show that any two
2785+-- weakest preconditions `P` and `P'` of a command `c` with respect to
2786+-- postcondition `Q` are logically equivalent; that is, `P <<->> P'`.
2787+
2788+def IsWp (P : Assertion) (c : Com) (Q : Assertion) : Prop :=
2789+  ValidHoareTriple P c Q ∧
2790+  ∀ P' : Assertion, ValidHoareTriple P' c Q → P' ->> P
