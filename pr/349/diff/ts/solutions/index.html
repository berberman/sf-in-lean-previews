6+--  # MoreStlc: More on the Simply Typed Lambda-Calculus
7+
8+--  ## Simple Extensions to STLC
9+
10+--  The simply typed lambda-calculus has a rich enough structure to make
11+--  its theoretical properties interesting, but it is not much of a
12+--  programming language!
13+--
14+--  In this chapter, we begin to close the gap with real-world languages by
15+--  introducing a number of familiar features that have straightforward
16+--  treatments at the level of typing.
17+
18+--  ### Numbers
19+
20+--  As we saw in the `StlcExtended` exercises at the end of the StlcProp
21+--  chapter, adding types, constants, and primitive operations for natural
22+--  numbers is easy - basically just a matter of combining the Types and
23+--  Stlc chapters. Adding more realistic numeric types like machine
24+--  integers and floats is also straightforward, though of course the
25+--  specifications of the numeric primitives become more fiddly.
26+
27+--  When writing a complex expression, it is useful to be able to give
28+--  names to some of its subexpressions to avoid repetition and increase
29+--  readability. Most languages provide one or more ways of doing this. In
30+--  OCaml and Haskell, for example, we can write `let x = t₁ in t₂` to mean
31+--  "reduce the expression `t₁` to a value and bind the name `x` to this
32+--  value while reducing `t₂`."
33+--
34+--  Our `let`-binder follows OCaml in choosing a standard *call-by-value*
35+--  evaluation order, where the `let`-bound term must be fully reduced
36+--  before reduction of the `let`-body can begin. The typing rule `let`
37+--  tells us that the type of a `let` can be calculated by calculating the
38+--  type of the `let`-bound term, extending the context with a binding with
39+--  this type, and in this enriched context calculating the type of the
40+--  body (which is then the type of the whole `let` expression).
41+--
42+--  At this point in the book, it's probably easier simply to look at the
43+--  rules defining this new feature than to wade through a lot of English
44+--  text conveying the same information. Here they are:
45+
46+--  Syntax:
47+--
48+--        t ::=                   Terms
49+--            | ...                 (other terms same as before)
50+--            | let x = t₁ in t₂    let-binding
51+--
52+--  Reduction:
53+--
54+--                                       t₁ ⟶ t₁'
55+--                           -------------------------------------        (let₁)
56+--                           let x = t₁ in t₂ ⟶ let x = t₁' in t₂
57+--
58+--                              ---------------------------------         (letValue)
59+--                              let x = v₁ in t₂ ⟶ [x := v₁] t₂
60+--
61+--  Typing:
62+--
63+--                   Γ ⊢ t₁ ⦂ τ₁      x ↦ τ₁ ; Γ ⊢ t₂ ⦂ τ₂
64+--                   -------------------------------------------      (let)
65+--                           Γ ⊢ let x = t₁ in t₂ ⦂ τ₂
66+
67+--  ### Pairs
68+
69+--  Our functional programming examples in Lean have made frequent use of
70+--  *pairs* of values. The type of such a pair is called a *product type*.
71+--
72+--  The formalization of pairs is almost too simple to be worth discussing.
73+--  However, let's look briefly at the various parts of the definition to
74+--  emphasize the common pattern.
75+
76+--  In Lean, there are two ways of extracting the components of a pair:
77+--  *pattern matching* and the projection operators `fst` and `snd`. Just
78+--  for fun, let's do our pairs the latter way. For example, here's how
79+--  we'd write a function that takes a pair of numbers and returns the pair
80+--  of their sum and difference:
81+--
82+--             λx : Nat × Nat.
83+--                let sum = fst x + snd x in
84+--                let diff = fst x - snd x in
85+--                (sum, diff)
86+
87+--  Adding pairs to the simply typed lambda-calculus, then, involves adding
88+--  two new forms of term - pairing, written `(t₁,t₂)`, and projection,
89+--  written `fst t` for the first projection from `t` and `snd t` for the
90+--  second projection - plus one new type constructor, `τ₁ × τ₂`, called
91+--  the *product* of `τ₁` and `τ₂`.
92+
93+--  Syntax:
94+--
95+--             t ::=                Terms
96+--                 | ...
97+--                 | (t₁, t₂)         pair
98+--                 | fst t            first projection
99+--                 | snd t            second projection
100+--
101+--             v ::=                Values
102+--                 | ...
103+--                 | (v₁, v₂)         pair value
104+--
105+--             τ ::=                Types
106+--                 | ...
107+--                 | τ₁ × τ₂          product type
108+
109+--  For reduction, we need several new rules specifying how pairs and
110+--  projection behave.
111+
112+--                                    t₁ ⟶ t₁'
113+--                               --------------------                        (pair₁)
114+--                               (t₁,t₂) ⟶ (t₁',t₂)
115+--
116+--                                    t₂ ⟶ t₂'
117+--                               --------------------                        (pair₂)
118+--                               (v₁,t₂) ⟶ (v₁,t₂')
119+--
120+--                                     t ⟶ t'
121+--                                 ------------------                        (fst₁)
122+--                                 fst t ⟶ fst t'
123+--
124+--                                ------------------                       (fstPair)
125+--                                 fst (v₁,v₂) ⟶ v₁
126+--
127+--                                     t ⟶ t'
128+--                                 ------------------                      (snd₁)
129+--                                 snd t ⟶ snd t'
130+--
131+--                                ------------------                       (sndPair)
132+--                                snd (v₁,v₂) ⟶ v₂
133+
134+--  Rules `fstPair` and `sndPair` say that, when a fully reduced pair meets
135+--  a first or second projection, the result is the appropriate component.
136+--  The congruence rules `fst₁` and `snd₁` allow reduction to proceed under
137+--  projections, when the term being projected from has not yet been fully
138+--  reduced. `pair₁` and `pair₂` reduce the parts of pairs: first the left
139+--  part, and then - when a value appears on the left - the right part. The
140+--  ordering arising from the use of the metavariables `v` and `t` in these
141+--  rules enforces a left-to-right evaluation strategy for pairs. (Note the
142+--  implicit convention that metavariables like `v` and `v₁` can only
143+--  denote values.) We've also added a clause to the definition of values,
144+--  above, specifying that `(v₁,v₂)` is a value. The fact that the
145+--  components of a pair value must themselves be values ensures that a
146+--  pair passed as an argument to a function will be fully reduced before
147+--  the function body starts executing.
148+
149+--  The typing rules for pairs and projections are straightforward.
150+
151+--                           Γ ⊢ t₁ ⦂ τ₁     Γ t₂ ⦂ τ₂
152+--                          ------------------------------              (pair)
153+--                            Γ ⊢(t₁, t₂) ⦂ τ₁ × τ₂
154+--
155+--                                 Γ ⊢ t ⦂ τ₁ × τ₂
156+--                              -----------------------                  (fst)
157+--                                  Γ ⊢ fst t ⦂ τ₁
158+--
159+--                                  Γ ⊢ t ⦂ τ₁ × τ₂
160+--                              -----------------------                   (snd)
161+--                                   Γ ⊢ snd t ⦂ τ₂
162+
163+--  `pair` says that `(t₁, t₂)` has type `τ₁ × τ₂` if `t₁` has type `τ₁`
164+--  and `t₂` has type `τ₂`. Conversely, `fst` and `snd` tell us that, if
165+--  `t` has a product type `τ₁ × τ₂` (i.e., if it will reduce to a pair),
166+--  then the types of the projections from this pair are `τ₁` and `τ₂`.
167+
168+--  ### Unit
169+
170+--  Another handy base type is the singleton type `Unit`.
171+
172+--  It has a single element - the term constant `unit` (with a small `u`) -
173+--  and a typing rule making `unit` an element of `Unit`. We also add
174+--  `unit` to the set of possible values - indeed, `unit` is the *only*
175+--  possible result of reducing an expression of type `Unit`.
176+
177+--  Syntax:
178+--
179+--             t ::=                Terms
180+--                 | ...               (other terms same as before)
181+--                 | unit              unit
182+--
183+--             v ::=                Values
184+--                 | ...
185+--                 | unit              unit value
186+--
187+--             τ ::=                Types
188+--                 | ...
189+--                 | Unit              unit type
190+--
191+--  Typing:
192+--
193+--                               ----------------                       (unit)
194+--                               Γ ⊢ unit ⦂ Unit
195+
196+--  It may seem a little strange to bother defining a type that has just
197+--  one element -- after all, wouldn't every computation living in such a
198+--  type be trivial?
199+--
200+--  This is a fair question, and indeed in the STLC the `Unit` type is not
201+--  especially critical (though we'll see two uses for it below). Where
202+--  `Unit` really comes in handy is in richer languages with *side effects*
203+--  -- e.g., assignment statements that mutate variables or pointers,
204+--  exceptions and other sorts of nonlocal control structures, etc. In such
205+--  languages, it is convenient to have a type for the (trivial) result of
206+--  an expression that is evaluated only for its effect.
207+
208+--   ----------------------------------------
209+
210+--  _Quiz:_
211+
212+--  Is `unit` the only term of type `Unit`?
213+--
214+--  (A) Yes
215+--
216+--  (B) No

220+--  ### Sums
221+
222+--  Many programs need to deal with values that can take two distinct
223+--  forms. For example, we might identify students in a university database
224+--  using *either* their name *or* their id number. A search function might
225+--  return *either* a matching value *or* an error code.
226+--
227+--  These are specific examples of a binary *sum type* (sometimes called a
228+--  *disjoint union*), which describes a set of values drawn from one of
229+--  two given types, e.g.:
230+--
231+--             Nat + Bool
232+
233+--  We create elements of these types by *tagging* elements of the
234+--  component types. For example, if `n` is a `Nat` then `inl n` is an
235+--  element of `Nat + Bool`; similarly, if `b` is a `Bool` then `inr b` is
236+--  a `Nat + Bool`. The names of the tags `inl` and `inr` arise from
237+--  thinking of them as functions
238+--
239+--             inl ⦂ Nat  → Nat + Bool
240+--             inr ⦂ Bool → Nat + Bool
241+--
242+--  that "inject" elements of `Nat` or `Bool` into the left and right
243+--  components of the sum type `Nat + Bool`. (But note that we don't
244+--  actually treat them as functions in the way we formalize them: `inl`
245+--  and `inr` are keywords, and `inl t` and `inr t` are primitive syntactic
246+--  forms, not function applications.)
247+
248+--  In general, the elements of a type `τ₁ + τ₂` consist of the elements of
249+--  `τ₁` tagged with the token `inl`, plus the elements of `τ₂` tagged with
250+--  `inr`.
251+--
252+--  (As we've seen in Lean programming, one important use of sums is
253+--  signaling errors:
254+--
255+--            div ⦂ Nat → Nat → (Nat + Unit)
256+--            div =
257+--              λx:Nat. λy:Nat,
258+--                if iszero y then
259+--                  inr unit
260+--                else
261+--                  inl ...
262+
263+--  The type `Nat + Unit` above is in fact isomorphic to `Option Nat` in
264+--  Lean - i.e., it's easy to write functions that translate back and
265+--  forth.
266+--
267+--  To *use* elements of sum types, we introduce a `case` construct (a very
268+--  simplified form of Lean's `match`) to destruct them. For example, the
269+--  following procedure converts a `Nat + Bool` into a `Nat`:
270+
271+--          getNat ⦂ Nat+Bool → Nat
272+--          getNat =
273+--            λx:Nat+Bool,
274+--              case x of
275+--                inl n => n
276+--              | inr b => if b then 1 else 0
277+--
278+--  More formally...
279+--
280+--  Syntax:
281+--
282+--             t ::=                Terms
283+--                 | ...               (other terms same as before)
284+--                 | inl τ₂ t₁         tagging (left)
285+--                 | inr τ₁ t₂         tagging (right)
286+--                 | case t of         case analysis
287+--                     inl x₁ => t₁
288+--                   | inr x₂ => t₂
289+--
290+--             v ::=                Values
291+--                 | ...
292+--                 | inl τ₂ v₁         tagged value (left)
293+--                 | inr τ₁ v₂         tagged value (right)
294+--
295+--             τ ::=                Types
296+--                 | ...
297+--                 | τ₁ + τ₂           sum type
298+--
299+--  Reduction:
300+--
301+--                                     t₁ ⟶ t₁'
302+--                              ------------------------                       (inl)
303+--                              inl τ₂ t₁ ⟶ inl τ₂ t₁'
304+--
305+--                                     t₂ ⟶ t₂'
306+--                              ------------------------                       (inr)
307+--                              inr τ₁ t₂ ⟶ inr τ₁ t₂'
308+--
309+--                                     t ⟶ t'
310+--                     -------------------------------------------            (case)
311+--                      case t of inl x₁ => t₁ | inr x₂ => t₂ ⟶
312+--                     case t' of inl x₁ => t₁ | inr x₂ => t₂
313+--
314+--                  -----------------------------------------------        (caseInl)
315+--                  case (inl τ₂ v₁) of inl x₁ => t₁ | inr x₂ => t₂
316+--                                 ⟶  [x₁ := v₁]t₁
317+--
318+--                  -----------------------------------------------        (caseInr)
319+--                  case (inr τ₁ v₂) of inl x₁ => t₁ | inr x₂ => t₂
320+--                                 ⟶  [x₂ := v₂]t₂
321+--
322+--  Typing:
323+--
324+--                                  Γ ⊢ t₁ ⦂ τ₁
325+--                         ----------------------------                      (inl)
326+--                             Γ ⊢ inl τ₂ t₁ ⦂ τ₁ + τ₂
327+--
328+--
329+--                                Γ ⊢ t₂ ⦂ τ₂
330+--                         ---------------------------                       (inr)
331+--                           Γ ⊢ inr τ₁ t₂ ⦂ τ₁ + τ₂
332+--
333+--
334+--                              Γ ⊢ t ⦂ τ₁ + τ₂
335+--                           x₁ ↦ τ₁; Γ ⊢ t₁ ⦂ τ₃
336+--                           x₂ ↦ τ₂; Γ ⊢ t₂ ⦂ τ₃
337+--               ----------------------------------------------------        (case)
338+--                   Γ ⊢ case t of inl x₁ => t₁ | inr x₂ => t₂ ⦂ τ₃
339+--
340+--  We use the type annotations on `inl` and `inr` to make the typing
341+--  relation deterministic (each term has at most one type), as we did for
342+--  functions.
343+
344+--  Without this extra information, the typing rule `inl`, for example,
345+--  would have to say that, once we have shown that `t₁` is an element of
346+--  type `τ₁`, we can derive that `inl t₁` is an element of `τ₁ + τ₂` for
347+--  *any* type `τ₂`. For example, we could derive both
348+--  `inl 5 : Nat + Nat`and `inl 5 : Nat + Bool` (and infinitely many other
349+--  types). This peculiarity (technically, a failure of uniqueness of
350+--  types) would mean t hat we cannot build a typechecking algorithm simply
351+--  by "reading the rules from bottom to top" as we could for all the other
352+--  features seen so far.
353+--
354+--  There are various ways to deal with this difficulty. One simple one --
355+--  which we've adopted here -- forces the programmer to explicitly
356+--  annotate the "other side" of a sum type when performing an injection.
357+--  This is a bit heavy for programmers (so real languages adopt other
358+--  solutions), but it is easy to understand and formalize.
359+

424+--  ### Lists
425+
426+--  The typing features we have seen can be classified into *base types*
427+--  like `Bool`, and *type constructors* like `→` and `×` that build new
428+--  types from old ones. Another useful type constructor is `List`. For
429+--  every type `τ`, the type `List τ` describes finite-length lists whose
430+--  elements are drawn from `τ`.
431+--
432+--  In principle, we could encode lists using pairs, sums, unit, and
433+--  *recursive* types. But giving semantics to recursive types is
434+--  non-trivial. Instead, we'll just discuss the special case of lists
435+--  directly.
436+--
437+--  Below we give the syntax, semantics, and typing rules for lists. Except
438+--  for the fact that explicit type annotations are mandatory on `nil` and
439+--  cannot appear on `cons`, these lists are essentially identical to those
440+--  we built in Rocq. We use `case`, rather than `head` and `tail`
441+--  operators, to destruct lists, to avoid dealing with questions like
442+--  "what is the `head` of the ∅ list?"
443+--
444+--  For example, here is a function that calculates the sum of the first
445+--  two elements of a list of numbers:
446+--
447+--  λ x:List Nat. case x of nil => 0 | a :: x' => case x' of nil => a | b
448+--  :: x'' => a + b
449+
450+--  Syntax:
451+--
452+--             t ::=                Terms
453+--                 | ...
454+--                 | nil τ             ∅ list
455+--                 | t₁ :: t₂          cons
456+--                 | case t₁ of        case analysis
457+--                     nil      => t₂
458+--                     | xh::xt => t₃
459+--
460+--             v ::=                Values
461+--                 | ...
462+--                 | nil τ             nil value
463+--                 | v₁ :: v₂          cons value
464+--
465+--             τ ::=                Types
466+--                 | ...
467+--                 | List τ            list of τs
468+--
469+--  Reduction:
470+--
471+--                                      t₁ ⟶ t₁'
472+--                             --------------------------                    (cons₁)
473+--                               t₁ :: t₂ ⟶ t₁' :: t₂
474+--
475+--                                      t₂ ⟶ t₂'
476+--                             --------------------------                    (cons₂)
477+--                               v₁ :: t₂ ⟶ v₁ :: t₂'
478+--
479+--                                    t₁ ⟶ t₁'
480+--                      -------------------------------------------         (listCase₁)
481+--                       (case t₁ of nil => t₂ | xh :: xt => t₃) ⟶
482+--                      (case t₁' of nil => t₂ | xh :: xt => t₃)
483+--
484+--                     ------------------------------------------          (listCaseNil)
485+--                     (case nil τ₁ of nil => t₂ | xh :: xt => t₃)
486+--                                      ⟶ t₂
487+--
488+--                    -------------------------------------------         (listCaseCons)
489+--                    (case (vh :: vt) of nil => t₂ | xh :: xt => t₃)
490+--                                ⟶ [xh:=vh][xt:=vt] t₃
491+--
492+--  Typing:
493+--
494+--                              ----------------------------                    (nil)
495+--                              Γ ⊢ nil τ₁ ⦂ List τ₁
496+--
497+--                           Γ ⊢ t₁ ⦂ τ₁      Γ ⊢ t₂ ⦂ List τ₁
498+--                  -------------------------------------------------           (cons)
499+--                               Γ ⊢ t₁ :: t₂ ⦂ List τ₁
500+--
501+--                              Γ ⊢ t₁ ⦂ List τ₁
502+--                              Γ ⊢ t₂ ⦂ τ₂
503+--                        (xh ↦ τ₁; xt ↦ List τ₁; Γ) ⊢ t₃ ⦂ τ₂
504+--                ----------------------------------------------------         (listCase)
505+--                   Γ ⊢ (case t₁ of nil => t₂ | xh :: xt => t₃) ⦂ τ₂
506+
507+--  ### General Recursion
508+
509+--  Another facility found in most programming languages (including Lean)
510+--  is the ability to define recursive functions. For example, we would
511+--  like to be able to define and use the factorial function like this:
512+--
513+--            let fact = λx:Nat.
514+--                         if x=0 then 1 else x * (fact (pred x))) in
515+--            fact 3.
516+--
517+--  Note that the right-hand side of this binder mentions `fact`, the
518+--  variable being bound - something that is not allowed according to the
519+--  way we defined `let` above.
520+
521+--  (The body of a `let` is typechecked in the same context as the `let`
522+--  itself, which means that the recursive occurrence of `fact` in the body
523+--  will not have a type in the context when it is looked up by the `var`
524+--  rule.)
525+
526+--  Changing the `let` rule to handle "recursive definitions" like this is
527+--  possible, but it requires some extra effort -- e.g., passing around an
528+--  extra "environment" of recursive function definitions in the definition
529+--  of the `step` relation. We're going to take a simpler path here.
530+
531+--  Here is another way of presenting recursive functions that is a bit
532+--  more verbose but equally powerful and much more straightforward to
533+--  formalize: instead of writing recursive definitions, we will define a
534+--  *fixed-point operator* called `fix` that performs the "unfolding" of
535+--  the recursive definition in the right-hand side as needed, during
536+--  reduction.
537+--
538+--  For example, instead of
539+--
540+--            fact = λax:Nat.
541+--                      if x=0 then 1 else x * (fact (pred x)))
542+--
543+--  we will write:
544+
545+--  fact =
546+--            fix
547+--              (λaf:Nat → Nat.
548+--                 λx:Nat.
549+--                    if x=0 then 1 else x * (f (pred x)))
550+
551+--  We can derive the latter from the former as follows:
552+--
553+--  - In the right-hand side of the definition of `fact`, replace recursive
554+--    references to `fact` by a fresh variable `f`.
555+--
556+--  - Add an abstraction binding `f` at the front, with an appropriate type
557+--    annotation. (Since we are using `f` in place of `fact`, which had
558+--    type `Nat→Nat`, we should require `f` to have the same type.) The new
559+--    abstraction has type `(Nat→Nat) → (Nat→Nat)`.
560+--
561+--  - Apply `fix` to this abstraction. This application has type `Nat→Nat`.
562+--
563+--  - Use all of this as the right-hand side of an ordinary `let`-binding
564+--    for `fact`.

566+--  For the mathematically inclined, the intuition here is that the
567+--  higher-order function `f` passed to `fix` is a *generator* for the
568+--  `fact` function: if `f` is applied to a function that "approximates"
569+--  the desired behavior of `fact` up to some number `n` (that is, a
570+--  function that returns correct results on inputs less than or equal to
571+--  `n` but we don't care what it does on inputs greater than `n`), then
572+--  `f` returns a slightly better approximation to `fact` -- a function
573+--  that returns correct results for inputs up to `n+1`. Applying `fix` to
574+--  this generator returns its *fixed point*, which is a function that
575+--  gives the desired behavior for all inputs `n`.
576+--
577+--  (The term "fixed point" is used here in exactly the same sense as in
578+--  ordinary mathematics, where a fixed point of a function `f` is an input
579+--  `x` such that `f(x) = x`. Here, a fixed point of a function `F` of type
580+--  `(Nat→Nat)→(Nat→Nat)` is a function `f` of type `Nat→Nat` such that
581+--  `F f` behaves the same as `f`.)
582+
583+--  Syntax:
584+--
585+--             t ::=                Terms
586+--                 | ...
587+--                 | fix t₁            fixed-point operator
588+--
589+--  Reduction:
590+--
591+--                                      t₁ ⟶ t₁'
592+--                                  ------------------                   (fix₁)
593+--                                  fix t₁ ⟶ fix t₁'
594+--
595+--                     --------------------------------------------      (fixAbs)
596+--                     fix (λxf:τ₁.t₁) ⟶ [xf:=fix (λxf:τ₁.t₁)] t₁
597+--
598+--  Typing:
599+--
600+--                                 Γ ⊢ t₁ ⦂ τ₁ → τ₁
601+--                                 ------------------                    (fix)
602+--                                 Γ ⊢ fix t₁ ⦂ τ₁
603+

791+--  ## Records
792+
793+--  As a final example of a basic extension of the STLC, let's look briefly
794+--  at how to define *records* and their types. Intuitively, records can be
795+--  obtained from pairs by two straightforward generalizations: they are
796+--  n-ary (rather than just binary) and their fields are accessed by
797+--  *label* (rather than position).
798+
799+--  Syntax:
800+--
801+--             t ::=                          Terms
802+--                 | ...
803+--                 | {i₁=t₁, ..., in=tn}        record
804+--                 | t.i                        projection
805+--
806+--             v ::=                          Values
807+--                 | ...
808+--                 | {i₁=v₁, ..., in=vn}         record value
809+--
810+--             τ ::=                          Types
811+--                 | ...
812+--                 | {i₁:τ₁, ..., in:τn}         record type
813+
814+--  The generalization from products should be pretty obvious. But it's
815+--  worth noticing the ways in which what we've actually written is even
816+--  *more* informal than the informal syntax we've used in previous
817+--  sections and chapters: we've used "`...`" in several places to mean
818+--  "any number of these," and we've omitted explicit mention of the usual
819+--  side condition that the labels of a record should not contain any
820+--  repetitions.
821+
822+--  Reduction:
823+--
824+--                                    ti ⟶ ti'
825+--                       ------------------------------------                  (rcd)
826+--                           {i₁=v₁, ..., im=vm, in=ti , ...}
827+--                       ⟶ {i₁=v₁, ..., im=vm, in=ti', ...}
828+--
829+--                                    t ⟶ t'
830+--                                  --------------                           (proj₁)
831+--                                  t.i ⟶ t'.i
832+--
833+--                            -------------------------                    (projRcd)
834+--                            {..., i=vi, ...}.i ⟶ vi
835+
836+--  Again, these rules are a bit informal. For example, the first rule is
837+--  intended to be read "if `ti` is the leftmost field that is not a value
838+--  and if `ti` steps to `ti'`, then the whole record steps..." In the last
839+--  rule, the intention is that there should be only one field called `i`,
840+--  and that all the other fields must contain values.
841+
842+--  The typing rules are also simple:
843+--
844+--                     Γ ⊢ t₁ ⦂ τ₁     ...     Γ ⊢ tn ⦂ Tn
845+--                -----------------------------------------------------        (rcd)
846+--                Γ ⊢ {i₁=t₁, ..., in=tn} ⦂ {i₁:τ₁, ..., in:Tn}
847+--
848+--
849+--                            Γ ⊢ t ⦂ {..., i:Ti, ...}
850+--                          ---------------------------------                  (proj)
851+--                                Γ ⊢ t.i ⦂ Ti
852+
853+--  There are several ways to approach formalizing the above definitions.
854+--
855+--  - We can directly formalize the syntactic forms and inference rules,
856+--    staying as close as possible to the form we've given them above. This
857+--    is conceptually straightforward, and it's probably what we'd want to
858+--    do if we were building a real compiler (in particular, it will allow
859+--    us to print error messages in the form that programmers will find
860+--    easy to understand). But the formal versions of the rules will not be
861+--    very pretty or easy to work with, because all the `...`s above will
862+--    have to be replaced with explicit quantifications or comprehensions.
863+--    For this reason, records are not included in the extended exercise at
864+--    the end of this chapter. (It is still useful to discuss them
865+--    informally here because they will help motivate the addition of
866+--    subtyping to the type system when we get to the Sub chapter.)
867+--
868+--  - Alternatively, we could look for a smoother way of presenting records
869+--    -- for example, a binary presentation with one constructor for the ∅
870+--    record and another constructor for adding a single field to an
871+--    existing record, instead of a single monolithic constructor that
872+--    builds a whole record at once. This is the right way to go if we are
873+--    primarily interested in studying the metatheory of the calculi with
874+--    records, since it leads to clean and elegant definitions and proofs.
875+--
876+--  - Finally, if we like, we can avoid formalizing records altogether, by
877+--    stipulating that record notations are just informal shorthands for
878+--    more complex expressions involving pairs and product types. We sketch
879+--    this approach in the next section.
880+
881+--  Let's see how records can be encoded using just pairs and `unit`. (This
882+--  clever encoding, as well as the observation that it also extends to
883+--  systems with subtyping, is due to Luca Cardelli.)
884+--
885+--  First, observe that we can encode arbitrary-size *tuples* using nested
886+--  pairs and the `unit` value. To avoid overloading the pair notation
887+--  `(t₁,t₂)`, we'll use curly braces without labels to write down tuples,
888+--  so `{}` is the ∅ tuple, `{5}` is a singleton tuple, `{5,6}]`is a
889+--  2-tuple (morally the same as a pair), `{5,6,7}` is a triple, etc.
890+--
891+--            {}                 ⟶  unit
892+--            {t₁, t₂, ..., tn}  ⟶  (t₁, trest)
893+--                                      where {t₂, ..., tn} ⟶ trest
894+--
895+--  Similarly, we can encode tuple types using nested product types:
896+--
897+--            {}                 ⟶  Unit
898+--            {τ₁, τ₂, ..., Tn}  ⟶  τ₁ * TRest
899+--                                      where {τ₂, ..., τn} ⟶ τn
900+--
901+--  The operation of projecting a field from a tuple can be encoded using a
902+--  sequence of second projections followed by a first projection:
903+--
904+--            t.0        ⟶  fst t
905+--            t.(n+1)    ⟶  (snd t).n
906+--
907+--  Next, suppose that there is some total ordering on record labels, so
908+--  that we can associate each label with a unique natural number. This
909+--  number is called the *position* of the label. For example, we might
910+--  assign positions like this:
911+--
912+--            LABEL   POSITION
913+--            a       0
914+--            b       1
915+--            c       2
916+--            ...     ...
917+--            bar     1395
918+--            ...     ...
919+--            foo     4460
920+--            ...     ...
921+--
922+--  We use these positions to encode record values as tuples (i.e., as
923+--  nested pairs) by sorting the fields according to their positions. For
924+--  example:
925+--
926+--            {a=5,b=6}       ⟶   {5,6}
927+--            {a=5,c=7}       ⟶   {5,unit,7}
928+--            {c=7,a=5}       ⟶   {5,unit,7}
929+--            {c=5,b=3}       ⟶   {unit,3,5}
930+--            {f=8,c=5,a=7}   ⟶   {7,unit,5,unit,unit,8}
931+--            {f=8,c=5}       ⟶   {unit,unit,5,unit,unit,8}
932+--
933+--  Note that each field appears in the position associated with its label,
934+--  that the size of the tuple is determined by the label with the highest
935+--  position, and that we fill in unused positions with `unit`.
936+--
937+--  We do exactly the same thing with record types:
938+--
939+--            {a:Nat,b:Nat}       ⟶   {Nat,Nat}
940+--            {c:Nat,a:Nat}       ⟶   {Nat,Unit,Nat}
941+--            {f:Nat,c:Nat}       ⟶   {Unit,Unit,Nat,Unit,Unit,Nat}
942+--
943+--  Finally, record projection is encoded as a tuple projection from the
944+--  appropriate position:
945+--
946+--            t.l ⟶ t.(position of l)
947+--
948+--  It is not hard to check that all the typing rules for the original
949+--  "direct" presentation of records are validated by this encoding. (The
950+--  reduction rules are "almost validated" -- not quite, because the
951+--  encoding reorders fields.)
952+
953+--  Of course, this encoding will not be very efficient if we happen to use
954+--  a record with label `foo`! But things are not actually as bad as they
955+--  might seem: for example, if we assume that our compiler can see the
956+--  whole program at the same time, we can *choose* the numbering of labels
957+--  so that we assign small positions to the most frequently used labels.
958+--  Indeed, there are industrial compilers that essentially do this!
959+
960+--  Just as products can be generalized to records, sums can be generalized
961+--  to n-ary labeled types called *variants*. Instead of `τ₁+τ₂`, we can
962+--  write something like `<l₁:τ₁,l₂:τ₂,...ln:τn>` where `l₁`,`l₂`,... are
963+--  field labels which are used both to build instances and as case arm
964+--  labels.
965+--
966+--  These n-ary variants give us almost enough mechanism to build arbitrary
967+--  inductive data types like lists and trees from scratch -- the only
968+--  thing missing is a way to allow *recursion* in type definitions. We
969+--  won't cover this here, but detailed treatments can be found in many
970+--  textbooks -- e.g., Types and Programming Languages (Pierce, 2002).
