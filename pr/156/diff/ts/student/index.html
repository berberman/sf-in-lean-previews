4added
5added-- So far we have discussed **parametric polymorphism**, where in Lean we can
6added-- declare a type variable
7added
8addedvariable (α : Type)
9added
10added-- without any further information about the details of the type `α`. Here we
11added-- are able to work with a type like `List α`, and can write functions like
12added-- `List.reverse` or `List.length` that only operate on the structure of a
13added-- list independently of its contents. Along with these we have corresponding
14added-- proofs like `List.length_reverse` that are similarly structural in nature.
15added
16added-- This is somewhat limiting, as we cannot inspect or non-trivially use any
17added-- particular `a : α`. What we might want in some situations rather than `α`
18added-- being completely generic is to partially specify its behavior. In Lean,
19added-- this happens through a form of "ad hoc polymorphism" called
20added-- **typeclasses**. This concept originated in the Haskell programming
21added-- language, and is analogous to features you may be familiar with in other
22added-- languages such as traits in Rust.
23added
24added-- ## First Example: Inhabited Types
25added
26added-- Suppose we wanted to specify that a type has at least one inhabitant —
27added-- i.e., that it is not empty. We have previously seen `structure`, which
28added-- would allow us to express this as
29added
30addedstructure HasOneStruct (α : Type) where
31added one : α
32added
33added-- As discussed previously, a structure is just an inductive type that comes
34added-- with a single constructor, in this case `HasOneStruct.mk`, along with a few
35added-- different syntaxes for convenience:
36added
37addeddef nat_hasOneStruct_mk : HasOneStruct Nat := HasOneStruct.mk 1
38added
39addeddef nat_hasOneStruct_brace : HasOneStruct Nat := {one := 1}
40added
41addeddef nat_hasOneStruct_where : HasOneStruct Nat where
42added one := 1
43added
44added-- All of these are the same value, a structure of type `HasOneStruct Nat`
45added-- that we can thing of as carrying a piece of data (a term that is not a
46added-- proposition), the number `1`, as evidence that this type is not empty. We
47added-- can use this in proofs such as
48added
49addedtheorem nat_hasOneStruct_eq_one : nat_hasOneStruct_mk.one = 1 := rfl
50added
51added-- to see how this structure provably contains the value that we have placed
52added-- within it. In Lean, typeclasses work very similarly, and in fact are
53added-- implemented as structures. The only difference in defining a typeclass is
54added-- that we instead use the `class` keyword:
55added
56addedclass HasOne (α : Type) where
57added one : α
58added
59added-- While the definition is essentially the same, including the constructor
60added-- `HasOne.mk`, the usage of typeclasses is different, and what allows us to
61added-- use them to express ad hoc polymorphism. Instead of using `def` to define
62added-- inhabitants of this type, we will instead use the `instance` keyword:
63added
64added-- Note to developers:
65added-- From GitHub (@chenson2018): Part of the point here is that we don't
66added-- usually refer to instances explicitly, even me providing an explicit
67added-- name is for pedagogy reasons. I'll make it more explicit in the text
68added-- that what we're looking for in the infoview is the presence of this
69added-- instance.
70added
71addedinstance instHasOneNat : HasOne Nat where
72added one := 1
73added
74added-- The definition is exactly the same as above (and any of the alternative
75added-- syntaxes work as well), but instead of being used as a definition that we
76added-- pass around, Lean will try to infer its usage through a process called
77added-- **typeclass synthesis** or **typeclass inference**. To help see this, let's
78added-- define another instance of `HasOne` for `Int`, the type of integers ... -2,
79added-- -1, 0, 1, 2, ...
80added
81addedinstance instHasOneInt : HasOne Int where
82added one := -1
83added
84added-- Instead of explicitly referring to a structure like we did in the proof
85added-- `nat_hasOneStruct_eq_one`, we can instead use `HasOne.one`, and Lean will
86added-- use typeclass inference to determine the intended meaning. As an example,
87added-- you can write
88added
89addedexample : HasOne.one = (1 : Nat) := rfl
90addedexample : HasOne.one = (-1 : Int) := rfl
91added
92added-- and based on the type annotations Lean will infer which of these instances
93added-- you intended to use. So these proofs are equivalent to
94added
95addedexample : instHasOneNat.one = (1 : Nat) := rfl
96addedexample : instHasOneInt.one = (-1 : Int) := rfl
97added
98added-- but without needing to explicitly refer to the instances `instHasOneNat`
99added-- and `instHasOneInt`. Another way that we can inspect what instance is being
100added-- using with the constructor of a typeclass is the option `pp.all`. For
101added-- example looking at
102added
103addedset_option pp.all true in
104addedexample : HasOne.one = (1 : Nat) := rfl
105added
106addedset_option pp.all true in
107addedexample : HasOne.one = (-1 : Int) := rfl
108added
109added-- we can see that `@HasOne.one Nat instHasOneNat` and
110added-- `@HasOne.one Int instHasOneInt` are the respective terms that appear on the
111added-- right hand side of each equality.
112added
113added-- Lean also has a command `#synth` that allows you to search for an instance
114added-- of a given type. So the command
115added
116added#synth HasOne Nat
117added
118added-- for instance prints `instHasOneNat`, informing us that this is the instance
119added-- found that has type `HasOne Nat`. In general, the assumption is that for
120added-- typeclasses like `HasOne` that include data, as opposed to solely proofs,
121added-- that these these instances should be unique to avoid ambiguity.

127added-- ## Proof-Carrying Typeclasses
128added
129added-- Notably, the above examples enforce no conditions on the data that they
130added-- carry, and we could provide any value that we would like for `HasOne.one`.
131added-- This could be misleading, for instance if we had instead defined an
132added-- instance
133added
134addedsf_experiment
135added instance : HasOne Nat where
136added one := 2
137added
138added-- we might have some counterintuitive proofs based on the name leading us to
139added-- believe the class contained the element `1`. In most languages that support
140added-- typeclasses it is not possible to enforce a notion of "lawfulness" as part
141added-- of the typeclass, and it falls to the author to ensure that any desired
142added-- invariants are satisfied.
143added
144added-- As an example, suppose that we wanted to express the idea that a type has
145added-- at least two distinct elements. A first attempt might be
146added
147addedsf_experiment
148added class HasTwoIncomplete (α : Type) where
149added one : α
150added two : α
151added

153added-- proof assistant, however, typeclasses can also carry proofs along with
154added-- data, so we can write
155added
156addedclass HasTwo (α : Type) where
157added one : α
158added two : α

162added-- in much the same way as before, except that now `HasTwo.one_neq_two`
163added-- requires a proof:
164added
165addedinstance : HasTwo Nat where
166added one := 1
167added two := 2

335added-- ## Maps
336added
337added-- Maps (or dictionaries) are ubiquitous data structures both in ordinary
338added-- programming and in the theory of programming languages; we're going to need
339added-- them in many places in the coming chapters.
340added
341added-- We'll define two flavors of maps: total maps, which include a "default"
342added-- element to be returned when a key being looked up doesn't exist, and
343added-- partial maps, which instead return an option to indicate success or
344added-- failure. Partial maps are defined in terms of total maps, using None as the
345added-- default element.
346added
347added-- ### Identifiers
348added
349added-- To define maps, we first need a type for the keys that we will use to index
350added-- into our maps. Instead of using concrete types, we will use a type
351added-- variables
352added
353addeduniverse u v
354addedvariable {α : Type u} {β : Type v} [BEq α] [ReflBEq α] [LawfulBEq α]
355added
356addedset_option linter.unusedSectionVars false
357added
358added-- where `α` is the type of our map keys and `β` the corresponding values.
359added-- Looking at `ReflBEq` and `LawfulBEq`, we see that these typeclasses:
360added
361added-- /-- `ReflBEq α` says that the `BEq` implementation is reflexive. -/
362added-- class ReflBEq (α) [BEq α] : Prop where
363added-- /-- `==` is reflexive, that is, `(a == a) = true`. -/
364added-- protected rfl {a : α} : a == a
365added
366added-- /--
367added-- A Boolean equality test coincides with propositional equality.
368added
369added-- In other words:
370added-- * `a == b` implies `a = b`.
371added-- * `a == a` is true.
372added-- -/
373added-- class LawfulBEq (α : Type u) [BEq α] : Prop extends ReflBEq α where
374added-- /-- If `a == b` evaluates to `true`, then `a` and `b` are equal in the logic. -/
375added-- eq_of_beq : {a b : α} → a == b → a = b
376added
377added-- provide the assumption that we have an boolean equality (`==`) on our keys
378added-- that is reflexive and coincides with proposition equality `=`.
379added
380added-- ### Total Maps
381added
382added-- Our main job in this chapter will be to build a definition of partial maps
383added-- that is similar in behavior to the one we saw in the Lists chapter, plus
384added-- accompanying lemmas about its behavior.
385added
386added-- This time around, though, we're going to use functions, rather than lists
387added-- of key-value pairs, to build maps. The advantage of this representation is
388added-- that it offers a more "extensional" view of maps: two maps that respond to
389added-- queries in the same way will be represented as exactly the same function,
390added-- rather than just as "equivalent" list structures. This simplifies proofs
391added-- that use maps.
392added
393added-- We build up to partial maps in two steps. First, we define a type of total
394added-- maps that return a default value when we look up a key that is not present
395added-- in the map.

402added-- can be looked up using a corresponding `a : α`.
403added

405added-- typeclass, which is the standard library's implementation of our `HasOne`
406added-- example from above:
407added
408addedvariable [Inhabited β]

410added-- The function `TotalMap.empty` yields an empty total map, given a default
411added-- element; this map always returns the default element when applied to any
412added-- string.

432added-- More interesting is the map-updating function, which (as always) takes a

8added-- # Stlc: The Simply Typed Lambda-Calculus
9added
10added-- The simply typed lambda-calculus (STLC) is a tiny core calculus embodying
11added-- the key concept of *functional abstraction*. This concept shows up in
12added-- pretty much every real-world programming language in some form (functions,
13added-- procedures, methods, etc.).
14added
15added-- We will follow exactly the same pattern as in the previous chapter when
16added-- formalizing this calculus (syntax, small-step semantics, typing rules) and
17added-- its main properties (progress and preservation). The new technical
18added-- challenges arise from the mechanisms of *variable binding* and
19added-- *substitution*. It will take some work to deal with these.
20added
21added-- The STLC lives in the lower-left front corner of the famous *lambda cube*
22added-- (also called the *Barendregt Cube*), which visualizes three sets of
23added-- features that can be added to its simple core:
24added
25added-- Calculus of Constructions
26added-- type operators +--------+
27added-- /| /|
28added-- / | / |
29added-- polymorphism +--------+ |
30added-- | | | |
31added-- | +-----|--+
32added-- | / | /
33added-- |/ |/
34added-- +--------+ dependent types
35added-- STLC
36added
37added-- Moving from bottom to top in the cube corresponds to adding *polymorphic
38added-- types* like `∀ α : Type, α → α`. Adding *just* polymorphism gives us the
39added-- famous Girard-Reynolds calculus, System F.
40added
41added-- Moving from front to back corresponds to adding *type operators* like
42added-- `List`.
43added
44added-- Moving from left to right corresponds to adding *dependent types* like
45added-- `∀ n, ArrayOfSize n`.
46added
47added-- The top right corner on the back, which combines all three features, is
48added-- called the *Calculus of Constructions*. First studied by Coquand and Huet,
49added-- it forms the foundation of Lean's logic.
50added
51added-- ## Overview
52added
53added-- The STLC is built on some collection of *base types*: booleans, numbers,
54added-- strings, etc. The exact choice of base types doesn't matter much -- the
55added-- definition of the language as well as its theoretical properties work out
56added-- the same no matter what we choose -- so for the sake of brevity let's take
57added-- just `Bool` for the moment. In the next chapter we'll see how to add more
58added-- base types, and in later chapters we'll enrich the pure STLC with other
59added-- useful constructs like pairs, records, subtyping, and mutable state.
60added
61added-- Starting from boolean constants and conditionals, we add three things:
62added
63added-- - variables
64added-- - function abstractions
65added-- - application
66added
67added-- This gives us the following collection of abstract syntax constructors
68added-- (written out first in informal BNF notation -- we'll formalize it below)
69added-- for STLC terms `t`.
70added
71added-- t ::= x (variable)
72added-- | λ x : T . t (abstraction)
73added-- | t t (application)
74added-- | true (constant true)
75added-- | false (constant false)
76added-- | if t then t else t (conditional)

78added-- The Greek letter λ ("lambda") in a function abstraction `λx:T. t` is what
79added-- gives the calculus its name. The variable `x` is called the *parameter* to
80added-- the function; the term `t` is its *body*. The annotation `:T` specifies the
81added-- *type* of arguments that the function can be applied to.
82added
83added-- The types of the STLC include `Bool`, which classifies the boolean
84added-- constants `true` and `false` as well as more complex computations that
85added-- yield booleans, plus *arrow types* that classify functions (as is the case
86added-- in Lean).
87added
88added-- T ::= Bool
89added-- | T → T
90added
91added-- Some examples of STLC terms:
92added
93added-- `λx:Bool. x`
94added

96added
97added-- `(λx:Bool. x) true`
98added

100added
101added-- `λx:Bool. if x then false else true`
102added
103added-- The boolean "not" function.
104added
105added-- `λx:Bool. true`
106added
107added-- The constant function that takes every (boolean) argument to `true`.
108added
109added-- `λx:Bool. λy:Bool. x`
110added
111added-- A two-argument function that takes two booleans and returns the first one.
112added
113added-- (As in Lean, a two-argument function in the lambda-calculus is really a
114added-- one-argument function whose body is also a one-argument function.)
115added
116added-- `(λx:Bool. λy:Bool. x) false true`
117added
118added-- A two-argument function that takes two booleans and returns the first one,
119added-- applied to the booleans `false` and `true`.
120added
121added-- (As in Lean, application associates to the left -- i.e., this expression is
122added-- parsed as `((λx:Bool. λy:Bool. x) false) true`.)
123added
124added-- `λf:Bool → Bool. f (f true)`
125added
126added-- A higher-order function that takes a *function* `f` (from booleans to

128added-- the result.
129added
130added-- `(λf:Bool → Bool. f (f true)) (λx:Bool. false)`
131added
132added-- The same higher-order function, applied to the constantly `false` function.
133added
134added-- The last two examples show, the STLC is a language of *higher-order*
135added-- functions: we can write down functions that take other functions as
136added-- arguments and/or return other functions as results.
137added
138added-- The STLC doesn't provide any primitive syntax for defining *named*
139added-- functions: i.e., all functions are "anonymous." We'll see in chapter
140added-- `MoreStlc` that it is easy to add named functions -- indeed, the
141added-- fundamental naming and binding mechanisms are exactly the same.
142added

194added
195added-- We next formalize the syntax of the STLC.

200added
201addedinductive Ty where
202added | bool
203added | arrow (T₁ T₂ : Ty)

206added
207addedinductive Tm where
208added | var (x : String)

215added-- We need some notation magic to set up the concrete syntax, as we did in the
216added-- Types chapter...
217added
218added-- The upshot of this section is that STLC types and terms are both written
219added-- inside one pair of brackets, `<{ … }>`, and that `~e` inside the brackets
220added-- escapes back to an arbitrary Lean expression:
221added
222added-- - `<{ Bool → Bool }>` is a type;
223added
224added-- - `<{ λ x : Bool . x }>` is a term -- a bare identifier inside the brackets
225added-- is the object-language variable of that name, so `<{ x }>` is the variable
226added-- `x`;
227added
228added-- - `<{ ~t₁ ~t₂ }>` applies one Lean-level term to another.
229added
230added-- Lean works out from context which of the two a given bracket holds, so the
231added-- same brackets serve for types, for terms, and -- when we come to typing --
232added-- for typing judgments too. How that works is in the collapsed blocks below;
233added-- nothing later in the chapter depends on it.
234added
235added-- _Details:_ Notation encoding: types
236added
237added-- The `stlcTy` grammar covers `Bool`, arrows (written `→` or `->`,
238added-- associating to the right), parentheses, and `~e`. A bare identifier other
239added-- than `Bool` is spliced in as a Lean term, so a local `T` -- or any Lean
240added-- expression of type `Ty` -- can appear directly inside the brackets.
241added
242added-- To extend the grammar, a later chapter adds a `syntax` line to the category
243added-- and a matching `macro_rules` case; that is all it takes to add a new type
244added-- construct.
245added
246addeddeclare_syntax_cat stlcTy
247addedsyntax:max "~" term:max : stlcTy
248addedsyntax:max "(" stlcTy ")" : stlcTy
249addedsyntax:max ident : stlcTy
250addedsyntax:50 stlcTy:51 " → " stlcTy:50 : stlcTy
251addedsyntax:50 stlcTy:51 " -> " stlcTy:50 : stlcTy
252addedsyntax:max (name := tyBracket) "<{ " stlcTy " }>" : term
253added
254addedmacro_rules (kind := tyBracket)
255added | `(<{ ~$T:term }>) => pure T
256added | `(<{ ($T:stlcTy) }>) => `(<{ $T:stlcTy }>)
257added | `(<{ $x:ident }>) =>
258added match x.getId.toString with
259added | "Bool" => `(Ty.bool)
260added | _ => `(($x : Ty))
261added | `(<{ $T₁:stlcTy → $T₂:stlcTy }>) => `(Ty.arrow <{ $T₁:stlcTy }> <{ $T₂:stlcTy }>)
262added | `(<{ $T₁:stlcTy -> $T₂:stlcTy }>) => `(Ty.arrow <{ $T₁:stlcTy }> <{ $T₂:stlcTy }>)
263added
264added-- We'll write types inside of `<{ ... }>` brackets:
265added
266added#check <{ Bool }>
267added#check <{ Bool -> Bool }>
268added#check <{ (Bool -> Bool) -> Bool }>
269added
270added-- _Details:_ Notation encoding: terms
271added
272added-- Terms are built from variables, application (associating to the left),
273added-- abstraction, the two boolean constants, and conditionals. A binding
274added-- occurrence -- the `x` in `λ x : T . t` -- has a small grammar of its own,
275added-- `stlcVar`, and `varStr` turns it into the string that `Tm.abs` stores.
276added
277added-- Because types and terms share the brackets, each `macro_rules` group says
278added-- which bracket it belongs to (`kind := tyBracket`, `kind := tmBracket`), and
279added-- each antiquote in a nested quotation says which grammar it came from. A
280added-- bare identifier is the one genuinely overlapping case: `Bool` in term
281added-- position would otherwise quietly become a variable named `Bool`, so that
282added-- rule rejects it, which also settles which grammar a lone `<{ Bool }>`
283added-- belongs to.
284added
285added-- The last production, `[x := s] t`, is the notation for substitution; we
286added-- give it its meaning when we define substitution below. It binds tighter
287added-- than application, so `[x:=s] t₁ t₂` is the application of `[x:=s] t₁` to
288added-- `t₂`, and a `λ` or `if` body must be parenthesized:
289added-- `[x:=s] (λ y : Bool . x)`.
290added
291addeddeclare_syntax_cat stlcVar
292addedsyntax:max ident : stlcVar
293addedsyntax:max "~" term:max : stlcVar
294added
295addedopen Lean in
296added/-- The string named by a variable in binding position. -/
297addeddef varStr (x : TSyntax `stlcVar) : MacroM Term :=
298added match x with
299added | `(stlcVar| $i:ident) => pure (quote i.getId.toString : Term)
300added | `(stlcVar| ~$e) => pure e
301added | _ => Macro.throwUnsupported
302added
303addeddeclare_syntax_cat stlcTm
304addedsyntax:max "~" term:max : stlcTm
305addedsyntax:max "(" stlcTm ")" : stlcTm
306addedsyntax:max ident : stlcTm
307addedsyntax:75 stlcTm:75 ppSpace stlcTm:76 : stlcTm
308addedsyntax:50 "λ " stlcVar " : " stlcTy " . " stlcTm:50 : stlcTm
309addedsyntax:50 "if " stlcTm:51 " then " stlcTm:50 " else " stlcTm:50 : stlcTm
310addedsyntax:max "[" stlcVar " := " stlcTm "] " stlcTm:max : stlcTm
311addedsyntax:max (name := tmBracket) "<{ " stlcTm " }>" : term
312added

314addedmacro_rules (kind := tmBracket)
315added | `(<{ ~$e:term }>) => pure e
316added | `(<{ ($t:stlcTm) }>) => `(<{ $t:stlcTm }>)
317added | `(<{ $x:ident }>) =>
318added match x.getId.toString with
319added | "true" => `(Tm.tru)
320added | "false" => `(Tm.fls)
321added | "Bool" => Macro.throwErrorAt x "`Bool` is a type, not a term"
322added | _ => `(Tm.var $(quote x.getId.toString))

324added | `(<{ λ $x : $T . $t }>) => do

473added-- ## Operational Semantics
474added
475added-- To define the small-step semantics of STLC terms, we begin, as always, by
476added-- defining the set of values. Next, we define the critical notions of *free
477added-- variables* and *substitution*, which are used in the reduction rule for
478added-- application expressions. And finally we give the small-step relation
479added-- itself.
480added
481added-- ### Values
482added
483added-- To define the values of the STLC, we have a few cases to consider.
484added
485added-- First, for the boolean part of the language, the situation is clear: `true`
486added-- and `false` are the only values. An `if` expression is never a value.
487added
488added-- Second, an application is not a value: it represents a function being
489added-- invoked on some argument, which clearly still has work left to do.
490added
491added-- Third, for abstractions, we have a choice:
492added
493added-- - We can say that `λx:T. t` is a value only when `t` is a value -- i.e., only
494added-- if the function's body has been reduced (as much as it can be without
495added-- knowing what argument it is going to be applied to).
496added
497added-- - Or we can say that `λx:T. t` is always a value, no matter whether `t` is
498added-- one or not -- in other words, we can say that reduction stops at
499added-- abstractions.
500added
501added-- Our usual way of evaluating expressions in Lean makes the first choice --
502added-- for example,
503added
504added#reduce fun _x : Bool => 3 + 4
505added
506added-- yields:
507added
508added-- fun _x => 7
509added
510added-- But Lean is rather unusual in this respect. Most functional programming
511added-- languages make the second choice -- reduction of a function's body only
512added-- begins when the function is actually applied to an argument.
513added
514added-- We also make the second choice here.
515added
516addedinductive Tm.IsValue : Tm → Prop where
517added | abs (x : String) (T₂ : Ty) (t₁ : Tm) : Tm.IsValue <{ λ ~x : ~T₂ . ~t₁ }>
518added | tru : Tm.IsValue <{ true }>
519added | fls : Tm.IsValue <{ false }>
520added
521added-- The example terms named above are all abstractions, hence all values. We
522added-- record that once each, so that the reduction examples can cite the fact by
523added-- name instead of unfolding the definition again at every use.
524added
525addedtheorem idB_value : idB.IsValue := .abs ..
526addedtheorem idBB_value : idBB.IsValue := .abs ..
527addedtheorem notB_value : notB.IsValue := .abs ..
528added

530added-- The Rocq source follows each inductive definition in this chapter with
531added-- a `Hint Constructors … : core`, registering the constructors with
532added-- `auto`; the proofs then lean on `auto`/`eauto` to assemble derivations.
533added-- We have no counterpart here: the proofs below name their constructors
534added-- explicitly, in the style of the Types chapter. Lean's `grind` would be
535added-- the closest analogue if a later pass wants automation.
536added
537added-- ### STLC Programs
538added
539added-- Finally, we must consider what constitutes a *complete* program.
540added
541added-- Intuitively, a "complete program" must not refer to any undefined
542added-- variables. We'll see shortly how to define the *free* variables in a STLC
543added-- term. A complete program, then, is one that is *closed* -- that is, that
544added-- contains no free variables.
545added
546added-- (Conversely, a term that may contain free variables is often called an
547added-- *open term*.)
548added
549added-- Note to developers (Chris Henson @chenson2018, before next release):
550added-- Is the "shortly" above setting wrong expectations? Where exactly are we
551added-- defining the free variables in a STLC term? BCP 25: Indeed, we need to
552added-- define "free"!
553added
554added-- Having made the choice not to reduce under abstractions, we don't need to
555added-- worry about whether variables are values, since we'll always be reducing
556added-- programs "from the outside in," and that means the `step` relation will
557added-- always be working with closed terms.
558added
559added-- ### Substitution
560added
561added-- Now we come to the heart of the STLC: the operation of *substituting* one
562added-- term for a variable in another term. This operation is used below to define
563added-- the operational semantics of function application, where we will need to
564added-- substitute the argument term for the function parameter in the function's
565added-- body. For example, we reduce
566added
567added-- (λx:Bool. if x then true else x) false
568added
569added-- to
570added
571added-- if false then true else false
572added
573added-- by substituting `false` for the parameter `x` in the body of the function.
574added
575added-- In general, we need to be able to substitute some given term `s` for
576added-- occurrences of some variable `x` in another term `t`. Informally, this is
577added-- written `[x:=s]t` and pronounced "substitute `s` for `x` in `t`."
578added
579added-- Here are some examples:
580added
581added-- - `[x:=true] (if x then true else false)` yields
582added-- `if true then true else false`
583added
584added-- - `[x:=true] x` yields `true`
585added
586added-- - `[x:=true] (if x then x else y)` yields `if true then true else y`
587added
588added-- - `[x:=true] y` yields `y`
589added
590added-- - `[x:=true] false` yields `false` (vacuous substitution)
591added
592added-- - `[x:=true] (λy:Bool. if y then x else false)` yields
593added-- `λy:Bool. if y then true else false`
594added
595added-- - `[x:=true] (λy:Bool. x)` yields `λy:Bool. true`
596added

769added-- ### Reduction
770added
771added-- The small-step reduction relation for STLC now follows the same pattern as
772added-- the ones we have seen before. Intuitively, to reduce a function
773added-- application, we first reduce its left-hand side (the function) until it
774added-- becomes an abstraction; then we reduce its right-hand side (the argument)
775added-- until it is also a value; and finally we substitute the argument for the
776added-- bound variable in the body of the abstraction. This last rule, written
777added-- informally as
778added
779added-- (λx:T. t₁₂) v₂ ⟶ [x:=v₂] t₁₂
780added
781added-- is traditionally called *beta-reduction*.
782added
783added-- value v
784added-- ----------------------- (appAbs)
785added-- (λx:T. t) v ⟶ [x:=v]t
786added
787added-- t₁ ⟶ t₁'
788added-- ---------------- (app1)
789added-- t₁ t₂ ⟶ t₁' t₂
790added
791added-- value v₁
792added-- t₂ ⟶ t₂'
793added-- ---------------- (app2)
794added-- v₁ t₂ ⟶ v₁ t₂'
795added
796added-- ... plus the usual rules for conditionals:
797added
798added-- -------------------------------- (ifTrue)
799added-- (if true then t₁ else t₂) ⟶ t₁
800added
801added-- --------------------------------- (ifFalse)
802added-- (if false then t₁ else t₂) ⟶ t₂
803added
804added-- t₁ ⟶ t₁'
805added-- ---------------------------------------------------- (ifStep)
806added-- (if t₁ then t₂ else t₃) ⟶ (if t₁' then t₂ else t₃)
807added
808added-- This is *call by value* reduction: to reduce an application `(t₁ t₂)`, we
809added
810added-- - first reduce `t₁` to a value: a function `λx:T. t`
811added
812added-- - then reduce the argument `t₂` to a value `v`
813added
814added-- - then reduce the application itself by substituting `v` for the bound
815added-- variable `x` in the body `t`.
816added
817added-- Formally:
818added
819addedsection
820addedset_option hygiene false in
821addedlocal notation:40 t:41 " ⟶ " t':41 => Step t t'
822added
823addedinductive Step : Tm → Tm → Prop where
824added | appAbs (x : String) (T : Ty) (t v : Tm) (hv : v.IsValue) :
825added <{ (λ ~x : ~T . ~t) ~v }> ⟶ <{ [~x := ~v] ~t }>
826added | app1 (t₁ t₁' t₂ : Tm) (h : t₁ ⟶ t₁') :
827added <{ ~t₁ ~t₂ }> ⟶ <{ ~t₁' ~t₂ }>
828added | app2 (v₁ t₂ t₂' : Tm) (hv : v₁.IsValue) (h : t₂ ⟶ t₂') :
829added <{ ~v₁ ~t₂ }> ⟶ <{ ~v₁ ~t₂' }>
830added | ifTrue (t₁ t₂ : Tm) :
831added <{ if true then ~t₁ else ~t₂ }> ⟶ t₁
832added | ifFalse (t₁ t₂ : Tm) :
833added <{ if false then ~t₁ else ~t₂ }> ⟶ t₂
834added | ifStep (t₁ t₁' t₂ t₃ : Tm) (h : t₁ ⟶ t₁') :
835added <{ if ~t₁ then ~t₂ else ~t₃ }> ⟶ <{ if ~t₁' then ~t₂ else ~t₃ }>
836addedend

1029added-- ### Contexts
1030added
1031added-- Although we are primarily interested in the binary relation `⊢ t ⦂ T`,
1032added-- relating a closed term `t` to its type `T`, we need to generalize a bit to
1033added-- make the definitions work.
1034added
1035added-- Consider checking that `λx:T₁₁. t₁₂` has type `T₁₁ → T₁₂`. Intuitively, we
1036added-- need to check that `t₁₂` has type `T₁₂`. However, we have removed the
1037added-- binder `λx`, so `x` may occur free in `t₁₂` (that is, `t₁₂` may be *open*).
1038added-- While checking that `t₁₂` has type `T₁₂`, we must remember that `x` has
1039added-- type `T₁₁`, in order to deal with these free occurrences of `x`. Similarly,
1040added-- `t₁₂` itself could contain abstractions, and typechecking their bodies
1041added-- could require looking up the declared types of yet more free variables.
1042added
1043added-- To keep track of all this, we add a third element to the relation, a
1044added-- *typing context* `Γ`, which records the types of the variables that may
1045added-- occur free in a term -- that is, Γ is a partial map from variables to
1046added-- types.
1047added
1048added-- The new *typing judgment* is written `Γ ⊢ t ⦂ T` and informally read as
1049added-- "term `t` has type `T`, given the types of free variables in `t` as
1050added-- specified by `Γ`".
1051added
1052added-- We'll also write `x ↦ T ; Γ` for "update the partial map `Γ` so that it
1053added-- maps `x` to `T`," following the notation from the `Typeclasses` chapter.
1054added
1055added-- With these refinements, we are ready to give informal and formal
1056added-- specifications of the typing relation.
1057added
1058added-- Note to developers (Chris Henson @chenson2018, before next release):
1059added-- I find the FULL explanation above much better than the TERSE one below,
1060added-- since the question below seems ill-posed without extra context. Why

1062added-- just look at closed terms as our programs?

1064addedabbrev Context := PartialMap String Ty
1065added
1066added-- A context is a `PartialMap` from variable names to types -- the partial
1067added-- maps of the `Typeclasses` chapter, which are total maps whose values are
1068added-- optional, so that `none` at a variable means "not bound here".
1069added
1070added-- ### Typing Relation
1071added
1072added-- Γ x = T₁
1073added-- ------------ (var)
1074added-- Γ ⊢ x ⦂ T₁
1075added
1076added-- x ↦ T₂ ; Γ ⊢ t₁ ⦂ T₁
1077added-- ------------------------- (abs)
1078added-- Γ ⊢ λx:T₂. t₁ ⦂ T₂ → T₁
1079added
1080added-- Γ ⊢ t₁ ⦂ T₂ → T₁
1081added-- Γ ⊢ t₂ ⦂ T₂
1082added-- ------------------ (app)
1083added-- Γ ⊢ t₁ t₂ ⦂ T₁
1084added
1085added-- ----------------- (tru)
1086added-- Γ ⊢ true ⦂ Bool
1087added
1088added-- ------------------ (fls)
1089added-- Γ ⊢ false ⦂ Bool
1090added
1091added-- Γ ⊢ t₁ ⦂ Bool Γ ⊢ t₂ ⦂ T₁ Γ ⊢ t₃ ⦂ T₁
1092added-- --------------------------------------------- (ite)
1093added-- Γ ⊢ if t₁ then t₂ else t₃ ⦂ T₁
1094added
1095added-- We can read the three-place relation `Γ ⊢ t ⦂ T` as: "under the assumptions
1096added-- in Γ, the term `t` has the type `T`."
1097added
1098added-- In the formal development, we write this judgment inside the same
1099added-- `<{ .. }>` brackets we use for types and terms, as introduced by the
1100added-- following notational conventions.
1101added
1102added-- A context is written `∅` when empty and `x ↦ T ; Γ` when extended with a
1103added-- binding, and `~e` escapes to a Lean expression of type `Context`. The whole
1104added-- judgment then goes inside the same `<{ … }>` brackets as terms, written
1105added-- with the turnstile and colon of the Types chapter: `<{ Γ ⊢ t ⦂ T }>`.
1106added
