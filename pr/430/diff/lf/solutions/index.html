1383+--  The Logic chapter's "Working with Decidable Properties" section

1388+--
1389+--  Recall from "Why We Need Typeclasses" that `[0, 1].elemPoly 0`'s `==`
1390+--  is filled in automatically by Lean, in contrast to
1391+--  `[0, 1].elemPolyEq Nat.beq 0`, which is handed `Nat.beq` explicitly.
1392+--  It's tempting to assume Lean fills in that very function as the `BEq`

1401+--  Not `Nat.beq` at all! Recall that `BEq`'s only field is
1402+--  `beq : α → α → Bool` — nothing more. `instBEqOfDecidableEq` builds a
1403+--  `BEq α` instance from a `DecidableEq α` one by setting
1404+--  `beq a b := decide (a = b)`: it takes the proof-carrying
1405+--  `Decidable (a = b)` value and uses `decide` to strip away the proof,
1406+--  keeping only the resulting `Bool`. `DecidableEq α` means
1407+--  `∀ a b : α, Decidable (a = b)`, so `Nat`'s `instDecidableEqNat` is
1408+--  exactly such a proof-producing decision procedure, and
1409+--  `instBEqOfDecidableEq` turns it into a `BEq Nat` instance for free — no
1410+--  one had to write one wrapping `Nat.beq` by hand. Because
1411+--  `decide (a = b)` genuinely computes whether `a = b` holds, this
1412+--  particular `beq` really does coincide with `=`, which is exactly why
1413+--  the derived instance is `LawfulBEq`.
1414+--
1415+--  But that agreement is a fact about *this* instance, not something `BEq`
1416+--  requires of every instance: `beq`'s only obligation is to return *some*
1417+--  `Bool`, with no proof attached — unlike `Decidable`'s constructors,
1418+--  whose whole point is to carry one. A hand-written `BEq` instance for
1419+--  some type could compute anything at all, whether or not it agrees with

1421+--  separately, as the Maps section did. So `List.elemPoly`'s `[BEq α]`
