1234+--  The Logic chapter's "Working with Decidable Properties" section
1235+--  explored the trade-offs between stating a claim as a boolean (of type
1236+--  `Bool`) and as a proposition (of type `Prop`). Here, we tie up a loose
1237+--  end from the start of this chapter, and along the way formalize
1238+--  *decidability* itself as a typeclass.
1239+--
1240+--  Recall from "Why We Need Typeclasses" that `[0, 1].elemPoly 0`'s `==`
1241+--  is filled in automatically by Lean, in contrast to
1242+--  `[0, 1].elemPolyEq Nat.beq 0`, which is handed `Nat.beq` explicitly.
1243+--  It's tempting to assume Lean fills in that very function as the `BEq`
1244+--  instance for `Nat` — but it doesn't. We can see this by asking Lean to
1245+--  synthesize the instance directly:
1246+
1247+#synth BEq Nat
1248+
1249+--  Output:
1250+--    instBEqOfDecidableEq
1251+
1252+--  Not `Nat.beq` at all! Recall that `BEq`'s only field is
1253+--  `beq : α → α → Bool` — nothing more. `instBEqOfDecidableEq` builds a
1254+--  `BEq α` instance from a `DecidableEq α` one by setting
1255+--  `beq a b := decide (a = b)`: it takes the proof-carrying
1256+--  `Decidable (a = b)` value and uses `decide` to strip away the proof,
1257+--  keeping only the resulting `Bool`. `DecidableEq α` means
1258+--  `∀ a b : α, Decidable (a = b)`, so `Nat`'s `instDecidableEqNat` is
1259+--  exactly such a proof-producing decision procedure, and
1260+--  `instBEqOfDecidableEq` turns it into a `BEq Nat` instance for free — no
1261+--  one had to write one wrapping `Nat.beq` by hand. Because
1262+--  `decide (a = b)` genuinely computes whether `a = b` holds, this
1263+--  particular `beq` really does coincide with `=`, which is exactly why
1264+--  the derived instance is `LawfulBEq`.
1265+--
1266+--  But that agreement is a fact about *this* instance, not something `BEq`
1267+--  requires of every instance: `beq`'s only obligation is to return *some*
1268+--  `Bool`, with no proof attached — unlike `Decidable`'s constructors,
1269+--  whose whole point is to carry one. A hand-written `BEq` instance for
1270+--  some type could compute anything at all, whether or not it agrees with
1271+--  `=`; that is exactly why `LawfulBEq` has to be stated and proved
1272+--  separately, as the Maps section did. So `List.elemPoly`'s `[BEq α]`
1273+--  constraint is the weakest assumption sufficient for a purely
1274+--  computational membership test, matching the interface the rest of the
1275+--  Lean ecosystem (hash maps, `deriving BEq`, and so on) already uses for
1276+--  comparisons — it doesn't require the caller to have decidable equality,
1277+--  or even a comparison that agrees with `=`, at all. `Decidable`, by
1278+--  contrast, is Lean's general-purpose mechanism for making an arbitrary
1279+--  *proposition* computational — not just equality, as we'll see shortly
1280+--  with the `even`/`Even` example — and it's what you reach for when you
1281+--  specifically need the underlying proof, not just a boolean.

1265---  with booleans (of type `Bool`), and with propositions (of type `Prop`).

1267---  Here are the key differences between `Bool` and `Prop`:
1268-
1269---  |                       | `Bool` | `Prop` |
1270---  | --------------------- | ------ | ------ |
1271---  | decidable?            |  yes   |   no   |

1275---  The crucial difference between the two worlds is decidability. Every
1276---  (closed) Lean expression of type `Bool` can be simplified in a finite
1277---  number of steps to either `true` or `false` — i.e., there is a
1278---  terminating mechanical procedure for deciding whether or not it is
1279---  true.
1280---
1281---  This means that, for example, the type `Nat → Bool` is inhabited only
1282---  by functions that, given a `Nat`, always yield either `true` or `false`
1283---  in finite time; and this, in turn, means (by a standard computability
1284---  argument) that there is no function in `Nat → Bool` that checks whether
1285---  a given number is the code of a terminating Turing machine.
1286---
1287---  By contrast, the type `Prop` includes both decidable and undecidable
1288---  mathematical propositions; in particular, the type `Nat → Prop` does
1289---  contain functions representing properties like "the nth Turing machine
1290---  halts." The second row in the table follows directly from this
1291---  essential difference. To evaluate a pattern match (or conditional) on a
1292---  boolean, we need to know whether the scrutinee evaluates to `true` or
1293---  `false`; this only works for `Bool`, not `Prop`.
