7+--  This is Type Systems, volume 3 of *Software Foundations in Lean*. It

10+--  Logic, which develops techniques for reasoning about the behavior of a

14+--  ## Overview
15+
16+--  To reason about a program, we represent it as a mathematical object
17+--  together with a mathematical function or relation for describing its
18+--  behavior. Our main approach to doing so is called *operational
19+--  semantics*, and it amounts to defining a kind of *abstract interpreter*
20+--  for the programs in a language. We present two styles of operational
21+--  semantics: the *big-step* style specifies a program's behavior by
22+--  relating it directly to its final value, while the *small-step* style
23+--  specifies a program's behavior as a series of computational steps. The
24+--  small-step approach is more involved, but also makes it possible to
25+--  reason about a program's evaluation in a more fine-grained manner.
26+--
27+--  After introducing operational semantics using a simple language of
28+--  arithmetic and boolean expressions (Slang), we turn to *types*, the
29+--  volume's central subject. A type is a static classification of what a
30+--  program computes, and a *type system* is a static reasoning system that
31+--  uses types to rule out whole categories of run-time errors before a
32+--  program is ever run. Working with a small language of numbers and
33+--  booleans, we define a type system for it and prove the two signature
34+--  theorems of type-system metatheory — *progress* (a well-typed term is
35+--  either a value or can take a step) and *preservation* (taking a step
36+--  preserves well-typedness) — which together guarantee that a well-typed
37+--  program can never "go wrong."
38+--
39+--  Finally, we turn our attention to the *simply typed lambda-calculus*
40+--  (STLC), a much richer language with a more interesting type system. We
41+--  start from a small untyped core and extend it with numbers, pairs,
42+--  sums, lists, and general recursion, proving progress and preservation
43+--  anew for the extended language. We then study *subtyping*, a mechanism
44+--  that lets a term of one type stand in for a term of another — motivated
45+--  by the way record types behave in object-oriented languages — and prove
46+--  progress and preservation once more for a language with subtyping. In
47+--  so doing, we work our way up to a fairly full featured programming
48+--  language.

7+--  # References: Typing Mutable References
8+
9+--  Up to this point, we have considered a variety of *pure* language
10+--  features, including functional abstraction, basic types such as numbers
11+--  and booleans, and structured types such as records and variants. These
12+--  features form the backbone of most programming languages — including
13+--  purely functional languages such as Haskell and "mostly functional"
14+--  languages such as ML, as well as imperative languages such as C and
15+--  object-oriented languages such as Java, C#, and Scala.
16+--
17+--  Most practical languages also include various *impure* features that
18+--  cannot be described in the simple semantic framework we have used so
19+--  far. In particular, besides just yielding results, computation in these
20+--  languages may assign to mutable variables (reference cells, arrays,
21+--  mutable record fields, etc.); perform input and output to files,
22+--  displays, or network connections; make non-local transfers of control
23+--  via exceptions, jumps, or continuations; engage in inter-process
24+--  synchronization and communication; and so on. In the literature on
25+--  programming languages, such "side effects" of computation are
26+--  collectively referred to as *computational effects*.
27+--
28+--  In this chapter, we'll see how one sort of computational effect —
29+--  mutable references — can be added to the calculi we have studied. The
30+--  main extension will be dealing explicitly with a *store* (or *heap*)
31+--  and *pointers* that name store locations. This extension is fairly
32+--  straightforward to define; the most interesting part is the refinement
33+--  we need to make to the statement of the type preservation theorem.
34+
35+--  ## Definitions
36+
37+--  Pretty much every programming language provides some form of assignment
38+--  operation that changes the contents of a previously allocated piece of
39+--  storage. (Lean is a rare exception!)
40+--
41+--  In some languages — notably ML and its relatives — the mechanisms for
42+--  name binding and those for assignment are kept separate. We can have a
43+--  variable `x` whose *value* is the number `5`, or we can have a variable
44+--  `y` whose value is a *reference* (or *pointer*) to a mutable cell whose
45+--  current contents is `5`. These are different things, and the difference
46+--  is visible to the programmer. We can add `x` to another number, but not
47+--  assign to it. We can use `y` to assign a new value to the cell that it
48+--  points to (by writing `y:=84`), but we cannot use `y` directly as an
49+--  argument to an operation like `+`. Instead, we must explicitly
50+--  *dereference* it, writing `!y` to obtain its current contents.
51+--
52+--  In most other languages — in particular, in all members of the C
53+--  family, including Java — *every* variable name refers to a mutable
54+--  cell, and the operation of dereferencing a variable to obtain its
55+--  current contents is implicit.
56+--
57+--  For purposes of formal study, it is useful to keep these mechanisms
58+--  separate. The development in this chapter will closely follow ML's
59+--  model. Applying the lessons learned here to C-like languages is a
60+--  straightforward matter of collapsing some distinctions and rendering
61+--  some operations such as dereferencing implicit instead of explicit.
62+

518+--  ### Side Effects and Sequencing
519+
520+--  The fact that we've chosen the result of an assignment expression to be
521+--  the trivial value `unit` allows a nice abbreviation for *sequencing*.
522+--  For example, we can write
523+
524+--  R:=succ(!R); !R
525+
526+--  as an abbreviation for
527+
528+--  (λX:Unit, !R) (R:=succ(!R))
529+
530+--  This has the effect of reducing two expressions in order and returning
531+--  the value of the second. Restricting the type of the first expression
532+--  to `Unit` helps the typechecker to catch some silly errors by
533+--  permitting us to throw away the first value only if it is really
534+--  guaranteed to be trivial.
535+--
536+--  Notice that, if the second expression is also an assignment, then the
537+--  type of the whole sequence will be `Unit`, so we can validly place it
538+--  to the left of another `;` to build longer sequences of assignments:
539+
540+--  R:=succ(!R); R:=succ(!R); R:=succ(!R); R:=succ(!R); !R
541+
542+--  Formally, we introduce sequencing as a *derived form* `tseq` that
543+--  expands into an abstraction and an application.
544+
545+/-- info: <{ R := succ (!R) ; !R }> : Tm -/
546+#guard_msgs in
547+#check <{R := succ (!R); !R}>

549+--  ### References and Aliasing
550+
551+--  It is important to bear in mind the difference between the *reference*
552+--  that is bound to some variable `r` and the *cell* in the store that is
553+--  pointed to by this reference.
554+--
555+--  If we make a copy of `r`, for example by binding its value to another
556+--  variable `s`, what gets copied is only the reference, not the contents
557+--  of the cell itself.
558+--
559+--  For example, after reducing
560+--
561+--      let R = ref 5 in
562+--      let S = R in
563+--      S := 82;
564+--      (!R)+1
565+--
566+--  the cell referenced by `R` will contain the value `82`, while the
567+--  result of the whole expression will be `83`. The references `R` and `S`
568+--  are said to be *aliases* for the same cell.
569+--
570+--  The possibility of aliasing can make programs with references quite
571+--  tricky to reason about. For example, the expression
572+--
573+--      R := 5; R := !S
574+--
575+--  assigns `5` to `R` and then immediately overwrites it with `S`'s
576+--  current value; this has exactly the same effect as the single
577+--  assignment
578+--
579+--      R := !S
580+--
581+--  *unless* we happen to do it in a context where `R` and `S` are aliases
582+--  for the same cell!
583+--
584+--      let R = ref 0 in
585+--      let S = R in
586+--      R := 5; R := !S
587+
588+--  ### Shared State
589+
590+--  Of course, aliasing is also a large part of what makes references
591+--  useful. In particular, it allows us to set up "implicit communication
592+--  channels" — shared state — between different parts of a program. For
593+--  example, suppose we define a reference cell and two functions that
594+--  manipulate its contents:
595+--
596+--      let C = ref 0 in
597+--      let Incc = λ_:Unit. (C := succ (!C); !C) in
598+--      let Decc = λ_:Unit. (C := pred (!C); !C) in
599+--        ...
600+--
601+--  Note that, since their argument types are `Unit`, the arguments to the
602+--  abstractions in the definitions of `Incc` and `Decc` are not providing
603+--  any useful information to the bodies of these functions (using the
604+--  wildcard `_` as the name of the bound variable is a reminder of this).
605+--  Instead, the purpose of these abstractions is to "slow down" the
606+--  execution of the function bodies. Since function abstractions are
607+--  values, the two `let`s are executed simply by binding these functions
608+--  to the names `Incc` and `Decc`, rather than by actually incrementing or
609+--  decrementing `C`. Later, each call to one of these functions results in
610+--  its body being executed once and performing the appropriate mutation on
611+--  `C`. Such functions are often called *thunks*.
612+--
613+--  In the context of these declarations, calling `Incc` results in changes
614+--  to `C` that can be observed by calling `Decc`. For example, if we
615+--  replace the `...` with `(Incc unit; Incc unit; Decc
616+--  unit)`, the result
617+--  of the whole program will be `1`.
618+
619+--  ### Objects
620+
621+--  We can go a step further and write a *function* that creates `C`,
622+--  `Incc`, and `Decc`, packages `Incc` and `Decc` together into a record,
623+--  and returns this record:
624+
625+--  Newcounter =
626+--    λ_:Unit.
627+--        let C = ref 0 in
628+--        let Incc = λ_:Unit. (C := succ (!C); !C) in
629+--        let Decc = λ_:Unit. (C := pred (!C); !C) in
630+--        {i=Incc, d=Decc}
631+
632+--  Now, each time we call `Newcounter`, we get a new record of functions
633+--  that share access to the same storage cell `C`. The caller of
634+--  `Newcounter` can't get at this storage cell directly, but can affect it
635+--  indirectly by calling the two functions. In other words, we've created
636+--  a simple form of *object*.
637+
638+--  let C₁ = newcounter unit in
639+--  let C₂ = newcounter unit in
640+--  // we've allocated two separate storage cells now!
641+--  let R₁ = C₁.i unit in
642+--  let R₂ = C₂.i unit in
643+--  R₂  // yields 1, not 2!

651+--  ### References to Compound Types
652+
653+--  A reference cell need not contain just a number: the primitives we've
654+--  defined above allow us to create references to values of any type,
655+--  including functions. For example, we can use references to functions to
656+--  give a(n inefficient) implementation of arrays of numbers as follows.
657+--
658+--  Write `NatArray` for the type `Ref (Nat→Nat)`.
659+--
660+--  Recall the `Equal` function from the MoreStlc chapter:
661+--
662+--      Equal =
663+--        fix
664+--          (λEq:Nat→Nat→Bool.
665+--              λM:Nat. λN:Nat.
666+--                if M=0 then iszero n
667+--                else if N=0 then false
668+--                else Eq (pred m) (pred n))
669+--
670+--  To build a new array, we allocate a reference cell and fill it with a
671+--  function that, when given an index, always returns `0`.
672+--
673+--      Newarray = λ_:Unit. ref (λN:Nat.0)
674+--
675+--  To look up an element of an array, we apply the function to the desired
676+--  index.
677+--
678+--      Lookup = λA:NatArray, λN:Nat. (!A) N
679+--
680+--  The interesting part of the encoding is the `Update` function. It takes
681+--  an array, an index, and a new value to be stored at that index, and it
682+--  does its job by creating (and storing in the reference) a new function
683+--  that, when it is asked for the value at this very index, returns the
684+--  new value that was given to `Update`, while on all other indices it
685+--  passes the lookup to the function that was previously stored in the
686+--  reference.
687+
688+--  Update = \A:NatArray, \M:Nat, \V:Nat,
689+--    let Oldf = !A in
690+--    A := (λN:Nat. if Equal M N then V else Oldf N);
691+
692+--  References to values containing other references can also be very
693+--  useful, allowing us to define data structures such as mutable lists and
694+--  trees.
695+
696+--  ### Exercise (2 stars): compact_update (Manually graded) ⭐⭐
697+
698+--  If we defined `Update` more compactly like this
699+--
700+--      Update = \A:NatArray, \M:Nat, \V:Nat,
701+--          A := (λN:Nat. if Equal M N then V else (!A) N);
702+--
703+--  would it behave the same?
704+
705+--  No: calls to `Lookup` with any index other than the one given to
706+--  `Update` will now diverge. The point is that we need to make sure we
707+--  look up the value stored in `A` *before* we overwrite it with the new
708+--  function. Otherwise, when we get around to doing the lookup, we will
709+--  find the new function, not the original one.
710+
711+--  ### Null References
712+
713+--  There is one final significant difference between our references and
714+--  C-style mutable variables: in C-like languages, variables holding
715+--  pointers into the heap may sometimes have the value `NULL`.
716+--  Dereferencing such a "null pointer" is an error, and results either in
717+--  a clean exception (Java and C#) or in arbitrary and possibly insecure
718+--  behavior (C and relatives like C++). Null pointers cause significant
719+--  trouble in C-like languages: the fact that any pointer might be null
720+--  means that any dereference operation in the program can potentially
721+--  fail.
722+--
723+--  Even in ML-like languages, there are sometimes situations where we may
724+--  or may not have a valid pointer in our hands. Fortunately, there is no
725+--  need to extend the basic mechanisms of references to represent such
726+--  situations: the sum types introduced in the MoreStlc chapter already
727+--  give us what we need.
728+--
729+--  First, we can use sums to build an analog of the `option` types
730+--  introduced in the Lists chapter of *Logical Foundations*. Define
731+--  `Option τ` to be an abbreviation for `Unit + τ`.
732+--
733+--  Then a "nullable reference to a `τ`" is simply an element of the type
734+--  `Option (Ref τ)`.
735+
736+--  ### Garbage Collection
737+
738+--  A last issue that we should mention before we move on with formalizing
739+--  references is storage *de*-allocation. We have not provided any
740+--  primitives for freeing reference cells when they are no longer needed.
741+--  Instead, like many modern languages (including OCaml, Haskell, Java,
742+--  etc.), we rely on the run-time system to perform *garbage collection*,
743+--  automatically identifying and reusing cells that can no longer be
744+--  reached by the program.
745+--
746+--  This is *not* just a question of taste in language design: it is
747+--  extremely difficult to achieve type safety in the presence of an
748+--  explicit deallocation operation.
749+--
750+--  One reason for this is the familiar *dangling reference* problem: we
751+--  allocate a cell holding a number, save a reference to it in some data
752+--  structure, use it for a while, then deallocate it and allocate a new
753+--  cell holding a boolean, possibly reusing the same storage. Now we can
754+--  have two names for the same storage cell — one with type `Ref Nat` and
755+--  the other with type `Ref Bool`.

759+--  Show how this can lead to a violation of type safety.
760+
761+--  Suppose the language provides a primitive `free` that takes a reference
762+--  cell as argument and releases its storage so that (say) the very next
763+--  allocation of a reference cell will obtain the same piece of memory.
764+--  Then the program
765+
766+--  let R = ref 0 in
767+--      let S = R in
768+--      free R;
769+--      let T = ref true in
770+--      T := false;
771+--      succ (!S)

773+--  will reduce to the stuck term `succ false`. Note that aliasing plays a
774+--  crucial role here in setting up the problem, since it prevents us from
775+--  detecting invalid deallocations by simply making `free r` illegal if
776+--  the variable `R` appears free in the remainder of the expression.
777+--
778+--  This sort of example is easy to mimic in a language like C with manual
779+--  memory management (our `ref` constructor corresponds to C's `malloc`,
780+--  our `free` to a simplified version of C's `free`).

783+
784+--  ### Locations
785+
786+--  The most subtle aspect of the treatment of references appears when we
787+--  consider how to formalize their operational behavior. One way to see
788+--  why is to ask, "What should be the *values* of type `Ref τ`?" The
789+--  crucial observation that we need to take into account is that reducing
790+--  a `ref` operator should *do* something — namely, allocate some storage
791+--  — and the result of the operation should be a reference to this
792+--  storage.
793+--
794+--  What, then, is a reference?
795+--
796+--  The run-time store in most programming-language implementations is
797+--  essentially just a big array of bytes. The run-time system keeps track
798+--  of which parts of this array are currently in use. When we need to
799+--  allocate a new reference cell, we allocate a large enough segment from
800+--  the free region of the store (4 bytes for integer cells, 8 bytes for
801+--  cells storing `Float`s, etc.), record somewhere that it is being used,
802+--  and return the index (typically, a 32- or 64-bit integer) of the start
803+--  of the newly allocated region. These indices are references.
804+--
805+--  For present purposes, there is no need to be quite so concrete. We can
806+--  think of the store as an array of *values*, rather than an array of
807+--  bytes, abstracting away from the different sizes of the run-time
808+--  representations of different values. A reference, then, is simply an
809+--  index into the store. (If we like, we can even abstract away from the
810+--  fact that these indices are numbers, but for purposes of formalization
811+--  in Lean it is convenient to use numbers.) We use the word *location*
812+--  instead of *reference* or *pointer* to emphasize this abstract quality.
813+--
814+--  Treating locations abstractly in this way will prevent us from modeling
815+--  the *pointer arithmetic* found in low-level languages such as C. This
816+--  limitation is intentional. While pointer arithmetic is occasionally
817+--  very useful, especially for implementing low-level services such as
818+--  garbage collectors, it cannot be tracked by most type systems: knowing
819+--  that location `n` in the store contains a `Float` doesn't tell us
820+--  anything useful about the type of location `n+4`. In C, pointer
821+--  arithmetic is a notorious source of type-safety violations.
822+
823+--  ### Stores
824+
825+--  Recall that, in the small-step operational semantics for Imp, the step
826+--  relation needed to carry along an auxiliary state in addition to the
827+--  program being executed. In the same way, once we have added reference
828+--  cells to the STLC, our step relation must carry along a store to keep
829+--  track of the contents of reference cells.
830+--
831+--  We could re-use the same functional representation we used for states
832+--  in Imp, but for carrying out the proofs in this chapter it is actually
833+--  more convenient to represent a store simply as a *list* of values. (The
834+--  reason we didn't use this representation before is that, in Imp, a
835+--  program could modify any location at any time, so states had to be
836+--  ready to map *any* variable to a value. However, in the STLC with
837+--  references, the only way to create a reference cell is with `ref t₁`,
838+--  which puts the value of `t₁` in a new reference cell and reduces to the
839+--  location of the newly created reference cell. When reducing such an
840+--  expression, we can just add a new reference cell to the end of the list
841+--  representing the store.)
842+

888+--  ### Reduction
889+
890+--  Next, we need to extend the operational semantics to take stores into
891+--  account. Since the result of reducing an expression will in general
892+--  depend on the contents of the store in which it is reduced, the
893+--  evaluation rules should take not just a term but also a store as
894+--  argument. Furthermore, since the reduction of a term can cause side
895+--  effects on the store, and these may affect the reduction of other terms
896+--  in the future, the reduction rules need to return a new store. Thus,
897+--  the shape of the single-step reduction relation needs to change from
898+--  `t ⟶ t'` to `t / ρ ⟶ t' / ρ'`, where `ρ` and `ρ'` are the starting and
899+--  ending states of the store.
900+--
901+--  To carry through this change, we first need to augment all of our
902+--  existing reduction rules with stores:
903+--
904+--                  value v₂
905+--      ---------------------------------- (appAbs)
906+--      (λx:τ₂,t₁) v₂ / ρ ⟶ [x:=v₂]t₁ / ρ
907+--
908+--                 t₁ / ρ ⟶ t₁' / ρ'
909+--      --------------------------------   (app₁)
910+--              t₁ t₂ / ρ ⟶ t₁' t₂ / ρ'
911+--
912+--                 value v₁
913+--                 t₂ / ρ ⟶ t₂' / ρ'
914+--      --------------------------------   (app₂)
915+--              v₁ t₂ / ρ ⟶ v₁ t₂' / ρ'
916+--
917+--  Note that the first rule here returns the store unchanged, since
918+--  function application, in itself, has no side effects. The other two
919+--  rules simply propagate side effects from premise to conclusion.
920+--
921+--  Now, the result of reducing a `ref` expression will be a fresh
922+--  location; this is why we included locations in the syntax of terms and
923+--  in the set of values. It is crucial to note that making this extension
924+--  to the syntax of terms does not mean that we intend *programmers* to
925+--  write terms involving explicit, concrete locations: such terms will
926+--  arise only as intermediate results during reduction. This may seem odd,
927+--  but it follows naturally from our design decision to represent the
928+--  result of every reduction step by a modified *term*. If we had chosen a
929+--  more "machine-like" model, e.g., with an explicit stack to contain
930+--  values of bound identifiers, then the idea of adding locations to the
931+--  set of allowed values might seem more obvious.
932+--
933+--  In terms of this expanded syntax, we can state reduction rules for the
934+--  new constructs that manipulate locations and the store. First, to
935+--  reduce a dereferencing expression `!t₁`, we must first reduce `t₁`
936+--  until it becomes a value:
937+--
938+--       t₁ / ρ ⟶ t₁' / ρ'
939+--      -------------------- (deref)
940+--      !t₁ / ρ ⟶ !t₁' / ρ'
941+--
942+--  Once `t₁` has finished reducing, we should have an expression of the
943+--  form `!l`, where `l` is some location. (A term that attempts to
944+--  dereference any other sort of value, such as a function or `unit`, is
945+--  erroneous, as is a term that tries to dereference a location that is
946+--  larger than the size ρ.length of the currently allocated store; the
947+--  reduction rules simply get stuck in this case. The type-safety
948+--  properties established below assure us that well-typed terms will never
949+--  misbehave in this way.)
950+--
951+--           l < ρ.length
952+--      ------------------------ (derefLoc)
953+--      !(loc l) / ρ ⟶ ρ[l] / ρ
954+--
955+--  Next, to reduce an assignment expression `t₁:=t₂`, we must first reduce
956+--  `t₁` until it becomes a value (a location), and then reduce `t₂` until
957+--  it becomes a value (of any sort):
958+--
959+--            t₁ / ρ ⟶ t₁' / ρ'
960+--      ------------------------------ (assign₁)
961+--      t₁ := t₂ / ρ ⟶ t₁' := t₂ / ρ'
962+--
963+--            t₂ / ρ ⟶ t₂' / ρ'
964+--      ------------------------------ (assign₂)
965+--      v₁ := t₂ / ρ ⟶ v₁ := t₂' / ρ'
966+--
967+--  Once we have finished with `t₁` and `t₂`, we have an expression of the
968+--  form `l:=v`, which we execute by updating the store to make location
969+--  `l` contain `v`:
970+--
971+--               l < ρ.length
972+--      -------------------------------- (assign)
973+--      loc l := v / ρ ⟶ unit / [l:=v]ρ
974+--
975+--  The notation `[l:=v]ρ` means "the store that maps `l` to `v` and maps
976+--  all other locations to the same thing as `ρ`". Note that the term
977+--  resulting from this reduction step is just `unit`; the interesting
978+--  result is the updated store.
979+--
980+--  Finally, to reduce an expression of the form `ref t₁`, we first reduce
981+--  `t₁` until it becomes a value:
982+--
983+--          t₁ / ρ ⟶ t₁' / ρ'
984+--      -------------------------- (ref)
985+--      ref t₁ / ρ ⟶ ref t₁' / ρ'
986+--
987+--  Then, to reduce the `ref` itself, we choose a fresh location at the end
988+--  of the current store — i.e., location `ρ.length` — and yield a new
989+--  store that extends `ρ` with the new value `v`.
990+--
991+--      -------------------------------- (refValue)
992+--      ref v / ρ ⟶ loc ρ.length / ρ, v
993+--
994+--  The value resulting from this step is the newly allocated location
995+--  itself. (Formally, `ρ, v` means `ρ.concat v` — i.e., to add a new
996+--  reference cell to the store, we append it to the end.)
997+--
998+--  Note that these reduction rules do not perform any kind of garbage
999+--  collection: we simply allow the store to keep growing without bound as
1000+--  reduction proceeds. This does not affect the correctness of the results
1001+--  of reduction (after all, the definition of "garbage" is precisely parts
1002+--  of the store that are no longer reachable and so cannot play any
1003+--  further role in reduction), but it means that a naive implementation of
1004+--  our evaluator might run out of memory where a more sophisticated
1005+--  evaluator would be able to continue by reusing locations whose contents
1006+--  have become garbage.
1007+--
1008+--  Here are the rules again, formally:

1106+--  ### Store typings
1107+
1108+--  Having extended our syntax and reduction rules to accommodate
1109+--  references, our last job is to write down typing rules for the new
1110+--  constructs (and, of course, to check that these rules are sound!).
1111+--
1112+--  Naturally, the key question is, "What is the type of a location?"
1113+--
1114+--  First of all, notice that this question doesn't arise when typechecking
1115+--  terms that programmers actually write. Concrete location constants
1116+--  arise only in terms that are the intermediate results of reduction;
1117+--  they are not in the language that programmers write. So we only need to
1118+--  determine the type of a location when we're in the middle of a
1119+--  reduction sequence, e.g., trying to apply the progress or preservation
1120+--  lemmas. Thus, even though we normally think of typing as a *static*
1121+--  program property, it makes sense for the typing of locations to depend
1122+--  on the *dynamic* progress of the program too.
1123+--
1124+--  As a first try, note that when we reduce a term containing concrete
1125+--  locations, the type of the result depends on the contents of the store
1126+--  that we start with. For example, if we reduce the term `!(loc 1)` in
1127+--  the store `unit, unit`, the result is `unit`; if we reduce the same
1128+--  term in the store `unit, λX:Unit.X`, the result is `λX:Unit.X`. With
1129+--  respect to the former store, the location `1` has type `Unit`, and with
1130+--  respect to the latter it has type `Unit→Unit`. This observation leads
1131+--  us immediately to a first attempt at a typing rule for locations:
1132+--
1133+--       Γ ⊢ ρ[l] : τ₁
1134+--      ------------------
1135+--      Γ ⊢ loc l : Ref τ₁
1136+--
1137+--  But where does `ρ` come from?
1138+--
1139+--  That is, to find the type of a location `l`, we look up the current
1140+--  contents of `l` in the store and calculate the type `τ₁` of the
1141+--  contents. The type of the location is then `Ref τ₁`.
1142+--
1143+--  Having begun in this way, we need to go a little further to reach a
1144+--  consistent state. In effect, by making the type of a term depend on the
1145+--  store, we have changed the typing relation from a three-place relation
1146+--  (between contexts, terms, and types) to a four-place relation (between
1147+--  contexts, *stores*, terms, and types). Since the store is, intuitively,
1148+--  part of the context in which we calculate the type of a term, let's
1149+--  write this four-place relation with the store to the left of the
1150+--  turnstile: `Γ; ρ ⊢ t : τ`. Our rule for typing references now has the
1151+--  form
1152+--
1153+--       Γ; ρ ⊢ ρ[l] : τ₁
1154+--      ---------------------
1155+--      Γ; ρ ⊢ loc l : Ref τ₁
1156+--
1157+--  and all the rest of the typing rules in the system are extended
1158+--  similarly with stores. (The other rules do not need to do anything
1159+--  interesting with their stores — just pass them from premise to
1160+--  conclusion.)
1161+--
1162+--  However, this rule will not quite do. For one thing, typechecking is
1163+--  rather inefficient, since calculating the type of a location `l`
1164+--  involves calculating the type of the current contents `v` of `l`. If
1165+--  `l` appears many times in a term `τ`, we will re-calculate the type of
1166+--  `v` many times in the course of constructing a typing derivation for
1167+--  `τ`. Worse, if `v` itself contains locations, then we will have to
1168+--  recalculate *their* types each time they appear. Worse yet, the
1169+--  proposed typing rule for locations may not allow us to derive anything
1170+--  at all if the store contains a *cycle*. For example, there is no finite
1171+--  typing derivation for the location `0` with respect to this store:
1172+
1173+--  λX:Nat. (!(loc 1)) X, λX:Nat. (!(loc 0)) X
1174+

1197+--  These problems arise from the fact that our proposed typing rule for
1198+--  locations requires us to recalculate the type of a location every time
1199+--  we mention it in a term. But this, intuitively, should not be
1200+--  necessary. After all, when a location is first created, we know the
1201+--  type of the initial value that we are storing into it. Suppose we are
1202+--  willing to enforce the invariant that the type of the value contained
1203+--  in a given location *never changes*; that is, although we may later
1204+--  store other values into this location, those other values will always
1205+--  have the same type as the initial one. In other words, we always have
1206+--  in mind a single, definite type for every location in the store, which
1207+--  is fixed when the location is allocated. Then these intended types can
1208+--  be collected together as a *store typing* — a finite function mapping
1209+--  locations to types.
1210+--
1211+--  As with the other type systems we've seen, this conservative typing
1212+--  restriction on allowed updates means that we will rule out as ill-typed
1213+--  some programs that could reduce perfectly well without getting stuck.
1214+--
1215+--  Just as we did for stores, we will represent a store type simply as a
1216+--  list of types: the type at index `i` records the type of the values
1217+--  that we expect to be stored in cell `i`.

1236+--  that `!(loc 1)` has type `Unit→Unit`. More generally, the typing rule
1237+--  for locations can be reformulated in terms of store typings like this:
1238+--

1245+--  relation, but it is parameterized on a store *typing* rather than a
1246+--  concrete store. The rest of the typing rules are analogously augmented
1247+--  with store typings.

1335+--  Of course, these typing rules will accurately predict the results of
1336+--  reduction only if the concrete store used during reduction actually
1337+--  conforms to the store typing that we assume for purposes of
1338+--  typechecking. This proviso exactly parallels the situation with free
1339+--  variables in the basic STLC: the substitution lemma promises that, if
1340+--  `Γ / δ ⊢ t : T`, then we can replace the free variables in `τ` with
1341+--  values of the types listed in `Γ` to obtain a closed term of type `τ`,
1342+--  which, by the type preservation theorem will reduce to a final result
1343+--  of type `τ` if it yields any result at all. We will see below how to
1344+--  formalize an analogous intuition for stores and store typings.
1345+--
1346+--  However, for purposes of typechecking the terms that programmers
1347+--  actually write, we do not need to do anything tricky to guess what
1348+--  store typing we should use. Concrete locations arise only in terms that
1349+--  are the intermediate results of reduction; they are not in the language
1350+--  that programmers write. Thus, we can simply typecheck the programmer's
1351+--  terms with respect to the *empty* store typing. As reduction proceeds
1352+--  and new locations are created, we will always be able to see how to
1353+--  extend the store typing by looking at the type of the initial values
1354+--  being placed in newly allocated cells; this intuition is formalized in
1355+--  the statement of the type preservation theorem below.

1366+--  ### Well-Typed Stores
1367+
1368+--  Since we have extended both the reduction relation (with initial and
1369+--  final stores) and the typing relation (with a store typing), we need to
1370+--  change the statement of preservation to include these parameters. But
1371+--  clearly we cannot just add stores and store typings without saying
1372+--  anything about how they are related — i.e., this is wrong:

1380+--  If we typecheck with respect to some set of assumptions about the types
1381+--  of the values in the store and then reduce with respect to a store that
1382+--  violates these assumptions, the result will be disaster. We say that a
1383+--  store `ρ` is *well typed* with respect to a store typing `δ` if the
1384+--  term at each location `l` in `ρ` has the type at location `l` in `δ`.
1385+--  Since only closed terms ever get stored in locations (why?), it
1386+--  suffices to type them in the empty context. The following definition of
1387+--  `StoreWellTyped` formalizes this:
1388+
1389+def StoreWellTyped (δ:StoreTy) (ρ:Store) :=
1390+  δ.length = ρ.length ∧
1391+  (∀ (l : Nat), l < ρ.length → <{ ∅ / δ ⊢ ~(ρ[l]) ⦂ ~(δ[l]) }>)
1392+
1393+--  Informally, we will write `δ ⊢ ρ` for `StoreWellTyped δ ρ`.
1394+
1395+scoped notation:40 δ:41 " ⊢ " ρ:41 => StoreWellTyped δ ρ

1397+--  Intuitively, a store `ρ` is consistent with a store typing `δ` if every
1398+--  value in the store has the type predicted by the store typing. The only
1399+--  subtle point is the fact that, when typing the values in the store, we
1400+--  supply the very same store typing to the typing relation. This allows
1401+--  us to type circular stores like the one we saw above.

1453+--  motivates the following definition. We say that the store type `δ'`
1454+--  *extends* `δ` if `δ'` is just `δ` with some new types added to the end.

1457+  | nil (δ' : StoreTy) : Extends δ' []

1514+
1515+--  We can now give the final, correct statement of the type preservation
1516+--  property:
1517+
1518+def preservation_theorem {δ : StoreTy} {t t' : Tm} {τ : Ty} {ρ ρ' : Store} :=
1519+  (hTy : <{ ∅ / δ ⊢ t ⦂ τ }>) →
1520+  (hStoreTy : δ ⊢ ρ) →
1521+  (hEval : t / ρ ⟶ t' / ρ') →
1522+    ∃ δ', Extends δ' δ ∧ (<{ ∅ / δ' ⊢ t' ⦂ τ }>) ∧ (δ' ⊢ ρ')

1524+--  Note that the preservation theorem merely asserts that there is *some*
1525+--  store typing `δ'` extending `δ` (i.e., agreeing with `δ` on the values
1526+--  of all the old locations) such that the new term `t'` is well typed
1527+--  with respect to `δ'`; it does not tell us exactly what `δ'` is. It is
1528+--  intuitively clear, of course, that `δ'` is either `δ` or else exactly
1529+--  `δ ++ [τ₁]`, where `τ₁` is the type of the value `v₁` in the extended
1530+--  store `ρ ++ [v₁]`, but stating this explicitly would complicate the
1531+--  statement of the theorem without making it any more useful: the weaker
1532+--  version above is already in the right form (because its conclusion
1533+--  implies its hypothesis) to "turn the crank" repeatedly and conclude
1534+--  that every *sequence* of reduction steps preserves well-typedness.
1535+--  Combining this with the progress property, we obtain the usual
1536+--  guarantee that "well-typed programs never go wrong."

1862+--  Write a careful informal proof of the preservation theorem,
1863+--  concentrating on the `app`, `deref`, `assign`, and `ref` cases.

1865+--  *Proof*: By induction on a derivation of `∅ / [] ⊢ t : τ`.
1866+--  - If the last rule in the derivation is `app`, then `t = t₁ t₂` for
1867+--    some `t₁` and `t₂` and `τ = τ₁₂`, with `∅ / δ ⊢ t₁ : τ₁₁ → τ₁₂` and
1868+--    `∅ / δ ⊢ t₂ : τ₁₁`. There are three cases to consider, one for each
1869+--    rule that could have been used to show that `t₁ t₂` takes a step to
1870+--    `t'`.
1871+--    - Suppose `t₁ t₂` takes a step by `app₁`, with `t₁` stepping to `t₁'`
1872+--      and new store `ρ'`. Then by the IH there is some store typing `δ'`
1873+--      such that `δ'` extends `δ`, `ρ'` is well typed with respect to
1874+--      `δ'`, and `∅ / δ' ⊢ t₁' : τ₁₁ → τ₁₂`. We also know
1875+--      `∅ / δ' ⊢ t₂ : τ₁₁` by the `store_weakening` lemma. Hence,
1876+--      `∅ / δ' ⊢ t₁' t₂` by `app`.
1877+--    - The `app₂` case is similar.
1878+--    - Suppose `t₁ t₂` takes a step by `appAbs`. Then `t₁ = λx:τ₁₁. t₁₂`
1879+--      and `t₁ t₂` steps to `[x:=t₂] t₁₂`; the desired result now follows
1880+--      from the substitution lemma, taking `δ' = δ`.
1881+--
1882+--  - If the last rule in the derivation is `ref`, then `t = ref t₁` for
1883+--    some `t₁` and `∅ / δ ⊢ t₁ : τ₁` for some `τ₁`, with `τ = Ref τ₁`.
1884+--    There are two cases to consider, one for each rule that could have
1885+--    been used to show that `ref t₁` takes a step to `t'`.
1886+--    - Suppose `ref t₁` takes a step by `ref`, with `t₁` stepping to `t₁'`
1887+--      and new store `ρ'`. Then by the IH there is some store typing `δ'`
1888+--      such that `δ'` extends `δ`, `ρ'` is well typed with respect to
1889+--      `δ'`, and `∅ / δ' ⊢ t₁' : τ₁`. Hence, `∅ / δ' ⊢ ref t₁' : Ref τ₁`
1890+--      by `ref`.
1891+--    - Suppose `ref t₁` takes a step by `refValue`. Then `t₁` is a value,
1892+--      `ρ' = ρ.concat t₁`, and `t'` is the length of `ρ` - i.e., the
1893+--      location of `t₁` in `ρ'`. If we choose `δ' = δ.concat τ₁`, we
1894+--      obtain
1895+--      - `δ'` extends `δ` by construction
1896+--      - `ρ'` is well typed with respect to `δ'` because `ρ` is well typed
1897+--        with respect to `δ` and the last element, `t₁`, has type `τ₁`
1898+--        under `δ`, hence also under `δ'` by the store weakening lemma
1899+--      - `∅ / δ' ⊢ l : Ref τ₁` by `loc` as required.
1900+--
1901+--  - If the last rule in the derivation is `deref`, then `t = !t₁` for
1902+--    some `t₁` and `∅ / δ ⊢ t₁ : Ref τ`. There are two cases to consider,
1903+--    one for each rule that could have been used to show that `!t₁` takes
1904+--    a step to `t'`.
1905+--    - Suppose `!t₁` takes a step by `deref`, with `t₁` stepping to `t₁'`
1906+--      and new store `ρ'`. Then by the IH there is some store typing `δ'`
1907+--      such that `δ'` extends `δ`, `ρ'` is well typed with respect to
1908+--      `δ'`, and `∅ / δ' ⊢ t₁' : Ref τ`. Hence, `∅ / δ' ⊢ !t₁' : τ` by
1909+--      `deref`.
1910+--    - Suppose `ref t₁` takes a step by `derefLoc`. Then `t₁` is some
1911+--      location `l` and `t'` is the contents of `ρ` at location `l`.
1912+--      Moreover, the typing rule used to derive `∅ / δ ⊢ l : Ref τ` must
1913+--      be `loc`, so the contents of `δ` at location `l` is `τ`. Now, since
1914+--      `ρ` is well typed with respect to `δ`, we know that
1915+--      `∅ / δ ⊢ t' : τ`, as required.
1916+--
1917+--  - If the last rule in the derivation is `assign`, then `t = t₁ := t₂`
1918+--    for some `t₁` and `t₂`, with `∅ / δ ⊢ t₁ : Ref τ₂` and
1919+--    `∅ / δ ⊢ t₂ : τ₂` for some `τ₂`; moreover, `τ = Unit`. There are now
1920+--    three cases to consider, one for each rule that could have been used
1921+--    to show that `t₁ := t₂` takes a step to `t'`.
1922+--    - The cases where `t₁ := t₂` takes a step by either `assign₁` or
1923+--      `assign₂` are similar to the congruence rule cases above.
1924+--
1925+--    - Suppose `t₁ := t₂` takes a step by `assign`. Then `t₁` is some
1926+--      location `l`, `t₂` is some value, `t'` is `unit`, and `ρ'` is
1927+--      formed from `ρ` by updating the contents of location `l` with `t₂`.
1928+--
1929+--      Moreover, the typing rule used to derive `∅ / δ ⊢ l : Ref τ₂` must
1930+--      be `loc`, so the contents of `δ` at location `l` is `τ₂`. Now,
1931+--      `∅ / δ ⊢ unit : Unit` by `unit`. Moreover, since `ρ` is well typed
1932+--      with respect to `δ` and we know `∅ / δ ⊢ t₂ : τ₂`, we know that
1933+--      `ρ'` is well typed with respect to `δ` by lemma
1934+--      `assign_pres_store_typing`. So we can take `δ' = δ` and finish this
1935+--      case.
1936+--
1937+--    - (Other cases elided...)
1938+--
1939+--  *QED*.
