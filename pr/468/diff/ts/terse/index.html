7+--  This is Type Systems, volume 3 of *Software Foundations

16+--  ## Overview
17+
18+--  To reason about a program, we represent it as a
19+--  mathematical object together with a mathematical
20+--  function or relation for describing its behavior. Our
21+--  main approach to doing so is called *operational
22+--  semantics*, and it amounts to defining a kind of
23+--  *abstract interpreter* for the programs in a language.
24+--  We present two styles of operational semantics: the
25+--  *big-step* style specifies a program's behavior by
26+--  relating it directly to its final value, while the
27+--  *small-step* style specifies a program's behavior as a
28+--  series of computational steps. The small-step approach
29+--  is more involved, but also makes it possible to reason
30+--  about a program's evaluation in a more fine-grained
31+--  manner.
32+--
33+--  After introducing operational semantics using a simple
34+--  language of arithmetic and boolean expressions (Slang),
35+--  we turn to *types*, the volume's central subject. A type
36+--  is a static classification of what a program computes,
37+--  and a *type system* is a static reasoning system that
38+--  uses types to rule out whole categories of run-time
39+--  errors before a program is ever run. Working with a
40+--  small language of numbers and booleans, we define a type
41+--  system for it and prove the two signature theorems of
42+--  type-system metatheory — *progress* (a well-typed term
43+--  is either a value or can take a step) and *preservation*
44+--  (taking a step preserves well-typedness) — which
45+--  together guarantee that a well-typed program can never
46+--  "go wrong."
47+--
48+--  Finally, we turn our attention to the *simply typed
49+--  lambda-calculus* (STLC), a much richer language with a
50+--  more interesting type system. We start from a small
51+--  untyped core and extend it with numbers, pairs, sums,
52+--  lists, and general recursion, proving progress and
53+--  preservation anew for the extended language. We then
54+--  study *subtyping*, a mechanism that lets a term of one
55+--  type stand in for a term of another — motivated by the
56+--  way record types behave in object-oriented languages —
57+--  and prove progress and preservation once more for a
58+--  language with subtyping. In so doing, we work our way up
59+--  to a fairly full featured programming language.

9+--  Most real languages include *impure* features
10+--  ("computational effects")...
11+--  - mutable pointer structures
12+--  - non-local control constructs (exceptions,

19+--  ## Definitions
20+
21+--  In most real-world programming languages, the mechanisms
22+--  of *name binding* and *storage allocation* are
23+--  (intentionally) confused: every name refers to a mutable
24+--  piece of storage.
25+--
26+--  Conceptually, it's cleaner to separate the two:
27+--  - use the mechanisms we already have for name binding
28+--    (abstraction, let);
29+--  - introduce new operations for allocating, changing, and
30+--    looking up the contents of references (pointers).
31+
32+--  ### Syntax
33+
34+namespace STLCRef
35+
36+open scoped MyGetElem
37+
38+--  The basic operations on references are *allocation*,
39+--  *dereferencing*, and *assignment*.
40+--  - To allocate a reference, we use the `ref` operator,
41+--    providing an initial value for the new cell.
42+--
43+--    For example, `ref 5` creates a new cell containing the
44+--    value `5` and reduces to a reference to that cell.
45+--
46+--  - To read the current value of this cell, we use the
47+--    dereferencing operator `!`.
48+--
49+--    For example, `!(ref 5)` reduces to `5`.
50+--
51+--  - To change the value stored in a cell, we use the
52+--    assignment operator.
53+--
54+--    If `r` is a reference, `r := 7` will store the value
55+--    `7` in the cell referenced by `r`.

381+--        Γ ⊢ ref t₁ ⦂ Ref τ₁
382+--
383+--            Γ ⊢ t₁ ⦂ Ref τ₁
384+--      ---------------------  (deref)
385+--           Γ ⊢ !t₁ ⦂ τ₁
386+--
387+--            Γ ⊢ t₁ ⦂ Ref τ₂
388+--            Γ ⊢ t₂ ⦂ τ₂
389+--      ---------------------  (assign)
390+--      Γ ⊢ t₁ := t₂ ⦂ Unit
391+--
392+--  The rule for locations will require a bit more
393+--  machinery, and this will motivate some changes to the
394+--  other rules; we'll come back to this later.

396+--  ### Values and Substitution
397+
398+--  Besides abstractions, numbers, and the unit value, we
399+--  have one new type of value: locations.
400+--
401+--  A location is a concrete pointer value — think of it
402+--  like an address in memory. Locations should never be
403+--  written directly by programmers; they are used to keep
404+--  track of the intermediate states of programs involving
405+--  references. In particular, the result of a `ref`
406+--  expression is a location.
407+
408+inductive Tm.IsValue : Tm → Prop :=
409+  | abs : forall x τ₂ t₁,
410+      IsValue <{λx : τ₂. t₁}>
411+  | nat : forall (n : Nat),
412+      IsValue (.const n)
413+  | unit :
414+      IsValue <{ unit }>
415+  | loc_ : forall (l : Nat),
416+      IsValue (.loc l)
417+
418+attribute [StlcRefEval] Tm.IsValue.abs Tm.IsValue.nat Tm.IsValue.unit Tm.IsValue.loc_
419+
420+--  Extending substitution to handle the new syntax of terms
421+--  is straightforward: substituting into a pointer leaves
422+--  it unchanged.
423+
424+def subst (x : String) (s : Tm) (t : Tm) : Tm :=
425+  match t with
426+  -- pure STLC
427+  | .var y =>
428+      if x = y then s else t
429+  | .abs y τ t₁ =>
430+      if x = y then t else <{ λ y : τ . [x := s] t₁ }>
431+  | .app t₁ t₂ =>
432+      <{ ([x := s] t₁) ([x := s] t₂) }>
433+  -- numbers
434+  | .const _ =>
435+      t
436+  | .succ t₁ =>
437+      <{ succ ([x := s] t₁) }>
438+  | .pred t₁ =>
439+      <{ pred ([x := s] t₁) }>
440+  | .mult t₁ t₂ =>
441+      <{ ([x := s] t₁) * ([x := s] t₂) }>
442+  | .ite0 t₁ t₂ t₃ =>
443+      <{
444+        if0 [x := s] t₁
445+        then [x := s] t₂
446+        else [x := s] t₃
447+      }>
448+  -- unit
449+  | .unit => <{ unit }>
450+  -- references
451+  | .ref t₁ =>  <{ ref ([x := s] t₁) }>
452+  | .deref t₁ =>  <{ !([x := s] t₁) }>
453+  | .loc n => .loc n
454+  | .assign t₁ t₂ =>
455+      <{ ([x := s] t₁) := ([x := s] t₂) }>

479+--  ### References and Aliasing
480+
481+--  It is important to bear in mind the difference between
482+--  the *reference* that is bound to some variable `r` and
483+--  the *cell* in the store that is pointed to by this
484+--  reference.
485+--
486+--  If we make a copy of `r`, for example by binding its
487+--  value to another variable `s`, what gets copied is only
488+--  the reference, not the contents of the cell itself.
489+--
490+--  For example, after reducing
491+--
492+--      let R = ref 5 in
493+--      let S = R in
494+--      S := 82;
495+--      (!R)+1
496+--
497+--  the cell referenced by `R` will contain the value `82`,
498+--  while the result of the whole expression will be `83`.
499+--  The references `R` and `S` are said to be *aliases* for
500+--  the same cell.
501+--
502+--  The possibility of aliasing can make programs with
503+--  references quite tricky to reason about. For example,
504+--  the expression
505+--
506+--      R := 5; R := !S
507+--
508+--  assigns `5` to `R` and then immediately overwrites it
509+--  with `S`'s current value; this has exactly the same
510+--  effect as the single assignment
511+--
512+--      R := !S
513+--
514+--  *unless* we happen to do it in a context where `R` and
515+--  `S` are aliases for the same cell!
516+--
517+--      let R = ref 0 in
518+--      let S = R in
519+--      R := 5; R := !S
520+
521+--  ### Shared State
522+
523+--  Of course, aliasing is also a large part of what makes
524+--  references useful. In particular, it allows us to set up
525+--  "implicit communication channels" — shared state —
526+--  between different parts of a program. For example,
527+--  suppose we define a reference cell and two functions
528+--  that manipulate its contents:
529+--
530+--      let C = ref 0 in
531+--      let Incc = λ_:Unit. (C := succ (!C); !C) in
532+--      let Decc = λ_:Unit. (C := pred (!C); !C) in
533+--        ...
534+--
535+--  The `Unit`-abstractions ("thunks") are used here to
536+--  prevent reduction until later.
537+
538+--  ### Objects
539+
540+--  We can go a step further and write a *function* that
541+--  creates `C`, `Incc`, and `Decc`, packages `Incc` and
542+--  `Decc` together into a record, and returns this record:
543+
544+--  Newcounter =
545+--    λ_:Unit.
546+--        let C = ref 0 in
547+--        let Incc = λ_:Unit. (C := succ (!C); !C) in
548+--        let Decc = λ_:Unit. (C := pred (!C); !C) in
549+--        {i=Incc, d=Decc}
550+
551+--  Now, each time we call `Newcounter`, we get a new record
552+--  of functions that share access to the same storage cell
553+--  `C`. The caller of `Newcounter` can't get at this
554+--  storage cell directly, but can affect it indirectly by
555+--  calling the two functions. In other words, we've created
556+--  a simple form of *object*.
557+
558+--  let C₁ = newcounter unit in
559+--  let C₂ = newcounter unit in
560+--  // we've allocated two separate storage cells now!
561+--  let R₁ = C₁.i unit in
562+--  let R₂ = C₂.i unit in
563+--  R₂  // yields 1, not 2!
564+
565+--  ### References to Compound Types
566+
567+--  A reference cell need not contain just a number: the
568+--  primitives we've defined above allow us to create
569+--  references to values of any type, including functions.
570+--  For example, we can use references to functions to give
571+--  a(n inefficient) implementation of arrays of numbers as
572+--  follows.
573+--
574+--  Write `NatArray` for the type `Ref (Nat→Nat)`.
575+--
576+--  To build a new array, we allocate a reference cell and
577+--  fill it with a function that, when given an index,
578+--  always returns `0`.
579+--
580+--      Newarray = λ_:Unit. ref (λN:Nat.0)
581+--
582+--  To look up an element of an array, we apply the function
583+--  to the desired index.
584+--
585+--      Lookup = λA:NatArray, λN:Nat. (!A) N
586+--
587+--  The interesting part of the encoding is the `Update`
588+--  function. It takes an array, an index, and a new value
589+--  to be stored at that index, and it does its job by
590+--  creating (and storing in the reference) a new function
591+--  that, when it is asked for the value at this very index,
592+--  returns the new value that was given to `Update`, while
593+--  on all other indices it passes the lookup to the
594+--  function that was previously stored in the reference.
595+
596+--  Update = \A:NatArray, \M:Nat, \V:Nat,
597+--    let Oldf = !A in
598+--    A := (λN:Nat. if Equal M N then V else Oldf N);
599+
600+--  References to values containing other references can
601+--  also be very useful, allowing us to define data
602+--  structures such as mutable lists and trees.
603+
604+--  ### Null References
605+
606+--  One more difference between our references and C-style
607+--  mutable variables: *null pointers*.
608+--  - In C, a pointer variable can contain either a valid
609+--    pointer into the heap or the special value `NULL`.
610+--  - A source of many errors and much tricky reasoning:
611+--    - (any pointer may potentially be "not there")
612+--    - but occasionally useful
613+--  - Nullable pointers are easy to implement using
614+--    references plus options (which can be built out of
615+--    disjoint sum types):
616+--
617+--      Option τ       =  Unit + τ
618+--      NullableRef τ  =  Ref (Option τ)
619+
620+--  ### Garbage Collection
621+
622+--  A last issue that we should mention before we move on
623+--  with formalizing references is storage *de*-allocation.
624+--  We have not provided any primitives for freeing
625+--  reference cells when they are no longer needed. Instead,
626+--  like many modern languages (including OCaml, Haskell,
627+--  Java, etc.), we rely on the run-time system to perform
628+--  *garbage collection*, automatically identifying and
629+--  reusing cells that can no longer be reached by the
630+--  program.
631+--
632+--  This is *not* just a question of taste in language
633+--  design: it is extremely difficult to achieve type safety
634+--  in the presence of an explicit deallocation operation.
635+--
636+--  One reason for this is the familiar *dangling reference*
637+--  problem: we allocate a cell holding a number, save a
638+--  reference to it in some data structure, use it for a
639+--  while, then deallocate it and allocate a new cell
640+--  holding a boolean, possibly reusing the same storage.
641+--  Now we can have two names for the same storage cell —
642+--  one with type `Ref Nat` and the other with type
643+--  `Ref Bool`.
644+
645+--  ## Operational Semantics
646+
647+--  ### Locations
648+
649+--  A reference names a location in the *store* (a.k.a.
650+--  heap).
651+--
652+--  What is the store?
653+--  - Concretely: An array of 8-bit bytes, indexed by 32-bit
654+--    integers.
655+--  - More abstractly: a list or array of values
656+--  - Even more abstractly: a partial function from
657+--    locations to values.
658+--
659+--  We'll choose the middle way here: A store is a list of
660+--  values, and a location is a natural-number index into
661+--  this list.
662+
663+--  ### Stores
664+
665+--  A store is just a *list* of values. (This more concrete
666+--  representation will be more convenient for proofs than
667+--  the functional representation we used in Imp.) We will
668+--  use the Greek letter ρ to represent stores.
669+
670+abbrev Store := List Tm
671+
672+--  We use `ρ[n]` to retrieve the value of the reference
673+--  cell at location `n` in the store `ρ`. Note that we must
674+--  give a default value to `nth` in case we try looking up
675+--  an index which is too large. (In fact, we never actually
676+--  do this, but *proving* that we don't will require a bit
677+--  of work.)
678+
679+open scoped MyGetElem
680+instance : MyGetElem Store Nat Tm where
681+  getElem ρ n := ρ.getD n <{unit}>

683+@[simp]
684+theorem Store_get_succ_tl (hd : Tm) (tl : Store) (n : Nat) :
685+  (hd :: tl)[n + 1] = tl[n] := by rfl
686+
687+@[simp]
688+theorem Store_get_zero_hd (hd : Tm) (tl : Store) :
689+  (hd :: tl)[0] = hd := by rfl
690+
691+--  To update the store, we use the `List.set` function,
692+--  which replaces the contents of a cell at a particular
693+--  index.
694+--
695+--      def List.set : (l : List α) → (n : Nat) → (a : α) → List α
696+--        | cons _ as, 0,          b => cons b as
697+--        | cons a as, Nat.succ n, b => cons a (set as n b)
698+--        | nil,       _,          _ => nil
699+--
700+--  As might be expected, we will also need some technical
701+--  lemmas; they are straightforward to prove.
702+
703+theorem Store_get_set_eq (ρ : Store) (l : Nat) (x : Tm)
704+  (h : l < ρ.length) :
705+  (ρ.set l x)[l] = x := by
706+  induction ρ generalizing l with
707+  | nil => simp_all
708+  | cons hd tl ih => cases l <;> simp_all
709+
710+theorem Store_get_set_neq (l₁ l₂ : Nat) (t : Tm) (ρ : Store) :
711+  l₁ ≠ l₂ ->
712+  (ρ.set l₂ t)[l₁] = ρ[l₁] := by
713+  induction ρ generalizing l₁ l₂ with
714+  | nil => simp
715+  | cons hd tl ih => cases l₁ <;> cases l₂ <;> simp_all

718+
719+--  First, we augment existing reduction rules with stores:
720+--
721+--                  v₂.IsValue
722+--      ------------------------------------ (appAbs)
723+--      (λx:τ₂. t₁) v₂ / ρ ⟶ [x:=v₂] t₁ / ρ
724+--
725+--                  t₁ / ρ ⟶ t₁' / ρ'
726+--      ---------------------------------    (app₁)
727+--               t₁ t₂ / ρ ⟶ t₁' t₂ / ρ'
728+--
729+--                 v₁.IsValue
730+--                  t₂ / ρ ⟶ t₂' / ρ'
731+--      ---------------------------------    (app₂)
732+--               v₁ t₂ / ρ ⟶ v₁ t₂' / ρ'
733+--
734+--  Now we can give the rules for the new constructs:
735+--
736+--      ------------------------------------    (refValue)
737+--           ref v / ρ ⟶ loc ρ.length / ρ,v
738+--
739+--              t₁ / ρ ⟶ t₁' / ρ'
740+--      ------------------------------          (ref)
741+--          ref t₁ / ρ ⟶ ref t₁' / ρ'
742+--
743+--            l < ρ.length
744+--      --------------------------              (derefLoc)
745+--        !(loc l) / ρ ⟶ ρ[l] / ρ
746+--
747+--              t₁ / ρ ⟶ t₁' / ρ'
748+--      ---------------------------             (deref)
749+--             !t₁ / ρ ⟶ !t₁' / ρ'
750+--
751+--                   l < ρ.length
752+--      --------------------------------------- (assign)
753+--      loc l := v / ρ ⟶ unit / List.set ρ l v
754+--
755+--              t₁ / ρ ⟶ t₁' / ρ'
756+--      --------------------------------        (assign₁)
757+--        t₁ := t₂ / ρ ⟶ t₁' := t₂ / ρ'
758+--
759+--              t₂ / ρ ⟶ t₂' / ρ'
760+--      --------------------------------        (assign₂)

770+  -- pure STLC
771+  | appAbs {x : String} {τ₂ : Ty} {t₁ v₂ : Tm} {ρ : Store}
772+      (h : v₂.IsValue) :
773+      <{(λ x : τ₂ . t₁) v₂}> / ρ ⟶
774+      <{ [x := v₂] t₁ }> / ρ
775+  | app₁ {t₁ t₁' t₂ : Tm} {ρ ρ' : Store}
776+      (h : t₁ / ρ ⟶ t₁' / ρ') :
777+      <{t₁ t₂}> / ρ ⟶ <{t₁' t₂}> / ρ'
778+  | app₂ {v₁ t₂ t₂' : Tm} {ρ ρ' : Store}
779+      (h₁ : v₁.IsValue)
780+      (h₂ : t₂ / ρ ⟶ t₂' / ρ') :
781+      <{v₁ t₂}> / ρ ⟶ <{v₁ t₂'}> / ρ'
782+  -- numbers
783+  | succNat {n : Nat} {ρ : Store} :
784+      <{ succ ~(Tm.const n) }> / ρ ⟶ Tm.const (n + 1) / ρ
785+  | succ {t₁ t₁' : Tm} {ρ ρ' : Store}
786+      (h : t₁ / ρ ⟶ t₁' / ρ') :
787+      <{ succ t₁ }> / ρ ⟶ <{ succ t₁' }> / ρ'
788+  | predConst {n : Nat} {ρ : Store} :
789+      <{ pred ~(Tm.const n) }> / ρ ⟶ Tm.const (n - 1) / ρ
790+  | pred {t₁ t₁' : Tm} {ρ ρ' : Store}
791+      (h : t₁ / ρ ⟶ t₁' / ρ') :
792+      <{ pred t₁ }> / ρ ⟶ <{ pred t₁' }> / ρ'
793+  | multConst {n₁ n₂ : Nat} {ρ : Store} :
794+      <{ ~(Tm.const n₁) * ~(Tm.const n₂) }> / ρ ⟶
795+      Tm.const (n₁ * n₂) / ρ
796+  | mult₁ {t₁ t₁' t₂ : Tm} {ρ ρ' : Store}
797+      (h : t₁ / ρ ⟶ t₁' / ρ') :
798+      <{ t₁ * t₂ }> / ρ ⟶ <{ t₁' * t₂ }> / ρ'
799+  | mult₂ {v₁ t₂ t₂' : Tm} {ρ ρ' : Store}
800+      (h₁ : v₁.IsValue)
801+      (h₂ : t₂ / ρ ⟶ t₂' / ρ') :
802+      <{ v₁ * t₂ }> / ρ ⟶ <{ v₁ * t₂' }> / ρ'
803+  | if0Step {t₁ t₁' t₂ t₃ : Tm} {ρ ρ' : Store}
804+      (h : t₁ / ρ ⟶ t₁' / ρ') :
805+      <{ if0 t₁ then t₂ else t₃ }> / ρ ⟶
806+      <{ if0 t₁' then t₂ else t₃ }> / ρ'
807+  | if0Zero {t₂ t₃ : Tm} {ρ : Store} :
808+      <{ if0 0 then t₂ else t₃ }> / ρ ⟶ t₂ / ρ
809+  | if0Nonzero {n : Nat} {t₂ t₃ : Tm} {ρ : Store} :
810+      <{ if0 ~(Tm.const (n + 1)) then t₂ else t₃ }> / ρ ⟶
811+      t₃ / ρ
812+  -- references
813+  | refValue {v : Tm} {ρ : Store}
814+      (h : v.IsValue) :
815+      <{ ref v }> / ρ ⟶ Tm.loc ρ.length / ρ.concat v
816+  | ref_ {t₁ t₁' : Tm} {ρ ρ' : Store}
817+      (h : t₁ / ρ ⟶ t₁' / ρ') :
818+      <{ ref t₁ }> / ρ ⟶ <{ ref t₁' }> / ρ'
819+  | derefLoc {l : Nat} {ρ : Store}
820+      (h : l < ρ.length) :

822+  | deref {t₁ t₁' : Tm} {ρ ρ' : Store}
823+      (h : t₁ / ρ ⟶ t₁' / ρ') :
824+      <{ !t₁ }> / ρ ⟶ <{ !t₁' }> / ρ'
825+  | assign {v : Tm} {l : Nat} {ρ : Store}
826+      (h₁ : v.IsValue)
827+      (h₂ : l < ρ.length) :
828+      <{ ~(Tm.loc l) := v }> / ρ ⟶ <{ unit }> / ρ.set l v
829+  | assign₁ {t₁ t₁' t₂ : Tm} {ρ ρ' : Store}

835+      <{ v₁ := t₂ }> / ρ ⟶ <{ v₁ := t₂' }> / ρ'

860+--  ### Store typings
861+
862+--  Naturally, the key question is, "What is the type of a
863+--  location?"
864+--
865+--  As a first try, observe that the type of a location is
866+--  connected to the contents of the store `ρ`.
867+--
868+--       Γ ⊢ ρ[l] : τ₁
869+--      ------------------
870+--      Γ ⊢ loc l : Ref τ₁
871+--
872+--  But where does `ρ` come from?
873+--
874+--  We could try adding `ρ` to the judgment: `Γ; ρ ⊢ t : τ`,
875+--  which gives us this rule:
876+--
877+--       Γ; ρ ⊢ ρ[l] : τ₁
878+--      ---------------------
879+--      Γ; ρ ⊢ loc l : Ref τ₁
880+--
881+--  But that means the *whole* store `ρ`, including all
882+--  dynamically created values, is needed *during
883+--  typechecking*. This does not seem like something we
884+--  want.
885+--
886+--  Worse yet, it doesn't work at all for *cyclic* stores.
887+--
888+--  For example, what is the type of location `0` in the
889+--  following store?
890+
891+--  λX:Nat. (!(loc 1)) X, λX:Nat. (!(loc 0)) X
892+
893+--  Instead, we establish an *invariant* that the type of
894+--  value stored in a location never changes.
895+--
896+--  This *static* representation of the store contents is
897+--  called a *store typing*:
898+
899+abbrev StoreTy := List Ty
900+
901+--  Here we represent locations as indices into a *list* of
902+--  types so the type at index `i` is the type of the values
903+--  stored in cell `i`.
904+
905+open scoped MyGetElem
906+instance : MyGetElem StoreTy Nat Ty where
907+  getElem δ n := δ.getD n <{Unit}>

916+--  We can use the store typing `δ` to give a type to any
917+--  location `l` like this:
918+--
919+--           l < δ.length
920+--      -----------------------
921+--      Γ; δ ⊢ loc l : Ref δ[l]
922+--
923+--  That is, as long as `l` is a valid location, we can
924+--  compute the type of `l` just by looking it up in `δ`.
925+--  Typing is again a four-place relation, but it is
926+--  parameterized on a store *typing* rather than a concrete
927+--  store. The rest of the typing rules are analogously
928+--  augmented with store typings.
929+
930+--  ### The Typing Relation
931+
932+--           l < δ.length
933+--      -----------------------  (loc)
934+--      Γ; δ ⊢ loc l : Ref δ[l]
935+--
936+--          Γ; δ ⊢ t₁ : τ₁
937+--      ----------------------   (ref)
938+--      Γ; δ ⊢ ref t₁ : Ref τ₁
939+--
940+--        Γ; δ ⊢ t₁ : Ref τ₁
941+--        ------------------     (deref)
942+--        Γ; δ ⊢ !t₁ : τ₁
943+--
944+--        Γ; δ ⊢ t₁ : Ref τ₂
945+--          Γ; δ ⊢ t₂ : τ₂
946+--      ----------------------   (assign)
947+--      Γ; δ ⊢ t₁ := t₂ : Unit
948+
949+inductive HasType (δ : StoreTy) : Context → Tm → Ty → Prop where
950+  -- pure STLC
951+  | var {Γ : Context} {x : String} {τ₁ : Ty}
952+      (h : Γ[x] = some τ₁) :
953+      <{ Γ / δ ⊢ ~(Tm.var x) ⦂ τ₁ }>
954+  | abs {Γ : Context} {x : String} {τ₁ τ₂ : Ty} {t₁ : Tm}
955+      (h : <{ x ↦ τ₂ ; Γ / δ ⊢ t₁ ⦂ τ₁ }>) :
956+      <{ Γ / δ ⊢ λ x : τ₂ . t₁ ⦂ τ₂ → τ₁ }>
957+  | app {Γ : Context} {τ₁ τ₂ : Ty} {t₁ t₂ : Tm}
958+      (h₁ : <{ Γ / δ ⊢ t₁ ⦂ τ₂ → τ₁ }>)
959+      (h₂ : <{ Γ / δ ⊢ t₂ ⦂ τ₂ }>) :
960+      <{ Γ / δ ⊢ t₁ t₂ ⦂ τ₁ }>
961+  -- numbers
962+  | const {Γ : Context} {n : Nat} :
963+      <{ Γ / δ ⊢ ~(Tm.const n) ⦂ Nat }>
964+  | succ {Γ : Context} {t₁ : Tm}
965+      (h : <{ Γ / δ ⊢ t₁ ⦂ Nat }>) :
966+      <{ Γ / δ ⊢ succ t₁ ⦂ Nat }>
967+  | pred {Γ : Context} {t₁ : Tm}
968+      (h : <{ Γ / δ ⊢ t₁ ⦂ Nat }>) :
969+      <{ Γ / δ ⊢ pred t₁ ⦂ Nat }>
970+  | mult {Γ : Context} {t₁ t₂ : Tm}
971+      (h₁ : <{ Γ / δ ⊢ t₁ ⦂ Nat }>)
972+      (h₂ : <{ Γ / δ ⊢ t₂ ⦂ Nat }>) :
973+      <{ Γ / δ ⊢ t₁ * t₂ ⦂ Nat }>
974+  | ite0 {Γ : Context} {t₁ t₂ t₃ : Tm} {τ : Ty}
975+      (h₁ : <{ Γ / δ ⊢ t₁ ⦂ Nat }>)
976+      (h₂ : <{ Γ / δ ⊢ t₂ ⦂ τ }>)
977+      (h₃ : <{ Γ / δ ⊢ t₃ ⦂ τ }>) :
978+      <{ Γ / δ ⊢ if0 t₁ then t₂ else t₃ ⦂ τ }>
979+  -- unit
980+  | unit {Γ : Context} :
981+      <{ Γ / δ ⊢ unit ⦂ Unit }>
982+  -- references
983+  | loc_ {Γ : Context} {l : Nat}
984+      (h : l < δ.length) :
985+      <{ Γ / δ ⊢ ~(Tm.loc l) ⦂ Ref ~(δ[l]) }>
986+  | ref_ {Γ : Context} {t₁ : Tm} {τ₁ : Ty}
987+      (h : <{ Γ / δ ⊢ t₁ ⦂ τ₁ }>) :
988+      <{ Γ / δ ⊢ ref t₁ ⦂ Ref τ₁ }>
989+  | deref {Γ : Context} {t₁ : Tm} {τ₁ : Ty}
990+      (h : <{ Γ / δ ⊢ t₁ ⦂ Ref τ₁ }>) :
991+      <{ Γ / δ ⊢ !t₁ ⦂ τ₁ }>
992+  | assign {Γ : Context} {t₁ t₂ : Tm} {τ₂ : Ty}
993+      (h₁ : <{ Γ / δ ⊢ t₁ ⦂ Ref τ₂ }>)
994+      (h₂ : <{ Γ / δ ⊢ t₂ ⦂ τ₂ }>) :
995+      <{ Γ / δ ⊢ t₁ := t₂ ⦂ Unit }>

1034+--  assumptions of that store typing"...
1035+
1036+def StoreWellTyped (δ:StoreTy) (ρ:Store) :=
1037+  δ.length = ρ.length ∧
1038+  (∀ (l : Nat), l < ρ.length → <{ ∅ / δ ⊢ ~(ρ[l]) ⦂ ~(δ[l]) }>)

1041+--  `StoreWellTyped δ ρ`.

1045+--  Intuitively, a store `ρ` is consistent with a store
1046+--  typing `δ` if every value in the store has the type
1047+--  predicted by the store typing. The only subtle point is
1048+--  the fact that, when typing the values in the store, we
1049+--  supply the very same store typing to the typing
1050+--  relation. This allows us to type circular stores like
1051+--  the one we saw above.

1054+--  preservation property:

1057+  theorem preservation_less_wrong (δ : StoreTy) (τ : Ty) (t t' : Tm) (ρ ρ' : Store) :

1059+    t / ρ ⟶ t' / ρ' →
1060+    δ ⊢ ρ →
1061+    <{ ∅ / δ ⊢ t' ⦂ τ }> := by

1066+--  The `refValue` rule is the problem
1067+--

1069+--      ref v / ρ ⟶ loc |ρ| / ρ,v

1107+      | nil => inversion h₂

1111+        | zero => rfl
1112+        | succ l =>

1115+          · assumption
