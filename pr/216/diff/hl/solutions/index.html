36--- In this chapter, we take a more serious look at how to use Lean as a tool
37--- to study other things. Our case study is a *simple imperative programming
38--- language* called Imp, embodying a tiny core fragment of conventional
39--- mainstream languages such as C and Java.
40-
41--- Here is a familiar mathematical function written in Imp.
42-
43---   Z := X;
44---   Y := 1;
45---   while (Z ≠ 0) {
46---     Y := Y * Z;
47---     Z := Z - 1;
48---   }
49-
50--- We concentrate here on defining the *syntax* and *semantics* of Imp; later
51--- in this volume we develop a theory of *program equivalence* and introduce
52--- *Hoare Logic*, a popular logic for reasoning about imperative programs.
53-
54--- We build Imp in three layers. The first — a core language of *arithmetic
55--- and boolean expressions* — is developed in its own chapter, *Slang*; read
56--- that one first. There you meet the abstract syntax of arithmetic
57--- expressions (`Aexp`) and boolean expressions (`Bexp`), their evaluation
58--- both as a recursive *function* and as an inductive *relation* (proved
59--- equivalent), and a small `optimize0plus` program transformation together
60--- with its correctness proof. Those expressions are *variable-free*.
61-
62--- This chapter picks up from there. First we extend the expressions with
63--- *variables*; then we add a language of *commands* — assignment,
64--- conditionals, sequencing, and loops.

67-

69--- arithmetic and boolean expressions with variables. To keep things simple,
70--- we'll assume that all variables are global and that they only hold numbers.

72--- ### States
73-
74--- Since we'll want to look variables up to find out their current values,
75--- we'll use total maps from the `Maps` chapter. A *machine state* (or just
76--- *state*) represents the current values of all variables at some point in
77--- the execution of a program.
78-

82--- as a total map from strings (variable names) to `Nat`, and will use `0` as
83--- the default value in the store.

282--- ### Delaborators
283-
284--- The notations above are *input* only: they teach Lean how to **read**
285--- `aexp
286--- { … }` and `bexp { … }`, but Lean still **prints** an expression
287--- using its raw constructors -- `example_aexp` shows up as
288--- `Aexp.plus (Aexp.num 3) …` rather than `aexp { 3 + X * 2 }`. A
289--- *delaborator* closes the loop. Where a `macro` turns surface syntax into a
290--- term (*elaboration*), a delaborator does the reverse: it turns an
291--- elaborated term back into surface syntax so that Lean's own output uses our
292--- concrete Imp notation.
293-
294--- Each delaborator walks a term of the given type and rebuilds the matching
295--- piece of `imp_aexp`/`imp_bexp` syntax; a subterm Lean doesn't recognize is
296--- printed with the `~` escape. The `@[delab …]` attribute registers the
297--- top-level function to fire whenever Lean is about to display a term headed
298--- by one of those constructors -- unless notation printing has been switched
299--- off with `set_option pp.notation false`, which lets us fall back to the raw
300--- constructors when debugging (see *Desugaring Notations* below). The
301--- companion *category parenthesizer* re-inserts the parentheses the grammar's
302--- precedences demand, so that, e.g., `(1 + 2) * 3` prints with its
303--- parentheses intact.
304-
305--- You do not need to understand the details, and the code is collapsed below
306--- for that reason. The result is that a `#check`, an `#eval`, or a proof goal
307--- mentioning an Imp expression is displayed in readable Imp syntax rather
308--- than as a pile of constructors.

333-
334--- In informal discussions, it is convenient to write the rules for
335--- `Aexp.EvalR` and similar relations in the more readable graphical form of
336--- *inference rules*, where the premises above the line justify the conclusion
337--- below the line. For example, the constructor `plus` can be written like
338--- this as an inference rule:
339-
340--- e1 ⇓ n1
341---                          e2 ⇓ n2
342---                     ------------------          (plus)
343---                     plus e1 e2 ⇓ n1+n2
344-
345--- Notice the structural correspondence between this rule and our version of
346--- the inductive type with unnamed hypotheses:
347-
348--- | plus (a1 a2 : Aexp) (n1 n2 : Nat) :
349---         EvalR a1 n1 →
350---         EvalR a2 n2 →
351---         EvalR (.plus a1 a2) (n1 + n2)
352-
353--- Formally, there is nothing deep about inference rules: they are just an
354--- informal notation for implications. You can read the rule name on the right
355--- as the name of the constructor and read each of the linebreaks between the
356--- premises above the line (as well as the line itself) as `→`. All the
357--- variables mentioned in the rule (`e1`, `n1`, etc.) are implicitly bound by
358--- universal quantifiers at the beginning. (Such variables are often called
359--- *metavariables* to distinguish them from the variables of whatever language
360--- we are defining. At the moment, our arithmetic expressions don't include
361--- variables, but we'll soon be adding them.) The whole collection of rules is
362--- understood as being wrapped, implicitly, in an inductive declaration. In
363--- informal prose, this is sometimes indicated by saying something like "Let
364--- `Aexp.EvalR` be the smallest relation closed under the following rules...".
365-
366--- To summarize: a group of inference rules corresponds to a single inductive
367--- definition; each rule's name corresponds to a constructor name; above the
368--- line are the premises, below the line the conclusion; metavariables like
369--- `e1` and `n1` are implicitly universally quantified. The whole collection
370--- of rules defines `⇓` as the smallest relation closed under them:
371-
372--- ---------                (num)
373---                         num n ⇓ n
