409+-- This facility is very powerful, and is used extensively in
410+-- Lean to define mathematical structures that carry both
411+-- operators and laws about how those operators interact. As a
412+-- simple example, let's use a typeclass to define a *monoid*,
413+-- a simple algebraic structure that includes four things:
414+
415+-- - an underlying set of data, represented by a type `α`,
416+
417+-- - an operator (which we'll write `⊗`, typed otimes) that
418+--   combines two elements of type `α` into one,
419+
420+-- - a particular element `id` of type `α`, which we call the
421+--   "identity element", and
422+
423+-- - some laws about the interaction of `⊗` and `id`, namely
424+--   that:
425+
426+--   - `∀ x, id ⊗ x = x = x ⊗ id`, and
427+
428+--   - `∀ x y z, x ⊗ (y ⊗ z) = (x ⊗ y) ⊗ z` (i.e., that `⊗` is
429+--     associative)
430+
431+-- We can express these requirements in the form of a
432+-- typeclass:
433+
434+-- first we define a notation typeclass for our operator ⊗
435+class OpSet (α : Type) where
436+  op : α → α → α
437+
438+infixr:70 " ⊗ " => OpSet.op
439+
440+class Monoid (α : Type) extends (OpSet α) where
441+  id : α
442+  left_id : ∀ (x : α), id ⊗ x = x
443+  right_id : ∀ (x : α), x ⊗ id = x
444+  assoc : ∀ (x y z : α), x ⊗ (y ⊗ z) = (x ⊗ y) ⊗ z
445+
446+-- The `extends` keyword indicates that the `Monoid` typeclass
447+-- extends the `OpSet` typeclass, which just defines a set with
448+-- an operator and some notation for it. The `Monoid` typeclass
449+-- "inherits" the fields of `OpSet`, similar to how a class
450+-- would in an object-oriented language.
451+

453+-- monoid, where `0` is the identity element. Note that we
454+-- don't have to define `Nat`'s `OpSet` instance separately, we
455+-- can define a single instance that implements both classes.
456+

489+-- In addition to defining instances of `Monoid`, we can also
490+-- prove some properties about monoids in general, just based
491+-- on the laws defined on the typeclass. One simple theorem
492+-- about monoids is that the identity element of a monoid is
493+-- unique. That is, if we have two monoids over the same set
494+-- with the same operator, their identity elements must also be
495+-- the same:
496+
497+theorem id_unique {α : Type} {m₁ m₂ : Monoid α} (h : m₁.op = m₂.op) : m₁.id = m₂.id := by
498+  obtain @⟨op₁, id₁, left_id₁, right_id₁, assoc₁⟩ := m₁
499+  obtain @⟨op₂, id₂, left_id₂, right_id₂, assoc₂⟩ := m₂
500+  have h' : id₁ = id₂ := by
501+    -- this introduces a use of m₁'s operator
502+    rw [← left_id₁ id₂]
503+    -- we use our hypothesis to rewrite m₁'s operator into m₂'s
504+    rw [h]
505+    -- then, we can use m₂'s right id
506+    rw [right_id₂]
507+  -- the goal `m₁.id = m₂.id` is equivalent with `id₁ = id₂` even though it displays `Monoid.id = Monoid.id`
508+  exact h'

511+-- `m₁` and `m₂` with the `obtain` tactic we saw in the Logic
512+-- chapter. When we do so however, because these are class
513+-- instances instead of normal structures, we preface our tuple
514+-- with the `@` symbol. When stepping through the above proof,
515+-- if the notation is confusing to you, remember that you can
516+-- set `set_option pp.all true` or
517+-- `set_option pp.explicit true` to make Lean show you more
518+-- clearly what is going on. For example, the goal is displayed
519+-- as `Monoid.id = Monoid.id` since the instances `m₁` and `m₂`
520+-- are implicit arguments to `Monoid.id`. Setting
521+-- `pp.explicit true` displays the goal as
522+-- `@Eq α (@Monoid.id α m₁) (@Monoid.id α m₂)`.
