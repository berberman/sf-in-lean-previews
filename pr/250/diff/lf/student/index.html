359+-- This facility is very powerful, and is used extensively in Lean to define
360+-- mathematical structures that carry both operators and laws about how those
361+-- operators interact. As a simple example, let's use a typeclass to define a
362+-- *monoid*, a simple algebraic structure that includes four things:
363+
364+-- - an underlying set of data, represented by a type `α`,
365+
366+-- - an operator (which we'll write `⊗`, typed otimes) that combines two
367+--   elements of type `α` into one,
368+
369+-- - a particular element `id` of type `α`, which we call the "identity
370+--   element", and
371+
372+-- - some laws about the interaction of `⊗` and `id`, namely that:
373+
374+--   - `∀ x, id ⊗ x = x = x ⊗ id`, and
375+--   - `∀ x y z, x ⊗ (y ⊗ z) = (x ⊗ y) ⊗ z` (i.e., that `⊗` is associative)
376+
377+-- We can express these requirements in the form of a typeclass:
378+
379+-- first we define a notation typeclass for our operator ⊗
380+class OpSet (α : Type) where
381+  op : α → α → α
382+
383+infixr:70 " ⊗ " => OpSet.op
384+
385+class Monoid (α : Type) extends (OpSet α) where
386+  id : α
387+  left_id : ∀ (x : α), id ⊗ x = x
388+  right_id : ∀ (x : α), x ⊗ id = x
389+  assoc : ∀ (x y z : α), x ⊗ (y ⊗ z) = (x ⊗ y) ⊗ z
390+
391+-- The `extends` keyword indicates that the `Monoid` typeclass extends the
392+-- `OpSet` typeclass, which just defines a set with an operator and some
393+-- notation for it. The `Monoid` typeclass "inherits" the fields of `OpSet`,
394+-- similar to how a class would in an object-oriented language.
395+

399+-- classes.

433+-- In addition to defining instances of `Monoid`, we can also prove some
434+-- properties about monoids in general, just based on the laws defined on the
435+-- typeclass. One simple theorem about monoids is that the identity element of
436+-- a monoid is unique. That is, if we have two monoids over the same set with
437+-- the same operator, their identity elements must also be the same:
438+
439+theorem id_unique {α : Type} {m₁ m₂ : Monoid α} (h : m₁.op = m₂.op) : m₁.id = m₂.id := by
440+  obtain @⟨op₁, id₁, left_id₁, right_id₁, assoc₁⟩ := m₁
441+  obtain @⟨op₂, id₂, left_id₂, right_id₂, assoc₂⟩ := m₂
442+  have h' : id₁ = id₂ := by
443+    -- this introduces a use of m₁'s operator
444+    rw [← left_id₁ id₂]
445+    -- we use our hypothesis to rewrite m₁'s operator into m₂'s
446+    rw [h]
447+    -- then, we can use m₂'s right id
448+    rw [right_id₂]
449+  -- the goal `m₁.id = m₂.id` is equivalent with `id₁ = id₂` even though it displays `Monoid.id = Monoid.id`
450+  exact h'

453+-- with the `obtain` tactic we saw in the Logic chapter. When we do so
454+-- however, because these are class instances instead of normal structures, we
455+-- preface our tuple with the `@` symbol. When stepping through the above
456+-- proof, if the notation is confusing to you, remember that you can set
457+-- `set_option pp.all true` or `set_option pp.explicit true` to make Lean show
458+-- you more clearly what is going on. For example, the goal is displayed as
