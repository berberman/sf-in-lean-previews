531--- ## Proof Rules
532-
533--- The goal of Hoare logic is to provide a *compositional* method for proving
534--- the validity of specific Hoare triples. That is, we want the structure of a
535--- program's correctness proof to mirror the structure of the program itself.
536--- To this end, in the sections below, we'll introduce a rule for reasoning
537--- about each of the different syntactic forms of commands in Imp -- one for
538--- assignment, one for sequencing, one for conditionals, etc. -- plus a couple
539--- of "structural" rules for gluing things together. We will then be able to
540--- prove programs correct using these proof rules, without ever unfolding the
541--- definition of `ValidHoareTriple`.

556--- ### Sequencing
557-
558--- If command `c1` takes any state where `P` holds to a state where `Q` holds,
559--- and if `c2` takes any state where `Q` holds to one where `R` holds, then
560--- doing `c1` followed by `c2` will take any state where `P` holds to one
561--- where `R` holds:
562-
563---    {{ P }} c1 {{ Q }}
564---    {{ Q }} c2 {{ R }}
565---   ----------------------  (hoare_seq)
566---   {{ P }} c1;c2 {{ R }}
567-
568-theorem hoare_seq (P Q R : Assertion) (c1 c2 : Com)
569-    (h1 : {{ Q }} ~c2 {{ R }}) (h2 : {{ P }} ~c1 {{ Q }}) :
570-    {{ P }} ~c1 ~c2 {{ R }} := by
571-  intro st st' h12 pre
572-  inversion h12 with
573-  | seq st'' hc1 hc2 =>
574-    exact h1 _ _ hc2 (h2 _ _ hc1 pre)
575-
576--- Note that, in the formal rule `hoare_seq`, the premises are given in
577--- backwards order (`c2` before `c1`). This matches the natural flow of
578--- information in many of the situations where we'll use the rule, since the
579--- natural way to construct a Hoare-logic proof is to begin at the end of the
580--- program (with the final postcondition) and push postconditions backwards
581--- through commands until we reach the beginning.

583--- ### Assignment
584-
585--- The rule for assignment is the most fundamental of the Hoare logic proof
586--- rules. Here's how it works.
587-
588--- Consider this incomplete Hoare triple:
589-
590---   {{ ??? }}  X := Y  {{ X = 1 }}
591-
592--- We want to assign `Y` to `X` and finish in a state where `X` is `1`. What
593--- could the precondition be?
594-
595--- One possibility is `Y = 1`, because if `Y` is already `1` then assigning it
596--- to `X` causes `X` to be `1`. That leads to a valid Hoare triple:
597-
598---   {{ Y = 1 }}  X := Y  {{ X = 1 }}
599-
600--- It may seem as though coming up with that precondition must have taken some
601--- clever thought. But there is a mechanical way we could have done it: if we
602--- take the postcondition `X = 1` and in it replace `X` with `Y`---that is,
603--- replace the left-hand side of the assignment statement with the right-hand
604--- side---we get the precondition, `Y = 1`.
605-
606--- That same idea works in more complicated cases. For example:
607-
608---   {{ ??? }}  X := X + Y  {{ X = 1 }}
609-
610--- If we replace the `X` in `X = 1` with `X + Y`, we get `X + Y = 1`. That
611--- again leads to a valid Hoare triple:
612-
613---   {{ X + Y = 1 }}  X := X + Y  {{ X = 1 }}
614-
615--- Why does this technique work? The postcondition identifies some property
616--- `P` that we want to hold of the variable `X` being assigned. In this case,
617--- `P` is "equals `1`". To complete the triple and make it valid, we need to
618--- identify a precondition that guarantees that property will hold of `X`.
619--- Such a precondition must ensure that the same property holds of *whatever
620--- is being assigned to* `X`. So, in the example, we need "equals `1`" to hold
621--- of `X + Y`. That's exactly what the technique guarantees.
622-
623--- In general, the postcondition could be some arbitrary assertion `Q`, and
624--- the right-hand side of the assignment could be some arbitrary arithmetic
625--- expression `a`:
626-
627---   {{ ??? }}  X := a  {{ Q }}
628-
629--- The precondition would then be `Q`, but with any occurrences of `X` in it
630--- replaced by `a`.
631-
632--- Let's introduce a notation for this idea of replacing occurrences: Define
633--- `Q \[X ↦ a`] to mean "`Q` where `a` is substituted in place of `X`".
634-
635--- This yields the Hoare logic rule for assignment:
636-
637---   {{ Q [X ↦ a] }}  X := a  {{ Q }}
638-
639--- One way of reading this rule is: If you want statement `X := a` to
640--- terminate in a state that satisfies assertion `Q`, then it suffices to
641--- start in a state that also satisfies `Q`, except where `a` is substituted
642--- for every occurrence of `X`.

645--- from the postcondition to the precondition. Actually it makes good sense to
646--- go in this direction: the postcondition is often what is more important,
647--- because it characterizes what will be true after running the code.

650--- We'll do that later in some exercises.

447+-- A *Hoare triple* is a claim about the state before and after executing a
448+-- command. A commond notation for Hoare triples, and the one we use in this
449+-- book, is
450+
451+--   {{P}} c {{Q}}
452+
453+-- meaning:
454+
455+-- - If command `c` begins execution in a state satisfying assertion `P`,
456+-- - and if `c` eventually terminates in some final state,
457+-- - then that final state will satisfy the assertion `Q`.
458+
459+-- Assertion `P` is called the *precondition* of the triple, and `Q` is the
460+-- *postcondition*.

463+

465+

469+-- a state in which `X = 1`.

473+--   ∀ m, {{X = m}} X := X + 1 {{X = m + 1}}

476+-- `{{X = m}} X :=
477+-- X + 1 {{X = m + 1}}` is valid for any choice of `m`. Note
478+-- that `m` in the two assertions is a reference to the *Lean* variable `m`,

708+-- ## Proof Rules
709+
710+-- The goal of Hoare logic is to provide a *compositional* method for proving
711+-- the validity of specific Hoare triples. That is, we want the structure of a
712+-- program's correctness proof to mirror the structure of the program itself.
713+-- To this end, in the sections below, we'll introduce a rule for reasoning
714+-- about each of the different syntactic forms of commands in Imp -- one for
715+-- assignment, one for sequencing, one for conditionals, etc. -- plus a couple
716+-- of "structural" rules for gluing things together. We will then be able to
717+-- prove programs correct using these proof rules, without ever unfolding the
718+-- definition of `ValidHoareTriple`.
719+
720+-- ### Skip
721+
722+-- Since `skip` doesn't change the state, it preserves any assertion `P`:
723+
724+--   --------------------  (hoare_skip)
725+--   {{ P }} skip {{ P }}
726+
727+theorem hoare_skip {P : Assertion} :
728+    {{ P }} skip {{ P }} := by
729+  rw [validHoareTriple_def]
730+  intro st st' h hpre
731+  inversion h
732+  exact hpre
733+
734+-- ### Sequencing
735+
736+-- If command `c1` takes any state where `P` holds to a state where `Q` holds,
737+-- and if `c2` takes any state where `Q` holds to one where `R` holds, then
738+-- doing `c1` followed by `c2` will take any state where `P` holds to one
739+-- where `R` holds:
740+
741+--    {{ P }} c1 {{ Q }}
742+--    {{ Q }} c2 {{ R }}
743+--   ----------------------  (hoare_seq)
744+--   {{ P }} c1; c2 {{ R }}
745+
746+theorem hoare_seq {P Q R : Assertion} {c1 c2 : Com}
747+    (h1 : {{ Q }} ~c2 {{ R }}) (h2 : {{ P }} ~c1 {{ Q }}) :
748+    {{ P }} ~c1; ~c2 {{ R }} := by
749+  rw [validHoareTriple_def]
750+  intro st st' h hpre
751+  inversion h with
752+  | seq st'' hc1 hc2 =>
753+    rw [validHoareTriple_def] at h1 h2
754+    exact h1 hc2 (h2 hc1 hpre)
755+
756+-- Note that, in the formal rule `hoare_seq`, the premises are given in
757+-- backwards order (`c2` before `c1`). This matches the natural flow of
758+-- information in many of the situations where we'll use the rule, since the
759+-- natural way to construct a Hoare-logic proof is to begin at the end of the
760+-- program (with the final postcondition) and push postconditions backwards
761+-- through commands until we reach the beginning.
762+
763+-- ### Assignment
764+
765+-- The rule for assignment is the most fundamental of the Hoare logic proof
766+-- rules. Here's how it works.
767+
768+-- Consider this incomplete Hoare triple:
769+
770+--   {{ ??? }}  X := Y  {{ X = 1 }}
771+
772+-- We want to assign `Y` to `X` and finish in a state where `X` is `1`. What
773+-- could the precondition be?
774+
775+-- One possibility is `Y = 1`, because if `Y` is already `1` then assigning it
776+-- to `X` causes `X` to be `1`. That leads to a valid Hoare triple:
777+
778+--   {{ Y = 1 }}  X := Y  {{ X = 1 }}
779+
780+-- It may seem as though coming up with that precondition must have taken some
781+-- clever thought. But there is a mechanical way we could have done it: if we
782+-- take the postcondition `X = 1` and in it replace `X` with `Y`---that is,
783+-- replace the left-hand side of the assignment statement with the right-hand
784+-- side---we get the precondition, `Y = 1`.
785+
786+-- That same idea works in more complicated cases. For example:
787+
788+--   {{ ??? }}  X := X + Y  {{ X = 1 }}
789+
790+-- If we replace the `X` in `X = 1` with `X + Y`, we get `X + Y = 1`. That
791+-- again leads to a valid Hoare triple:
792+
793+--   {{ X + Y = 1 }}  X := X + Y  {{ X = 1 }}
794+
795+-- Why does this technique work? The postcondition identifies some property
796+-- `P` that we want to hold of the variable `X` being assigned. In this case,
797+-- `P` is "equals `1`". To complete the triple and make it valid, we need to
798+-- identify a precondition that guarantees that property will hold of `X`.
799+-- Such a precondition must ensure that the same property holds of *whatever
800+-- is being assigned to* `X`. So, in the example, we need "equals `1`" to hold
801+-- of `X + Y`. That's exactly what the technique guarantees.
802+
803+-- In general, the postcondition could be some arbitrary assertion `Q`, and
804+-- the right-hand side of the assignment could be some arbitrary arithmetic
805+-- expression `a`:
806+
807+--   {{ ??? }}  X := a  {{ Q }}
808+
809+-- The precondition would then be `Q`, but with any occurrences of `X` in it
810+-- replaced by `a`.
811+
812+-- Let's introduce a notation for this idea of replacing occurrences: Define
813+-- `Q \[X ↦ a`] to mean "`Q` where `a` is substituted in place of `X`".
814+
815+-- This yields the Hoare logic rule for assignment:
816+
817+--   {{ Q [X ↦ a] }}  X := a  {{ Q }}
818+
819+-- One way of reading this rule is: If you want statement `X := a` to
820+-- terminate in a state that satisfies assertion `Q`, then it suffices to
821+-- start in a state that also satisfies `Q`, except where `a` is substituted
822+-- for every occurrence of `X`.
823+
824+-- To many people, this rule seems "backwards" at first, because it proceeds
825+-- from the postcondition to the precondition. Actually it makes good sense to
826+-- go in this direction: the postcondition is often what is more important,
827+-- because it characterizes what will be true after running the code.
828+
829+-- Nonetheless, it's also possible to formulate a "forward" assignment rule.
830+-- We'll do that later in some exercises.
831+
832+-- Here are some valid instances of the assignment rule:

834+--   {{ (X ≤ 5) [X ↦ X + 1] }}         (that is, X + 1 ≤ 5)

838+--   {{ (X = 3) [X ↦ 3] }}              (that is, 3 = 3)
