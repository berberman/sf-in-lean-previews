470added-- ## Hoare Triples, Informally
471added
472added-- A *Hoare triple* is a claim about the state before and after
473added-- executing a command:
474added
475added-- {{P}} c {{Q}}
476added
477added-- This means:
478added
479added-- - If command `c` begins execution in a state satisfying
480added-- assertion `P`,
481added
482added-- - and if `c` eventually terminates in some final state,
483added
484added-- - then that final state will satisfy the assertion `Q`.
485added
486added-- Assertion `P` is called the *precondition* of the triple,
487added-- and `Q` is the *postcondition*.
488added
489added-- For example,
490added
491added-- - The Hoare triple
492added
493added-- {{X = 0}} X := X + 1 {{X = 1}}
494added
495added-- states that command `X := X + 1` will transform a state in
496added-- which `X = 0` to a state in which `X = 1`.
497added
498added-- - On the other hand,
499added
500added-- ∀ m, {{X = m}} X := X + 1 {{X = m + 1}}
501added
502added-- is a *proposition* stating that the Hoare triple
503added-- `{{X = m}} X :=
504added-- X + 1 {{X = m + 1}}` is valid for any choice
505added-- of `m`. Note that `m` in the two assertions is a reference
506added-- to the *Lean* variable `m`, which is bound outside the Hoare
507added-- triple.
508added

628added-- We formalize valid Hoare triples in Lean as follows:
629added
630addeddef ValidHoareTriple
631added (P : Assertion) (c : Com) (Q : Assertion) : Prop :=
632added ∀ st st',
633added (st =[ c ]=> st') →
634added P st →
635added Q st'

638added-- `NOTATION: SAZ 2024 One trickiness of these notations is that we
639added-- want the [com] and [assn] grammars to be "open", so that they can
640added-- include expressions parsed by the full [constr] grammar of Rocq.
641added-- However, then there is a conflict of precedence of the
642added-- "application" cases:

708added-- ## Proof Rules
709added
710added-- We want to be able to *prove* Hoare triples formally.
711added
712added-- Here's our plan:
713added
714added-- - introduce one "proof rule" for each Imp syntactic form
715added
716added-- - plus a couple of "structural rules" that help glue proofs
717added-- together
718added
719added-- - prove these rules correct in terms of the definition of
720added-- `ValidHoareTriple`
721added
722added-- - prove programs correct using these proof rules, without ever
723added-- unfolding the definition of `ValidHoareTriple`
724added
725added-- ### Skip
726added
727added-- Since `skip` doesn't change the state, it preserves any
728added-- assertion `P`:
729added
730added-- -------------------- (hoare_skip)
731added-- {{ P }} skip {{ P }}
732added
733addedtheorem hoare_skip (P : Assertion) :
734added {{P}} skip; {{P}} := by
735added intro st st' h hp
736added inversion h
737added assumption
738added
739added-- ### Sequencing
740added
741added-- If command `c1` takes any state where `P` holds to a state
742added-- where `Q` holds, and if `c2` takes any state where `Q` holds
743added-- to one where `R` holds, then doing `c1` followed by `c2`
744added-- will take any state where `P` holds to one where `R` holds:
745added
746added-- {{ P }} c1 {{ Q }}
747added-- {{ Q }} c2 {{ R }}
748added-- ---------------------- (hoare_seq)
749added-- {{ P }} c1;c2 {{ R }}
750added
751addedtheorem hoare_seq (P Q R : Assertion) (c1 c2 : Com)
752added (h1 : {{Q}} ~c2 {{R}}) (h2 : {{P}} ~c1 {{Q}}) :
753added {{P}} ~c1 ~c2 {{R}} := by
754added intro st st' h12 pre
755added inversion h12 with
756added | seq st'' hc1 hc2 =>
757added exact h1 _ _ hc2 (h2 _ _ hc1 pre)

759added-- ### Assignment
760added
761added-- How can we complete this triple?
762added
763added-- {{ ??? }} X := Y {{ X = 1 }}
764added
765added-- One natural possibility is:
766added
767added-- {{ Y = 1 }} X := Y {{ X = 1 }}
768added
769added-- The precondition is just the postcondition, but with `X`
770added-- replaced by `Y`.
771added
772added-- How about this one?
773added
774added-- {{ ??? }} X := X + Y {{ X = 1 }}
775added
776added-- Replace `X` with `X + Y`:
777added
778added-- {{ X + Y = 1 }} X := X + Y {{ X = 1 }}
779added
780added-- This works because "equals 1" holding of `X` is guaranteed
781added-- by the property "equals 1" holding of whatever is being
782added-- assigned to `X`.
783added
784added-- In general, the postcondition could be some arbitrary
785added-- assertion `Q`, and the right-hand side of the assignment
786added-- could be some arbitrary arithmetic expression `a`:
787added
788added-- {{ ??? }} X := a {{ Q }}
789added
790added-- The precondition would then be `Q`, but with any occurrences
791added-- of `X` in it replaced by `a`.
792added
793added-- Let's introduce a notation for this idea of replacing
794added-- occurrences: Define `Q \[X ↦ a`] to mean "`Q` where `a` is
795added-- substituted in place of `X`".
796added
797added-- This yields the Hoare logic rule for assignment:
798added
799added-- {{ Q [X ↦ a] }} X := a {{ Q }}
800added
801added-- One way of reading this rule is: If you want statement
802added-- `X := a` to terminate in a state that satisfies assertion
803added-- `Q`, then it suffices to start in a state that also
804added-- satisfies `Q`, except where `a` is substituted for every
805added-- occurrence of `X`.
806added
807added-- Here are some valid instances of the assignment rule:
808added
809added-- {{ (X ≤ 5) [X ↦ X + 1] }} (that is, X + 1 ≤ 5)
810added-- X := X + 1
811added-- {{ X ≤ 5 }}
812added
813added-- {{ (X = 3) [X ↦ 3] }} (that is, 3 = 3)
814added-- X := 3
815added-- {{ X = 3 }}
816added
817added-- {{ (0 ≤ X ∧ X ≤ 5) [X ↦ 3] }}. (that is, 0 ≤ 3 ∧ 3 ≤ 5)
818added-- X := 3
819added-- {{ 0 ≤ X ∧ X ≤ 5 }}
820added
821added-- To formalize the rule, we must first formalize the idea of
822added-- "substituting an expression for an Imp variable in an
823added-- assertion", which we refer to as assertion substitution, or
824added-- `Assertion.sub`.
825added
826added-- Intuitively, given a proposition `P`, a variable `X`, and an
827added-- arithmetic expression `a`, we want to derive another
828added-- proposition `P'` that is just the same as `P` except that
829added-- `P'` should mention `a` wherever `P` mentions `X`.
830added
831added-- This operation is related to the idea of substituting Imp
832added-- expressions for Imp variables that we saw in *Equiv*
833added-- (`subst_aexp` and friends). The difference is that, here,
834added-- `P` is an arbitrary Lean assertion, so we can't directly
835added-- "edit" its text.
836added
837added-- However, we can achieve the same effect by evaluating `P` in
838added-- an updated state, defined as follows:
839added
840addeddef Assertion.sub (x : Ident) (a : Aexp) (P : Assertion) : Assertion :=
841added fun (st : State) => P (x →ₜ a.eval st ; st)
842added
843added-- Note to developers (before next release):
844added-- This concrete syntax is hard to read in comments because
845added-- of all the square brackets. Something like
846added-- `P with X ↦ a` would be much better. I guess the same
847added-- will apply to the lambda-calculus chapters... BCP 25: I
848added-- still think this is a good idea, and I had a quick go at
849added-- implementing it, but did not succeed yet.
850added
851added/-- Assertion substitution: `P [X ↦ a]` -/
852addedsyntax:100 assn:100 " [" ident " ↦ " imp_aexp "]" : assn
853added
854addedmacro_rules
855added | `({{ $P [$x ↦ $a] }}) => `(Assertion.sub $x (aexp { $a }) ({{ $P }}))
856added
857added-- This notation allows us to write this operation as:
858added
859added-- P [ X ↦ a ]
860added
861added-- That is, `P [X ↦ a]` stands for an assertion -- let's call
862added-- it `P'` -- that behaves just like `P` except that, wherever
863added-- `P` looks up the variable `X` in the current state, `P'`
864added-- instead uses the value of the expression `a`.
865added
866added-- We can demonstrate formally that we have captured intuitive
867added-- meaning of "assertion subsitution" by proving some example
868added-- logical equivalences:
869added
870addednamespace ExampleAssertionSub
871addedexample :
872added {{ (X ≤ 5) [X ↦ 3] }} <<->> {{ 3 ≤ 5 }} := by
873added constructor <;> (unfold AssertImplies Assertion.sub; intro st h; exact h)
874added
875addedexample :
876added {{ (X ≤ 5) [X ↦ X + 1] }} <<->> {{ (X + 1) ≤ 5 }} := by
877added constructor <;> (unfold AssertImplies Assertion.sub; intro st h; exact h)
878added
879addedend ExampleAssertionSub

1148added-- `TotalMap.update_same`, and `TotalMap.update_permute`. Make

1151added-- ### Consequence
1152added
1153added-- Sometimes the preconditions and postconditions we get from
1154added-- the Hoare rules won't quite be the ones we want in the
1155added-- particular situation at hand -- they may be logically
1156added-- equivalent but have a different syntactic form that fails to
1157added-- unify with the goal we are trying to prove, or they actually
1158added-- may be logically weaker (for preconditions) or stronger (for
1159added-- postconditions) than what we need.
1160added
1161added-- For instance,
1162added
1163added-- {{(X = 3) [X ↦ 3]}} X := 3 {{X = 3}},
1164added
1165added-- follows directly from the assignment rule, but
1166added
1167added-- {{True}} X := 3 {{X = 3}}
1168added
1169added-- does not. This triple is valid, but it is not an instance of
1170added-- `hoare_asgn` because `True` and `(X = 3) \[X ↦ 3`] are not
1171added-- syntactically equal assertions.
1172added
1173added-- However, they are logically *equivalent*, so if one triple
1174added-- is valid, then the other must certainly be as well. We can
1175added-- capture this observation with the following rule:
1176added
1177added-- {{P'}} c {{Q}}
1178added-- P <<->> P'
1179added-- ---------------------
1180added-- {{P}} c {{Q}}
1181added
1182added-- Taking this line of thought a bit further, we can see that
1183added-- strengthening the precondition or weakening the
1184added-- postcondition of a valid triple always produces another
1185added-- valid triple. This observation is captured by two *Rules of
1186added-- Consequence*.
1187added
1188added-- {{P'}} c {{Q}}
1189added-- P ->> P'
1190added-- ----------------------------- (hoare_consequence_pre)
1191added-- {{P}} c {{Q}}
1192added
1193added-- {{P}} c {{Q'}}
1194added-- Q' ->> Q
1195added-- ----------------------------- (hoare_consequence_post)
1196added-- {{P}} c {{Q}}
1197added
1198added-- Here are the formal versions:
1199added
1200addedtheorem hoare_consequence_pre (P P' Q : Assertion) (c : Com)
1201added (hhoare : {{P'}} ~c {{Q}}) (himp : P ->> P') :
1202added {{P}} ~c {{Q}} := by
1203added unfold ValidHoareTriple
1204added intro st st' heval hpre
1205added apply hhoare st st'
1206added · assumption
1207added · apply himp
1208added assumption
1209added
1210addedtheorem hoare_consequence_post (P Q Q' : Assertion) (c : Com)
1211added (hhoare : {{P}} ~c {{Q'}}) (himp : Q' ->> Q) :
1212added {{P}} ~c {{Q}} := by
1213added unfold ValidHoareTriple
1214added intro st st' heval hpre
1215added apply himp
1216added apply hhoare st st'
1217added · assumption
1218added · assumption
1219added
1220added-- For example, we can use the first consequence rule like
1221added-- this:
1222added
1223added-- {{ True }} ->>
1224added-- {{ (X = 1) [X ↦ 1] }}
1225added-- X := 1
1226added-- {{ X = 1 }}
1227added
1228added-- Or, formally...
1229added
1230addedtheorem hoare_asgn_example1 :
1231added {{True}} X := 1; {{X = 1}} := by
1232added sorry
1233added
1234added-- We can also use it to prove the example mentioned earlier.
1235added
1236added-- {{ X < 4 }} ->>
1237added-- {{ (X < 5)[X ↦ X + 1] }}
1238added-- X := X + 1
1239added-- {{ X < 5 }}
1240added
1241added-- Or, formally ...
1242added
1243addedtheorem assertion_sub_example2 :
1244added {{X < 4}}
1245added X := X + 1;
1246added {{X < 5}} := by
1247added sorry
1248added
1249added-- Finally, here is a combined rule of consequence that allows
1250added-- us to vary both the precondition and the postcondition.
1251added
1252added-- {{P'}} c {{Q'}}
1253added-- P ->> P'
1254added-- Q' ->> Q
1255added-- ----------------------------- (hoare_consequence)
1256added-- {{P}} c {{Q}}
1257added
1258addedtheorem hoare_consequence (P P' Q Q' : Assertion) (c : Com)
1259added (htriple : {{P'}} ~c {{Q'}}) (hpre : P ->> P') (hpost : Q' ->> Q) :
1260added {{P}} ~c {{Q}} := by
1261added apply hoare_consequence_pre (P' := P')
1262added · apply hoare_consequence_post (Q' := Q')
1263added · assumption
1264added · assumption
1265added · assumption

1446added-- ### Conditionals
1447added
1448added-- What sort of rule do we want for reasoning about conditional
1449added-- commands?
1450added
1451added-- Certainly, if the same assertion `Q` holds after executing
1452added-- either of the branches, then it holds after the whole
1453added-- conditional. So we might be tempted to write:
1454added
1455added-- {{P}} c1 {{Q}}
1456added-- {{P}} c2 {{Q}}
1457added-- ---------------------------------
1458added-- {{P}} if b then c1 else c2 {{Q}}
1459added
1460added-- However, this is rather weak. For example, using this rule,
1461added-- we cannot show
1462added
1463added-- {{ True }}
1464added-- if X = 0
1465added-- then Y := 2
1466added-- else Y := X + 1
1467added-- end
1468added-- {{ X ≤ Y }}
1469added
1470added-- since the rule doesn't tell us enough about the state in
1471added-- which the assignments take place in the "then" and "else"
1472added-- branches.
1473added
1474added-- Better:
1475added
1476added-- {{P ∧ b}} c1 {{Q}}
1477added-- {{P ∧ ¬ b}} c2 {{Q}}
1478added-- ------------------------------------ (hoare_if)
1479added-- {{P}} if b then c1 else c2 end {{Q}}
1480added
1481added-- To make this formal, we need a way of formally "lifting" any
1482added-- bexp `b` to an assertion.
1483added
1484added-- We'll write `bassertion b` for the assertion "the boolean
1485added-- expression `b` evaluates to `true`."
1486added
1487addeddef bassertion (b : Bexp) : Assertion :=
1488added fun st => (b.eval st = true)
1489added
1490added@[simp] theorem bassertion_apply (b : Bexp) (st : State) :
1491added bassertion b st = (b.eval st = true) := rfl
1492added
1493addedinstance : Coe Bexp Assertion := ⟨bassertion⟩
1494added
1495added-- A useful fact about `bassertion`:
1496added
1497added-- Note to developers (before next release):
1498added-- `Robert Rand: This isn't an identity but that's because
1499added-- we're using [~(bassertion b st)] in our triples, instead of a more
1500added-- direct/intuitive predicate.
1501added--
1502added-- Some alternatives: 1) P_True b and P_False b (defined directly as
1503added-- desired) 1) bassertion b false (adds relevant argument to bassertion)
1504added-- 2) ((bassertion (!b)) st) (clearer, but less direct).`
1505added
1506addedtheorem bexp_eval_false (b : Bexp) (st : State) (h : b.eval st = false) :
1507added ¬ ((bassertion b) st) := by
1508added simp [bassertion, h]
1509added
1510added-- Note to developers (One An @meluge):

1513added-- `congruence` tactic?

1515added-- Now we can formalize the Hoare proof rule for conditionals
1516added-- and prove it correct.
1517added
1518added-- The statement of the rule reads: given
1519added-- `htrue : {{ P ∧ b }} ~c1 {{Q}}` and
1520added-- `hfalse : {{ P ∧ ¬b }} ~c2 {{Q}}`, we can conclude
1521added-- `{{P}} if (~b) { ~c1 } else { ~c2 } {{Q}}`.
1522added
1523added-- That is (unwrapping the notations):
1524added
1525added-- theorem hoare_if (P Q : Assertion) (b : Bexp) (c1 c2 : Com)
1526added-- (htrue : ValidHoareTriple (fun st => P st ∧ bassertion b st) c1 Q)
1527added-- (hfalse : ValidHoareTriple (fun st => P st ∧ ¬ (bassertion b st)) c2 Q) :
1528added-- ValidHoareTriple P (Com.cond b c1 c2) Q
1529added
1530addedtheorem hoare_if (P Q : Assertion) (b : Bexp) (c1 c2 : Com)
1531added (htrue : {{ P ∧ b }} ~c1 {{Q}}) (hfalse : {{ P ∧ ¬b }} ~c2 {{Q}}) :
1532added {{P}} if (~b) { ~c1 } else { ~c2 } {{Q}} := by
1533added intro st st' hE hP
1534added inversion hE with
1535added | ifTrue hb hc => exact htrue _ _ hc ⟨hP, hb⟩
1536added | ifFalse hb hc => exact hfalse _ _ hc ⟨hP, bexp_eval_false b st hb⟩

1635added-- ### While Loops
1636added
1637added-- The Hoare rule for `while` loops is based on the idea of a
1638added-- *command invariant* (or just *invariant*): an assertion
1639added-- whose truth is guaranteed after executing a command,
1640added-- assuming it is true before.
1641added
1642added-- That is, an assertion `P` is a command invariant of `c` if
1643added
1644added-- {{P}} c {{P}}
1645added
1646added-- holds. Note that the command invariant might temporarily
1647added-- become false in the middle of executing `c`, but by the end
1648added-- of `c` it must be restored.
1649added
1650added-- The Hoare while rule combines the idea of a command
1651added-- invariant with information about when guard `b` does or does
1652added-- not hold.
1653added
1654added-- {{P ∧ b}} c {{P}}
1655added-- --------------------------------- (hoare_while)
1656added-- {{P}} while b do c end {{P ∧ ¬b}}
1657added
1658added-- Note to developers:
1659added-- HIDE: The big comment will not display nicely. But I
1660added-- guess it's folded...
1661added
1662addedtheorem hoare_while (P : Assertion) (b : Bexp) (c : Com)
1663added (hhoare : {{P ∧ b}} ~c {{P}}) :
1664added {{P}} while (~b) { ~c } {{P ∧ ¬b}} := by
1665added intro st st' heval hP
1666added /- We proceed by induction on `heval`, because, in the "keep
1667added looping" case, its hypotheses talk about the whole loop instead
1668added of just `c`. The auxiliary statement `key` generalizes over an
1669added arbitrary command, together with an equation remembering that the
1670added command is the original loop; otherwise, that information would
1671added be lost in the induction. The cases for commands other than
1672added `while` are dismissed because their equations are contradictory. -/
1673added have key : ∀ (cmd : Com) (s s' : State), (s =[ cmd ]=> s') →
1674added cmd = (imp { while (~b) { ~c } }) → P s →
1675added P s' ∧ ¬ bassertion b s' := by
1676added intro cmd s s' hev
1677added induction hev with
1678added | whileFalse b0 s0 c0 hb =>
1679added intro heq hp
1680added injection heq with e1 _
1681added subst e1
1682added exact ⟨hp, bexp_eval_false _ _ hb⟩
1683added | whileTrue s0 s0' s0'' b0 c0 hb hc hloop ih1 ih2 =>
1684added intro heq hp
1685added injection heq with e1 e2
1686added subst e1 e2
1687added exact ih2 rfl (hhoare _ _ hc ⟨hp, hb⟩)
1688added | skip s0 => intro heq; simp at heq
1689added | asgn s0 a n x h => intro heq; simp at heq
1690added | seq c1 c2 s0 s0' s0'' h1 h2 ih1 ih2 => intro heq; simp at heq
1691added | ifTrue s0 s0' b0 c1 c2 hb hc ih => intro heq; simp at heq
1692added | ifFalse s0 s0' b0 c1 c2 hb hc ih => intro heq; simp at heq
1693added exact key _ st st' heval rfl hP
1694added
