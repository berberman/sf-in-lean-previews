1279+--  ### Automation with `solve_by_elim`
1280+
1281+--  When experimenting with definitions of programming languages in Lean,
1282+--  we often want to see what a particular term steps to - i.e., we want to
1283+--  find proofs for goals of the form `t ⟶* t'`. Consider, for example,
1284+--  reducing an arithmetic expression using the small-step relation
1285+--  `AStep`.
1286+
1287+example : (.p (.c 3) (.p (.c 3) (.c 4))) ⟶* (.c 10) := by
1288+  apply Multi.step (y := .p (.c 3) (.c 7))
1289+  . apply Step.plusRight
1290+    . apply IsValue.const
1291+    . apply Step.plus
1292+  . apply Multi.step (y := .c 10)
1293+    . apply Step.plus
1294+    . apply Multi.refl
1295+
1296+--  Proofs that one term normalizes to another must repeatedly apply
1297+--  `Multi.step` until the term reaches a normal form, with some very
1298+--  simple intermediate steps along the way. Thankfully, we can automate
1299+--  this process with a new tactic: `solve_by_elim`. When supplied with a
1300+--  list of constructors, `solve_by_elim [c₁, c₂, c₃, ...]` will attempt to
1301+--  apply these constructors repeatedly to a goal. It will also
1302+--  automatically attempt to use simple tactics like `rfl`, `trivial`,
1303+--  `congr` and hypotheses from the context in order to solve simple goals.
1304+--  So, for example, the proof above also be written:
1305+
1306+example : (.p (.c 3) (.p (.c 3) (.c 4))) ⟶* (.c 10) := by
1307+  repeat apply Multi.step <;>
1308+    try solve_by_elim [Step.plusRight, Step.plusLeft, Step.plus, IsValue.const]
1309+
1310+--  This one script would suffice to prove most concrete reduction
1311+--  sequences for this simple language. To make it work for others, we
1312+--  would need to supply constructors for those other languages to
1313+--  `solve_by_elim`. The languages we will study in this book can grow to a
1314+--  large number of constructors for their `Step` relations, so we'd like a
1315+--  way to supply all of them to `solve_by_elim` more easily. Luckily, Lean
1316+--  supports this. We can register a constructor (or lemma) for use with
1317+--  `solve_by_elim` with an `attribute` command:
1318+
1319+--  THE FOLLOWING DETAILS CAN BE SKIPPED (Attributes)
1320+--  The command below tags all of these constructors with the `SimpleArith`
1321+--  attribute, which we can then use to automatically pull all of these
1322+--  constructors in when we use `solve_by_elim`. However, due to a
1323+--  limitation of Lean, this attribute needs to be pre-declared in a
1324+--  different file; we can't create it here and then immediately use it.
1325+--
1326+--  For this book, we've predeclared all the attributes we'll use in a file
1327+--  called `AttributeDecls.lean`, following the typical pattern from
1328+--  libraries like Mathlib.
1329+--  END DETAILS
1330+
1331+attribute [SimpleArith] Step.plusRight Step.plusLeft Step.plus IsValue.const
1332+
1333+--  This `using` option then tells `solve_by_elim` to try to use every
1334+--  constructor we've registered with the supplied attribute:
1335+
1336+example : (.p (.c 3) (.p (.c 3) (.c 4))) ⟶* (.c 10) := by
1337+  repeat apply Multi.step <;>
1338+    try solve_by_elim using SimpleArith
1339+
1340+--  We can package all this up into a dedicated tactic for solving
1341+--  reduction sequences, which we'll call `normalize`:
1342+
1343+syntax "normalize" " using " ident,+ : tactic
1344+
1345+macro_rules
1346+  | `(tactic| normalize using $xs,*) =>
1347+    `(tactic| repeat apply Multi.step <;> try solve_by_elim (maxDepth:=10) using $xs,*)
1348+
1349+--  And voilà:
1350+
1351+example : (.p (.c 3) (.p (.c 3) (.c 4))) ⟶* (.c 10) := by
1352+  normalize using SimpleArith

1288+--  It's worth noting that `apply_rules` relies on an important property of
1289+--  our typing rules - namely, that they are *syntax directed*. A syntax
1290+--  directed judgment is one where the syntax of a term completely
1291+--  determines which rule can be applied at any given time; only one rule
1292+--  can be applied to each term. This is important because `apply_rules`
1293+--  just applies the first rule in its set of constructors or lemmas that
1294+--  it can - it doesn't backtrack if that rule isn't correct. So, making
1295+--  sure that only one rule can apply to any given term is important to
1296+--  ensure that `apply_rules` always discovers a valid derivation, if one
1297+--  exists.
