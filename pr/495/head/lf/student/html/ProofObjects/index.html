10. ProofObjects: The Curry-Howard Correspondence🔗

This setting is enabled to make some tricky mistakes harder to make.

set_option autoImplicit false

"Algorithms are the computational content of proofs." (Robert Harper)

We have seen that Lean has mechanisms both for programming, using inductive data types like Nat or List and functions over these types, and for proving properties of these programs, using inductive propositions (like Even), implication, universal quantification, and the like. So far, we have mostly treated these mechanisms as if they were quite separate, and for many purposes this is a good way to think. But we have also seen hints that Lean's programming and proving facilities are closely related. For example, the keyword inductive is used to declare both data types and propositions, and → is used both to describe the type of functions on data and logical implication. This is not just a syntactic accident! In fact, programs and proofs in Lean are almost the same thing. In this chapter we will study this connection in more detail.

We have already seen the fundamental idea: provability in Lean is always witnessed by evidence. When we construct the proof of a basic proposition, we are actually building a tree of evidence, which can be thought of as a concrete data structure.

If the proposition is an implication like A → B, then its proof is an evidence transformer: a recipe for converting evidence for A into evidence for B. So at a fundamental level, proofs are simply programs that manipulate evidence.

Question: If evidence is data, what are propositions themselves?

Answer: They are types!

Look again at the formal definition of the Even property. For illustrative purposes, we've made the implicit argument {n : Nat} to Even.succ_succ explicit.

namespace EvenProp inductive Even : Nat → Prop where | zero : Even 0 | succ_succ (n : Nat) (h : Even n) : Even (n + 2)

We can pronounce the ":" here as either "has type" or "is a proof of." For example, the second line in the definition of Even declares that (Even.zero : Even 0). Instead of "Even.zero has type Even 0," we can say that "Even.zero is a proof of Even 0."

This pun between types and propositions — between : as "has type" and : as "is a proof of" or "is evidence for" — is called the Curry-Howard correspondence. It proposes a deep connection between the world of logic and the world of computation:

propositions  ~  types
proofs        ~  programs

See Wadler (2015)Philip Wadler (2015). “Propositions as Types”. Communications of the ACM. 58(12), pp. 75–84. for a brief history and modern exposition.

Many useful insights follow from this connection. To begin with, it gives us a natural interpretation of the type of the Even.succ_succ constructor.

The type of Even.succ_succ says that it is a function (better: a data constructor) taking two arguments (one number n plus evidence for Even n) and returning evidence that n + 2 is even.

Even.succ_succ : ∀ (n : Nat), Even n → Even (n + 2)#check @Even.succ_succ 
Even.succ_succ : ∀ (n : Nat), Even n → Even (n + 2)

This can be read "Even.succ_succ is a constructor that takes two arguments — a number n and evidence for the proposition Even n — and yields evidence for the proposition Even (n + 2)."

Now let's look again at an earlier proof involving Even.

theorem even_4 : Even 4 := ⊢ Even 4 ⊢ Even 2 ⊢ Even 0 All goals completed! 🐙

Just as with ordinary data values and functions, we can use the #print command to see the proof object that results from this proof script.

theorem EvenProp.even_4 : Even 4 := Even.succ_succ 2 (Even.succ_succ 0 Even.zero)#print even_4 
theorem EvenProp.even_4 : Even 4 :=
Even.succ_succ 2 (Even.succ_succ 0 Even.zero)

Indeed, we can also write down this proof object directly, with no need for a proof script at all:

Even.succ_succ 2 (Even.succ_succ 0 Even.zero) : Even (2 + 2)#check (Even.succ_succ 2 (Even.succ_succ 0 Even.zero) : Even (2 + 2)) 
Even.succ_succ 2 (Even.succ_succ 0 Even.zero) : Even (2 + 2)

The expression Even.succ_succ 2 (Even.succ_succ 0 Even.zero) instantiates the parameterized constructor Even.succ_succ with the specific arguments 2 and 0 plus the corresponding proof objects for its premises Even 2 and Even 0. Alternatively, we can think of Even.succ_succ as a primitive "evidence constructor" that, when applied to a particular number, wants to be further applied to evidence that this number is even; its type,

∀ (n : Nat), Even n → Even (n + 2)

expresses this functionality, in the same way that the polymorphic type {α : Type} → List α expresses the fact that the constructor List.nil can be thought of as a function from types to empty lists with elements of that type.

The fact that the some arguments are implicit, like {α} of List and {n} of the real Even.succ_succ, actually doesn't make a difference at all: List is still taking one argument, and Even.succ_succ is still taking two. Implicit arguments are just a usability feature that tells Lean to figure some arguments out when we apply a definition (like Even.succ_succ) to an explicit argument (like a proof of Even n). In this case, since Even n contains n, we don't need to pass n in to begin with, and can mark it as implicit with the curly braces as {n}.

We saw in the Logic chapter that we can use function application syntax to instantiate universally quantified variables in lemmas, as well as to supply evidence for assumptions that these lemmas impose. For instance:

theorem even_4' : Even 4 := ⊢ Even 4 All goals completed! 🐙

10.1. Proof Scripts🔗

The proof objects we've been discussing lie at the core of how Lean operates. When Lean is following a proof script, what is happening internally is that it is gradually constructing a proof object — a term whose type is the proposition being proved. All the tactics following by tell it how to build up a term of the required type. To see this process in action, we provide a show_proof command to display the current state of the proof tree at various points in the following tactic proof.

At any given moment, Lean has constructed a term with a "hole" (indicated by ?_ here, and so on), and it knows what type of evidence is needed to fill this hole.

Each hole corresponds to a subgoal, and the proof is finished when there are no more subgoals. At this point, the evidence we've built is stored in the global context (i.e. Lean's environment that it uses for type-checking) under the name given in the theorem command.

Tactic proofs are convenient, but they are not essential in Lean: in principle, we can always just construct the required evidence by hand. Then we can write a proof term directly following a := (instead of writing by and then tactics) to introduce a global name for this evidence.

theorem even_4''' : Even 4 := Even.succ_succ 2 (Even.succ_succ 0 Even.zero)

10.2. Quantifiers, Implications, Functions🔗

In Lean's computational universe (where data structures and programs live), there are two sorts of values that have arrows in their types: constructors introduced by inductively defined data types, and functions.

Similarly, in Lean's logical universe (where we carry out proofs), there are two ways of giving evidence for an implication: constructors introduced by inductively defined propositions, and... functions!

For example, consider this statement:

theorem even_plus4 (n : Nat) (h : Even n) : Even (n + 4) := n:Nath:Even n⊢ Even (n + 4) n:Nath:Even n⊢ Even (n + 2) n:Nath:Even n⊢ Even n All goals completed! 🐙

What is the proof object corresponding to even_plus4?

We're looking for an expression whose type is ∀ (n : Nat), Even n → Even (n + 4) — that is, a function that takes two arguments (one number and a piece of evidence) and returns a piece of evidence!

Here it is:

theorem even_plus4' : ∀ (n : Nat), Even n → Even (n + 4) := fun (n : Nat) => fun (h : Even n) => Even.succ_succ (n + 2) (Even.succ_succ n h)

Recall that fun n => blah means "the function that, given n, yields blah," and that Lean treats n + 4 and n + 2 + 2 as synonyms. Another equivalent way to write this definition is:

theorem even_plus4'' (n : Nat) (h : Even n) : Even (n + 4) := Even.succ_succ (n + 2) (Even.succ_succ n h) even_plus4'' : ∀ (n : Nat), Even n → Even (n + 4)#check (even_plus4'' : ∀ (n : Nat), Even n → Even (n + 4))

10.2.1. Dependency, Equivalence, and Proof Irrelevance🔗

When we view the proposition being proved by even_plus4 as a function type, one interesting point becomes apparent: The second argument's type, Even n, mentions the value of the first argument, n.

While such dependent types are not found in most mainstream programming languages, they can be quite useful in programming too, as the flurry of activity in the functional programming community over the past couple of decades (and recently, most notably Lean!) demonstrates. Dependent types sit at the "highest corner" of the Lambda Cube (see the Stlc chapter of Type Systems): types can depend on values in addition to other types.

Notice that both implication (→) and quantification (∀) correspond to functions on evidence. In fact, they are really the same thing: → is just a shorthand for a degenerate use of ∀ where there is no dependency, i.e., no need to give a name to the type on the left-hand side of the arrow:

   ∀ (x : Nat), Nat
=  ∀ (_ : Nat), Nat
=  Nat        → Nat

For example, consider this proposition:

def even_plus2 : Prop := ∀ (n : Nat), ∀ (Variable name `E` is not explicitly referenced. Hint: The binding can be removed (if unused) or named `_` (if used implicitly). Alternatively, prefix the name with `_` to silence this warning: [apply] _E Note: This linter can be disabled with `set_option linter.unusedVariables false`E : Even n), Even (n + 2)

A proof term inhabiting this proposition would be a function with two arguments: a number n and some evidence E that n is even. But the name E for this evidence is not used in the rest of the statement of even_plus2, so it's a bit silly to bother making up a name for it. We could write it like this instead, using the dummy identifier _ in place of a real name:

def even_plus2' : Prop := ∀ (n : Nat), ∀ (_ : Even n), Even (n + 2)

Or, equivalently, we can write it in a different, familiar way:

def even_plus2'' : Prop := ∀ (n : Nat), Even n → Even (n + 2)

In general, "P → Q" is just syntactic sugar for "∀ (_ : P), Q".

When we write theorem statements in Lean, we often will name the quantified evidence with a name often beginning with h:

theorem even_plus2_thm : ∀ (n : Nat) (Variable name `heven` is not explicitly referenced. Hint: The binding can be removed (if unused) or named `_` (if used implicitly). Alternatively, prefix the name with `_` to silence this warning: [apply] _heven Note: This linter can be disabled with `set_option linter.unusedVariables false`heven : Even n), Even (n + 2) := ⊢ ∀ (n : Nat), Even n → Even (n + 2) n:Nath:Even n⊢ Even (n + 2); n:Nath:Even n⊢ Even n; All goals completed! 🐙

And we will also put the names before the :, which saves needing to use intro:

theorem even_plus2_thm' (n : Nat) (heven : Even n) : Even (n + 2) := n:Natheven:Even n⊢ Even (n + 2) n:Natheven:Even n⊢ Even n; All goals completed! 🐙

All of these theorem statements are equivalent! When we write def, we are just writing down the statement — the type. When we write theorem, we are stating the type and then providing a witness after the := (either with by and tactics or directly with a term). We can even show the two definitions are equivalent in Lean itself:

theorem even_plus2_defs_same : even_plus2 = even_plus2'' := ⊢ even_plus2 = even_plus2'' All goals completed! 🐙

Remember that theorem statements are just types, so rfl here is just comparing two types.

What about the two theorems? Here, we are asking if two proofs — which we now know are both functions — are equal. Then, do we need to use funext?

theorem even_plus2_theorems_same : even_plus2_thm = even_plus2_thm' := ⊢ even_plus2_thm = even_plus2_thm' All goals completed! 🐙

Surprisingly, we don't. This is because Lean has a special feature called definitional proof irrelevance. It says that any two proofs of the same proposition are definitionally equal. So we could write the same proof again however we wanted— with different tactics, using terms instead of tactics, etc.— and we would still have "the same theorem."

theorem even_plus2_thm'' (n : Nat) (heven : Even n) : Even (n + 2) := n:Natheven:Even n⊢ Even (n + 2) All goals completed! 🐙 theorem even_plus2_theorems_still_same : even_plus2_thm = even_plus2_thm'' := ⊢ even_plus2_thm = even_plus2_thm'' All goals completed! 🐙

10.4. Building Proof Objects Incrementally (Optional)🔗

As you probably noticed while solving the exercises earlier in the chapter, constructing proof objects is more involved than constructing the corresponding tactic proofs. Fortunately, there's a simple trick to help in the construction: we can use the term sorry as placeholder of any type we like.

As an example, let's walk through the process of constructing a proof object demonstrating the evenness of 8.

theorem even_8_atmpt_1 : Even 8 := sorry

Maybe we can use Even.succ_succ to construct a term of type Even 8? Recall that Even.succ_succ is of type

∀ (n : Nat), Even n → Even (n + 2)

If we can demonstrate that 6 is even, we should be done.

theorem even_8_atmpt_2 : Even 8 := Even.succ_succ 6 sorry

In the attempt above, we've omitted the proofs that 6 is even, but it can easily be constructed following the same procedure:

theorem even_8_atmpt_3 : Even 8 := Even.succ_succ 6 (Even.succ_succ 4 sorry) theorem even_8_atmpt_4 : Even 8 := Even.succ_succ 6 (Even.succ_succ 4 (Even.succ_succ 2 sorry)) theorem even_8_atmpt_5 : Even 8 := Even.succ_succ 6 (Even.succ_succ 4 (Even.succ_succ 2 (Even.succ_succ 0 Even.zero)))

To recap, we've been guided by an informal proof that we have in our minds, and we check the high level details before completing the intricacies of the proof. The sorry term allows us to do this.

10.5. Practical Uses of Terms in Proofs🔗

In the Even examples, we show how to build proofs using terms to illustrate that they are one and they same. But in this particular example, doing so is impractical: the proof terms above are verbose and arguably harder to write and follow than a tactic proof, which is more aligned with most people's style of reasoning. So the question naturally arises- would we ever use terms in real Lean proofs? The answer is yes, and we show some examples where such use is both helpful and actively encouraged in real Lean developments.

Here are some of the places where terms most often appear in Lean proofs:

  1. rfl: The term rfl is used very often as a full proof instead of by rfl (which references the tactic rfl of the same name) and is even preferred in Lean's Mathlib, which writes its @[simp] definitional lemmas this way.

theorem two_add_two : 2 + 2 = 4 := rfl @[simp] theorem length_cons {α : Type} (x : α) (xs : List α) : (x :: xs).length = xs.length + 1 := rfl

  1. To succinctly apply an existing lemma, possibly via dot notation on proofs

theorem add_comm_flip (a b : Nat) : b + a = a + b := Nat.add_comm b a theorem le_chain {a b c : Nat} (h₁ : a ≤ b) (h₂ : b ≤ c) : a ≤ c := Nat.le_trans h₁ h₂

  1. Within anonymous constructors and projections for And (∧), Iff (↔), and Exists (∃)

theorem and_swap {P Q : Prop} (h : P ∧ Q) : Q ∧ P := ⟨h.2, h.1⟩ theorem iff_swap {P Q : Prop} (h : P ↔ Q) : Q ↔ P := ⟨h.2, h.1⟩ theorem exists_double : ∃ n, n + n = 4 := ⟨2, rfl⟩

  1. fun for implications (as in even_plus4')

theorem imp_trans {P Q R : Prop} (hpq : P → Q) (hqr : Q → R) : P → R := fun hp => hqr (hpq hp)

  1. Proof fields of structures/instances (as in Typeclasses' Monoid laws)

structure PosNat where val : Nat pos : 0 < val def three : PosNat where val := 3 pos := Nat.succ_pos 2

Using terms in proofs can be more succinct and more useful than writing out tactics. Try out using terms like rfl directly in your proofs in this book and see what you discover.

10.6. Logical Connectives as Inductive Types🔗

We have already seen how tactics are not "special" in Lean: they are just manipulators of terms. Recall that Lean's logical connectives are also not "special:" only universal quantification (with implication as a special case) is built into Lean; all the others are defined inductively. Now that we know more about the relationship between terms and tactics, we can delve further into more advanced ways to work with logical connectives. Let's see how.

10.6.1. Conjunction🔗

To prove that P ∧ Q holds, we must present evidence for both P and Q. Thus, it makes sense to define a proof object for P ∧ Q to consist of a pair of two proofs: one for P and another one for Q. This leads to the following definition.

structure And (P Q : Prop) : Prop where intro :: left : P right : Q

Now that we have pulled back the covers a bit further, we can reveal another fact: a structure is just an inductive type with one constructor and whose fields have names. By default, the constructor is called mk, which we can rename to <name> using <name> ::, as in the example.

We can also see that this definition of And matches core And exactly: a structure with constructor intro and fields left/right (except that core uses a and b instead of P Q).

10.6.3. Existential Quantification🔗

To give evidence for an existential quantifier, we package a witness x together with a proof that x satisfies the property P:

inductive Exists {α : Type} (P : α → Prop) : Prop where | intro : ∀ (w : α), P w → Exists P

This probably needs a little unpacking. The core definition is for a type former Exists that can be used to build propositions of the form Exists P, where P itself is a function from witness values in the type α to propositions. The Exists.intro constructor then offers a way of constructing evidence for Exists p, given a witness w and a proof of P w.

The notation in the standard library is a slight extension of the above, enabling syntactic forms such as ∃ x y, P x y. The standard library's Exists also takes P implicitly.

The more familiar form ∃ x, Even x desugars to an expression involving Exists:

∃ n, Even n : Prop#check (Exists (fun n => Even n) : Prop) 
∃ n, Even n : Prop

Here's how to define an explicit proof object involving Exists:

theorem some_nat_is_even : ∃ n, Even n := Exists.intro 4 (Even.succ_succ 2 (Even.succ_succ 0 Even.zero))

False is equally simple — indeed, so simple it may look syntactically wrong at first glance!

inductive False : Prop

That is, False is an inductive type with no constructors — i.e., no way to build evidence for it. For example, there is no way to complete the following definition such that it succeeds.

theorem contra : False := Type mismatch True.intro has type True but is expected to have type FalseTrue.intro

But it is possible to destruct False by pattern matching. There can be no patterns that match it, since it has no constructors. To handle this, Lean uses the nomatch construct.

theorem false_implies_zero_eq_one : False → 0 = 1 := fun contra => nomatch contra

Since there are no branches to evaluate, the nomatch expression can be given any type we want, including 0 = 1. Fortunately, it's impossible to ever cause the nomatch to be evaluated, because we can never construct a value of type False to pass to the function.

10.7. Equality🔗

Even Lean's equality relation is not built in. We can define it ourselves:

inductive Eq {α : Type} : α → α → Prop where | refl : ∀ (x : α), Eq x x scoped infix:50 " =' " => Eq

The way to think about this definition (which mirrors the standard library's) is that, given a set α, it defines a family of propositions "x is equal to y," parameterized by x and indexed by y from α. There is just one way of constructing evidence for members of this family: applying the constructor Eq.refl to a type α and a single value x : α, which yields evidence that x is equal to x.

Other types of the form Eq x y where x and y are not the same are thus uninhabited.

We can use Eq.refl to construct evidence that, for example, 2 = 2. Can we also use it to construct evidence that 1 + 1 = 2? Yes, we can. Indeed, it is the very same piece of evidence!

The reason is that Lean treats as "the same" any two terms that are convertible according to a simple set of computation rules.

These rules, which are similar to those used by #eval, include evaluation of function application, inlining of definitions, and simplification of matches.

10.8. Lean's Trusted Computing Base🔗

One question that arises with any automated proof assistant is "why should we trust it?" — i.e., what if there is a bug in the implementation that renders all its reasoning suspect?

While it is impossible to allay such concerns completely, the fact that Lean is based on the Curry-Howard correspondence gives it a strong foundation. Because propositions are just types and proofs are just terms, checking that an alleged proof of a proposition is valid just amounts to type-checking the term. Type checkers are relatively small and straightforward programs, so the "trusted computing base" for Lean — the part of the code that we have to believe is operating correctly — is small too.

How, then, does Lean relegate its large set of complex behaviors to a small codebase?

Lean is organized in two layers. The elaborator is large and complicated: it handles notation, implicit arguments, match, recursion, and tactics. Its output is a plain term in Lean's core type theory, which it hands to the kernel. Only the kernel is trusted. It is small, and its job is just to type-check that term, computing as needed to decide whether two types are the same.

This division means that a bug in the elaborator, or in a tactic, cannot lead Lean to accept a false theorem: at worst, it produces a term that the kernel then rejects. Every declaration, whether written as a term or built by tactics, is checked by the kernel when it is added to the environment.

Two checks you might expect a typechecker to perform, exhaustiveness of match and termination of recursive functions, happen in the elaborator, because the kernel's language actually has no match and no recursion at all. The kernel's language for destructuring values only has the notion of a recursor: a primitive function that is exhaustive and terminating by construction. If the elaborator cannot express a definition in terms of the recursors generated by the kernel, it rejects the definition.

There are some mild exceptions to this, like partial def, but those exceptions have strict rules imposed upon them to prevent a proof of False, and in general it is the translation to recursors that catches such bugs.

We can see the elaborator refuse definitions that would otherwise let us prove False:

theorem or_bogus : ∀ (P Q : Prop), P ∨ Q → P := fun (P Q : Prop) (A : P ∨ Q) => Missing cases: (Or.inr _)match A with | Or.inl h => h

All the types here match correctly, but the match only considers one of the possible constructors for Or. Lean's exhaustiveness check will reject this definition.

def infinite_loop {α : Type} (n : Nat) : α := infinite_loop n cannot use specified measure for structural recursion: it is unchanged in the recursive callstermination_by structural n theorem falso : False := Type mismatch infinite_loop 0 has type ?m.1 of sort `Type` but is expected to have type False of sort `Prop`infinite_loop 0

Recursive function infinite_loop purports to return a value of any type α that you would like. (The termination_by structural n annotation tells Lean that it recurses on argument n, not α.) Were Lean to allow infinite_loop, then falso would be definable, thus giving evidence for False. So Lean rejects infinite_loop.

Besides the kernel, we also trust the handful of axioms Lean assumes, such as propext. The command #print axioms shows which axioms a theorem depends on. The tactic native_decide goes further, trusting Lean's compiler too, which is why careful developments avoid it.

10.10. Working with Proof Irrelevance🔗

In Logic we saw that functional extensionality (funext) is a core property of Lean. A similar notion about propositions also exists in a Lean, this time as a core axiom:

-- Written out, propositional extensionality looks like this: def propositional_extensionality : Prop := ∀ (P Q : Prop), (P ↔ Q) → P = Q -- Lean calls it `propext`: propext {a b : Prop} : (a ↔ b) → a = b#check propext 
propext {a b : Prop} : (a ↔ b) → a = b

Propositional extensionality asserts that if two propositions are equivalent — i.e., each implies the other — then they are in fact equal. The proof objects for the propositions might be syntactically different terms. But propositional extensionality overlooks that, just as functional extensionality overlooks the syntactic differences between functions.
