5+--  # ProofObjects: The Curry-Howard Correspondence
6+
7+--  This setting is enabled to make some tricky mistakes harder to make.
8+
9+set_option autoImplicit false
10+
11+--  "Algorithms are the computational content of proofs." (Robert Harper)
12+
13+--  We have seen that Lean has mechanisms both for *programming*, using
14+--  inductive data types like `Nat` or `List` and functions over these
15+--  types, and for *proving* properties of these programs, using inductive
16+--  propositions (like `Even`), implication, universal quantification, and
17+--  the like. So far, we have mostly treated these mechanisms as if they
18+--  were quite separate, and for many purposes this is a good way to think.
19+--  But we have also seen hints that Lean's programming and proving
20+--  facilities are closely related. For example, the keyword `inductive` is
21+--  used to declare both data types and propositions, and `→` is used both
22+--  to describe the type of functions on data and logical implication. This
23+--  is not just a syntactic accident! In fact, programs and proofs in Lean
24+--  are almost the same thing. In this chapter we will study this
25+--  connection in more detail.
26+--
27+--  We have already seen the fundamental idea: provability in Lean is
28+--  always witnessed by *evidence*. When we construct the proof of a basic
29+--  proposition, we are actually building a tree of evidence, which can be
30+--  thought of as a concrete data structure.
31+--
32+--  If the proposition is an implication like `A → B`, then its proof is an
33+--  evidence *transformer*: a recipe for converting evidence for A into
34+--  evidence for B. So at a fundamental level, proofs are simply programs
35+--  that manipulate evidence.
36+--
37+--  Question: If evidence is data, what are propositions themselves?
38+--
39+--  Answer: They are types!
40+--
41+--  Look again at the formal definition of the `Even` property. For
42+--  illustrative purposes, we've made the implicit argument `{n : Nat}` to
43+--  `Even.succ_succ` explicit.
44+
45+namespace EvenProp
46+inductive Even : Nat → Prop where
47+  | zero : Even 0
48+  | succ_succ (n : Nat) (h : Even n) : Even (n + 2)
49+
50+--  We can pronounce the ":" here as either "has type" or "is a proof of."
51+--  For example, the second line in the definition of `Even` declares that
52+--  `(Even.zero : Even 0)`. Instead of "`Even.zero` has type `Even 0`," we
53+--  can say that "`Even.zero` is a proof of `Even 0`."
54+--
55+--  This pun between types and propositions — between `:` as "has type" and
56+--  `:` as "is a proof of" or "is evidence for" — is called the
57+--  *Curry-Howard correspondence*. It proposes a deep connection between
58+--  the world of logic and the world of computation:
59+--
60+--      propositions  ~  types
61+--      proofs        ~  programs
62+--
63+--  See Wadler (2015) for a brief history and modern exposition.
64+--
65+--  Many useful insights follow from this connection. To begin with, it
66+--  gives us a natural interpretation of the type of the `Even.succ_succ`
67+--  constructor.
68+--
69+--  The type of `Even.succ_succ` says that it is a *function* (better: a
70+--  data *constructor*) taking two arguments (one number `n` plus evidence
71+--  for `Even n`) and returning evidence that `n + 2` is even.
72+
73+#check @Even.succ_succ
74+
75+--  Output:
76+--    Even.succ_succ : ∀ (n : Nat), Even n → Even (n + 2)
77+
78+--  This can be read "`Even.succ_succ` is a constructor that takes two
79+--  arguments — a number `n` and evidence for the proposition `Even n` —
80+--  and yields evidence for the proposition `Even (n + 2)`."
81+--
82+--  Now let's look again at an earlier proof involving `Even`.
83+
84+theorem even_4 : Even 4 := by
85+  apply Even.succ_succ
86+  apply Even.succ_succ
87+  apply Even.zero
88+
89+--  Just as with ordinary data values and functions, we can use the
90+--  `#print` command to see the *proof object* that results from this proof
91+--  script.
92+
93+#print even_4
94+
95+--  Output:
96+--    theorem EvenProp.even_4 : Even 4 :=
97+--    Even.succ_succ 2 (Even.succ_succ 0 Even.zero)
98+
99+--  Indeed, we can also write down this proof object directly, with no need
100+--  for a proof script at all:
101+
102+#check (Even.succ_succ 2 (Even.succ_succ 0 Even.zero)
103+  : Even (2 + 2))
104+
105+--  Output:
106+--    Even.succ_succ 2 (Even.succ_succ 0 Even.zero) : Even (2 + 2)
107+
108+--  The expression `Even.succ_succ 2 (Even.succ_succ 0 Even.zero)`
109+--  instantiates the parameterized constructor `Even.succ_succ` with the
110+--  specific arguments `2` and `0` plus the corresponding proof objects for
111+--  its premises `Even 2` and `Even 0`. Alternatively, we can think of
112+--  `Even.succ_succ` as a primitive "evidence constructor" that, when
113+--  applied to a particular number, wants to be further applied to evidence
114+--  that this number is even; its type,
115+--
116+--      ∀ (n : Nat), Even n → Even (n + 2)
117+--
118+--  expresses this functionality, in the same way that the polymorphic type
119+--  `{α : Type} → List α` expresses the fact that the constructor
120+--  `List.nil` can be thought of as a function from types to empty lists
121+--  with elements of that type.
122+--
123+--  The fact that the some arguments are implicit, like `{α}` of `List` and
124+--  `{n}` of the real `Even.succ_succ`, actually doesn't make a difference
125+--  at all: `List` is still taking one argument, and `Even.succ_succ` is
126+--  still taking two. Implicit arguments are just a usability feature that
127+--  tells Lean to figure some arguments out when we apply a definition
128+--  (like `Even.succ_succ`) to an explicit argument (like a proof of
129+--  `Even n`). In this case, since `Even n` contains `n`, we don't need to
130+--  pass `n` in to begin with, and can mark it as implicit with the curly
131+--  braces as `{n}`.
132+--
133+--  We saw in the Logic chapter that we can use function application syntax
134+--  to instantiate universally quantified variables in lemmas, as well as
135+--  to supply evidence for assumptions that these lemmas impose. For
136+--  instance:
137+
138+theorem even_4' : Even 4 := by
139+  apply Even.succ_succ 2 (Even.succ_succ 0 Even.zero)

141+--  ## Proof Scripts
142+
143+--  The *proof objects* we've been discussing lie at the core of how Lean
144+--  operates. When Lean is following a proof script, what is happening
145+--  internally is that it is gradually constructing a proof object — a term
146+--  whose type is the proposition being proved. All the tactics following
147+--  `by` tell it how to build up a term of the required type. To see this
148+--  process in action, we provide a `show_proof` command to display the
149+--  current state of the proof tree at various points in the following
150+--  tactic proof.
151+--
152+--  `show_proof` wraps a tactic script and prints the partial proof term —
153+--  a term with *holes* where the remaining proof obligations are — before
154+--  and after each step. A term's holes are shown as `?_`.
155+
156+--  THE FOLLOWING DETAILS CAN BE SKIPPED (Tactic: show_proof)
157+section ShowProof
158+open Lean Elab Tactic Meta
159+
160+/-- Like `instantiateMVars`, but also substitutes holes
161+whose assignment Lean delays until they are complete
162+(e.g., the body under an `intro`). -/
163+partial def instantiatePartial (e : Expr) : MetaM Expr := do
164+  let e ← instantiateMVars e
165+  transform e (pre := fun e => do
166+    let .mvar m := e.getAppFn | return .continue
167+    let some d ← getDelayedMVarAssignment? m
168+      | return .continue
169+    let v ← instantiatePartial (mkMVar d.mvarIdPending)
170+    let args := e.getAppArgs
171+    let n := d.fvars.size
172+    let v :=
173+      (v.abstract d.fvars).instantiateRevRange 0 n args
174+    return .done (mkAppN v args[n:]))
175+
176+/-- `show_proof tac₁ … tacₙ` runs the tactics in order,
177+printing the partial proof term (with `?_` for unfilled
178+holes) before the first tactic and after each one. -/
179+elab "show_proof" seq:tacticSeq : tactic => do
180+  let root ← getMainGoal
181+  let s := seq.raw[0]
182+  let tacs :=
183+    if s.getKind == ``Parser.Tactic.tacticSeqBracketed then
184+      s[1].getSepArgs
185+    else s[0].getSepArgs
186+  let render : TacticM Format := do
187+    let e ← instantiatePartial (mkMVar root)
188+    withOptions
189+      (fun o => (o.setBool `pp.mvars false).setBool
190+        `pp.fieldNotation false)
191+      (ppExpr e)
192+  let mut out ← render
193+  for t in tacs do
194+    evalTactic t
195+    let tac ← PrettyPrinter.ppTactic ⟨t⟩
196+    out := out ++ .line ++ .line ++ f!"after {tac}:" ++
197+      .nest 2 (.line ++ (← render))
198+  logInfo m!"{out}"
199+
200+end ShowProof

275+--  ## Quantifiers, Implications, Functions
276+
277+--  In Lean's computational universe (where data structures and programs
278+--  live), there are two sorts of values that have arrows in their types:
279+--  *constructors* introduced by `inductive`ly defined data types, and
280+--  *functions*.
281+--
282+--  Similarly, in Lean's logical universe (where we carry out proofs),
283+--  there are two ways of giving evidence for an implication: constructors
284+--  introduced by `inductive`ly defined propositions, and... functions!
285+--
286+--  For example, consider this statement:
287+
288+theorem even_plus4 (n : Nat) (h : Even n) :
289+    Even (n + 4) := by
290+  apply Even.succ_succ
291+  apply Even.succ_succ
292+  apply h
293+
294+--  What is the proof object corresponding to `even_plus4`?
295+--
296+--  We're looking for an expression whose *type* is
297+--  `∀ (n : Nat), Even n → Even (n + 4)` — that is, a *function* that takes
298+--  two arguments (one number and a piece of evidence) and returns a piece
299+--  of evidence!
300+--
301+--  Here it is:
302+
303+theorem even_plus4' : ∀ (n : Nat), Even n → Even (n + 4) :=
304+  fun (n : Nat) => fun (h : Even n) =>
305+    Even.succ_succ (n + 2) (Even.succ_succ n h)
306+
307+--  Recall that `fun n => blah` means "the function that, given `n`, yields
308+--  `blah`," and that Lean treats `n + 4` and `n + 2 + 2` as synonyms.
309+--  Another equivalent way to write this definition is:
310+
311+theorem even_plus4'' (n : Nat) (h : Even n) :
312+    Even (n + 4) :=
313+  Even.succ_succ (n + 2) (Even.succ_succ n h)
314+
315+#check (even_plus4'' : ∀ (n : Nat), Even n → Even (n + 4))
316+
317+--  ### Dependency, Equivalence, and Proof Irrelevance
318+
319+--  When we view the proposition being proved by `even_plus4` as a function
320+--  type, one interesting point becomes apparent: The second argument's
321+--  type, `Even n`, mentions the *value* of the first argument, `n`.
322+--
323+--  While such *dependent types* are not found in most mainstream
324+--  programming languages, they can be quite useful in programming too, as
325+--  the flurry of activity in the functional programming community over the
326+--  past couple of decades (and recently, most notably Lean!) demonstrates.
327+--  Dependent types sit at the "highest corner" of the Lambda Cube (see the
328+--  `Stlc` chapter of *Type Systems*): types can depend on *values* in
329+--  addition to other types.
330+--
331+--  Notice that both implication (`→`) and quantification (`∀`) correspond
332+--  to functions on evidence. In fact, they are really the same thing: `→`
333+--  is just a shorthand for a degenerate use of `∀` where there is no
334+--  dependency, i.e., no need to give a name to the type on the left-hand
335+--  side of the arrow:
336+--
337+--         ∀ (x : Nat), Nat
338+--      =  ∀ (_ : Nat), Nat
339+--      =  Nat        → Nat
340+--
341+--  For example, consider this proposition:
342+
343+def even_plus2 : Prop :=
344+  ∀ (n : Nat), ∀ (E : Even n), Even (n + 2)
345+
346+--  A proof term inhabiting this proposition would be a function with two
347+--  arguments: a number `n` and some evidence `E` that `n` is even. But the
348+--  name `E` for this evidence is not used in the rest of the statement of
349+--  `even_plus2`, so it's a bit silly to bother making up a name for it. We
350+--  could write it like this instead, using the dummy identifier `_` in
351+--  place of a real name:
352+
353+def even_plus2' : Prop :=
354+  ∀ (n : Nat), ∀ (_ : Even n), Even (n + 2)
355+
356+--  Or, equivalently, we can write it in a different, familiar way:
357+
358+def even_plus2'' : Prop :=
359+  ∀ (n : Nat), Even n → Even (n + 2)
360+
361+--  In general, "`P → Q`" is just syntactic sugar for "`∀ (_ : P), Q`".
362+--
363+--  When we write theorem statements in Lean, we often *will* name the
364+--  quantified evidence with a name often beginning with `h`:
365+
366+theorem even_plus2_thm :
367+  ∀ (n : Nat) (heven : Even n), Even (n + 2) := by
368+    intro n h; constructor; assumption
369+
370+--  And we will also put the names before the `:`, which saves needing to
371+--  use `intro`:
372+
373+theorem even_plus2_thm' (n : Nat) (heven : Even n) :
374+    Even (n + 2) := by
375+    constructor; assumption
376+
377+--  *All* of these theorem statements are equivalent! When we write `def`,
378+--  we are just writing down the statement — the type. When we write
379+--  `theorem`, we are stating the type and then providing a witness after
380+--  the `:=` (either with `by` and tactics or directly with a term). We can
381+--  even show the two definitions are equivalent in Lean itself:
382+
383+theorem even_plus2_defs_same :
384+    even_plus2 = even_plus2'' := by rfl
385+
386+--  Remember that theorem statements are just types, so `rfl` here is just
387+--  comparing two types.
388+--
389+--  What about the two theorems? Here, we are asking if two *proofs* —
390+--  which we now know are both *functions* — are equal. Then, do we need to
391+--  use `funext`?
392+
393+theorem even_plus2_theorems_same :
394+    even_plus2_thm = even_plus2_thm' := by rfl
395+
396+--  Surprisingly, we don't. This is because Lean has a special feature
397+--  called *definitional proof irrelevance*. It says that any two proofs of
398+--  the same proposition are definitionally equal. So we could write the
399+--  same proof again however we wanted— with different tactics, using terms
400+--  instead of tactics, etc.— and we would still have "the same theorem."
401+
402+theorem even_plus2_thm'' (n : Nat) (heven : Even n) :
403+    Even (n + 2) := by
404+    exact Even.succ_succ n heven
405+
406+theorem even_plus2_theorems_still_same :
407+  even_plus2_thm = even_plus2_thm'' := by rfl
408+

507+--  the corresponding tactic proofs. Fortunately, there's a simple trick to
508+--  help in the construction: we can use the *term* `sorry` as placeholder
509+--  of any type we like.
510+--
511+--  As an example, let's walk through the process of constructing a proof
512+--  object demonstrating the evenness of `8`.
513+
514+theorem even_8_atmpt_1 : Even 8 := sorry
515+
516+--  Maybe we can use `Even.succ_succ` to construct a term of type `Even 8`?
517+--  Recall that `Even.succ_succ` is of type
518+--
519+--      ∀ (n : Nat), Even n → Even (n + 2)
520+--
521+--  If we can demonstrate that `6` is even, we should be done.
522+
523+theorem even_8_atmpt_2 : Even 8 := Even.succ_succ 6 sorry
524+
525+--  In the attempt above, we've omitted the proofs that `6` is even, but it
526+--  can easily be constructed following the same procedure:
527+
528+theorem even_8_atmpt_3 : Even 8 :=
529+  Even.succ_succ 6 (Even.succ_succ 4 sorry)
530+
531+theorem even_8_atmpt_4 : Even 8 :=
532+  Even.succ_succ 6 (Even.succ_succ 4
533+    (Even.succ_succ 2 sorry))
534+
535+theorem even_8_atmpt_5 : Even 8 :=
536+  Even.succ_succ 6 (Even.succ_succ 4
537+    (Even.succ_succ 2 (Even.succ_succ 0 Even.zero)))
538+
539+--  To recap, we've been guided by an informal proof that we have in our
540+--  minds, and we check the high level details before completing the
541+--  intricacies of the proof. The `sorry` term allows us to do this.
542+
543+end IncrementalProofObjects

545+--  ## Practical Uses of Terms in Proofs
546+
547+--  In the `Even` examples, we show how to build proofs using terms to
548+--  illustrate that they are one and they same. But in this particular
549+--  example, doing so is impractical: the proof terms above are verbose and
550+--  arguably harder to write and follow than a tactic proof, which is more
551+--  aligned with most people's style of reasoning. So the question
552+--  naturally arises- would we ever use terms in *real* Lean proofs? The
553+--  answer is yes, and we show some examples where such use is both helpful
554+--  and actively encouraged in real Lean developments.
555+--
556+--  Here are some of the places where terms most often appear in Lean
557+--  proofs:
558+--  1. `rfl`: The *term* `rfl` is used very often as a full proof instead
559+--     of `by rfl` (which references the *tactic* `rfl` of the same name)
560+--     and is even preferred in Lean's Mathlib, which writes its `@[simp]`
561+--     definitional lemmas this way.
562+
563+theorem two_add_two : 2 + 2 = 4 := rfl
564+
565+@[simp]
566+theorem length_cons {α : Type} (x : α) (xs : List α) :
567+    (x :: xs).length = xs.length + 1 := rfl
568+
569+--  2. To succinctly apply an existing lemma, possibly via dot notation on
570+--     proofs
571+
572+theorem add_comm_flip (a b : Nat) : b + a = a + b := Nat.add_comm b a
573+theorem le_chain {a b c : Nat} (h₁ : a ≤ b) (h₂ : b ≤ c) : a ≤ c :=
574+  Nat.le_trans h₁ h₂
575+
576+--  3. Within anonymous constructors and projections for `And` (`∧`), `Iff`
577+--     (`↔`), and `Exists` (`∃`)
578+
579+theorem and_swap {P Q : Prop} (h : P ∧ Q) : Q ∧ P := ⟨h.2, h.1⟩
580+theorem iff_swap {P Q : Prop} (h : P ↔ Q) : Q ↔ P := ⟨h.2, h.1⟩
581+theorem exists_double : ∃ n, n + n = 4 := ⟨2, rfl⟩
582+
583+--  4. `fun` for implications (as in `even_plus4'`)
584+
585+theorem imp_trans {P Q R : Prop} (hpq : P → Q) (hqr : Q → R) :
586+    P → R :=
587+  fun hp => hqr (hpq hp)
588+
589+--  5. Proof fields of structures/instances (as in Typeclasses' Monoid
590+--     laws)
591+
592+structure PosNat where
593+  val : Nat
594+  pos : 0 < val
595+def three : PosNat where
596+  val := 3
597+  pos := Nat.succ_pos 2
598+
599+--  Using terms in proofs can be more succinct and more useful than writing
600+--  out tactics. Try out using terms like `rfl` directly in your proofs in
601+--  this book and see what you discover.

603+--  ## Logical Connectives as Inductive Types
604+
605+--  We have already seen how tactics are not "special" in Lean: they are
606+--  just manipulators of terms. Recall that Lean's logical connectives are
607+--  also not "special:" only universal quantification (with implication as
608+--  a special case) is built into Lean; all the others are defined
609+--  inductively. Now that we know more about the relationship between terms
610+--  and tactics, we can delve further into more advanced ways to work with
611+--  logical connectives. Let's see how.
612+
613+namespace Props
614+
615+--  ### Conjunction
616+
617+--  To prove that `P ∧ Q` holds, we must present evidence for both `P` and
618+--  `Q`. Thus, it makes sense to define a proof object for `P ∧ Q` to
619+--  consist of a pair of two proofs: one for `P` and another one for `Q`.
620+--  This leads to the following definition.
621+
622+namespace AndPlayground
623+
624+structure And (P Q : Prop) : Prop where
625+  intro ::
626+  left : P
627+  right : Q
628+
629+--  Now that we have pulled back the covers a bit further, we can reveal
630+--  another fact: a `structure` is just an inductive type with one
631+--  constructor and whose fields have names. By default, the constructor is
632+--  called `mk`, which we can rename to `<name>` using `<name> ::`, as in
633+--  the example.
634+--
635+--  We can also see that this definition of `And` matches core `And`
636+--  exactly: a `structure` with constructor `intro` and fields
637+--  `left`/`right` (except that core uses `a` and `b` instead of `P` `Q`).
638+
639+#print _root_.And
640+
641+--  Output:
642+--    structure _root_.And (a b : Prop) : Prop
643+--    number of parameters: 2
644+--    fields:
645+--      _root_.And.left : a
646+--      _root_.And.right : b
647+--    constructor:
648+--      _root_.And.intro {a b : Prop} (left : a) (right : b) : a ∧ b
649+
650+--  Notice the similarity with the definition of the `MyProd` type, given
651+--  in chapter Poly; the only difference is that `MyProd` takes `Type`
652+--  arguments, whereas `And` takes `Prop` arguments.
653+
654+#print MyProd
655+
656+--  Output:
657+--    structure MyProd (α β : Type) : Type
658+--    number of parameters: 2
659+--    fields:
660+--      MyProd.fst : α
661+--      MyProd.snd : β
662+--    constructor:
663+--      MyProd.mk {α β : Type} (fst : α) (snd : β) : MyProd α β
664+
665+--  This similarity should clarify why `cases`, `obtain` `⟨hp, hq⟩`, and
666+--  `intro` `⟨hp, hq⟩` patterns can be used on a conjunctive hypothesis.
667+--  Case analysis allows us to consider all possible ways in which `P ∧ Q`
668+--  was proved — here just one (the `And.intro` constructor).
669+
670+theorem proj1' (P Q : Prop) (hpq : And P Q) : P := by
671+    cases hpq with
672+    | intro hp _ => exact hp
673+
674+theorem and_comm (P Q : Prop) : And P Q ↔ And Q P := by
675+  constructor
676+  · intro h
677+    obtain ⟨hp, hq⟩ := h
678+    constructor
679+    · exact hq
680+    · exact hp
681+  · intro h
682+    obtain ⟨hq, hp⟩ := h
683+    constructor
684+    · exact hp
685+    · exact hq
686+
687+end AndPlayground
688+
689+--  This shows why the inductive (structure) definition of `And` can be
690+--  manipulated by tactics as we've been doing. We can also use it to build
691+--  proofs directly, using pattern-matching. For instance:
692+
693+theorem proj1'' (P Q : Prop) (hpq : P ∧ Q) : P :=
694+  match hpq with
695+  | And.intro hp _ => hp
696+
697+theorem and_comm'_aux (P Q : Prop) (h : P ∧ Q) : Q ∧ P :=
698+  match h with
699+  | And.intro hp hq => And.intro hq hp
700+
701+theorem and_comm' (P Q : Prop) : P ∧ Q ↔ Q ∧ P :=
702+  Iff.intro (and_comm'_aux P Q) (and_comm'_aux Q P)
703+
704+--  Here, `Iff.intro` is doing exactly the same thing as `And.intro`; it
705+--  builds the `Iff` `structure` with its two arguments.

971+--  ## Equality
972+
973+namespace EqualityPlayground
974+
975+--  Even Lean's equality relation is not built in. We can define it
976+--  ourselves:
977+
978+inductive Eq {α : Type} : α → α → Prop where
979+  | refl : ∀ (x : α), Eq x x
980+
981+scoped infix:50 " =' " => Eq
982+
983+--  The way to think about this definition (which mirrors the standard
984+--  library's) is that, given a set `α`, it defines a *family* of
985+--  propositions "`x` is equal to `y`," parameterized by `x` and indexed by
986+--  `y` from `α`. There is just one way of constructing evidence for
987+--  members of this family: applying the constructor `Eq.refl` to a type
988+--  `α` and a single value `x : α`, which yields evidence that `x` is equal
989+--  to `x`.
990+--
991+--  Other types of the form `Eq x y` where `x` and `y` are not the same are
992+--  thus uninhabited.
993+--
994+--  We can use `Eq.refl` to construct evidence that, for example, `2 = 2`.
995+--  Can we also use it to construct evidence that `1 + 1 = 2`? Yes, we can.
996+--  Indeed, it is the very same piece of evidence!
997+--
998+--  The reason is that Lean treats as "the same" any two terms that are
999+--  *convertible* according to a simple set of computation rules.
1000+--
1001+--  These rules, which are similar to those used by `#eval`, include
1002+--  evaluation of function application, inlining of definitions, and
1003+--  simplification of `match`es.
1004+--
1005+--  Lean terms are "the same" if they are *convertible* according to a
1006+--  simple set of computation rules: evaluation of function applications,
1007+--  inlining of definitions, and simplification of `match`es.
1008+
1009+theorem four : 2 + 2 =' 1 + 3 := by
1010+  apply Eq.refl
1011+
1012+--  The `rfl` tactic that we have used to prove equalities of the form
1013+--  `x = y` up to now is essentially just shorthand for `apply Eq.refl`.
1014+--
1015+--  In tactic-based proofs of equality, the conversion rules are normally
1016+--  hidden in uses of `simp` (either explicit or implicit in other tactics
1017+--  such as `rfl`).
1018+--
1019+--  But you can see them directly at work in the following explicit proof
1020+--  objects:
1021+
1022+theorem four' : 2 + 2 =' 1 + 3 :=
1023+  Eq.refl 4
1024+
1025+theorem singleton : ∀ (α : Type) (x : α),
1026+    [] ++ [x] =' x :: [] :=
1027+  fun (α : Type) (x : α) => Eq.refl [x]
1028+
1029+--  We can also pattern-match on an equality proof:
1030+
1031+theorem eq_add : ∀ (n1 n2 : Nat),
1032+    n1 =' n2 → (n1 + 1) =' (n2 + 1) :=
1033+  fun n1 n2 heq =>
1034+    match heq with
1035+    | Eq.refl _ => Eq.refl (n1 + 1)
1036+
1037+--  By pattern-matching against `n1 =' n2`, we replace `n2` with `n1` in
1038+--  the type we have to produce, so instead of `(n1 + 1) =' (n2 + 1)`, we
1039+--  now have to produce something of type `(n1 + 1) =' (n1 + 1)`, which we
1040+--  establish by `Eq.refl (n1 + 1)`.
1041+--
1042+--  A tactic-based proof runs into some difficulties if we try to use our
1043+--  usual repertoire of tactics, such as `rw` and `rfl`. Those work with
1044+--  relations that Lean knows about, such as `=`, but not with our `='`. We
1045+--  could teach Lean about `='` (by registering a reflexivity lemma for
1046+--  `rfl`, or by working in a *quotient type* where `='` becomes `=`, for
1047+--  `rw`), but a simpler way is to use `cases` and `apply` instead.
1048+
1049+sf_expect_failure_in
1050+  example (n1 n2 : Nat) (heq : n1 =' n2) :
1051+      (n1 + 1) =' (n2 + 1) := by
1052+    rw [heq] -- doesn't work for _our_ =' relation
1053+
1054+sf_expect_failure_in
1055+  example (n1 : Nat) : (n1 + 1) =' (n1 + 1) := by
1056+    rfl -- doesn't work for _our_ =' relation
1057+
1058+theorem eq_add' (n1 n2 : Nat) (heq : n1 =' n2) :
1059+    (n1 + 1) =' (n2 + 1) := by
1060+  cases heq -- n2 replaced by n1 in the goal!
1061+  apply Eq.refl
1062+

1152+--  ## Lean's Trusted Computing Base
1153+
1154+--  One question that arises with any automated proof assistant is "why
1155+--  should we trust it?" — i.e., what if there is a bug in the
1156+--  implementation that renders all its reasoning suspect?
1157+--
1158+--  While it is impossible to allay such concerns completely, the fact that
1159+--  Lean is based on the Curry-Howard correspondence gives it a strong
1160+--  foundation. Because propositions are just types and proofs are just
1161+--  terms, checking that an alleged proof of a proposition is valid just
1162+--  amounts to *type-checking* the term. Type checkers are relatively small
1163+--  and straightforward programs, so the "trusted computing base" for Lean
1164+--  — the part of the code that we have to believe is operating correctly —
1165+--  is small too.
1166+--
1167+--  How, then, does Lean relegate its large set of complex behaviors to a
1168+--  small codebase?
1169+--
1170+--  Lean is organized in two layers. The *elaborator* is large and
1171+--  complicated: it handles notation, implicit arguments, `match`,
1172+--  recursion, and tactics. Its output is a plain term in Lean's core type
1173+--  theory, which it hands to the *kernel*. Only the kernel is trusted. It
1174+--  is small, and its job is just to type-check that term, computing as
1175+--  needed to decide whether two types are the same.
1176+--
1177+--  This division means that a bug in the elaborator, or in a tactic,
1178+--  cannot lead Lean to accept a false theorem: at worst, it produces a
1179+--  term that the kernel then rejects. Every declaration, whether written
1180+--  as a term or built by tactics, is checked by the kernel when it is
1181+--  added to the environment.
1182+--
1183+--  Two checks you might expect a typechecker to perform, exhaustiveness of
1184+--  `match` and termination of recursive functions, happen in the
1185+--  elaborator, because the kernel's language actually has no `match` and
1186+--  no recursion at all. The kernel's language for destructuring values
1187+--  only has the notion of a *recursor*: a primitive function that is
1188+--  exhaustive and terminating by construction. If the elaborator cannot
1189+--  express a definition in terms of the recursors generated by the kernel,
1190+--  it rejects the definition.
1191+--
1192+--  There are some mild exceptions to this, like `partial def`, but those
1193+--  exceptions have strict rules imposed upon them to prevent a proof of
1194+--  `False`, and in general it is the translation to recursors that catches
1195+--  such bugs.
1196+--
1197+--  We can see the elaborator refuse definitions that would otherwise let
1198+--  us prove `False`:
1199+
1200+sf_expect_failure_in
1201+  theorem or_bogus : ∀ (P Q : Prop), P ∨ Q → P :=
1202+    fun (P Q : Prop) (A : P ∨ Q) =>
1203+      match A with
1204+      | Or.inl h => h
1205+
1206+--  All the types here match correctly, but the `match` only considers one
1207+--  of the possible constructors for `Or`. Lean's exhaustiveness check will
1208+--  reject this definition.
1209+
1210+sf_expect_failure_in
1211+  def infinite_loop {α : Type} (n : Nat) : α :=
1212+    infinite_loop n
1213+  termination_by structural n
1214+  
1215+  theorem falso : False := infinite_loop 0
1216+
1217+--  Recursive function `infinite_loop` purports to return a value of any
1218+--  type `α` that you would like. (The `termination_by structural n`
1219+--  annotation tells Lean that it recurses on argument `n`, not `α`.) Were
1220+--  Lean to allow `infinite_loop`, then `falso` would be definable, thus
1221+--  giving evidence for `False`. So Lean rejects `infinite_loop`.
1222+--
1223+--  Besides the kernel, we also trust the handful of *axioms* Lean assumes,
1224+--  such as `propext`. The command `#print axioms` shows which axioms a
1225+--  theorem depends on. The tactic `native_decide` goes further, trusting
1226+--  Lean's compiler too, which is why careful developments avoid it.
