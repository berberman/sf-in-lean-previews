53--- ## Decorated Programs
54-
55--- The beauty of Hoare Logic is that it is *syntax directed*: the structure of
56--- proofs exactly follows the structure of programs.
57-
58--- We can record the essential ideas of a Hoare-logic proof — omitting
59--- low-level calculational details — by "decorating" a program with
60--- appropriate assertions on each of its commands.
61-
62--- Such a *decorated program* carries within itself an argument for its own
63--- correctness.
64-
65--- For example, consider the program:
66-
67---   X := m;
68---   Z := p;
69---   while X <> 0 do
70---     Z := Z - 1;
71---     X := X - 1
72---   end
73-
74--- Here is one possible specification for this program, in the form of a Hoare
75--- triple:
76-
77---   {{ True }}
78---   X := m;
79---   Z := p;
80---   while X <> 0 do
81---     Z := Z - 1;
82---     X := X - 1
83---   end
84---   {{ Z = p - m }}
85-
86--- (Note the *parameters* `m` and `p`, which stand for fixed-but-arbitrary
87--- numbers. Formally, they are simply Lean variables of type `Nat`.)
88-
89--- Here is a decorated version of this program, embodying a proof of this
90--- specification:
91-
92---   {{ True }} ->>
93---   {{ m = m }}
94---     X := m
95---                        {{ X = m }} ->>
96---                        {{ X = m /\ p = p }};
97---     Z := p;
98---                        {{ X = m /\ Z = p }} ->>
99---                        {{ Z - X = p - m }}
100---     while X <> 0 do
101---                        {{ Z - X = p - m /\ X <> 0 }} ->>
102---                        {{ (Z - 1) - (X - 1) = p - m }}
103---       Z := Z - 1
104---                        {{ Z - (X - 1) = p - m }};
105---       X := X - 1
106---                        {{ Z - X = p - m }}
107---     end
108---   {{ Z - X = p - m /\ ~ (X <> 0) }} ->>
109---   {{ Z = p - m }}
110-
111--- Concretely, a decorated program consists of the program's text interleaved
112--- with assertions (sometimes multiple assertions separated by ->>).
113-
114--- A decorated program can be viewed as a compact representation of a proof in
115--- Hoare Logic: the assertions surrounding each command specify the Hoare
116--- triple to be proved for that part of the program using one of the Hoare
117--- Logic rules, and the structure of the program itself shows how to assemble
118--- all these individual steps into a proof for the whole program.
119-
120--- Our goal is to verify such decorated programs "mostly automatically." But,
121--- before we can verify anything, we need to be able to *find* a proof for a
122--- given specification, and for this we need to discover the right assertions.
123--- This can be done in an almost mechanical way, with the exception of finding
124--- loop invariants. In the remainder of this section, we explain in detail how
125--- to construct decorations for several short programs, all of which are loop
126--- free or have simple loop invariants. We'll return to finding more
127--- interesting loop invariants later in the chapter.
128-
129--- ### Example: Swapping
130-
131--- Consider the following program, which swaps the values of two variables
132--- using addition and subtraction, instead of by assigning to a temporary
133--- variable.
134-
135---   X := X + Y;
136---   Y := X - Y;
137---   X := X - Y
138-
139--- We can give a proof, in the form of decorations, that this program is
140--- correct — i.e., it really swaps `X` and `Y` — as follows.
141-
142---   (1)    {{ X = m /\ Y = n }} ->>
143---   (2)    {{ (X + Y) - ((X + Y) - Y) = n /\ (X + Y) - Y = m }}
144---            X := X + Y
145---   (3)                     {{ X - (X - Y) = n /\ X - Y = m }};
146---            Y := X - Y
147---   (4)                     {{ X - Y = n /\ Y = m }};
148---            X := X - Y
149---   (5)    {{ X = n /\ Y = m }}
150-
151--- The decorations can be constructed as follows:
152-
153--- - We begin with the undecorated program (the unnumbered lines).
154-
155--- - We add the specification — i.e., the outer precondition (1) and
156---   postcondition (5). In the precondition, we use parameters `m` and `n` to
157---   remember the initial values of variables `X` and `Y` so that we can refer
158---   to them in the postcondition (5).
159-
160--- - We work backwards, mechanically, starting from (5) and proceeding until we
161---   get to (2). At each step, we obtain the precondition of the assignment from
162---   its postcondition by substituting the assigned variable with the
163---   right-hand-side of the assignment. For instance, we obtain (4) by
164---   substituting `X` with `X - Y` in (5), and we obtain (3) by substituting `Y`
165---   with `X - Y` in (4).
166-
167--- - Finally, we verify that (1) logically implies (2) — i.e., that the step
168---   from (1) to (2) is a valid use of the law of consequence — by doing a bit
169---   of high-school algebra.

171--- ### Example: Simple Conditionals
172-
173--- Here is a simple decorated program using conditionals:
174-
175---   (1)   {{ True }}
176---           if X <= Y then
177---   (2)                    {{ True /\ X <= Y }} ->>
178---   (3)                    {{ (Y - X) + X = Y \/ (Y - X) + Y = X }}
179---             Z := Y - X
180---   (4)                    {{ Z + X = Y \/ Z + Y = X }}
181---           else
182---   (5)                    {{ True /\ ~(X <= Y) }} ->>
183---   (6)                    {{ (X - Y) + X = Y \/ (X - Y) + Y = X }}
184---             Z := X - Y
185---   (7)                    {{ Z + X = Y \/ Z + Y = X }}
186---           end
187---   (8)   {{ Z + X = Y \/ Z + Y = X }}
188-
189--- These decorations can be constructed as follows:
190-
191--- - We start with the outer precondition (1) and postcondition (8).
192-
193--- - Following the format dictated by the `hoare_if` rule, we copy the
194---   postcondition (8) to (4) and (7). We conjoin the precondition (1) with the
195---   guard of the conditional to obtain (2). We conjoin (1) with the negated
196---   guard of the conditional to obtain (5).
197-
198--- - In order to use the assignment rule and obtain (3), we substitute `Z` by
199---   `Y - X` in (4). To obtain (6) we substitute `Z` by `X - Y` in (7).
200-
201--- - Finally, we verify that (2) implies (3) and (5) implies (6). Both of these
202---   implications crucially depend on the ordering of `X` and `Y` obtained from
203---   the guard. For instance, knowing that `X <= Y` ensures that subtracting `X`
204---   from `Y` and then adding back `X` produces `Y`, as required by the first
205---   disjunct of (3). Similarly, knowing that `~ (X <= Y)` ensures that
206---   subtracting `Y` from `X` and then adding back `Y` produces `X`, as needed
207---   by the second disjunct of (6). Note that `n - m + m = n` does *not* hold
208---   for arbitrary natural numbers `n` and `m` (for example, [3 - 5 + 5 = 5]).

266--- ### Example: Division
267-
268--- Let's do one more example of simple reasoning about a loop.
269-
270--- The following Imp program calculates the integer quotient and remainder of
271--- parameters `m` and `n`.
272-
273---   X := m;
274---   Y := 0;
275---   while n <= X do
276---     X := X - n;
277---     Y := Y + 1
278---   end;
279-
280--- If we replace `m` and `n` by concrete numbers and execute the program, it
281--- will terminate with the variable `X` set to the remainder when `m` is
282--- divided by `n` and `Y` set to the quotient.
283-
284--- In order to give a specification to this program we need to remember that
285--- dividing `m` by `n` produces a remainder `X` and a quotient `Y` such that
286--- `n * Y + X = m /\ X < n`.
287-
288--- It turns out that we get lucky with this program and don't have to think
289--- very hard about the loop invariant: the loop invariant is just the first
290--- conjunct, `n * Y + X = m`, and we can use this to decorate the program.
291-
292---    (1)  {{ True }} ->>
293---    (2)  {{ n * 0 + m = m }}
294---           X := m;
295---    (3)                     {{ n * 0 + X = m }}
296---           Y := 0;
297---    (4)                     {{ n * Y + X = m }}
298---           while n <= X do
299---    (5)                     {{ n * Y + X = m /\ n <= X }} ->>
300---    (6)                     {{ n * (Y + 1) + (X - n) = m }}
301---             X := X - n;
302---    (7)                     {{ n * (Y + 1) + X = m }}
303---             Y := Y + 1
304---    (8)                     {{ n * Y + X = m }}
305---           end
306---    (9)  {{ n * Y + X = m /\ ~ (n <= X) }} ->>
307---   (10)  {{ n * Y + X = m /\ X < n }}
308-
309--- Assertions (4), (5), (8), and (9) are derived mechanically from the loop
310--- invariant and the loop's guard. Assertions (8), (7), and (6) are derived
311--- using the assignment rule going backwards from (8) to (6). Assertions (4),
312--- (3), and (2) are again backwards applications of the assignment rule.
313-
314--- Now that we've decorated the program it only remains to check that the uses
315--- of the consequence rule are correct — i.e., that (1) implies (2), that (5)
316--- implies (6), and that (9) implies (10). This is indeed the case:
317-
318--- - (1) ->> (2): trivial, by algebra.
319-
320--- - (5) ->> (6): because `n <= X`, we are guaranteed that the subtraction in
321---   (6) does not get zero-truncated. We can therefore rewrite (6) as
322---   `n * Y + n + X - n` and cancel the `n`s, which results in the left conjunct
323---   of (5).
324-
325--- - (9) ->> (10): if `~ (n <= X)` then `X < n`. That's straightforward from
326---   high-school algebra. So, we have a valid decorated program.

378--- ## Formal Decorated Programs
379-
380--- Our informal conventions for decorated programs amount to a way of
381--- "displaying" Hoare triples, in which commands are annotated with enough
382--- embedded assertions that checking the validity of a triple is reduced to
383--- simple logical and algebraic calculations showing that some assertions
384--- imply others.
385-
386--- In this section, we show that this presentation style can be made
387--- completely formal — and indeed that checking the validity of decorated
388--- programs can be largely automated.

725--- (4) `d2` is locally consistent with respect to `P2`

946--- ## Finding Loop Invariants
947-
948--- Once the outermost precondition and postcondition are chosen, the only
949--- creative part of a verifying program using Hoare Logic is finding the right
950--- loop invariants. The reason this is difficult is the same as the reason
951--- that inductive mathematical proofs are:
952-
953--- - Strengthening a *loop invariant* means that you have a stronger assumption
954---   to work with when trying to establish the postcondition of the loop body,
955---   but it also means that the loop body's postcondition is harder to prove.
956-
957--- - Similarly, strengthening an *induction hypothesis* means that you have a
958---   stronger assumption to work with when trying to complete the induction step
959---   of the proof, but it also means that the statement being proved inductively
960---   is harder to prove.
961-
962--- This section explains how to approach the challenge of finding loop
963--- invariants through a series of examples and exercises.
964-
965--- ### Example: Slow Subtraction
966-
967--- The following program subtracts the value of `X` from the value of `Y` by
968--- repeatedly decrementing both `X` and `Y`. We want to verify its correctness
969--- with respect to the pre- and postconditions shown:
970-
971---   {{ X = m /\ Y = n }}
972---     while X <> 0 do
973---       Y := Y - 1;
974---       X := X - 1
975---     end
976---   {{ Y = n - m }}
977-
978--- To verify this program, we need to find an invariant `Inv` for the loop. As
979--- a first step we can leave `Inv` as an unknown and build a *skeleton* for
980--- the proof by applying the rules for local consistency, working from the end
981--- of the program to the beginning, as usual, and without doing any thinking
982--- at all yet.
983-
984--- This leads to the following skeleton:
985-
986---   (1)    {{ X = m /\ Y = n }}  ->>                   (a)
987---   (2)    {{ Inv }}
988---            while X <> 0 do
989---   (3)              {{ Inv /\ X <> 0 }}  ->>          (c)
990---   (4)              {{ Inv [X |-> X-1] [Y |-> Y-1] }}
991---              Y := Y - 1;
992---   (5)              {{ Inv [X |-> X-1] }}
993---              X := X - 1
994---   (6)              {{ Inv }}
995---            end
996---   (7)    {{ Inv /\ ~ (X <> 0) }}  ->>                (b)
997---   (8)    {{ Y = n - m }}
998-
999--- Examining this skeleton, we can see that any valid `Inv` will have to
1000--- respect three conditions:
1001-
1002--- - (a) it must be *weak* enough to be implied by the loop's precondition,
1003---   i.e., (1) must imply (2);
1004-
1005--- - (b) it must be *strong* enough to imply the program's postcondition, i.e.,
1006---   (7) must imply (8);
1007-
1008--- - (c) it must be *preserved* by a single iteration of the loop, assuming that
1009---   the loop guard also evaluates to true, i.e., (3) must imply (4).
1010-
1011--- These conditions are actually independent of the particular program and
1012--- specification we are considering: every loop invariant has to satisfy them.
1013-
1014--- One way to find a loop invariant that simultaneously satisfies these three
1015--- conditions is by using an iterative process: start with a "candidate"
1016--- invariant (e.g., a guess or a heuristic choice) and check the three
1017--- conditions above; if any of the checks fails, try to use the information
1018--- that we get from the failure to produce another — hopefully better —
1019--- candidate invariant, and repeat.
1020-
1021--- For instance, in the reduce-to-zero example above, we saw that, for a very
1022--- simple loop, choosing `True` as a loop invariant did the job. Maybe it will
1023--- work here too. To find out, let's try instantiating `Inv` with `True` in
1024--- the skeleton above and see what we get...
1025-
1026---   (1)    {{ X = m /\ Y = n }} ->>                    (a - OK)
1027---   (2)    {{ True }}
1028---            while X <> 0 do
1029---   (3)                   {{ True /\ X <> 0 }} ->>     (c - OK)
1030---   (4)                   {{ True }}
1031---              Y := Y - 1;
1032---   (5)                   {{ True }}
1033---              X := X - 1
1034---   (6)                   {{ True }}
1035---            end
1036---   (7)    {{ True /\ ~(X <> 0) }} ->>                 (b - WRONG!)

1040--- not the case that `True /\ X = 0` (7) implies `Y = n - m` (8). In fact, the
1041--- two assertions are completely unrelated, so it is very easy to find a
1042--- counterexample to the implication (say, `Y = X = m = 0` and `n = 1`).

1047--- instantiate `Inv` with `Y = n - m`, and try checking conditions (a) to (c)

1738-
1739--- Some preconditions are more interesting than others. For example, the Hoare
1740--- triple
1741-
1742---   {{ False }}  X := Y + 1  {{ X <= 5 }}

1747--- to achieve the postcondition `X <= 5`.
1748-

1750-
1751---   {{ Y <= 4 /\ Z = 0 }}  X := Y + 1 {{ X <= 5 }}
1752-
1753--- has a useful precondition: it tells us that, if we can somehow create a
1754--- situation in which we know that `Y <= 4 /\ Z = 0`, then running this
1755--- command will produce a state satisfying the postcondition. However, this
1756--- precondition is not as useful as it could be, because the `Z = 0` clause in
1757--- the precondition actually has nothing to do with the postcondition
1758--- `X <= 5`.

1761-
1762---   {{ Y <= 4 }}  X := Y + 1  {{ X <= 5 }}

1765--- with respect to the postcondition `X <= 5`.

1768--- respect to postcondition `X <= 5`. Think of *weakest* here as meaning
1769--- "easiest to satisfy": a weakest precondition is one that as many states as
1770--- possible can satisfy.

1773-
1774--- - `P` is a precondition, that is, `{{P}} c {{Q}}`; and

1777---   `{{P'}} c {{Q}}` then `P' ->> P`.
