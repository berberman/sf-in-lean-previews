34+--  ## Tactics `injection` and `contradiction`
35+
36+--  Recall the definition of natural numbers:
37+
38+sf_recall
39+  inductive Nat : Type where
40+    | zero
41+    | succ (n : Nat)
42+
43+--  By this definition, every number has exactly one of two forms: either
44+--  it is the constructor `0` or it is built by applying the constructor
45+--  `.succ` to another number. There are two important consequences of this
46+--  definition:
47+--
48+--  - The constructor `.succ` is *injective* (or *one-to-one*). That is, if
49+--    `n + 1 = m + 1`, it must also be that `n = m`.
50+--
51+--  - The constructors `0` and `.succ` are *disjoint*. That is, `0` is not
52+--    equal to `n + 1` for any `n`.
53+--
54+--  Similar principles apply to every inductively defined type: all
55+--  constructors are injective, and the values built from distinct
56+--  constructors are never equal. For lists, the `List.cons` constructor is
57+--  injective and the empty list `List.nil` is different from every
58+--  non-empty list. For booleans, `true` and `false` are different. (Since
59+--  `true` and `false` take no arguments, their injectivity is neither here
60+--  nor there.) And so on.
61+
62+--  ### Injectivity
63+
64+--  We can *prove* the injectivity of `Nat.succ` by using the `Nat.pred`
65+--  function:
66+
67+example (n m : Nat)
68+    (h : n + 1 = m + 1) :
69+    n = m := by
70+  have : n = Nat.pred (n + 1) := by rfl
71+  /- The hypothesis name defaults to `this` when unspecified. -/
72+  rewrite [this, h]
73+  rw [Nat.pred_succ]
74+
75+--  This technique for injectivity can be generalized to any constructor by
76+--  writing the equivalent of `pred` — i.e., writing a function that
77+--  "undoes" one application of the constructor.
78+--
79+--  As a convenient alternative, Lean provides a tactic called `injection`
80+--  that allows us to exploit the injectivity of any constructor. Here is
81+--  an alternate proof of the above theorem using `injection`:
82+
83+example (n m : Nat)
84+    (h : n + 1 = m + 1) :
85+    n = m := by
86+  injection h
87+
88+--  Writing `injection h` asks Lean to generate all equations that it can
89+--  infer from `h` using the injectivity of constructors, adding them to
90+--  the context. In the present example, Lean can infer that `n = m` from
91+--  `n + 1 = m + 1`. When a generated equation satisfies the goal, as is
92+--  the case here, the `injection` tactic automatically closes the goal.
93+
94+--  When generated equations do not immediately close the goal, we can add
95+--  `with` to name the equations to be added to the context (otherwise Lean
96+--  generates names for us).
97+
98+example (n m o : Nat)
99+    (h : [n, m] = [o, o]) :
100+    n = m := by
101+  injection h with h₁ h₂
102+  injection h₂ with h₃
103+  rw [h₁, h₃]
104+
105+--  There is also a related tactic, `injections`, that applies the
106+--  `injection` tactic to all hypotheses, repeatedly. Using it simplifies
107+--  the proof of the above example.
108+
109+example (n m o : Nat)
110+    (h : [n, m] = [o, o]) :
111+    n = m := by
112+  injections h₁ _ h₃
113+  rw [h₁, h₃]

115+--  ### Exercise (3 stars): injection_ex3 ⭐⭐⭐
116+
117+theorem injection_ex3 {α : Type} (x y z : α) (l j : List α)
118+    (h₁ : x :: y :: l = z :: j)
119+    (h₂ : j = z :: l) :
120+    x = y := by
121+  injections hxz hyl_j
122+  rw [h₂] at hyl_j
123+  injection hyl_j with hyz
124+  rw [hyz, hxz]

126+--  So much for injectivity of constructors. What about disjointness?
127+
128+--  The principle of disjointness says that two terms beginning with
129+--  different constructors (like `0` and `Nat.succ`, or `true` and `false`)
130+--  can never be equal. Therefore, any time we find ourselves in a context
131+--  where we've *assumed* that two such terms are equal, we are justified
132+--  in concluding anything we want, since the assumption is nonsensical.
133+
134+--  The `contradiction` tactic embodies this principle. If the context
135+--  contains a contradictory hypothesis, such as `false = true`,
136+--  `contradiction` solves the current goal immediately. Some examples:
137+
138+example (n m : Nat)
139+    (h : false = true) :
140+    n = m := by
141+  contradiction
142+
143+example (n : Nat)
144+    (h : n + 1 = 0) :
145+    2 + 2 = 5 := by
146+  contradiction
147+
148+--  These examples are instances of a logical principle known as the
149+--  *principle of explosion*, which asserts that a contradictory hypothesis
150+--  entails anything (even manifestly false things!).
151+
152+--  Note to developers (Mike Hicks @mwhicks1):
153+--      Is there a way to relate this to the interpretation of implication
154+--      P -> Q where it is true when P is false and Q is true? It seems
155+--      like maybe this is a computational interpretation so perhaps not.
156+
157+--  In the above example, `n + 1` is shorthand for a constructor
158+--  application `Nat.succ n` so contradiction applies to it directly.
159+--  Sometimes you need to do a little work to expose a contradictory
160+--  hypothesis involving constructors. For example, recall that `Nat.add`
161+--  recurses on its second argument, so deriving a contradiction from
162+--  `1 + n = 0` is not direct.
163+
164+sf_expect_failure_in
165+  example (n : Nat)
166+      (h : 1 + n = 0) :
167+      2 + 2 = 5 := by
168+    contradiction -- doesn't work because `1 + n` doesn't reduce to `n.succ`.
169+
170+--  To fix it, rewriting with `Nat.one_add` changes the hypothesis from
171+--  `1 + n = 0` to `n.succ = 0`. Then Lean can immediately recognize this
172+--  as impossible.
173+
174+example (n : Nat)
175+    (h : 1 + n = 0) :
176+    2 + 2 = 5 := by
177+  rw [Nat.one_add] at h
178+  contradiction
179+
180+--  If you find the principle of explosion confusing, remember that these
181+--  proofs are *not* simply showing that the conclusion of the statement
182+--  holds. Rather, they are showing that, *if* the nonsensical situation
183+--  described by the premise did somehow hold, *then* the nonsensical
184+--  conclusion would hold too (because we'd be living in an inconsistent
185+--  universe where every statement is true).
186+--
187+--  We'll explore the principle of explosion in more detail in the next
188+--  chapter.
189+

191+
192+theorem disjoint_ex3 {α : Type} (x y z : α) (l : List α)
193+    (h : x :: y :: l = []) :
194+    x = z := by
195+  contradiction

304+--  ### Tactic `congr`
305+
306+--  The injectivity of constructors allows us to reason that
307+--  `∀ (n m : Nat), n + 1 = m + 1 → n = m`. The converse of this
308+--  implication is also true:
309+
310+example (n m : Nat) (h : n = m) :
311+    n + 1 = m + 1 := by
312+  rw [h]
313+
314+--  Note to developers (Mike Hicks @mwhicks1):
315+--      Is the general "fact" highlighted below a *principle* of
316+--      *congruence* ? Let's say so if that's the case.
317+
318+--  This is an instance of a more general fact about both constructors
319+--  *and* functions:
320+
321+example {α β : Type} (f : α → β) (x y : α)
322+    (h : x = y) : f x = f y := by
323+  rw [h]
324+
325+--  There is a tactic named `congr` that can prove such goals directly.
326+--  Given a goal of the form `f a₁ ... aₙ = g b₁ ... bₙ`, the tactic
327+--  `congr` will produce subgoals of the form `f = g`, `a₁ = b₁`, ...,
328+--  `aₙ = bₙ`. At the same time, any of these subgoals that are simple
329+--  enough (e.g., immediately provable by `rfl`) will be automatically
330+--  discharged.
331+
332+example (n m : Nat) (h : n = m) :
333+    n + 1 = m + 1 := by
334+  congr
335+
336+--  The `congr` tactic also accepts a numerical argument, which tells Lean
337+--  how deeply to decompose the goal. So, given a goal like
338+--  `((a, b), (c, d)) = ((e, f), (g, h))`, `congr 1` only applies `congr`
339+--  once to the goal, and would produce two subgoals: `(a, b) = (e, f)` and
340+--  `(c, d) = (g, h)`. `congr 2`, meanwhile, would apply `congr` again to
341+--  both these subgoals, and produce four subgoals: `a = e`, `b = f`,
342+--  `c = g` and `d = h`. Using `congr` without an argument always
343+--  decomposes the goal as deeply as possible.
344+--
345+--  Why does Lean provide this level of flexibility? Depending on what we
346+--  are trying to prove, deeper applications of `congr` may make our goal
347+--  unprovable. Consider this example:
348+
349+sf_expect_failure_in
350+  example (a b c d : Nat) (hab : a = b) (hcd : c = d) :
351+      (a, c + 1) = (b, 1 + d) := by
352+    congr
353+
354+--  We now have three goals: `c = 1`, `1 = d`, and `1 = d`, but these are
355+--  not provable from our hypotheses! `congr` has gone too deep.
356+
357+--  Output:
358+--    unsolved goals
359+--    case e_snd.e_a
360+--    a b c d : Nat
361+--    hab : a = b
362+--    hcd : c = d
363+--    ⊢ c = 1
364+--
365+--    case e_snd.e_a.e_2
366+--    a b c d : Nat
367+--    hab : a = b
368+--    hcd : c = d
369+--    ⊢ 1 = d
370+--
371+--    case e_snd.e_a.e_3
372+--    a b c d : Nat
373+--    hab : a = b
374+--    hcd : c = d
375+--    ⊢ 1 = d
376+
377+example (a b c d : Nat) (hab : a = b) (hcd : c = d) :
378+    (a, c + 1) = (b, 1 + d) := by
379+  /- Only shallowly using `congr` here allows us to complete the proof -/
380+  congr 1
381+  rw [Nat.add_comm]
382+  congr
383+
384+--  Note to developers (Niklas Halonen @xhalo32):
385+--      The above proof can be made simpler by just rewriting before the
386+--      `congr`, so arguably it doesn't require limiting the depth.
387+--
388+--      `example (a b c d : Nat) (hab : a = b) (hcd : c = d) :
389+--          (a, c + 1) = (b, 1 + d) := by
390+--        rw [Nat.add_comm]
391+--        congr`

393+--  ## More about `cases`
394+
395+--  We've seen many examples where the `cases` tactic is used to perform
396+--  case analysis of the value of some variable. The tactic offers more
397+--  general-purpose functionality, too.
398+
399+--  For example, it turns out that `cases` builds in this same reasoning
400+--  that the `injection` and `contradiction` tactics exploit about the
401+--  injectivity and disjointness of constructors. Here are a few examples.
402+
403+-- substitution
404+example (x : Nat) (h : x = 0) : Nat.succ x = 1 := by
405+  cases h
406+  rfl
407+
408+-- disjointness
409+example (h : (0 : Nat) = 1) : 2 = 3 := by
410+  cases h
411+
412+-- injectivity
413+example {m n : Nat} (h : Nat.succ m = Nat.succ n) : m = n := by
414+  cases h
415+  rfl
416+
417+--  Sometimes we need to reason by cases on the result of some
418+--  *expression*. We can do so with `cases`, directly. Here is an example:
419+
420+def chooseIf {α : Type} (test : α → Bool) (x y : α) : α :=
421+  if test x then x else y
422+
423+theorem chooseIf_self {α : Type} (test : α → Bool) (x : α) :
424+    chooseIf test x x = x := by
425+  rw [chooseIf]
426+  cases test x <;> rfl
427+
428+--  After *unfolding* `chooseIf` in the above proof, we find that we are
429+--  stuck on `(if test x = true then x else x) = x`. But either `test x` is
430+--  `true` or it isn't, so we can use `cases (test x)` to let us reason
431+--  about the two cases.
432+--
433+--  In general, the `cases` tactic can perform case analysis on the results
434+--  of arbitrary computations. If `e` has an inductively defined type `T`,
435+--  then `cases e` generates one subgoal for each constructor of `T`,
436+--  specializing the goal to that case. It does not necessarily rewrite
437+--  occurrences of `e` in hypotheses; when that information is needed, we
438+--  can save an equation as described below.
439+
440+--  ### Destructing Tuples
441+
442+--  `cases` is useful when we are dealing with inductively defined types
443+--  that can be one thing or another; a `Bool` is either a `false` or a
444+--  `true`, and a `Nat` is either `0` or `succ n`. When we want more
445+--  information about inductively defined types that are products of
446+--  multiple things, we instead want a way to get the pieces of that value
447+--  out from it.
448+--
449+--  When we have a value `v : α × β` in our context, we can get the first
450+--  and second projections of `v` using this tactic:
451+--
452+--      let ⟨a, b⟩ := v
453+
454+--  ### Exercise (3 stars): zip_unzip' ⭐⭐⭐
455+
456+--  Here is an implementation of the `unzip` function mentioned in chapter
457+--  Poly:
458+
459+def unzip' {α β : Type} (l : List (α × β)) : List α × List β := (
460+  match l with
461+  | [] => ([], [])
462+  | (x, y) :: t =>
463+    let (lx, ly) := unzip' t
464+    (x :: lx, y :: ly))
465+
466+--  Prove that `unzip'` and `zip` are inverses in the following sense.
467+--  Remember that you can use `dsimp only` to simplify expressions
468+--  involving pairs and `fst` and `snd`.
469+
470+theorem zip_unzip' {α β : Type} (l : List (α × β))
471+    (l₁ : List α) (l₂ : List β)
472+    (h : unzip' l = (l₁, l₂)) :
473+    zip l₁ l₂ = l := by
474+  induction l generalizing l₁ l₂ with
475+  | nil =>
476+    rw [unzip'] at h
477+    injections h₁ h₂
478+    rw [← h₁, ← h₂, zip]
479+  | cons x xs ih =>
480+    let ⟨a, b⟩ := x
481+    rw [unzip'] at h
482+    injections h₁ h₂
483+    rw [← h₁, ← h₂, zip, ih]
484+    dsimp only

486+--  ### Splitting with Equations
487+
488+--  When using `cases`, we can specify to Lean that it should remember an
489+--  equality between a compound expression and what we are decomposing it
490+--  into, using `cases h : ...` syntax. This information can actually be
491+--  critical, and, if we leave it out, we might lack information we need to
492+--  complete a proof.
493+
494+--  For example, suppose we define a function `keepIf` like this:
495+
496+def keepIf {α : Type} (test : α → Bool) (x : α) : Option α :=
497+  if test x then some x else none
498+
499+--  Now suppose that we want to prove `keepIf_some`. If we start the proof
500+--  like this (with no `h : ⋯` on the `cases`)...
501+
502+sf_expect_failure_in
503+  theorem keepIf_some {α : Type} (test : α → Bool) (x y : α)
504+      (h : keepIf test x = some y) :
505+      x = y := by
506+    rw [keepIf] at h
507+    cases (test x)
508+
509+--  Output:
510+--    unsolved goals
511+--    case false
512+--    α : Type
513+--    test : α → Bool
514+--    x y : α
515+--    h : (if test x = true then some x else none) = some y
516+--    ⊢ x = y
517+--
518+--    case true
519+--    α : Type
520+--    test : α → Bool
521+--    x y : α
522+--    h : (if test x = true then some x else none) = some y
523+--    ⊢ x = y
524+
525+--  ... then we are stuck at this point because the context does not
526+--  contain enough information to prove the goal. Because `test x` appears
527+--  in our hypothesis, rather than in our goal, `cases (test x)` does not
528+--  automatically replace the expression with `false` or `true` like it did
529+--  during the proof of `chooseIf`. We want to add an equation to the
530+--  context that records which case we are in. This is precisely what the
531+--  `h : ⋯` qualifier does.
532+
533+theorem keepIf_some {α : Type} (test : α → Bool) (x y : α)
534+    (h : keepIf test x = some y) :
535+    x = y := by
536+  rw [keepIf] at h
537+  cases hTest : test x
538+  -- Now we have the same state as at the point where we got stuck
539+  -- above, except that the context contains an extra equality
540+  -- assumption, which is exactly what we need to make progress.
541+  · rw [hTest] at h
542+    contradiction
543+  · rw [hTest] at h
544+    injections

383---  The principle of disjointness says that two terms beginning with
384---  different constructors (like `0` and `Nat.succ`, or `true` and `false`)

386---  where we've *assumed* that two such terms are equal, we are justified
387---  in concluding anything we want, since the assumption is nonsensical.

404---  *principle of explosion*, which asserts that a contradictory hypothesis
405---  entails anything (even manifestly false things!).

581---  Given a goal of the form `f a₁ ... aₙ = g b₁ ... bₙ`, the tactic
582---  `congr` will produce subgoals of the form `f = g`, `a₁ = b₁`, ...,
583---  `aₙ = bₙ`. At the same time, any of these subgoals that are simple
584---  enough (e.g., immediately provable by `rfl`) will be automatically
585---  discharged.

588-    n + 1 = m + 1 := by

592---  how deeply to decompose the goal. So, given a goal like
593---  `((a, b), (c, d)) = ((e, f), (g, h))`, `congr 1` only applies `congr`
594---  once to the goal, and would produce two subgoals: `(a, b) = (e, f)` and
595---  `(c, d) = (g, h)`. `congr 2`, meanwhile, would apply `congr` again to
596---  both these subgoals, and produce four subgoals: `a = e`, `b = f`,
597---  `c = g` and `d = h`. Using `congr` without an argument always
598---  decomposes the goal as deeply as possible.
