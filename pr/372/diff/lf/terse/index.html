8+--  ## Tactics `injection` and `contradiction`
9+
10+--  The constructors of inductive types are *injective* (aka
11+--  *one-to-one*) and *disjoint*. E.g., for `Nat`:
12+--
13+--  - if `n + 1 = m + 1` then it must be that `n = m`
14+--  - `0` is not equal to `n + 1` for any `n`
15+
16+--  ### Injectivity
17+
18+--  We can *prove* the injectivity of `Nat.succ` by using
19+--  the `Nat.pred` function:
20+
21+example (n m : Nat)
22+    (h : n + 1 = m + 1) :
23+    n = m := by
24+  have : n = Nat.pred (n + 1) := by rfl
25+  /- The hypothesis name defaults to `this` when unspecified. -/
26+  rewrite [this, h]
27+  rw [Nat.pred_succ]
28+
29+--  As a convenience, the `injection` tactic allows us to
30+--  exploit injectivity of any constructor (not just
31+--  `Nat.succ`).
32+
33+example (n m : Nat)
34+    (h : n + 1 = m + 1) :
35+    n = m := by
36+  injection h
37+
38+--  When generated equations do not immediately close the
39+--  goal, we can add `with` to name the equations to be
40+--  added to the context (otherwise Lean generates names for
41+--  us).

44+    (h : [n, m] = [o, o]) :
45+    n = m := by
46+  sorry

49+--  applies the `injection` tactic to all hypotheses,
50+--  repeatedly. Using it simplifies the proof of the above

66+--  So much for injectivity of constructors. What about
67+--  disjointness?
68+
69+--  Two terms beginning with different constructors (like
70+--  `0` and `Nat.succ`, or `true` and `false`) can never be
71+--  equal.
72+
73+--  The `contradiction` tactic embodies this principle. If
74+--  the context contains a contradictory hypothesis, such as
75+--  `false = true`, `contradiction` solves the current goal
76+--  immediately. Some examples:
77+
78+example (n m : Nat)
79+    (h : false = true) :
80+    n = m := by

83+example (n : Nat)
84+    (h : n + 1 = 0) :
85+    2 + 2 = 5 := by
86+  contradiction
87+
88+--  These examples are instances of a logical principle
89+--  known as the *principle of explosion*, which asserts
90+--  that a contradictory hypothesis entails anything (even
91+--  manifestly false things!).
92+
93+--  In the above example, `n + 1` is shorthand for a
94+--  constructor application `Nat.succ n` so contradiction
95+--  applies to it directly. Sometimes you need to do a
96+--  little work to expose a contradictory hypothesis
97+--  involving constructors. For example, recall that
98+--  `Nat.add` recurses on its second argument, so deriving a
99+--  contradiction from `1 + n = 0` is not direct.

290+
291+--  We've seen many examples where the `cases` tactic is
292+--  used to perform case analysis of the value of some
293+--  variable. The tactic offers more general-purpose
294+--  functionality, too.

297+--  it solve some goals involving disjointness and
298+--  injectivity, as well as substitution, of constructors:

325+--  ### Destructing Tuples
326+
327+--  `cases` is useful when we are dealing with inductively
328+--  defined types that can be one thing or another; a `Bool`
329+--  is either a `false` or a `true`, and a `Nat` is either
330+--  `0` or `succ n`. When we want more information about
331+--  inductively defined types that are products of multiple
332+--  things, we instead want a way to get the pieces of that
333+--  value out from it.
334+--
335+--  When we have a value `v : α × β` in our context, we can
336+--  get the first and second projections of `v` using this
337+--  tactic:

339+--      let ⟨a, b⟩ := v

341+--  ### Splitting with Equations
342+
343+--  When using `cases`, we can specify to Lean that it
344+--  should remember an equality between a compound
345+--  expression and what we are decomposing it into, using
346+--  `cases h : ...` syntax. This information can actually be
347+--  critical, and, if we leave it out, we might lack
348+--  information we need to complete a proof.
349+
350+def keepIf {α : Type} (test : α → Bool) (x : α) : Option α :=

354+--  we can use it.

358+    x = y := by

362+  -- above, except that the context contains an extra equality
363+  -- assumption, which is exactly what we need to make progress.
